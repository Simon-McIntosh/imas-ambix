Frame-quality filter (sidecar mask)

Status: Active — empirical audit landed 2026-05-28; implementation queued as a v1 follow-on after production 1209004 completes. Non-blocking for the current fine-tune run.

§1 — Why now

The 2026-05-28 frame-quality audit (30 random shots, 67 754 frames, results at /work/projects/imas_gpu/mast-tokens/v1/frames-quality-audit-2026-05-28.json) quantified a category of error frames that the entire pipeline has been silently processing as if they were valid plasma data:

CategoryHeuristicPrevalence (sample)Worst shot in sample
All-saturated ("all white")mean > 1000, std < 10.00 % — none found—
Near-black blankmean < 5, std < 11.79 % (1 210 / 67 754)24827: 15.6 % (1 125 / 7 202)
Entirely degenerate shotshot max ≤ 162 of 30 shots (22719 max=13, 26160 max=16)22719: 100 % degenerate

Three concrete failure modes the filter prevents:

  1. Wasted decoder capacity. Production fine-tune 1209004 samples ~50 frames per shot × 7 500 train shots = 375 k frames. At 1.79 % prevalence ≈ 6 700 blank frames in the training set. These trivially satisfy L1 (decoder learns to output near-zero) without learning anything useful about plasma reconstruction — capacity that should have gone to transient frames is burned on noise.
  2. Garbage tokens from degenerate shots. For shots like 22719 where the camera was on but recorded only noise (max=13), the per-shot (lo, hi) normalization stretches that 13-count noise to the full [0, 255] range. The encoder then sees pure noise and produces meaningless LFQ token IDs, which the world model will later try to learn temporal patterns from.
  3. Artificially deflated rFID. Blank frames are trivially reconstructed (the decoder maps near-zero tokens back to near-zero output) so they contribute very low per-frame FID error. A mean rFID that includes blanks therefore understates the actual error on physically-relevant frames. See companion plan tokenizer-transient-fidelity for the stratified-metric solution.

§2 — Approach

Per-shot JSON sidecar at /work/projects/imas_gpu/mast-tokens/v1/frame-quality/<shot_id>-<camera>.json with the following schema:

{
  "shot": 24827,
  "camera": "rbb",
  "n_frames": 7202,
  "n_valid": 6077,
  "n_blank": 1125,
  "n_saturated": 0,
  "n_constant": 0,
  "valid_fraction": 0.8438,
  "shot_min": 0,
  "shot_max": 1023,
  "shot_min_nonblank": 2,
  "shot_max_nonblank": 1023,
  "valid_mask": "01001110…",      // hex-packed bitmask, len = ceil(n_frames/4)
  "computed_at": "2026-05-28T17:00:00Z",
  "computed_by": "ambix data frame-quality-scan v1.0",
  "schema_version": 1
}

Key design choices:

  • Sidecar, not re-tokenization. The corpus token files at /work/projects/imas_gpu/mast-tokens/v1/frames/<shot>/rbb.zarr/ stay byte-identical. The mask only tells downstream consumers which token rows to skip. Avoids the ~7 h corpus re-encode that would otherwise be required, and keeps existing offsets stable for any prior consumer that already has token indices baked in.
  • Both stats AND mask co-located. The shot scan reads every frame once and computes per-shot (lo, hi) alongside the validity mask. This merges naturally with task #11 (the per-shot stats cache) — both are per-shot metadata that justify a single full-frame pass.
  • Hex-packed bitmask. For a 14 360-frame shot the mask is < 2 KB. Trivial to gzip if storage becomes a concern.
  • Schema version pinned. Consumers gate on schema_version; bumping it triggers a re-scan rather than silent compatibility issues.

§3 — Acceptance criteria

  1. Per-shot sidecar exists for every shot in the rbb tokenized corpus (9 528 files at /work/projects/imas_gpu/mast-tokens/v1/frame-quality/).
  2. imas_ambix.tokenizer.finetune_decoder._scan_shots() reads the sidecar and excludes invalid frames from its entry list.
  3. imas_ambix.bench.stream_worker (and any other val-pool consumer) similarly skips invalid frames.
  4. Inspection of known-bad shot 24827 shows mask-valid count in [6000, 6200] (≈ 1100 blanks excluded out of 7 202).
  5. Inspection of entirely-degenerate shot 22719 shows valid_fraction = 0; consumers drop this shot wholesale.
  6. A re-bench of 1209004's weights with the filter applied shows the stratified rfid_quiescent bin no longer contains blank frames (check via count_blank in the bench output).
  7. New training run shows training pool size reduced by the audited 1.79 % (±0.5 % per-shot variance) — confirms the mask is wired correctly end-to-end.

§4 — Implementation phases

Phase 1 — Audit module + CLI

Land imas_ambix/data/frame_quality.py with the per-shot function compute_shot_quality(shot_id, zarr_path, camera) -> dict that reads ALL frames, applies the heuristics from §1, and returns the schema-1 dict. Add CLI: ambix data frame-quality-scan --camera rbb [--shot-list FILE] [--workers N] [--overwrite].

Uses the same in-process streaming pattern as stream_encode.py — torch DataLoader workers reading zarr stores, no subprocess daemon, no prefetch threads — to avoid the node-drain failure modes from prior incidents. Includes the STOP-FILE check from AGENTS.md §2a-cancel.

Phase 2 — Corpus scan SLURM

Single SLURM job to scan the full 9 528-shot rbb corpus. Header follows the three-layer pattern from AGENTS.md §2a-cancel-time: --time=02:00:00 (~2x expected runtime of ~30-60 min), --signal=B:USR1@600, AMBIX_SOFT_TIME_LIMIT=5100 (85 % of ceiling).

Output: 9 528 sidecar JSONs. Aggregate stats logged: total invalid frames, per-shot invalid distribution, list of entirely-degenerate shots. The aggregate goes into a NEW followup on this plan (not the consuming plans) so we have a single canonical "corpus is now filtered" reference.

Phase 3 — Fine-tune integration

Update imas_ambix/tokenizer/finetune_decoder._scan_shots(): read the sidecar before sampling frame indices; drop invalid indices from the entry list; log the resulting "valid frames available" and the filter-effective-fraction. Add a fallback: if the sidecar is missing for a shot, fall back to the existing 200-sample stats path AND emit a warning (so missing sidecars don't silently propagate).

Phase 4 — Bench integration

Update imas_ambix/bench/stream_worker.py: read the sidecar mask; in run_worker, drop frames where mask[i] = False before feeding to encode/decode. Adjust the n_items per-shot report so the bench output reflects only-valid frames. Update v0-rbb-100shot.yaml and the finetune variant: no change needed to the metric list (the existing rfid_stratified already handles blank classification via the spatial-std heuristic; the sidecar just prevents the blanks from being included in the bench pool in the first place).

Phase 5 — Validation + re-bench

Re-bench production 1209004's plasma-decoder-v1-merged.ckpt with the filter applied. Compare the new bench result against the unfiltered baseline:

  • count_blank in rfid_stratified should drop to ~0
  • rfid_quiescent may rise slightly (no more easy blanks "helping" the mean)
  • rfid_transient unchanged (transients were never blank)
  • rfid_overall rises slightly — this is correct, the unfiltered number was misleadingly low

Document the before/after in a comment on this plan. If transient rFID is the gate (see tokenizer-transient-fidelity), the overall rFID change is informational.

§5 — Out of scope

  • Re-tokenization of the corpus. Existing tokens stay unchanged; only the mask is added. Re-encoding would be a separate v2 project costing ~7 h GPU.
  • Other cameras. Initial scope is rbb only. IR (rir) follows the same pattern but is gated on the IR-codebook decision in the parent tokenizers plan.
  • Subtler degeneracy modes (e.g., frames with realistic mean but no plasma signal — pure background light). v1 catches the obvious near-black case; physics-aware detection (low gradient, no filamentary structure) is a v2 ML-classifier project.
  • Re-scoring previously-trained models. We only re-bench production 1209004's weights; we don't retroactively re-evaluate the earlier baseline bench 1208918.

§6 — Compute

Phase 2 corpus scan: I/O-bound (~30-60 min wall-clock on betelgeuse, single-GPU sufficient since this is metadata only — no model forward). Phase 3-4 are pure code changes. Phase 5 re-bench: standard 100-shot in-process bench (~9 min) using the same SLURM pattern as scripts/slurm/bench_rbb.sbatch.
