Incident RCA — node 98dci4-gpu-0003 drained 2026-05-27 16:04:35. Verdict: self-inflicted (a probe job hung on a doomed network download and could not be killed). No other-user / Group B involvement — proven below. This is the third drain (see RCA #2, 12:04:46), but a new mechanism: network I/O, not a CUDA deadlock.

One-line cause

Batch-size probe job 1208591 ran with the wrong working directory (the repo, not the Open-MAGVIT2 root), so the vendored LPIPS loss in VQModel.__init__ resolved its CWD-relative weights path to a non-existent file and fell back to downloading vgg.pth from heibox.uni-heidelberg.de. betelgeuse has no outbound network, so the download hung in uninterruptible I/O during model init, before any CUDA call. A scancel could not reap the process within SLURM's UnkillableStepTimeout (~60 s), slurmd logged Kill task failed and auto-drained the node.

Timeline (local)

  • 15:56:37 — job 1208591 (ambix-bsprobe) starts; model init begins.
  • ~15:56:40 — LPIPS loader prints Downloading vgg_lpips model from https://heibox.uni-heidelberg.de/… and blocks (no network).
  • 16:03:34 — I scancel the hung job; SIGTERM sent, process does not exit (stuck in I/O).
  • 16:04:35 — 1208591.batch End, ExitCode 0:15; slurmd: STEPD TERMINATED … DUE TO JOB NOT ENDING WITH SIGNALS; node Reason=Kill task failed [root@2026-05-27T16:04:35].

The 61-second gap (16:03:34 → 16:04:35) is exactly the UnkillableStepTimeout window.

Attribution — 100% ours, zero Group B

sacct -a -N 98dci4-gpu-0003 --starttime=15:50 --endtime=16:06 lists only mcintos/grpa jobs in the window — no other account, no Group B step. The node Reason timestamp root@16:04:35 matches 1208591.batch End 16:04:35 to the second. There is no ambiguity: this drain is mine.

GPU state — expected clean

The job hung in VQModel.__init__ (LPIPS download), before model.to("cuda") — so no CUDA context was ever created and no GPU memory was allocated by this job. Unlike RCA #1/#2 (CUDA-wedged), a --gpu-reset or reboot should not be required; the GPUs should come back clean. Admin should still verify before resume.

Fix (committed 1657bb9)

scripts/slurm/stream_encode_rbb.sbatch hardened so a wrong CWD can never trigger a download again:

  • cd to the magvit2 root so the LPIPS CWD-relative weights path resolves to the on-disk file; the encoder script is invoked by absolute path.
  • Force offline: HF_HUB_OFFLINE=1, TRANSFORMERS_OFFLINE=1, HF_DATASETS_OFFLINE=1 — any stray fetch fails fast instead of hanging.
  • Preflight assertion: abort with a clear 1-line error if vgg.pth is missing at the expected path — converts a node-drain risk into an immediate clean exit.

Admin instructions to resume

  1. Confirm GPUs are clean (no stuck procs — expected, since the job never reached CUDA): 
    ssh 98dci4-gpu-0003 'nvidia-smi; ps -eo pid,stat,cmd | grep -iE "python|defunct" | grep -v grep'
  2. Resume (no GPU reset expected): 
    sudo scontrol update nodename=98dci4-gpu-0003 state=resume reason=""
  3. Only if a python proc is wedged in D state holding GPU memory: nvidia-smi --gpu-reset (or reboot), then resume.

Lessons

  • Never let a GPU job attempt network I/O on betelgeuse. The node has no egress; a download hangs uninterruptibly and a kill of that hang drains the node. Offline env + a preflight file check make misconfiguration fail fast.
  • A scancel is not free. Cancelling a job stuck in network/GPFS I/O can drain the node just as a CUDA-wedge does. Prefer preventing the hang to killing it.
  • CWD is load-bearing for vendored model code. Open-MAGVIT2's LPIPS uses a CWD-relative weights path; any harness that runs it must cd to the magvit2 root (and the production sbatch now does).

Is this all our fault? Attribution vs. fragility

These are two separate questions, and conflating them is what makes the node look entirely like an ambix problem when it is not:

DrainTriggerWhose trigger?
#1 — 2026-05-26 18:18CUDA-init failure ("Not responding"), coincident with Group B contention Ambiguous / shared — Group B was active on the node
#2 — 2026-05-27 12:04our prefetch producer/consumer deadlockOurs (job logic)
#3 — 2026-05-27 16:04wrong-CWD → no-network download hang + our scancelOurs (trigger)

Trigger ≠ outage. Yes, 2 of 3 triggers were our jobs (the third was at least partly external). We own that and have hardened our jobs accordingly. But the trigger is a routine, recoverable user mistake — a hung process. What turns it into a shared, multi-hour outage is the node/cluster configuration, and that is independent of who pulled the trigger:

  • No auto-recovery. A single unkillable step DRAINs the whole node and it stays down until a human runs scontrol resume — even when the GPUs are provably clean. Today the job never touched CUDA, yet the node has sat drained for ~45 min awaiting manual action. That is pure configuration fragility, not a property of our code.
  • Egress that DROPs instead of REJECTs. A correctly air-gapped node would make a stray download fail in milliseconds. Instead the connection hung for minutes — long enough to wedge the step. A network-policy choice, not ours.
  • Single node, two groups, shared fate. Any wedge by either group takes the resource offline for both. A provisioning choice that amplifies every individual error into a collective outage.
  • Manual gpu-reset for D-state cleanup. Inherent to the OS/driver, but with no health-check automation every instance needs a human.

Conclusion. We own our triggers and have closed them (offline+preflight, SIGTERM handlers, watchdogs, in-process pipeline). But the severity and duration of each event is a property of the cluster setup, not of ambix. The identical triggers — from us, from Group B, or from a hardware hiccup — would be self-healing non-events on a node configured for resilient shared use. The recommendations below are the levers that make that true.

Recommendations for SDCC admins — node resilience

Three drains in two days from three different failure modes (CUDA deadlock, prefetch deadlock, no-network download hang) point at a structural fragility: SLURM's default reaction to any unkillable step is to DRAIN the whole node, and recovery is a manual scontrol resume. On a single shared H200 split between two groups, one user's wedge becomes everyone's multi-hour outage. We have hardened our jobs (offline + preflight + SIGTERM handlers + watchdogs), but defence-in-depth on the node side would make the resource far more robust for both groups:

  1. Automatic health-check + resume (highest value). A HealthCheckProgram / nhc (or controller cron) that, on a node in DRAIN with Reason=Kill task failed, verifies the GPUs are clean (nvidia-smi shows no compute procs, memory near 0) and orphaned PIDs are gone, then auto-resumes — escalating to a human only when a process is genuinely wedged or GPU memory is dirty. This turns the common clean case (like today's — the job never touched CUDA) from a multi-hour manual outage into seconds.
  2. cgroup-based process tracking. Ensure ProctrackType=proctrack/cgroup + TaskPlugin=task/cgroup (cgroup v2 cgroup.kill) so an escaped process tree (DataLoader workers, subprocess daemons) is reaped via the cgroup freezer rather than by PID signalling. Note this does not rescue a genuinely D-state (uninterruptible) process — see (3)/(4) for that — but it removes the "orphaned child survived" class entirely.
  3. Egress: REJECT, don't DROP. betelgeuse has no outbound network, but today's download hung for minutes rather than failing — the classic signature of a firewall that silently DROPs packets so the client waits out a long connect/read timeout. Configuring egress to REJECT (send RST/ICMP-unreachable) makes any stray network call fail in milliseconds instead of blocking — which would have prevented this drain outright, for any user.
  4. Shared-filesystem I/O timeouts. The unkillable class is processes stuck in D state on a GPFS/driver syscall. Where feasible, GPFS/NFS mount timeouts (so I/O errors rather than blocks indefinitely) and keeping the NVIDIA fabric-manager/persistence-mode healthy reduce how often a process becomes truly unreapable.
  5. Diagnose before draining. Set UnkillableStepProgram to capture /proc/<pid>/stack, nvidia-smi, and the process tree at the moment of the unkillable event, and consider a modest bump to UnkillableStepTimeout so a merely-slow teardown isn't misread as wedged. This makes every future RCA instant instead of forensic.

Priority order for impact-vs-effort: (1) auto-resume health-check and (3) egress REJECT are the two changes that would have prevented today's outage entirely; (2) and (4) reduce the frequency of the harder D-state class.
