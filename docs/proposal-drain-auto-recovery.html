SDCC Admin Proposal — node 98dci4-gpu-0003, partition betelgeuse, reservation gpu_0003_grpA. Contact: Simon McIntosh, simon.mcintosh@iter.org.

§1 — Executive Summary

Node 98dci4-gpu-0003 — the only NVIDIA H200 NVLink node in Group A's allocation — has been drained at least four times since 2026-05-26, with each event taking 2–4 hours to recover. Recovery has required manual SDCC admin intervention in every case: identifying the residual processes, running nvidia-smi --gpu-reset or rebooting, and issuing scontrol update … state=resume. The delay between the drain and the admin response (notification latency + timezone + working hours) accounts for the majority of the outage window.

Each drain follows the same SLURM-level mechanism: a process in uninterruptible kernel sleep (D state) survives past UnkillableStepTimeout (currently 60 s), slurmstepd logs "Kill task failed", and the node auto-drains. The underlying driver surfaces (CXI/Slingshot network, GPFS, NVIDIA GPU driver) are now pinned to the CXI/Slingshot fabric by the 2026-06-17 forensic capture (§1a, §2b) — but regardless of whether the root cause is eliminated, the outage from any future drain is determined entirely by the speed of recovery. Application-side mitigations (STOP-FILE cooperative shutdown, three-layer sbatch time-limit defence, in-process encoders) are already deployed and reduce the frequency of D-states, but cannot eliminate them: a D-state task does not receive signals and cannot be reached by application code.

This proposal addresses the recovery half of the problem with three independent mechanisms — an UnkillableStepProgram handler, a SLURM epilog GPU-clean gate, and a HealthCheckProgram auto-resume policy — that together shrink recovery from 2+ hours to under 5 minutes, without requiring the root cause to be fully understood first. Each mechanism is independent; even partial deployment provides immediate benefit.

§1a — Root cause & attribution: environmental, not application

Was this drain caused by anything we did? No — not by a code defect, a misconfiguration, or misuse. It is an environmental, node-level failure: a process entered uninterruptible kernel sleep (D state) on the CXI / Slingshot fabric while servicing an ordinary GPFS read, and that wait outlived UnkillableStepTimeout. This attribution is settled and now directly observed:

  • The settled finding holds. The drain campaign ran 16 deliberate reproduction attempts — SIGKILL mid-collective, scancel on live CUDA/NCCL, #SBATCH --time expiry into a hung process, and the verbatim code of a job that had previously drained the node — and produced zero drains. Sustained D-state is stochastic driver/fabric/GPFS state, not a property of any code path (rca-node-drain-final-2026-06-03).
  • The 2026-06-17 capture confirms it. The D-state holder was the encode process blocked on cxiWaitEventWait — an ordinary Slingshot-fabric read, not a CUDA/NCCL call or a buggy code path (§2b). The NVIDIA-RM contention in nvidia-smi is downstream collateral.
  • What "we" contributed is an occasion, not a cause. The wedge landed in the kill window of our job's 12 h time-limit teardown — but because --time expiry was tested 16× without draining, the teardown is not reliably causal; it merely provided one of many moments at which the environmental D-state could coincide with the kill window. A D-state task receives no signals, so no application-side change (signal handler, time-limit tuning, in-process encoder) can prevent it; our mitigations reduce D-state frequency, not the underlying fabric wedge.

Refinement (2026-06-18, §2c). A second live capture sharpens this. The uninterruptible wait surface is unchanged (CXI fabric serving GPFS — cxiWaitEventWait seen a third time), so the environmental attribution stands. But this drain — unlike all prior ones — had a clear application trigger: a 4-rank DDP job that crashed mid-collective during a cold-start I/O storm, with d_alloc_parallel (GPFS metadata) joining the wedge. The distinction matters: the fabric wedge is still the environmental cause (no signal can clear a D-state), but launch concurrency and a dying-rank-mid-collective are an occasion we can make rarer from our side — a clean DDP init (no rank dies mid-NCCL) plus staggered/warmed GPFS reads and lower cold-start concurrency (2-rank has never drained). These reduce frequency, not the underlying wedge.

Implication. Because the cause is environmental, the two levers that matter are (1) recovery automation to bound the outage (this proposal, §3–§5) and (2) a fabric/driver-level fix by SDCC/HPE to remove the wedge itself (§6a). Application code cannot close this on its own — but §2c shows we can lower how often it is triggered.

§2c — 2026-06-18: second live capture — same fabric wedge, but with a clear application TRIGGER

A second drain was captured live by the sidecar. Unlike every prior drain (which had no identifiable application cause and was ruled environmental/stochastic), this one has a clear, reproducible trigger: the teardown of a crashed 4-rank DDP job. This is a new and actionable data point — it does not overturn the "environmental wedge surface" finding, but it identifies a code-level event that reliably provokes it.

Sequence (clean attribution). Job 1219733 (a 4×H200 DDP world-model training) crashed at DDP construction — rank 0 raised, leaving ranks 1–3 mid init_process_group/NCCL. The job was scancelled at 17:09:01; the surviving ranks could not be reaped and the node DRAINED at Reason=Kill task failed [root@2026-06-18T17:10:02] — a ~61 s gap, again matching UnkillableStepTimeout ≈ 60 s (§5a). DeepSeek-V4-Flash, co-tenant on 2 cards, was unaffected throughout (a drain blocks new jobs, it does not kill running ones).

D-state wedge (sidecar of 1219733, kill window). The same fabric surface as §2b dominates, confirming cxiWaitEventWait a third time (2026-06-17 live, and now twice more):

What this adds to the root cause. The §2b finding stands — the uninterruptible wait is the CXI fabric serving GPFS, environmental and signal-immune. What is new is the trigger: a 4-rank cold-start I/O storm. When four ranks simultaneously cold-read the GPFS plan/token stores at job start, d_alloc_parallel (GPFS dentry allocation) joins cxiWaitEventWait as a dominant wedge — i.e. the concurrency of the launch is what pushes the fabric/GPFS path into the uninterruptible state. A rank that then dies mid-collective leaves its peers blocked on that wedged path, and they cannot be killed → drain. This is consistent with the observation that the 2-rank configuration never drained: fewer concurrent cold readers, less metadata contention.

Application-side mitigations (do not need admin; complement §3/§5). Because this drain has a code-level trigger, we can reduce its probability from our side:

  • Avoid the dying-rank-mid-collective pattern. The companion fix (rank-0 broadcasts the model shape so ranks build identically; commit on main) removes the DDP-init crash that wedged the peers here — a clean init means no rank dies mid NCCL, so the peers never enter the unkillable fabric wait. Fix the crash, remove the drain trigger.
  • Tame the cold-start I/O storm. Stagger per-rank GPFS reads at startup (rank-0-first then broadcast where possible), warm the token/plan cache before the parallel open, and prefer the node-local NVMe assembled-sample cache over repeated GPFS metadata hits — directly attacking the d_alloc_parallel contention.
  • Lower concurrency when feasible. Fewer simultaneous cold readers (2-rank has never drained); 4-rank is acceptable but should pair with the staggered/warmed reads above.

None of these is a guarantee — a D-state task still receives no signals, so the §3 UnkillableStepProgram + 120 s timeout and the §5 auto-resume remain the only robust recovery. But they lower how often we light the fuse. Forensics: /work/projects/imas_gpu/logs/drain-sidecar-1219733.{csv,smi,node}.

§3 — Proposed Change 1: UnkillableStepProgram + Timeout Increase

Request: Configure UnkillableStepProgram (currently (null)) with a root diagnostic and recovery handler, and raise UnkillableStepTimeout from 60 s to 120 s in the betelgeuse partition config (or slurm.conf).

Why the timeout matters. Multi-GPU NCCL teardown — the dominant workload on this node — legitimately takes 30–60 s in clean conditions. UnkillableStepTimeout = 60 s means that a clean teardown at the slow end of its normal range triggers a drain. The hard cap is 126 s (SchedMD bug #11103). Raising to 120 s gives healthy teardown adequate margin without approaching the cap.

Why UnkillableStepProgram matters. When a step is declared unkillable, SLURM runs this program as root before draining. It is the only point where kernel-level diagnostics can be captured (e.g. /proc/<pid>/stack, /proc/sysrq-trigger) and where an automated recovery can be triggered. Without it, every drain requires manual intervention. With it, the handler can: diagnose, reset the GPU(s), and schedule a node resume — all within the SLURM drain window.

Proposed handler script (/etc/slurm/unkillable_step.sh):

#!/bin/bash
# /etc/slurm/unkillable_step.sh
# Run as root when a step is declared unkillable (before node drain).
# Env provided by SLURM: SLURM_JOB_ID, SLURM_JOB_NODELIST, SLURMD_NODENAME

LOG="/var/log/slurm/unkillable_${SLURM_JOB_ID}_$(date +%Y%m%d_%H%M%S).log"
exec > "$LOG" 2>&1
set -x

echo "=== UnkillableStep handler: job $SLURM_JOB_ID on $(hostname) ==="
date

# 1. Capture kernel state for RCA
echo "--- /proc/*/stack for cgroup PIDs ---"
CGPATH=$(systemctl show --property=ControlGroup "slurmstepd.scope" 2>/dev/null | cut -d= -f2)
if [[ -n "$CGPATH" ]]; then
    for pid in $(cat "/sys/fs/cgroup${CGPATH}/cgroup.procs" 2>/dev/null); do
        echo "PID $pid stat=$(cat /proc/$pid/stat 2>/dev/null | awk '{print $3}') wchan=$(cat /proc/$pid/wchan 2>/dev/null)"
        cat /proc/$pid/stack 2>/dev/null || true
    done
fi

echo "--- nvidia-smi ---"
nvidia-smi 2>&1 || true

echo "--- nvidia-smi accounting ---"
nvidia-smi --query-accounted-apps=gpu_uuid,pid,gpu_name,mem_used -d RUNNING 2>&1 || true

echo "--- dmesg NVRM/Xid (last 50 lines) ---"
dmesg 2>/dev/null | grep -iE 'NVRM|Xid|nvidia' | tail -50 || true

echo "--- sysrq-w (kernel task state dump to dmesg) ---"
echo w > /proc/sysrq-trigger 2>/dev/null || true
sleep 2
dmesg 2>/dev/null | tail -30

# 2. Attempt GPU reset for each GPU assigned to the job
echo "--- GPU reset attempt ---"
GPUS=$(scontrol show job "$SLURM_JOB_ID" 2>/dev/null \
       | grep -oP 'GRES=gpu:\d+\(IDX:\K[0-9,]+' || true)
if [[ -n "$GPUS" ]]; then
    for gpu in $(echo "$GPUS" | tr ',' ' '); do
        echo "Attempting nvidia-smi --gpu-reset -i $gpu ..."
        timeout 120 nvidia-smi --gpu-reset -i "$gpu" 2>&1 || echo "Reset failed or timed out for GPU $gpu"
    done
else
    echo "Could not determine GPU indices from scontrol; skipping per-GPU reset"
fi

# 3. Verify GPU health before scheduling resume
echo "--- post-reset nvidia-smi ---"
nvidia-smi 2>&1 || true

UNHEALTHY=$(nvidia-smi 2>&1 | grep -c "ERR\|Failed\|Xid" || true)
if [[ "$UNHEALTHY" -eq 0 ]]; then
    echo "GPUs appear healthy — scheduling node resume in 30s"
    (sleep 30 && scontrol update nodename="$SLURMD_NODENAME" \
        state=resume reason="auto-recovered: UnkillableStepProgram GPU reset OK") &
else
    echo "GPU health check failed — leaving node drained; manual intervention required"
    echo "See $LOG for diagnostics"
fi

echo "=== Handler complete ==="

Proposed slurm.conf additions (betelgeuse partition or global, whichever is appropriate):

# Raise timeout: 60s tips normal NCCL teardown into a drain; 120s gives healthy jobs margin.
# Hard cap is 126s (SchedMD bug #11103).
UnkillableStepTimeout=120

# Root handler: diagnose + attempt recovery before the node is left drained.
UnkillableStepProgram=/etc/slurm/unkillable_step.sh

Risks and caveats:

  • The GPU-reset attempt inside the handler uses timeout 120 to prevent the handler itself from hanging if the GPU is in a deeply wedged state. If reset times out, the node is left drained — the same outcome as today, but with a diagnostic log.
  • Per-GPU reset index detection from scontrol may need adjustment depending on GRES format. The script includes a fallback note.
  • The 30-second delay before scontrol resume gives the GPU driver time to re-initialise after reset. This is a conservative estimate; reduce if empirically safe.
  • UnkillableStepProgram must be executable by root and located on all nodes where it will run.

§4 — Proposed Change 2: Epilog GPU-Clean Gate

Request: Add a SLURM epilog script for the betelgeuse partition that verifies no compute processes remain and that the GPUs are clean after each GPU job completes. If the check fails, drain-with-reason rather than releasing the node to the next job.

Why this is the cascade-breaker. The 2026-06-02 RCA identified that production drains are a cascade: the 2026-05-26 Event 0 left a dirty GPU, and each subsequent NCCL teardown wedged permanently on that dirty context. Without a clean-gate, an incomplete or abbreviated recovery (admin resumes before GPUs are confirmed clean) allows a wedged GPU context to propagate to the next job. The epilog gate breaks the cascade at job boundaries: if any GPU process remains after a job exits, the node is drained before the next allocation.

Proposed epilog script (/etc/slurm/epilog.d/10_gpu_clean_gate.sh):

#!/bin/bash
# /etc/slurm/epilog.d/10_gpu_clean_gate.sh
# Only run for jobs with GPU allocation.
[[ -z "$CUDA_VISIBLE_DEVICES" ]] && exit 0

LOG="/var/log/slurm/epilog_gpu_${SLURM_JOB_ID}_$(date +%Y%m%d_%H%M%S).log"
exec > "$LOG" 2>&1

echo "=== GPU epilog gate: job $SLURM_JOB_ID ==="
date

FAIL=0

# 1. Check for residual compute processes on assigned GPUs
RESIDUAL=$(nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader \
    --id="$CUDA_VISIBLE_DEVICES" 2>/dev/null | grep -c . || true)
if [[ "$RESIDUAL" -gt 0 ]]; then
    echo "ERROR: $RESIDUAL residual compute process(es) still hold GPU(s) $CUDA_VISIBLE_DEVICES"
    nvidia-smi --query-compute-apps=pid,used_memory,process_name --format=csv \
        --id="$CUDA_VISIBLE_DEVICES" 2>&1 || true
    FAIL=1
fi

# 2. Check for GPU error / Xid state
XID_ERR=$(dmesg 2>/dev/null | grep -c "Xid" || true)
if [[ "$XID_ERR" -gt 0 ]]; then
    echo "WARNING: $XID_ERR Xid error(s) in dmesg since last boot"
    dmesg 2>/dev/null | grep "Xid" | tail -10
    # Xid alone is informational; only fail if combined with residual procs
fi

# 3. Drain node if GPUs are not clean
if [[ "$FAIL" -ne 0 ]]; then
    echo "DRAIN: GPUs not clean after job $SLURM_JOB_ID — draining node to prevent cascade"
    echo "See $LOG for details"
    scontrol update nodename="$(hostname -s)" \
        state=drain reason="epilog: GPU not clean after job $SLURM_JOB_ID — see $LOG"
    exit 1
fi

echo "GPU clean gate: PASS"
exit 0

Recommended prolog (/etc/slurm/prolog.d/10_gpu_clean_check.sh) to refuse a new allocation on a node where GPUs are still held:

#!/bin/bash
# /etc/slurm/prolog.d/10_gpu_clean_check.sh
[[ -z "$CUDA_VISIBLE_DEVICES" ]] && exit 0

RESIDUAL=$(nvidia-smi --query-compute-apps=pid --format=csv,noheader \
    --id="$CUDA_VISIBLE_DEVICES" 2>/dev/null | grep -c . || true)
if [[ "$RESIDUAL" -gt 0 ]]; then
    echo "PROLOG FAIL: GPUs $CUDA_VISIBLE_DEVICES still have $RESIDUAL process(es) — rejecting allocation"
    exit 1
fi
exit 0

Risks and caveats:

  • Never call nvidia-smi --gpu-reset while a process holds the device — it will hang. The epilog here only drains; reset must happen after the process has been cleared (manually or via UnkillableStepProgram).
  • The CUDA_VISIBLE_DEVICES variable is set by SLURM for GPU jobs. Verify the variable name matches SLURM's GRES plugin configuration on this cluster (it may be SLURM_JOB_GPUS depending on version).
  • False positives are possible if a job's GPU teardown is slower than SLURM's epilog timeout. Adding a short sleep (5–10 s) before the residual check reduces this risk.
  • Multi-tenant use: if two groups share GPUs on the same node (not the case for this reservation, but worth noting), the check must be restricted to the GPUs allocated to the completing job.

§5 — Proposed Change 3: HealthCheckProgram Auto-Resume

Request: Configure a HealthCheckProgram for the betelgeuse partition (or node) that polls GPU health periodically and triggers a node resume when the GPUs pass a health check, eliminating the need for a human to issue scontrol resume after a successful GPU reset.

Option A — SLURM HealthCheckProgram (preferred). Available in SLURM 23.11+; runs on the node at HealthCheckInterval second intervals:

# In slurm.conf (global or partition override):
HealthCheckProgram=/etc/slurm/health_check_gpu.sh
HealthCheckInterval=60
HealthCheckNodeState=ANY

#!/bin/bash
# /etc/slurm/health_check_gpu.sh
# Returns 0 if node is healthy; non-zero to keep drain / trigger re-drain.

# Check all GPUs are accessible and not in error state
if ! nvidia-smi -q &>/dev/null; then
    echo "health_check: nvidia-smi failed — node not healthy"
    exit 1
fi

# Check no residual compute processes from prior jobs
RESIDUAL=$(nvidia-smi --query-compute-apps=pid --format=csv,noheader 2>/dev/null \
    | grep -c . || true)
if [[ "$RESIDUAL" -gt 0 ]]; then
    echo "health_check: $RESIDUAL residual GPU process(es) remain — not resuming"
    exit 1
fi

# Check for zombie processes (should not exist after clean job teardown)
ZOMBIES=$(ps -eo stat | grep -c "^Z" || true)
if [[ "$ZOMBIES" -gt 5 ]]; then
    # Threshold 5 to avoid false positives from unrelated system zombies
    echo "health_check: $ZOMBIES zombie processes — not resuming"
    exit 1
fi

echo "health_check: PASS — all GPUs healthy, no residual processes"
exit 0

When HealthCheckProgram returns 0 and the node is in a drained state, SLURM 23.11+ will automatically issue an internal resume. Confirm the exact behaviour with the installed SLURM version — the auto-resume semantics vary between minor versions.

Option B — Cron fallback (if HealthCheckProgram auto-resume is not available or not suitable for this deployment):

#!/bin/bash
# /etc/cron.d/slurm_gpu_auto_resume — runs every 5 minutes as root
NODE="98dci4-gpu-0003"

STATE=$(scontrol show node "$NODE" 2>/dev/null | grep -oP 'State=\S+')
if echo "$STATE" | grep -qi "drain"; then
    # Node is drained — check if GPUs are now clean
    RESIDUAL=$(ssh -o BatchMode=yes "$NODE" \
        "nvidia-smi --query-compute-apps=pid --format=csv,noheader 2>/dev/null | grep -c ." \
        2>/dev/null || echo 99)
    if [[ "$RESIDUAL" -eq 0 ]]; then
        nvidia-smi_status=$(ssh -o BatchMode=yes "$NODE" "nvidia-smi -q" 2>/dev/null; echo "EXIT=$?")
        if echo "$nvidia_smi_status" | grep -q "EXIT=0"; then
            scontrol update nodename="$NODE" state=resume \
                reason="auto-resume: health check passed (cron)"
            logger -t slurm_auto_resume "Resumed $NODE after health check"
        fi
    fi
fi

Risks and caveats:

  • The HealthCheckProgram auto-resume behaviour in SLURM requires verification against the exact installed version. In some versions it only clears the NOT_RESPONDING state, not a manual drain.
  • Option B requires SSH access from the admin host to the GPU node, which may not be available outside of a SLURM allocation context. Adjust to use SLURM's srun --nodelist if needed.
  • Both options should be preceded by a GPU reset step (see §3 handler). Auto- resume without a preceding reset is only safe when the prior drain was not GPU-wedge-related (e.g., the 2026-05-27b TCP I/O event). For GPU-wedge drains, the reset is required first — which is why §3 and §5 are complementary.

§6 — Why This Is Urgent

  • Drain frequency: 4 drain events in 13 days (2026-05-26 to 2026-05-28), plus an accidental drain during controlled drain-window testing (job 1209813). The instrumented campaign has produced 14 controlled attempts with 0 intentional drains — the drain trigger is understood to require a pre-wedged GPU state — but production conditions can re-create that precondition.
  • Outage duration per event: 2–4 hours, dominated by notification latency and manual response time. None of the four events self-recovered.
  • Lost GPU-hours (Group A): Conservatively 4 × 2 h × 4 GPUs = 32 GPU-hours lost to drain recovery. At H200 spot pricing (~$4–8/GPU-h), this is $128–$256 in equivalent compute time across four events, not counting researcher productivity.
  • Node uniqueness: 98dci4-gpu-0003 is the sole H200 NVLink node in Group A's allocation. There is no failover. Every drain is a complete work stoppage for Group A GPU workloads.
  • Group B impact: Group B shares the same physical node under a separate reservation. All four drain events took the node offline for both groups simultaneously. sacct analysis confirmed no Group B involvement in causing the drains, but Group B bears recovery cost equally.
  • Root cause timeline: The drain-window-campaign (active) is investigating the root cause under a coordinated admin window. That investigation may take additional weeks. Recovery automation provides immediate blast-radius reduction independent of root cause resolution.

§6a — Prevention vs recovery: what eliminates the drain vs what bounds it

This is, by design, a recovery proposal — it shrinks the outage from 2+ hours to under 5 minutes without requiring the root cause to be eliminated first. That is the right immediate lever because the root cause is environmental and outside application control (§1a). For completeness, the full prevention picture:
