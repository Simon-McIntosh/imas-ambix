§0 — TL;DR

The problem with our analysis is methodological, not technical. Fourteen reproduction attempts have failed to drain the node on demand (13 deliberate attempts: 0 drains; 1 accidental drain, job 1209813). Every deliberate attempt bisected forward from a guess — pick a candidate wedge (infinite kernel, blocking event sync, rwlock deadlock, NCCL teardown), build it, watch it get reaped cleanly. That search has a 0/13 record and each attempt is itself the top drain risk on the only H200 node. We are searching the wrong way.

New direction. We already own a confirmed drain artifact: the exact pre-928ed0d MWE-01 code that drained the node as job 1209813. Instead of guessing forward, resurrect that exact code and bisect backward from a known-draining state — removing one element per run until the drain stops. And for the first time, capture the SLURM side of the chain (slurmd log, full Reason= string, UnkillableStepTimeout value, live cgroup-PID enumeration through the give-up window) — the half every RCA inferred but none ever observed.

Execution. One coordinated drain window with an SDCC admin standing by to resume. Run Track C first (deterministic non-GPU cgroup wedge — validates the capture stack + the SLURM chain + the admin recovery loop without risking GPU state), then Track A (faithful resurrection + backward bisection). Track B (a new hypothesis-led reproducer) is held in reserve. In parallel, no window needed: a Recovery-track admin proposal so any future drain self-heals in minutes rather than hours.

§1 — Why the current analysis is wrong

Six RCA/evidence documents (rca-node-drain-2026-05-27{,b}.html, -05-28.html, rca-drain-deep-analysis-2026-06-01.html, drain-mwe-evidence-2026-06-01.html, rca-node-drain-mechanism-2026-06-02.html) and the scripts/drain-tests/ suite were audited. The audit found a coherent story resting on an unobserved causal half, plus internal contradictions the latest doc papers over rather than resolves.

Three contradictions the documents never reconcile

  • Healthy-GPU risk flips. The 05-27 and 05-28 RCAs claim ordinary CUDA/NCCL operations on a healthy GPU drove a permanent D-state → drain. The 06-02 RCA flips this: D-state on a healthy GPU is transient (lock released in ms, task oscillates D→R, queued SIGKILL lands), and a sustained drain requires a GPU already wedged by an earlier failure. These cannot both be true.
  • Event 3 causality retracted-by-implication. The 05-28 RCA blames an agent scancel on a healthy DDP job. The 06-02 "cascade-only" conclusion implies the drain came from an already-wedged GPU seeded by an earlier event — quietly contradicting the 05-28 narrative without ever re-analysing it.
  • NCCL teardown state: D vs S. The earlier docs assert the ncclCommAbort() teardown is D-state (uninterruptible). MWE-06b (job 1209935) measured it as S-state (interruptible): SLURM fired mid-teardown and SIGTERM landed in <1 s. The 06-02 RCA still cites the D-state teardown path (NCCL upstream #829) as the surface of the two logged drains, never reconciling the measurement that contradicts it.

The single methodological flaw

Every deliberate reproduction started from a clean, single-user, reserved node and guessed forward toward a wedge. The strongest possible synthetic case — an infinite GPU kernel plus a blocking event sync (blocksync, job 1210259), explicitly built so "SIGKILL cannot reap" — was reaped cleanly at the time limit. The rwlock-deadlock readers (1210274) never blocked: 150 000+ malloc/free cycles still progressing. On this node's current stack we cannot manufacture a sustained unkillable process on demand. That is a strong, repeatable result — and it tells us the trigger lives in conditions a clean synthetic test does not recreate, OR in the one artifact we already captured and keep walking past.

Two principles replace "guess a wedge, build it, hope it drains":

  1. Bisect backward from the confirmed artifact, not forward from a guess. Resurrect the exact pre-928ed0d MWE-01 v1 (the collective-mismatch code that ran as 1209813) verbatim, version-pinned and frozen. If it drains, we hold the first end-to-end captured mechanism. Then remove one element per run — full DDP backward → raw collectives; kill-timing alignment; rank teardown order — until the drain stops. The element whose removal stops the drain is the minimal trigger. A probabilistic race is budgeted for (repeat the verbatim run before concluding — see decision window-repeat-count).
  2. Close the SLURM-side gap on every run. A standing capture harness records, alongside the existing observer (/proc/<pid>/stat + wchan + dmesg/Xid + nvidia-smi): the slurmd/slurmstepd log tail, the live scontrol show node Reason=, the UnkillableStepTimeout/KillWait config, and a per-second enumeration of all PIDs in the job cgroup with their state/wchan through the give-up window. For the first time both halves of the causal chain are observed in the same event.

§6 — Safety guardrails (binding)

  • No drains outside the coordinated window. Per the user decision, there is no standing forensic sidecar on production jobs; all intentional drains happen only with an admin on standby.
  • No scancel on any CUDA/GPU job (AGENTS.md §2a rule #5) — the in-window kills use SLURM --time expiry by design (that is the trigger under test), never an agent scancel.
  • Admin confirms GPUs clean before resume — resume only after nvidia-smi --gpu-reset / reboot verifies clean GPUs, else the next run inherits a dirty device and confounds the bisection.
  • Each run resets the board. Backward bisection is only valid if every run starts from a confirmed-clean node; the admin loop guarantees this.
