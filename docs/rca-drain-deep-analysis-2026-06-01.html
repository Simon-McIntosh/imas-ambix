Research / Reference — Definitive drain-event analysis for node 98dci4-gpu-0003 covering all events from 2026-05-26 through 2026-05-28. Four drain events (one ambiguous, three self-inflicted) plus one near-miss. Total cost: ≥ 2 h of unplanned downtime across three consecutive days on the project's only H200 node. This document synthesises findings across five individual RCAs, maps each event to a root kernel mechanism, assesses current code hardening status, and defines a test and admin-change programme to eliminate residual risk.

DO NOT submit SLURM jobs based on this document. Test plans are design-only until approved and scheduled.

Event 0 detail — CUDA Init Failure (2026-05-26 18:18)

cuInit() rc=3 (CUDA_ERROR_NOT_INITIALIZED) — the CUDA runtime API became non-functional while NVML continued to respond normally. This is the canonical symptom of the NVIDIA driver state machine entering an inconsistent state between two cgroup contexts sharing a physical device. Group B's job (murawan/1208566) started at approximately the same time. Exact attribution cannot be determined without NVIDIA driver-level tracing. Hypothesis: concurrent cuInit() from two different user spaces under separate cgroups triggered a race in the driver's device-initialisation lock, leaving one context in a half-initialised state.

Key observables:

  • nvidia-smi (NVML path) reported GPUs normally — driver alive
  • cuInit() (CUDA Runtime path) returned error 3 — user-space runtime path broken
  • Node state: DOWN+DRAIN+NOT_RESPONDING
  • Recovery required full module reload and reboot — driver-level reset insufficient

Event 1 detail — Prefetch Deadlock (2026-05-27 12:04)

Job 1208195 ran the rbb bulk-encode pipeline with the legacy prefetch double-buffer enabled (commit 4f7ab48). Architecture: a bounded queue.Queue fed by a producer thread pool (one thread per shot), drained by a consumer that encoded frames and wrote to Zarr. One producer raised an exception on a malformed shot. The exception killed the producer thread without signalling the queue (no sentinel, no error queue). The consumer called queue.get() on an empty queue with no producers alive — deadlock.

At this point the main process was in a valid Python-level block but inside a blocking C call (queue.get() with timeout=None → sem_timedwait in glibc → kernel futex wait). The CUDA context was live (VQModel loaded). When scancel arrived, SIGTERM queued but could not fire because the Python interpreter was in the kernel futex wait — a D-state from the scheduler's perspective. Result: UnkillableStepTimeout expired → drain.

Token freeze observable: progress was frozen at 2,119 shots with zero delta over 30 s — the monitoring heuristic that detected the hang before it became a manual intervention.

Event 2 detail — Network I/O Hang (2026-05-27 16:04)

Job 1208591 (ambix-bsprobe) was submitted with the wrong working directory. VQModel.__init__() invokes LPIPS vendored code which resolves vgg.pth using a CWD-relative path. With the wrong CWD the file was not found. LPIPS fell back to downloading it from heibox.uni-heidelberg.de. However, the betelgeuse partition has no outbound network — the firewall DROPs (not REJECTs) packets. A DROP causes the TCP client to wait for the full retransmission timeout (kernel default: ~2–7 min for the SYN sequence). The urllib download call entered kernel I/O wait — D-state — before any CUDA context was ever created.

Key insight: no GPU involved. The drain was caused by a non-CUDA network hang. This demonstrates that the drain mechanism is a general property of uninterruptible kernel sleep (D-state), not specific to CUDA or NCCL. Any syscall that enters uninterruptible wait — read(), connect(), sem_wait(), futex(), ioctl() on a hung device — produces the same unkillable condition and the same drain outcome.

Event 3 detail — Agent scancel on Healthy DDP (2026-05-28 13:52)

Job 1208975 (single-GPU finetune) was running normally — training, full GPU utilisation, loss decreasing — when the orchestrating agent issued scancel 1208975 to free the reservation so it could apply a code fix. At the moment SIGTERM arrived, rank-0 was inside loss.backward(), which calls into cuBLAS and NCCL collectives (dist.all_reduce for gradient synchronisation). Python signal handlers only run between bytecodes; the interpreter was deep in C++ code and could not process the pending SIGTERM for the duration of the backward pass (measured at 0.8–2 s per step, but potentially longer under load).

The existing AGENTS.md §2a rule at the time prohibited scancel on wedged jobs. Job 1208975 was healthy — the rule did not apply by its literal text. This was a rule-gap failure, not a rule-violation failure. The rule has been strengthened to prohibit scancel on any CUDA-DDP job.

After 1208975 drained the node, job 1208980 (4-GPU DDP) launched into a dirty node — inheriting orphaned CUDA contexts — and amplified the incident by holding GPU memory that blocked recovery.

§2 — The five failure mechanisms

Every event maps to one or more of five root mechanisms. Understanding each mechanism independently is the key to selecting the right countermeasure.

M1 — Python signal handler blocked by C++

This is the most counterintuitive mechanism and the one that underlies three of four self-inflicted events. Python's signal handling model guarantees only that signals are noticed between bytecodes — specifically, the eval_breaker flag is set by the OS signal handler (a very short C function), and the interpreter checks this flag at the start of each bytecode evaluation. The key word is between: while Python is inside a C extension (any call that does not return to the bytecode evaluator), the eval_breaker check cannot run.

For CUDA workloads this means the window of vulnerability is the duration of any CUDA kernel, synchronise call, or NCCL collective. These calls can last milliseconds (simple operations) to multiple seconds (backward pass with NCCL all-reduce across 4 GPUs on NVLink). During this window, a SIGTERM is queued but silent.

The practical consequences:

  • A try: ... except KeyboardInterrupt or signal.signal(SIGTERM, handler) does nothing while inside a NCCL call. The exception or handler cannot fire.
  • threading.Event flags set from the signal handler don't help the main thread — it's still blocked in C++.
  • Even ctypes.pythonapi.PyErr_SetInterrupt() from another thread has the same limitation: the flag is set, but the main interpreter loop isn't running.
  • The only reliable way to exit cleanly is to check a stop condition at a Python-controlled boundary between C calls — this is exactly what the STOP-FILE polling mechanism provides.

M2 — Uninterruptible kernel sleep (D-state)

Linux process states relevant to this incident:

StateCodeDescriptionSignals received?SIGKILL effective?
RunningROn CPU or runqueueYesYes
Interruptible sleepSWaiting, can be interruptedYesYes
Uninterruptible sleepDKernel I/O or device operation in progressNoNo — must complete kernel call first
ZombieZExited, parent hasn't reapedNoNo (already dead)

A D-state process cannot receive signals of any kind until the kernel call completes. This is by design — interrupting a kernel write to a block device or a network socket mid-operation would leave kernel data structures in an inconsistent state. The problem is that for some operations — a blocked TCP connection to a dropped-packet firewall, a hung GPFS operation, a wedged CUDA ioctl — the kernel call never returns. The process is permanently D-state.

SLURM's kill sequence:

  1. scancel or time-limit fires → SIGTERM sent to job step
  2. SLURM waits UnkillableStepTimeout (default 60 s on betelgeuse)
  3. SIGKILL sent → also ineffective for D-state processes
  4. SLURM waits a second internal timeout
  5. slurmd logs "Kill task failed" → node marked DRAIN

The drain is therefore triggered by the combination of D-state + timeout expiry, not by the signal itself. A process that handles SIGTERM cleanly within the timeout window (i.e., is in S or R state when SIGTERM arrives) will never cause a drain.

M3 — Producer/consumer thread deadlock

The legacy bulk_encode_frames.py prefetch architecture (commit 4f7ab48) used a bounded queue.Queue(maxsize=2) with a thread pool of producers (one per shot batch) and a single consumer that drove the VQModel encoder. The critical missing invariant: producers did not send a sentinel or signal on exception. A failed producer silently exited the thread; the consumer continued calling queue.get(timeout=None) on an empty queue with all producers dead — a classic producer/consumer deadlock.

The underlying queue.get() with no timeout calls Condition.wait() → threading.Condition → pthread mutex → futex → TASK_UNINTERRUPTIBLE sleep. The process is now D-state and the M2 mechanism takes over. This is why retiring the legacy architecture was not merely a performance fix (though it delivered 308 fps vs the legacy's throughput) but a safety fix.

The replacement (stream_encode.py) uses a torch DataLoader with worker processes (not threads), a bounded prefetch factor, and explicit error propagation via DataLoader's standard exception channel. The main process never blocks on a queue indefinitely — the DataLoader worker pool has a defined timeout, and a crashed worker surfaces as an exception in the main iterator loop.

M4 — Network I/O D-state

The betelgeuse partition's firewall policy DROPs outbound packets rather than REJECTing them. The distinction matters enormously:

PolicyClient behaviourD-state durationDrain risk
DROP (current) SYN sent, no reply → kernel TCP retransmit: exponential backoff up to ~127 s; connect() returns ETIMEDOUT after full sequence Up to ~2–7 min HIGH — well beyond UnkillableStepTimeout
REJECT (recommended) SYN sent → immediate RST → connect() returns ECONNREFUSED in < 1 ms < 1 ms NONE — Python exception propagates normally

With a REJECT policy, any accidental outbound connection attempt fails fast — the exception propagates back to Python, the job logs an error, and the user can fix the problem. The drain cannot occur. This is the single highest-leverage admin change for eliminating M4.

The preflight assertions (HF_HUB_OFFLINE=1, assert vgg.pth.exists() in sbatch) are application-level mitigations that prevent the wrong-CWD trigger; the REJECT-not-DROP policy is the infrastructure-level backstop that prevents any accidental network hang from draining the node regardless of cause.

M5 — cgroup CUDA context collision

Event 0 is the least well-understood mechanism. The observable was: NVML (accessed via nvidia-smi C API, which bypasses the CUDA runtime) showed the GPUs healthy, but the CUDA Runtime API returned CUDA_ERROR_NOT_INITIALIZED for any cuInit() call in the Group A cgroup context.

The NVIDIA driver maintains a per-device initialisation state machine. When two user-space CUDA runtimes initialise simultaneously on the same physical device — even under separate cgroup namespaces — they share a single driver-side device struct. A race in the driver's device-init lock (hypothesised; not confirmed without NVIDIA source access) could leave the device's runtime state set to "initialising by another process" from Group A's perspective, causing all subsequent cuInit() calls to return error 3.

This mechanism requires coordination with Group B and NVIDIA to reproduce and confirm. Test T4 (§5) defines the minimal reproduction. This is the only event where the fix is primarily on the NVIDIA side (MPS, MIG, or driver fix).

§3 — Kernel mechanism: why SIGKILL doesn't work

A common misconception is that SIGKILL is the "ultimate" termination signal that always works. This is false for processes in TASK_UNINTERRUPTIBLE (D-state). Understanding why requires looking at what the kernel actually does when a D-state process receives SIGKILL.

Normal signal delivery

For a running or interruptible-sleeping process:

  1. Signal sent to process → kernel sets pending signal bit in task_struct.pending
  2. Kernel sets TIF_SIGPENDING flag on the task
  3. On the next return from kernel to user space (syscall return, interrupt return), the kernel checks TIF_SIGPENDING
  4. If set, kernel calls do_signal() → signal delivered to process
  5. For SIGKILL: kernel calls do_exit() → process terminates

D-state signal delivery

For a D-state process the sequence breaks at step 3:

  1. Signal sent → task_struct.pending updated, TIF_SIGPENDING set — same as above
  2. Process is in TASK_UNINTERRUPTIBLE inside a kernel wait (e.g. wait_for_completion(), mutex_lock() in a driver, page_fault() for I/O). The wait function does NOT check TIF_SIGPENDING — that is the definition of uninterruptible.
  3. The process never returns to user space. Step 3 above never triggers. Signals accumulate in pending but cannot be delivered.
  4. SIGKILL has no special path through D-state waits — it requires the same "return to user space" checkpoint that all other signals need.

Why CUDA enters D-state

CUDA operations that enter D-state include:

  • ioctl(fd, NVIDIA_IOCTL_ALLOC_MEMORY, ...) — GPU memory allocation via the NVIDIA kernel module. The driver may block waiting for GPU firmware responses.
  • ioctl(fd, NVIDIA_IOCTL_GPU_RUN_SYNC, ...) — synchronisation barrier. Blocks until all previously submitted CUDA kernels complete. If a kernel hangs, this blocks forever.
  • NVLink P2P operations — NCCL uses NVLink for inter-GPU communication. The kernel-side NVLink driver enters uninterruptible waits during data transfers.
  • GPFS file operations — read(), write() on GPFS can enter D-state during network retransmissions.

The UnkillableStepTimeout sequence in detail

# Timeline for a D-state process under scancel:
t=0s:   scancel issued → SLURM sends SIGTERM to all processes in job step
t=0s:   SIGTERM pending in task_struct — PROCESS DOES NOT NOTICE (in D-state)
t=60s:  UnkillableStepTimeout expires → SLURM sends SIGKILL
t=60s:  SIGKILL pending in task_struct — ALSO INEFFECTIVE (still D-state)
t=~62s: SLURM waits second internal timeout for SIGKILL to take effect
t=~62s: slurmd concludes task cannot be killed → logs "Kill task failed"
t=~62s: slurmd calls slurmctld to mark node DRAIN
t=~62s: Node leaves reservation pool — GROUP A LOSES ALL GPU ACCESS

The cgroup v2 kill path

Linux cgroups v2 (kernel 5.14+) added a cgroup.kill interface that writes 1 to /sys/fs/cgroup/.../cgroup.kill, which causes the kernel to kill all processes in the cgroup atomically via the cgroup lifecycle mechanism rather than via signal delivery. This path CAN reap D-state processes because it works at the cgroup-teardown level — the kernel removes the cgroup, which causes the associated memory and device resources to be released, allowing the D-state wait to unblock. This is the mechanism behind admin recommendation R3.

Why the STOP-FILE approach fundamentally avoids D-state

The STOP-FILE polling mechanism works because the training loop checks the stop condition between CUDA calls, at a point in time when the Python interpreter is in user space and the CUDA synchronize has already returned. Specifically, the check happens after optimizer.step() completes (all CUDA kernels flushed) and before the next model(batch) call. At this moment:

  • The Python interpreter is running bytecodes (not in C++)
  • No CUDA kernels are in flight
  • No NCCL collectives are in progress
  • A simple Path.exists() call (a fast, interruptible VFS stat) returns immediately
  • If the file exists, the Python code voluntarily calls break → teardown → exit 0

The process never enters D-state; SLURM never needs to send SIGTERM; the node is never drained.

preempt_v4flash.sh — MEDIUM RISK (inference server)

Uses scancel directly — but inference servers (SGLang/vLLM) are not DDP training jobs, so the drain risk is materially lower.

Inference servers load the model once and serve many requests concurrently via a thread pool or async event loop. They typically are NOT inside NCCL collectives — they use tensor-parallel operations that are structured differently. However, a mid-inference CUDA kernel (especially during a long prefill) could still enter D-state if scancel arrives at an unfortunate moment.

Recommended approach: Before issuing scancel, call the server's graceful-shutdown API endpoint (SGLang provides POST /flush_cache and a stop mechanism; vLLM has similar). Wait for in-flight requests to complete, then use a stop-file or shutdown API, and only fall back to scancel as a last resort.

§6 — Test plans (design only — DO NOT SUBMIT JOBS)

Six minimal reproducers. Each is designed to isolate one mechanism and confirm or deny the hypothesised behaviour. All require scheduling and user approval before running. The goal is: (a) vendor bug reports with minimal reproducers, (b) confirmation of SLURM config values (UnkillableStepTimeout), and (c) validation that fixes work as intended.

T1 — Minimal Unkillable D-State (CUDA)

Purpose: Confirm the exact UnkillableStepTimeout value on betelgeuse and establish a baseline D-state repro with no training or NCCL complexity.

Mechanism tested: M2

Expected outcome: Process enters D-state, SLURM escalates to SIGKILL after ~60 s, then marks "Kill task failed" and drains node.

Script design (do not run — design only):

#!/usr/bin/env python3
# t1_minimal_d_state.py — DESIGN ONLY, DO NOT SUBMIT
# Purpose: Enter CUDA D-state via a blocking synchronize loop
# Requires: --gres=gpu:1, submitted to betelgeuse with --time=00:05:00
import torch, time, signal, sys

def handler(signum, frame):
    print(f"[t1] Received signal {signum} at {time.time():.2f}", flush=True)
    # Intentionally do nothing — we are testing D-state unkillability
    pass

signal.signal(signal.SIGTERM, handler)
signal.signal(signal.SIGINT, handler)

device = torch.device("cuda:0")
torch.cuda.init()
print(f"[t1] CUDA initialised. PID={os.getpid()}", flush=True)

# Fill GPU with a large tensor to ensure CUDA context is fully initialised
x = torch.ones(1024, 1024, 1024, dtype=torch.float16, device=device)
torch.cuda.synchronize()

print("[t1] Entering infinite synchronize loop — will enter D-state", flush=True)
t_start = time.time()
while True:
    # Launch a kernel that runs forever
    # torch.cuda.synchronize() after it will block in D-state
    torch.matmul(x[:1024, :1024], x[:1024, :1024])  # fast, completes
    time.sleep(1)
    print(f"[t1] Alive at t={time.time()-t_start:.0f}s", flush=True)
    # After scancel: expect SIGTERM to be "received" (handler prints) but
    # process to NOT exit — handler fires between bytecodes in the sleep()
    # After 60s: expect SIGKILL → no effect → drain

Measurement protocol:

  1. Submit job; wait for "Entering infinite synchronize loop" in log
  2. Issue scancel <jobid> from login node
  3. Record: (a) time from scancel to "Kill task failed" in slurmd log, (b) whether handler printed "Received signal 15", (c) whether process appeared in D-state in ps -eo pid,stat,cmd
  4. Observe whether node drains; if so, record drain timestamp vs scancel

Alternative (non-draining) version: Modify the loop to check a stop-file before each torch.matmul. Touch the stop-file from login node. Confirm: process exits cleanly within 1 loop iteration (~1 s). Node not drained. This validates the STOP-FILE bypass.

Node drain risk: HIGH. This test is designed to drain the node. Only run when an admin is standing by to resume immediately. Coordinate with SDCC before submitting.

T2 — NCCL Collective Signal Test (2-rank)

Purpose: Confirm that (a) scancel on a 2-rank DDP job in the middle of dist.all_reduce drains the node, and (b) the STOP-FILE mechanism exits cleanly from the same code path.

Mechanism tested: M1 + M2

STOP_FILE = pathlib.Path(os.environ.get("AMBIX_STOP_FILE", "/tmp/t2.stop"))

def handler(signum, frame):
    print(f"[t2 rank{rank}] SIGTERM received at t={time.time():.2f}", flush=True)

dist.init_process_group("nccl")
rank = dist.get_rank()
device = torch.device(f"cuda:{rank}")

signal.signal(signal.SIGTERM, handler)
print(f"[t2 rank{rank}] init complete. STOP_FILE={STOP_FILE}", flush=True)

x = torch.ones(256, 256, 256, device=device)
step = 0

while True:
    step += 1
    # Check stop-file FIRST — before any CUDA
    if STOP_FILE.exists():
        print(f"[t2 rank{rank}] STOP-FILE detected at step {step} — clean exit", flush=True)
        break
    
    # Simulate forward+backward: large NCCL collective
    loss = x.mean()
    loss.backward()
    dist.all_reduce(x.grad, op=dist.ReduceOp.SUM)  # This is the dangerous moment
    x.grad = None
    torch.cuda.synchronize()
    
    print(f"[t2 rank{rank}] step {step} complete", flush=True)
    time.sleep(2)  # Slow loop so we can issue scancel during all_reduce

dist.destroy_process_group()
print(f"[t2 rank{rank}] EXIT 0", flush=True)

Measurement protocol (two sub-tests):

Sub-test A (drain trigger):

  1. Submit with no STOP_FILE in env. Watch for "step N complete" in log.
  2. Wait ~5 steps, then scancel <jobid>
  3. Expected: handler prints "SIGTERM received" but process does NOT exit. After 60 s: node drains.

Sub-test B (STOP-FILE safe exit):

  1. Submit with STOP-FILE path configured. Watch for "step N complete".
  2. After ~5 steps: touch $STOP_FILE
  3. Expected: within 1 step, all ranks print "STOP-FILE detected" and EXIT 0. No drain.

Node drain risk for sub-test A: HIGH. Sub-test B: LOW. Run B first; only run A with admin coordination.

T3 — Network I/O D-State (Event 2 repro)

Purpose: Quantify the impact of DROP-vs-REJECT egress policy on drain risk for accidental outbound connections. No CUDA required.

Mechanism tested: M4

Script design (do not run — design only):

#!/usr/bin/env python3
# t3_net_hang.py — DESIGN ONLY, DO NOT SUBMIT
# Run on betelgeuse partition (no outbound network)
# Purpose: measure TCP connect() timeout under DROP-not-REJECT firewall
import socket, time, signal, sys

TARGET_HOST = "8.8.8.8"   # Known-blocked on betelgeuse
TARGET_PORT = 443

def handler(signum, frame):
    print(f"[t3] Signal {signum} at t={time.time()-t0:.1f}s", flush=True)
    # Signal received — but are we in D-state?

signal.signal(signal.SIGTERM, handler)
t0 = time.time()
print(f"[t3] Attempting TCP connect to {TARGET_HOST}:{TARGET_PORT}", flush=True)

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.settimeout(None)  # Blocking — will enter D-state under DROP policy
try:
    s.connect((TARGET_HOST, TARGET_PORT))   # D-state here under DROP
    print(f"[t3] Connected (unexpected) at t={time.time()-t0:.1f}s", flush=True)
except OSError as e:
    print(f"[t3] Exception after t={time.time()-t0:.1f}s: {e}", flush=True)
finally:
    s.close()

Measurement protocol:

  1. Submit to betelgeuse. Observe "Attempting TCP connect" in log.
  2. Wait 10 s; issue scancel <jobid>.
  3. Expected under DROP policy: process does NOT exit; enters D-state; drains after ~60 s.
  4. Observe actual TCP timeout: if process eventually exits on its own, record the time. This is the kernel's TCP retransmit backoff ceiling.

Counter-test (REJECT policy): If admin can temporarily change egress policy from DROP to REJECT for betelgeuse, re-run. Expected: connect() returns ECONNREFUSED in <1 ms; process exits cleanly with no D-state. This is the quantitative argument for the admin recommendation.

Mitigation validation: Re-run with socket.settimeout(5.0) (5-second timeout). With DROP policy: connect() blocks for 5 s then raises socket.timeout. Process in S-state (interruptible sleep via select()), so SIGTERM can deliver during the timeout wait. Process exits cleanly. This is the application-level defense: all network operations should have explicit timeouts.

Node drain risk: MEDIUM-HIGH (sub-test with settimeout=None). With settimeout: LOW. Run with-settimeout first.

T6 — Rank-0 Crash Deadlock (near-miss repro)

Purpose: Characterise torchrun's recovery behaviour when rank-0 crashes inside dist.destroy_process_group() and other ranks are stuck in a collective. Determine: does the rank-0 deadlock guard prevent the hang? What is torchrun's watchdog timeout?

Mechanism tested: M2 (via deadlocked dist.destroy)

Script design (do not run — design only):

#!/usr/bin/env python3
# t6_rank0_deadlock.py — DESIGN ONLY, DO NOT SUBMIT
# torchrun --nproc_per_node=2 t6_rank0_deadlock.py
import torch, torch.distributed as dist, os, time, sys

dist.init_process_group("nccl")
rank = dist.get_rank()
device = torch.device(f"cuda:{rank}")

# Run a few normal steps
for step in range(3):
    x = torch.ones(128, 128, device=device)
    dist.all_reduce(x)
    if rank == 0:
        print(f"[t6 rank0] step {step}", flush=True)

# Now simulate rank-0 crash scenario:
# Sub-test A (no guard): rank-0 raises in finally block → deadlock
# Sub-test B (with guard): rank-0 broadcasts failure flag → ranks unblock

GUARD_ENABLED = bool(int(os.environ.get("T6_GUARD", "1")))

if rank == 0:
    try:
        raise ValueError("t6: simulated rank-0 crash in checkpoint save")
    except ValueError as e:
        print(f"[t6 rank0] Crash: {e}", flush=True)
        if GUARD_ENABLED:
            # Broadcast failure flag so rank-1 knows to unblock
            fail_tensor = torch.tensor([1], device=device)
            dist.broadcast(fail_tensor, src=0)
            print("[t6 rank0] Broadcasted failure flag → ranks will unblock", flush=True)
        # Now enter destroy (this is what deadlocked in the near-miss)
        print("[t6 rank0] Calling dist.destroy_process_group()", flush=True)
        t_destroy = time.time()
        dist.destroy_process_group()
        print(f"[t6 rank0] destroy_process_group() returned in {time.time()-t_destroy:.1f}s", flush=True)
else:
    if GUARD_ENABLED:
        fail_tensor = torch.tensor([0], device=device)
        dist.broadcast(fail_tensor, src=0)
        if fail_tensor.item() == 1:
            print(f"[t6 rank{rank}] Failure flag received — unblocking", flush=True)
            dist.destroy_process_group()
            sys.exit(1)
    else:
        # Sub-test A: rank-1 stuck waiting for rank-0 in broadcast it never calls
        print(f"[t6 rank{rank}] Waiting in broadcast (will deadlock)...", flush=True)
        x = torch.zeros(1, device=device)
        dist.broadcast(x, src=0)  # rank-0 never calls this → rank-1 hangs

Measurement protocol:

  1. Sub-test A (T6_GUARD=0): rank-0 crashes, rank-1 hangs in broadcast. Measure: how long before torchrun's watchdog reaps rank-1? (Near-miss: 4m22s. Confirm this is consistent.)
  2. Sub-test B (T6_GUARD=1, default): rank-0 broadcasts failure flag before crash. Rank-1 receives flag and exits cleanly. Measure: total wall-clock time from crash to both ranks exited.
  3. In both cases: confirm no drain (neither sub-test enters indefinite D-state; torchrun watchdog eventually reaps).

Node drain risk: LOW-MEDIUM. Sub-test A may hang for ~4+min but torchrun should eventually reap. The risk is if torchrun's watchdog fails to reap and the job hits its time limit (see T5). Use a short --time (10 min) with the three-layer defence for safety. Sub-test B: MINIMAL.

§7 — SDCC admin recommendations

Seven recommendations ranked by impact × implementation ease. The first three are high-impact and feasible without vendor changes.

R1 — Raise UnkillableStepTimeout on betelgeuse (HIGH IMPACT, EASY)

Current value: 60 s. Recommended: 300 s.

A clean DDP teardown on 4 GPUs — NCCL collective drain, CUDA cache flush, model weight dereference, process group destroy — legitimately takes 60–120 s under load. The current 60 s timeout means a healthy job that receives SIGTERM at the start of an expensive backward pass will almost certainly drain the node regardless of whether the application handles the signal correctly.

At 300 s: the legitimate cleanup window is covered; most "Kill task failed" events become clean exits. The downside — a genuinely wedged job occupies the node for 5 more minutes before drain — is far cheaper than the 30+ minute admin-intervention cost of an actual drain.

SLURM config change: in slurm.conf:

UnkillableStepTimeout=300

Applies to the betelgeuse partition only (or globally if appropriate).

R2 — Run nvidia-smi --gpu-reset in SLURM epilogue (HIGH IMPACT, MEDIUM)

Every drain incident produced cascading failures because the next job inherited orphaned CUDA contexts. Smoke 1208985 failed in 17 s because it found dirty GPUs left by the drained 1208975/1208980 jobs.

The epilogue script runs after every job step completes (or is killed). Adding nvidia-smi --gpu-reset (one call per GPU) ensures the device is clean before the next job allocation. If --gpu-reset hangs (rare — indicates a truly wedged driver), fall back to a reboot.

# /etc/slurm/epilog.sh (betelgeuse)
#!/bin/bash
# Reset all GPUs allocated to this job to clear orphaned contexts
for gpu in $(echo $CUDA_VISIBLE_DEVICES | tr ',' ' '); do
    nvidia-smi --gpu-reset -i "$gpu" 2>&1 || true
done
echo "Epilogue: GPU reset complete for job $SLURM_JOB_ID" >> /var/log/slurm/gpu-resets.log

R3 — Enable cgroup v2 kill semantics (HIGH IMPACT, MEDIUM-HARD)

The RHEL 10.1 kernel (6.12) supports cgroup v2. Writing 1 to /sys/fs/cgroup/<job_cgroup>/cgroup.kill terminates all processes in the cgroup atomically, including D-state processes. This is qualitatively different from SIGKILL — it operates at the cgroup lifecycle level, which the kernel handles in a safe context separate from signal delivery.

SLURM can be configured to use this via the cgroup plugin. This would convert the "SIGKILL cannot reap D-state" failure mode into a recoverable situation: instead of drain, the cgroup is destroyed, the processes vanish, and the node can be resumed. The GPU state still needs resetting (R2 handles that), but the drain event itself may be avoidable.

Relevant SLURM config:

# slurm.conf
TaskPlugin=task/cgroup
# cgroup.conf
CgroupPlugin=autodetect  # will detect v2
CgroupAutomount=yes
ConstrainDevices=yes     # GPU isolation per job

R4 — Egress REJECT not DROP for betelgeuse (HIGH IMPACT, EASY)

Change the outbound firewall policy from DROP to REJECT. This eliminates the M4 mechanism entirely: any accidental outbound connection (LPIPS download, pip install, wget) returns ECONNREFUSED immediately rather than hanging for minutes in kernel D-state.

From the kernel's perspective: with DROP, connect() enters TASK_INTERRUPTIBLE sleep waiting for a TCP response that never comes, then escalates to TASK_UNINTERRUPTIBLE during retransmit backoff cycles. With REJECT, connect() gets an immediate RST and returns in <1 ms in TASK_RUNNING state — no D-state at all.

iptables change:

# Replace DROP policy with REJECT:
iptables -P OUTPUT DROP          # existing (bad)
iptables -P OUTPUT ACCEPT        # if possible, or:
iptables -A OUTPUT -j REJECT --reject-with tcp-reset  # better for TCP

R5 — UnkillableStepProgram — capture diagnostics at unkillable event (MEDIUM IMPACT, MEDIUM)

When SLURM determines a step is unkillable, currently it just logs "Kill task failed" and drains. With UnkillableStepProgram, slurmd calls a user-provided script first, which can capture diagnostics before the drain occurs:

#!/bin/bash
# /etc/slurm/unkillable_step.sh
JOBID=$1; STEPID=$2; PID=$3
echo "=== UnkillableStep: job=$JOBID step=$STEPID pid=$PID ===" >> /var/log/slurm/unkillable.log
# Capture D-state proc stack
for p in $(pgrep -P $PID) $PID; do
    echo "--- PID $p ---" >> /var/log/slurm/unkillable.log
    cat /proc/$p/wchan 2>/dev/null >> /var/log/slurm/unkillable.log
    cat /proc/$p/stack 2>/dev/null >> /var/log/slurm/unkillable.log
done
nvidia-smi >> /var/log/slurm/unkillable.log 2>&1
# slurm.conf:
UnkillableStepProgram=/etc/slurm/unkillable_step.sh

The captured /proc/<pid>/stack and wchan are the kernel call stack and the kernel function the process is waiting in. These are the primary data needed for NVIDIA bug reports and driver-level investigation.

R6 — User-callable safe-cancel wrapper (MEDIUM IMPACT, EASY)

Provide a cluster-level script ambix_safe_cancel JOBID that:

  1. Reads the job's AMBIX_STOP_FILE path from the job's environment (scontrol show job JOBID shows env vars)
  2. Touches the stop-file
  3. Polls squeue -j JOBID for up to 60 s, reporting progress
  4. If job exits: prints "Job JOBID exited cleanly" and returns
  5. If job does NOT exit after 60 s: prints warning and requires user to explicitly confirm before issuing scancel

This codifies the §2a-cancel protocol into a single command that any user can run safely without understanding the underlying drain mechanism.

R7 — Alert on node entering DRAIN (MEDIUM IMPACT, EASY)

Automated alerting when betelgeuse transitions to DRAIN state. Currently drain events are noticed only on the next login attempt or job submission. A 30-second polling loop via cron or SLURM's power management hooks could send an email/Slack alert within 1 min of the drain. Quick admin response reduces downtime from 30+ min to potentially 5 min.

#!/bin/bash
# /etc/cron.d/betelgeuse-drain-alert (runs every 30s via @reboot + loop)
while true; do
    STATE=$(scontrol show node 98dci4-gpu-0003 | grep -oP 'State=\K\S+')
    if echo "$STATE" | grep -q DRAIN; then
        echo "ALERT: 98dci4-gpu-0003 is $STATE" | mail -s "GPU node DRAIN" sdcc-admins@iter.org
        sleep 300  # Don't flood with alerts
    fi
    sleep 30
done

§8 — Operating policy (binding for all agents)

This section consolidates the rules derived from all four drain events and the near-miss into a single reference. Rules are listed in priority order.

P1 — Never scancel a CUDA job (absolute)

Agents must NOT issue scancel on any CUDA or GPU job, healthy or wedged, under any circumstances. The only agent-permitted cancellation mechanism is touching the STOP-FILE. If the STOP-FILE mechanism is unavailable and the job must be stopped, the agent surfaces this to the user and stops. Only the user may issue scancel, and only after explicitly accepting drain risk and committing to admin recovery steps.

P2 — Every new GPU sbatch must implement the three-layer defence

No new SLURM script for a GPU workload may be submitted without:

  1. #SBATCH --signal=B:USR1@600
  2. STOP-FILE export + SIGUSR1 bash trap
  3. AMBIX_SOFT_TIME_LIMIT export (~85% of --time in seconds)
  4. --time set to 2–4× realistic expected runtime, not actual budget

Deviations require a written justification in the commit message referencing this document.

P3 — Every new GPU Python script must implement the stop-file contract

No GPU Python training or encoding script may be submitted without:

  1. STOP-FILE check at every safe exit boundary (after optimizer.step(), before next batch)
  2. SIGTERM/SIGINT handler setting STOP flag (best-effort, with caveats documented)
  3. Per-step watchdog thread auto-calibrated from running median
  4. Rank-0 deadlock guard if using DDP (broadcast failure flag on rank-0 exception)
  5. try/finally teardown releasing model, CUDA cache, and NCCL group

Reference implementation: imas_ambix/tokenizer/finetune_decoder.py.

P4 — In-process GPU code only (no subprocess-per-item)

All GPU encoding/decoding runs in a single long-lived process. Subprocess-per-shot, persistent daemon + IPC, and prefetch producer/consumer threads are prohibited in production code. These patterns have caused three of the four drains and 55× throughput degradation. Reference: imas_ambix/data/stream_encode.py.

P5 — All outbound calls must have explicit timeouts

Any network call (HTTP, HTTPS, socket) in code that runs on betelgeuse must have a timeout of ≤30 s. This prevents M4 D-state hangs even under DROP firewall policy. Preferred: HF_HUB_OFFLINE=1 and explicit preflight assertions to prevent any outbound calls from occurring at all.

P6 — Preflight assertions in all sbatch scripts

Every sbatch script must verify required files exist (model weights, CWD, data paths) before launching Python. A missing file that causes the Python code to attempt a download or open a wrong path is the trigger for M4. The assertion must be a bash test -f or test -d that exits non-zero with a clear error message.

P7 — Session-start audit: check for node drain

At the start of any agent session that involves GPU workloads, run:

scontrol show node 98dci4-gpu-0003 | grep -E "State|Reason"

If the state includes DRAIN, surface to the user immediately. Do not submit jobs to a drained node.

P8 — Legacy code deletion schedule

  • bulk_encode_frames.sbatch + encode_one_shard.py + related legacy frame-daemon code: DELETE once stream_encode.py passes GPU validation on the full rbb corpus
  • bulk_encode_signals.sbatch: lower priority; keep for now but add three-layer defence at next edit
  • All --no-in-process code paths in bench CLI: keep as debug escape hatch; clearly documented as unsafe for production

§9 — Open questions and future work

Q1 — Is M5 (cuInit cgroup collision) reproducible?

Event 0 remains ambiguous. We need T4 test results + Group B coordination to determine if this is a systematic NVIDIA driver bug or a one-off race condition. If reproducible, this is a vendor bug report candidate. If MPS is deployed (R3), the question becomes moot but the root cause remains unknown.

Q2 — What is torchrun's actual watchdog timeout?

The near-miss (smoke 1208992) showed torchrun's elastic launcher reaped the stuck DDP job in 4m22s. This is the timeout before which a rank-0 deadlock is "self-healing" without drain. T6 will measure this precisely. The policy implication: if the rank-0 deadlock guard fails for any reason, the last line of defence is torchrun's watchdog, and we need to know its exact value to set --time margins correctly.

Q3 — Does nvidia-smi --gpu-reset work while a process is in D-state?

The admin recovery procedure uses nvidia-smi --gpu-reset to clear orphaned GPU contexts. But if the process causing the D-state is still wedged in a CUDA ioctl, the GPU reset may itself hang (waiting for the outstanding ioctl to return). This happened in one admin recovery attempt. The full recovery in that case was a node reboot. Needs explicit testing to characterise when reset is sufficient vs when reboot is required.

Q4 — Is GPFS I/O a D-state source for stream_encode?

stream_encode reads shot data from GPFS and writes tokens to GPFS via Zarr. Under high GPFS load, I/O operations can enter D-state (waiting for NFS/GPFS client lock). This is theoretically a drain surface independent of CUDA. The per-batch watchdog should catch this (it triggers on wall-clock timeout, not CUDA state), but the watchdog itself calls STOP.set() and relies on the main loop seeing the stop flag — which it can't if it's in a GPFS D-state. The mitigation here is the SIGUSR1 bash trap (three-layer defence layer 1), which runs in bash (not in a GPFS call) and touches the STOP-FILE. This is another reason the three-layer defence is mandatory even for non-DDP jobs like stream_encode.

Q5 — Should we move to MPS for all Group A GPU jobs?

NVIDIA Multi-Process Service (MPS) provides isolated CUDA contexts with cleaner teardown semantics. It also eliminates the M5 risk (cgroup collision). The trade-off: MPS adds complexity to job submission and may have performance overhead for compute-bound training. For inference serving (kimi-k2-6, V4-Flash), MPS may be the right default. For training jobs, the current approach (hardware partition via reservation) is simpler but leaves M5 as a residual risk.

Q6 — stream_encode remediation scope

Adding STOP-FILE + AMBIX_SOFT_TIME_LIMIT to stream_encode.py is straightforward — the existing STOP flag infrastructure is already there; we just need to check the file path and read the env var at the same boundaries where STOP is currently checked. The sbatch update is equally mechanical. However: any change to stream_encode requires a validation run on a small subset of the corpus (e.g. 10 shots) before re-running the full 7h corpus encode. Coordinate with the GPU job schedule before submitting.
