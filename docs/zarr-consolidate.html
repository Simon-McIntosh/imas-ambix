Run zarr.consolidate_metadata() once across the L1 and L2 corpora so every xarray.open_zarr() lands fast (~10 ms) instead of falling back to a non-consolidated listing (10–100× slower). Eliminates the RuntimeWarning spam and removes the 0.5–2 s per-shot Zarr-open tax.

§1 · Problem statement

Every ambix data audit and ambix data bulk-encode-frames worker prints:

RuntimeWarning: Failed to open Zarr store with consolidated metadata,
but successfully read with non-consolidated metadata.
This is typically much slower for opening a dataset.

On the 9,527-shot rbb corpus, this pays 0.5–2 s of metadata listing per shot. The cost was directly visible as 0% GPU utilisation on the failed signals job and the 12-minute startup of the failed frames job. With 4 GPUs each fetching shots concurrently this becomes a real I/O bottleneck — the encode loop is CPU/IO-bound rather than GPU-bound.

Every open_zarr() without a consolidated .zmetadata file must recursively list every group and array in the Zarr hierarchy via GPFS. Consolidation writes a single .zmetadata JSON at the shot root; subsequent opens read it in one GPFS roundtrip.

§2 · Fix — zarr.consolidate_metadata()

Run once across both corpora:

import zarr
from pathlib import Path

for shot_zarr in Path('/work/projects/imas_gpu/mast/level2/shots').glob('*.zarr'):
    zarr.consolidate_metadata(str(shot_zarr))

for shot_zarr in Path('/work/projects/imas_gpu/mast/level1/shots').glob('*.zarr'):
    zarr.consolidate_metadata(str(shot_zarr))

Writes a .zmetadata file at each shot root. Subsequent open_zarr(..., consolidated=True) reads it in one HTTP/GPFS roundtrip instead of recursively listing groups. The operation is idempotent — safe to re-run when new shots arrive.

Deliver as scripts/consolidate_zarr_metadata.py: a single-file CLI taking --root and --workers flags so it can be run on both corpora in parallel and scheduled for future ingestion runs.
