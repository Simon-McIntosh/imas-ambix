Incident RCA — plasma-decoder-finetune production run 1209004 measured training-time best rFID 12.488 (apparent 23 % improvement from baseline 16.25), but the matching bench re-run 1209047 measured rFID 27.40 — a 69 % regression below baseline. Verdict: silent correctness bug in the fine-tune dataset (PIL.Image.resize vs corpus contract F.interpolate). Fixed in commit 2649370; corrective fine-tune submitted as job 1209073.

One-line cause

Training resized frames to 256×256 using PIL.Image.resize; the corpus encoder (and therefore the bench, world-model, and every other downstream consumer of the LFQ tokens) uses torch.nn.functional.interpolate(bilinear, align_corners=False) with no antialias. PIL and torch bilinear produce subtly different pixel values for the same input — the decoder overfit to the PIL-input distribution and performs worse than the untrained ImageNet baseline when fed F.interpolate-resized frames at bench time.

Mechanism — why the regression below baseline?

Counter-intuitively, the fine-tuned decoder is WORSE than the untrained ImageNet decoder. Two reinforcing effects:

  1. Distribution shift at the decoder input. The decoder sees quantised codes produced by the encoder from F.interpolate-resized inputs at bench time. At training time, the encoder was fed PIL-resized inputs. The two produce different pixel values for the same raw frame → different uint8 → different floats fed to the encoder → different LFQ quantisation regions hit → different token IDs → the decoder sees a token distribution at bench time that it never saw during training.
  2. The decoder over-specialised. The untrained ImageNet decoder is robust across a wide pixel distribution (its training data on ImageNet includes natural variation). Fine-tuning narrowed it to the PIL-resized plasma-frame distribution. When that narrow distribution is no longer what the encoder feeds it (bench uses F.interpolate), the decoder's narrow specialisation is now actively hurting — it has reduced robustness to inputs the ImageNet pretrain handled fine.

The math: PIL's bilinear filter and torch's F.interpolate bilinear filter differ in the convolution kernel weights AT THE NON-INTEGER SAMPLE POINTS — PIL uses a slightly wider triangular filter footprint at sub-pixel offsets, torch uses an exact bilinear interpolant. The two are mathematically distinct. Maximum per-pixel uint8 difference is typically 1-3 counts, but it's enough to push borderline LFQ-quantisation samples across partition boundaries, which is precisely what the C1 EMA-seed RCA identified as the silent-correctness-killer pattern.

Why this slipped past the deep review

The 2026-05-28 deep review caught seven bugs (commit fa0c3b6) including the per-shot normalisation mismatch (C2) which is in the same class as C5. But C2 was framed as "the value-side contract" (min/max normalisation), and the review focused there. The spatial-resampling-side contract didn't get the same scrutiny because:

  • The PIL-based code looked syntactically fine and uses a long-standing PIL pattern.
  • The corpus encoder's resize is in stream_encode.py (separate module); the fine-tune dataset is in finetune_decoder.py. No grep would link them unless you were looking for "what does corpus do here vs what does training do here" for every operator in the chain.
  • Training and bench were not byte-equivalence-tested against each other — only the fine-tune's internal consistency was tested via the smoke (which trained AND eval'd through PIL, so resize artifacts cancelled within the smoke's pipeline but not against the bench's pipeline).

Lesson: the byte-equivalence contract isn't just about value normalisation; it covers every operator that transforms the input on its way to the encoder. A new test should compare a training batch and a bench batch from the SAME source frame and assert torch.allclose bitwise. Tracked as a follow-up in §followups.

Fix (commit 2649370)

--- imas_ambix/tokenizer/finetune_decoder.py
+++ imas_ambix/tokenizer/finetune_decoder.py
@@ __getitem__:
- from PIL import Image
+ import torch.nn.functional as _F
  ...
- img = Image.fromarray(frame).resize(
-     (self.image_size, self.image_size), Image.BILINEAR
- )
- frame = _np.asarray(img)
+ # Match corpus encoder's resize EXACTLY (no antialias, align_corners=False).
+ t = torch.from_numpy(_np.ascontiguousarray(frame)).float()
+ t = t.permute(2, 0, 1).unsqueeze(0)
+ t = _F.interpolate(
+     t, size=(self.image_size, self.image_size),
+     mode="bilinear", align_corners=False,
+ )
+ t = t.squeeze(0).permute(1, 2, 0).clamp(0, 255).round()
+ return t.to(torch.uint8)

Verified on shot 15086 (native 402 × 512) that the new code path produces a 256 × 256 × 3 uint8 tensor in the [0, 255] range using the exact same operator the corpus encoder uses.

Impact & what we're rerunning

  • Corrective fine-tune submitted as job 1209073. Same recipe as 1209004 (10 k steps, 7 500 train + 2 000 val shots, 4×H200 DDP, all C1-C4 + H1-H3 fixes intact); only the resize operator changed. Expected wall-clock ≈ 1 h 30 m.
  • Training-time rFID will rise — and that is correct. The over-optimistic 12.488 measurement should disappear; the new training-time rFID will be aligned with what the bench measures. If the corrective run lands at training rFID ≈ 16 and bench rFID ≈ 16, the fix is working but the decoder isn't improving on plasma — expected, and that's the signal for the v1 plans. If training rFID < baseline and bench rFID confirms within 1-2 points, the fine-tune IS improving the decoder, just at smaller magnitude than the broken measurement claimed.
  • v1 plans remain blocked. transient-fidelity and cosmos-evaluation each carry a f-phase0-trigger-check followup that consumes the bench result; both will re-fire when the 1209073-derived ckpt is benched. Until then, neither plan activates.
  • Prior smoke results (1209002 et al.) remain valid as correctness signals — they validated the training pipeline self-consistency (loss decreasing, no NaN, no drain). Their rFID numbers were also PIL-pipeline so equally over-optimistic, but they were never used as gate measurements; only the bench-aligned numbers count.
