Incident RCA — node 98dci4-gpu-0003 drained 2026-05-28 13:52:08. Verdict: self-inflicted (agent scancel on a healthy CUDA-DDP job). No Group B involvement — proven below.

One-line cause

The orchestrating agent issued scancel 1208975 to free the reservation for an improved code revision. The cancelled job's rank-0 CUDA process was inside a NCCL collective at the moment SIGTERM arrived; the Python signal handler could not run because Python's interpreter only processes signals between bytecodes, and we were in a multi-second C++ call to torch.cuda.synchronize / NCCL all-reduce. UnkillableStepTimeout expired → "Kill task failed" → drain.

Why §2a's existing rule did not save us

The current AGENTS.md §2a says:

"Never scancel a CUDA-wedged job and assume clean teardown."

The rule was scoped to wedged jobs. Today's cancelled job was healthy (training, 100 % GPU on rank 0, loss decreasing) — the agent assumed the SIGTERM handler in finetune_decoder.py would unwind cleanly inside the UnkillableStepTimeout window. It cannot, and the rule failed to apply by its literal reading. The strengthened rule (§prevention below) is now scope-broadened to any CUDA-DDP job, healthy or wedged.

Why scancel cannot unwind a healthy CUDA-DDP rank

  1. Python signal handlers run only between bytecodes. signal.signal() sets a flag the interpreter checks at the next opcode boundary.
  2. loss.backward() calls into C++ (autograd engine + cuBLAS + NCCL). The C++ stack does not periodically yield to Python's signal-check, so SIGTERM received mid-backward is queued, not handled, until the call returns to Python.
  3. DDP gradient sync uses NCCL collectives (all_reduce). These are blocking kernel-mode operations that wait on every peer. If any peer's return is delayed, all ranks sit in the collective.
  4. SIGKILL cannot reap a process in uninterruptible kernel sleep (D state) — kernel calls (CUDA, GPFS, NCCL) must return first.
  5. After UnkillableStepTimeout (~60 s) slurmd marks "Kill task failed" → DRAIN. The reservation goes offline until an admin runs scontrol update state=resume.

Prevention — STOP-FILE mechanism (binding)

Signals are unsuitable for cancelling CUDA-DDP jobs. The replacement is a stop-file polled at safe exit boundaries:

Contract

  1. Every long-running agent-launched GPU training script writes its job's stop-file path into stdout at startup, and the sbatch sets AMBIX_STOP_FILE=/work/projects/imas_gpu/stops/<jobid>.stop.
  2. The training loop checks STOP_FILE.exists() at every step — immediately after optimiser.step(), before fetching the next batch. The check is a single stat() call (~ μs); cost is negligible vs a 0.5 s training step.
  3. If the stop-file exists: break the training loop. Normal try/finally teardown runs (model release, NCCL destroy, GPU cache clear, file flush). Process exits with code 0 inside ~5 s.
  4. To cancel a job: touch /work/projects/imas_gpu/stops/<jobid>.stop. Never scancel unless the stop-file mechanism is unavailable AND the job is genuinely wedged AND the user has authorised it.

Edge case — job is genuinely wedged (no progress for > 10 min)

If a job never reaches a stop-file check (deadlocked NCCL, hung GPFS), the stop-file mechanism cannot rescue it. In that case the only options are:

  1. Wait for SLURM time limit to expire (preferred — natural cleanup).
  2. Wait for our internal watchdog (per-step timeout) to STOP.set() — but only if its own check happens to land between collectives.
  3. Ask the user to take responsibility for a scancel, accepting the drain risk and committing to perform the admin recovery (§admin).

The agent must never scancel a CUDA-DDP job on its own initiative.

Feedback to SDCC admin (server hardening recommendations)

Three drains in three days on the only H200 node points to fragility that agent discipline alone cannot fully fix. The application side has now landed all reasonable mitigations (SIGTERM handler, watchdog, in-process training, stop-file mechanism); residual risk is on the SLURM / kernel side. Suggestions ranked by impact:

  1. Raise UnkillableStepTimeout on betelgeuse from the default 60 s to 300 s. A clean DDP teardown — particularly NCCL collective drain + model release + CUDA cache empty on 4 ranks — can legitimately take 60–120 s on slow days. A 300 s window would convert most "Kill task failed" events into clean exits. Trade-off: a genuinely wedged job ties up the node 4 min longer before drain, but that's far cheaper than the multi-hour admin intervention to resume after a drain.
  2. Run nvidia-smi --gpu-reset in the SLURM epilogue (or use PrologFlags=Contain + an epilogue script) so a previous job's leaked GPU state never bleeds into the next. This is the single biggest source of "1208975 drained but 1208980 amplified it" cascades in our incident history.
  3. Use cgroups v2 with the kill semantics enabled (cgroup.kill in /sys/fs/cgroup/...). On v2-capable kernels this lets SLURM kill the entire cgroup atomically — including processes in D state, because cgroup destruction propagates through the kernel scheduler in a way SIGKILL does not.
  4. Switch to NVIDIA MPS (Multi-Process Service) or container-isolated GPU access for each job. When the container goes away, the GPU context is cleaned up automatically by NVIDIA's runtime; no orphaned CUDA contexts.
  5. Alert on node entering DRAIN within 60 s rather than on the next admin walk-through — every minute of drain costs the user a job slot, and quick admin response can often resume the node before the next shift's queue empties.
  6. Provide a user-callable safe-cancel wrapper (e.g. sbatch_safe_cancel JOBID) that first touches a known AMBIX_STOP_FILE path, polls for graceful exit for 60 s, and only falls back to scancel if the job is genuinely wedged. This codifies the §prevention rule above into the cluster's tooling so users don't need to remember the right mechanism per job.
