Incident RCA — node 98dci4-gpu-0003 drained 2026-05-28 13:52:08. Verdict: self-inflicted (agent scancel on a healthy CUDA-DDP job). No Group B involvement — proven below.

One-line cause

The orchestrating agent issued scancel 1208975 to free the reservation for an improved code revision. The cancelled job's rank-0 CUDA process was inside a NCCL collective at the moment SIGTERM arrived; the Python signal handler could not run because Python's interpreter only processes signals between bytecodes, and we were in a multi-second C++ call to torch.cuda.synchronize / NCCL all-reduce. UnkillableStepTimeout expired → "Kill task failed" → drain.

Why §2a's existing rule did not save us

The current AGENTS.md §2a says:

"Never scancel a CUDA-wedged job and assume clean teardown."

The rule was scoped to wedged jobs. Today's cancelled job was healthy (training, 100 % GPU on rank 0, loss decreasing) — the agent assumed the SIGTERM handler in finetune_decoder.py would unwind cleanly inside the UnkillableStepTimeout window. It cannot, and the rule failed to apply by its literal reading. The strengthened rule (§prevention below) is now scope-broadened to any CUDA-DDP job, healthy or wedged.

Does SIGTERM immediately drain the node?

No — and that's important to be precise about. A clean SIGTERM handler that exits within the timeout window does not drain the node. The drain happens because of what comes after SIGTERM fails to unwind a CUDA-DDP process within SLURM's UnkillableStepTimeout window. The full sequence:

  1. SLURM sends SIGTERM to every process in the job step (via scancel, time-limit, or admin intervention). Up to this point, the node is fine — SIGTERM is a polite request to exit.
  2. Python receives the signal flag but cannot act on it while inside C++. Python signal handlers only run between bytecodes; while the interpreter is in a multi-second C call to loss.backward() (autograd + cuBLAS + NCCL), the signal flag is set but the handler doesn't fire.
  3. NCCL collectives are atomic. dist.all_reduce inside backward blocks all 4 ranks in kernel mode (D state) on NVLink P2P transactions. Until every rank completes the collective, no rank can return to Python and run the signal handler. Even if one rank's SIGTERM handler did fire and called STOP.set(), the other ranks are still in the collective waiting for it.
  4. SLURM waits UnkillableStepTimeout (default 60 s on betelgeuse) for the process to exit voluntarily. If the process hasn't exited:
  5. SLURM sends SIGKILL. SIGKILL is uncatchable — but it also cannot reap a process in uninterruptible kernel sleep (D state). The kernel call (CUDA driver, GPFS, NCCL P2P) has to return before any signal — including SIGKILL — can be delivered to the process. For a wedged CUDA call that never returns, SIGKILL is effectively a no-op.
  6. SLURM waits a second timeout. If the process still hasn't exited:
  7. slurmd marks "Kill task failed" → node DRAIN. This is the actual drain. The reservation goes offline until an admin runs scontrol update state=resume. Stale GPU memory from the un-reaped process persists and must be cleared with nvidia-smi --gpu-reset or a node reboot before resume — otherwise the next job inherits dirty CUDA contexts and fails (as smoke 1208985 demonstrated within minutes of resume).

So SIGTERM is not the drain trigger. The drain trigger is the combination of (a) SIGTERM unable to reach a Python handler because of step 2, plus (b) the process unable to be force-killed because of step 5, plus (c) the timeout in step 7. A CPU-bound process or a GPU process between collectives can handle SIGTERM cleanly within the timeout, and those cases do not drain.

The fundamental cure is therefore: do not let SIGTERM arrive during a collective. The STOP-FILE mechanism (§prevention) achieves this by giving the script a way to exit voluntarily at a known clean boundary, without SIGTERM ever being sent. The three-layer time-limit defence (§time-limits) extends this to time-bounded jobs.

This is also why scancel --signal=SIGUSR1 doesn't help: any signal sent to the worker python processes during a collective has the same queued-handler problem. Only signals sent to the bash batch script (--signal=B:USR1@N) can fire promptly, because bash isn't running CUDA.

Prevention — STOP-FILE mechanism (binding)

Signals are unsuitable for cancelling CUDA-DDP jobs. The replacement is a stop-file polled at safe exit boundaries:

Contract

  1. Every long-running agent-launched GPU training script writes its job's stop-file path into stdout at startup, and the sbatch sets AMBIX_STOP_FILE=/work/projects/imas_gpu/stops/<jobid>.stop.
  2. The training loop checks STOP_FILE.exists() at every step — immediately after optimiser.step(), before fetching the next batch. The check is a single stat() call (~ μs); cost is negligible vs a 0.5 s training step.
  3. If the stop-file exists: break the training loop. Normal try/finally teardown runs (model release, NCCL destroy, GPU cache clear, file flush). Process exits with code 0 inside ~5 s.
  4. To cancel a job: touch /work/projects/imas_gpu/stops/<jobid>.stop. Never scancel unless the stop-file mechanism is unavailable AND the job is genuinely wedged AND the user has authorised it.

If a job never reaches a stop-file check (deadlocked NCCL, hung GPFS), the stop-file mechanism cannot rescue it. In that case the only options are:

  1. Wait for our internal watchdog (per-step timeout) to STOP.set() — but only if its own check happens to land between collectives.
  2. Ask the user to take responsibility for a scancel, accepting the drain risk and committing to perform the admin recovery (§admin).

The agent must never scancel a CUDA-DDP job on its own initiative.

Update — SLURM time limits ARE scancel-equivalent

(Added 2026-05-28 16:00, post-session insight.) The original RCA listed "wait for SLURM time limit to expire" as an option for wedged jobs, framing it as preferred — natural cleanup. That guidance was wrong. A SLURM time limit firing is functionally identical to scancel: slurmd sends SIGTERM to the job step, the same Python-signal-handler-can't-run-mid-NCCL problem applies, the same UnkillableStepTimeout expires, the same drain occurs.

Any #SBATCH --time=N we set is therefore a delayed scancel with the same drain risk. Setting --time=24:00:00 means: "in 24 hours, if I'm still running, auto-scancel me." That is exactly the dangerous action §prevention above forbids — just timer-delayed.

Three-layer fix for time-bounded GPU jobs

Replace the dangerous --time-only pattern with a three-layer defence:

LayerMechanismEffect
1. Pre-warning signal #SBATCH --signal=B:USR1@600 + bash trap that touches the STOP-FILE SLURM sends SIGUSR1 to the batch script (not the workers) 10 min before time limit. Bash traps it cleanly (no NCCL involvement) and touches ${AMBIX_STOP_FILE}. The python workers see the file at the next step boundary and exit normally with code 0. Clean exit, no SIGTERM, no drain.
2. Internal soft wall-clock AMBIX_SOFT_TIME_LIMIT env var — training loop checks time.monotonic() - t_start > soft_limit at every step boundary Backup if the SIGUSR1 trap fails or the bash script dies. Same clean-exit behaviour as STOP-FILE detection. Set this to ~85 % of --time so it fires before the SLURM signal.
3. --time as ceiling only Set --time to 2-4× the realistic expected runtime Final safety net if both layers 1 and 2 fail. The bigger the gap between expected runtime and --time, the smaller the chance of hitting it — and if you DO hit it, you have evidence something is genuinely wedged (triggering the wedged-job protocol in §prevention).

Why the signal-to-bash pattern works where signal-to-workers fails

The bash batch script is a plain shell process. Signal traps in bash execute as soon as the current foreground builtin returns — they do not get queued behind multi-second C++ NCCL calls (because bash isn't running NCCL). So the SIGUSR1 trap fires within milliseconds, touches the STOP-FILE, and the python workers detect it at the next step boundary. The path SLURM-signal → bash-trap → file → python-poll is entirely safe for CUDA-DDP processes — the only signal target is the bash, which has no GPU involvement.

Contrast: --signal=USR1@N (no B:) sends the signal to the job step, i.e. the python workers themselves. That has the same problem as scancel — the workers can't process the signal while inside a collective.

Recommended sbatch header pattern

#SBATCH --time=04:00:00              # Safety ceiling (2-4× expected)
#SBATCH --signal=B:USR1@600          # SIGUSR1 → batch script, 10 min before limit

mkdir -p /work/projects/imas_gpu/stops
export AMBIX_STOP_FILE=/work/projects/imas_gpu/stops/${SLURM_JOB_ID}.stop
rm -f "${AMBIX_STOP_FILE}"

# Layer 1: SIGUSR1 trap → touch STOP-FILE
_on_sigusr1() {
    echo "[sbatch] SIGUSR1 received — SLURM time limit approaches; touching STOP-FILE"
    touch "${AMBIX_STOP_FILE}"
}
trap _on_sigusr1 USR1

# Layer 2: pass soft wall-clock limit to training script via env
# Set to ~85% of --time, in seconds
export AMBIX_SOFT_TIME_LIMIT=12240   # 3h24m, for a 4h ceiling

Additional findings from the same session

Smoke 1208992 — rank-0 crash deadlock (4m22s near-miss)

After applying all 7 correctness fixes, smoke 1208992 hit a different deadlock: rank 0 crashed during _save_checkpoint with ValueError: non contiguous tensor 'conv_in.weight' (BN-fused conv weights are non-contiguous in channels-last layout, which safetensors.save_file rejects). Rank 0 entered its finally block and hung in dist.destroy_process_group(); ranks 1-3 stuck in dist.broadcast() waiting for rank 0.

torchrun's elastic launcher reaped the workers in 4 m 22 s (presumably its own watchdog) — we got lucky. Had it not, the next SLURM time-limit fire would have drained the node, and there was already 30 min of contention with another job's recovery.

Fix landed (commit 0d8cb54):

  • .detach().cpu().contiguous() before safetensors.save_file — the immediate bug.
  • Rank-0 deadlock guard: every rank-0-only block in the training loop is wrapped in try/except. Any exception sets rank0_failed = 1 and the broadcast tensor is OR'd with that flag, so non-primary ranks always unblock and exit together.

Smoke 1208998 — GPU 0 idle during eval (perf, not drain)

The "C4 fix" (rFID on rank 0 only) introduced a separate-but-related issue: during the rank-0 eval window (~106 s per eval), GPU 0 ran imas_ambix.eval.metrics.rfid() on CPU (no .to(device)) while GPUs 1-3 spin-waited on dist.broadcast. The user observation was "GPU 0 at 0%, others at 100%" — looked like a hang, was actually CPU-bound rFID. The pattern persists across eval windows in a way that an observer can't distinguish from a wedge.

Fix landed (commits 8eb3afd + 995d3c4): distributed eval — each rank runs encode/decode + InceptionV3 feature extraction on its own GPU; only the small (N, 2048) feature tensors are gathered to rank 0 for the Frechet distance computation. Eval time dropped from 106.5 s → 13.4 s (8× faster) and GPU 0 participates throughout.

Feedback to SDCC admin (server hardening recommendations)

Three drains in three days on the only H200 node points to fragility that agent discipline alone cannot fully fix. The application side has now landed all reasonable mitigations (SIGTERM handler, watchdog, in-process training, stop-file mechanism); residual risk is on the SLURM / kernel side. Suggestions ranked by impact:

  1. Raise UnkillableStepTimeout on betelgeuse from the default 60 s to 300 s. A clean DDP teardown — particularly NCCL collective drain + model release + CUDA cache empty on 4 ranks — can legitimately take 60–120 s on slow days. A 300 s window would convert most "Kill task failed" events into clean exits. Trade-off: a genuinely wedged job ties up the node 4 min longer before drain, but that's far cheaper than the multi-hour admin intervention to resume after a drain.
  2. Run nvidia-smi --gpu-reset in the SLURM epilogue (or use PrologFlags=Contain + an epilogue script) so a previous job's leaked GPU state never bleeds into the next. This is the single biggest source of "1208975 drained but 1208980 amplified it" cascades in our incident history.
  3. Use cgroups v2 with the kill semantics enabled (cgroup.kill in /sys/fs/cgroup/...). On v2-capable kernels this lets SLURM kill the entire cgroup atomically — including processes in D state, because cgroup destruction propagates through the kernel scheduler in a way SIGKILL does not.
  4. Switch to NVIDIA MPS (Multi-Process Service) or container-isolated GPU access for each job. When the container goes away, the GPU context is cleaned up automatically by NVIDIA's runtime; no orphaned CUDA contexts.
  5. Alert on node entering DRAIN within 60 s rather than on the next admin walk-through — every minute of drain costs the user a job slot, and quick admin response can often resume the node before the next shift's queue empties.
  6. Provide a user-callable safe-cancel wrapper (e.g. sbatch_safe_cancel JOBID) that first touches a known AMBIX_STOP_FILE path, polls for graceful exit for 60 s, and only falls back to scancel if the job is genuinely wedged. This codifies the §prevention rule above into the cluster's tooling so users don't need to remember the right mechanism per job.
