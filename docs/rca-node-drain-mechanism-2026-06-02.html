RCA / for SDCC admins — Root-cause analysis of the repeated drain events on the shared 4×H200 node 98dci4-gpu-0003 (driver 595.58.03, CUDA 13.2.1, NCCL 2.21.5, PyTorch 2.5.1, RHEL 10.1 / kernel 6.12). This document supersedes and corrects the earlier deep-analysis and MWE-evidence notes, whose conclusions were inconclusive and in three specific places wrong (§5). It is backed by direct kernel-state measurement (process state + wchan captured at the moment of the kill) — the measurement that was never taken before.

Sections: Verdict · Corrected event log · Mechanism · Direct evidence · Why it could not be reproduced · Corrections to prior RCA · Reproducer suite · Admin mitigations · Followups

§1 — Verdict (single root cause)

A SLURM node drains when, and only when, a process in the job's cgroup is in uninterruptible kernel sleep (Linux D state / TASK_UNINTERRUPTIBLE) and stays there past UnkillableStepTimeout (currently 60 s). A D-state task cannot receive any signal — not SIGTERM, not SIGKILL. slurmstepd signals it, waits, fails to reap it, logs "Kill task failed" / "giving up after 63 sec", and slurmctld marks the node DRAIN.

On this node the D-state lives in the NVIDIA GPU kernel driver: internal driver lock acquisition (os_acquire_rwlock_read, os_acquire_rwlock_write, os_acquire_semaphore) and UVM device-handle retention (uvm_gpu_retain_by_uuid). It is entered when PyTorch tears down a stuck NCCL communicator — ncclCommAbort() internally calls cudaStreamSynchronize(), which blocks in the driver ioctl on a GPU operation that never completes (NCCL upstream issue #829).

All four drain events reduce to this one mechanism. The various "triggers" enumerated in the prior analysis (NCCL count-mismatch, network download, scancel timing, DDP param-mismatch) are not five independent root causes — they are just different ways to arrive at a stuck NCCL teardown on a GPU that is already wedged. The drain itself is one kernel-level fact: D-state in the NVIDIA driver, surviving SIGKILL, past a 60 s timeout.

§3 — The mechanism in one paragraph

A GPU job's NCCL collective gets stuck on the device (a peer never arrives, a ring is desynchronised, or the GPU is already wedged). PyTorch's NCCL watchdog fires and calls ncclCommAbort() to tear the communicator down. Per NCCL #829, ncclCommAbort() internally calls cudaStreamSynchronize() on the stream that owns the stuck kernel; that ioctl enters the NVIDIA driver and blocks acquiring an internal lock (os_acquire_rwlock_* / os_acquire_semaphore) or a UVM handle (uvm_gpu_retain_by_uuid). The thread is now in TASK_UNINTERRUPTIBLE. SLURM's SIGTERM → 30 s KillWait → SIGKILL all queue but cannot be delivered. After UnkillableStepTimeout (60 s) slurmstepd gives up → Kill task failed → node drains. Recovery needs nvidia-smi --gpu-reset (which itself hangs if a process still holds the device) or a reboot.

§4 — Direct evidence (the measurement nobody took)

We built a separate-allocation observer (scripts/drain-tests/instrumented/observe_state.sh) — a CPU-only SLURM job on the same node, outside the workload's cgroup, so it survives the workload's SIGKILL and the drain. SLURM does not isolate the PID namespace, so it reads /proc/<pid>/stat (state) and /proc/<pid>/wchan (the kernel function the task sleeps in) for every rank, every 0.5 s, throughout the kill window. Every "D-state vs S-state" claim in the prior corpus was inferred from log strings; these are measured.

D-state directly observed in the NVIDIA driver during a stuck NCCL teardown (jobs 1210225 and 1210246, wchan column):

1780382986.224,443718,D,os_acquire_rwlock_read,...python
1780382987.376,443717,D,uvm_gpu_retain_by_uuid,...python
1780382989.336,443716,D,uvm_gpu_retain_by_uuid,...python
1780380463.192,179883,D,os_acquire_rwlock_read,...python
1780380463.192,179884,D,os_acquire_rwlock_write,...python

These are exactly the NVIDIA kernel-driver lock/UVM functions cited in NVIDIA's own bug reports (open-gpu-kernel-modules #278, "os_acquire_semaphore deadlock → D-state up to 30 min"). A second D-state surface appeared in the same captures — cxiWaitEventWait (the Slingshot/CXI network driver), the kernel analogue of the Event-2 network hang.

Production drain signature (job 1208980 stderr; 1209813 identical):

[rank0] Future for ProcessGroup abort timed out after 600000 ms
slurmstepd: error: *** JOB 1208980 … CANCELLED … DUE TO TIME LIMIT ***
slurmstepd: error: *** JOB 1208980 … STEPD TERMINATED … DUE TO JOB NOT ENDING WITH SIGNALS ***
slurmstepd: error: Container 631913 in cgroup plugin has 4 processes, giving up after 63 sec

Corroboration (authoritative): NCCL #829 (abort → cudaStreamSynchronize D-state, closed "not planned"); SchedMD slurm.conf docs (D-state cannot be signalled; UnkillableStepProgram); NVIDIA nvidia-smi docs (--gpu-reset fails/hangs while a process holds the device → reboot). Full source list in the research appendix held with this RCA.

§5 — Why the drain could not be reproduced on demand

This is the question the prior fleet could not answer, and it is the heart of the RCA. We ran five instrumented experiments designed to drain the node (committed under scripts/drain-tests/instrumented/): seq_divergence, ddp_mismatch, stuck_collective, gpu_sleep_sync (single-GPU _sleep+synchronize), and abort_stuck (ncclCommAbort on an in-flight stuck collective — the exact production path). None drained the node. The node stayed healthy through all five; admin recovery was never needed.

The observer shows why. On a healthy GPU the driver-lock D-states are transient: the lock is released within milliseconds, the process oscillates D → R, and the queued SIGKILL lands the instant the task leaves D — clean kill, no drain. We watched ranks pass through D,os_acquire_rwlock_write and back to R repeatedly, then exit as zombies the moment the time-limit kill arrived.

A drain requires the D-state to be permanent, which requires the GPU itself to be wedged so the driver lock is never released — a genuinely stuck kernel, a GSP-firmware hang, or a CUDA context left dirty by a previous unclean teardown. That condition is not reachable from a clean start; it is produced by a prior drain/wedge. Hence the production drains were a cascade: the Event-0 cuInit wedge degraded the device; each subsequent job's NCCL teardown then hung permanently on the degraded GPU (note 1208980's "0 params" and 1209813's 156 s init — both symptoms of starting on an already-dirty device), and recovery that resumed the node without fully resetting the GPUs re-seeded the next drain.

Practical consequence: the fleet's inability to "trigger the drain with a known cause" was not a gap in effort — it reflects a real property of the system. You cannot drain a healthy GPU node this way. The actionable lever is therefore not "stop the trigger" (there are many) but "never let a job start on, or leave behind, a dirty GPU" and "make the unkillable window self-diagnosing and self-recovering" (§7).

The new instrumented suite lives in scripts/drain-tests/instrumented/ and is the correct minimal-working-example set for this RCA. Each is committed and self-documents its expected process state and recovery.

To force a sustained drain for an end-to-end recovery drill, the GPU must first be genuinely wedged (e.g. an admin-induced GSP/firmware fault, or running abort_stuck on a device left dirty by a prior unclean kill). We deliberately did not brute-force that on the shared node.

§8 — SDCC admin mitigations (ranked)

Application-side hardening is already in place (STOP-FILE cooperative cancellation, three-layer sbatch time-limit defence, in-process encoders, HF_HUB_OFFLINE preflight). The remaining leverage is at the cluster/driver level. Ranked by impact × ease; details and exact config in the followups below.

  1. Epilog / prolog GPU-clean gate (breaks the cascade — highest structural impact). After every GPU job, verify no compute process remains and the GPUs are healthy (nvidia-smi -q); if a process lingers, drain-with-reason rather than release; before the next job, ensure clean GPUs (reset only when no process holds the device). This stops a dirty GPU from wedging the next job — the cascade driver.
  2. Set UnkillableStepProgram (makes drains self-diagnosing & self-recovering). Currently (null). As root it can capture /proc/<pid>/stack + wchan (we cannot — non-root /proc/*/stack is denied), run echo w > /proc/sysrq-trigger, snapshot nvidia-smi + dmesg (Xid), then schedule a reboot. Turns every future drain into a logged, auto-recovered event.
  3. Raise UnkillableStepTimeout 60 s → 120 s. Hard cap 126 s (SchedMD bug #11103). Covers legitimate multi-GPU NCCL teardown (30–60 s) so transient waits no longer tip into a drain. Does not fix a permanent D-state, but removes the marginal cases.
  4. Egress REJECT not DROP on betelgeuse. Makes an accidental outbound call fail instantly (ECONNREFUSED) instead of hanging in kernel TCP wait — removes the Event-2 / cxiWaitEventWait D-state surface.
  5. Alert on DRAIN + resume only after verified-clean GPUs. Cuts downtime from "noticed next login" to minutes; resuming before the GPUs are confirmed clean re-seeds the cascade.
  6. Eliminate concurrent cross-cgroup CUDA init (the Event-0 seed). Investigate MPS or MIG, or serialise Group A / Group B cuInit, to prevent the shared-device init race that produced the original cuInit rc=3 wedge.
