RCA / for SDCC admins — node 98dci4-gpu-0003 (4×H200, driver 595.58.03, CUDA 13.2.1, NCCL 2.21.5, PyTorch 2.5.1, RHEL 10.1 / kernel 6.12). Concise statement of the validated cause and the surgical fix. Working record and the instrumented reproducer suite are linked at the end.

§1 — Cause

A SLURM node drains when a process in the job's cgroup is in uninterruptible kernel sleep (TASK_UNINTERRUPTIBLE, the D state) and stays there past UnkillableStepTimeout (currently 60 s). A D-state task cannot receive any signal — not SIGTERM, not SIGKILL — so slurmstepd cannot reap the step, logs Kill task failed, and the node is drained.

That single SLURM-level cause has three observed kernel-driver instances on this node — the production workload spends uninterruptible time in all three (measured wchan, this study):

  • CXI / Slingshot network driver — cxiWaitEventWait, cxiBlockingMutexAcquire. NCCL's transport here is libfabric/CXI, so collectives wait in the NIC driver; this is also the surface of the "download / network hang" event.
  • GPFS filesystem — d_alloc_parallel, folio_wait_bit_common. The DataLoader's GPFS reads; this is the surface of the prefetch-deadlock event.
  • NVIDIA GPU driver — os_acquire_rwlock_read/write, os_acquire_semaphore, uvm_gpu_retain_by_uuid. Entered when PyTorch tears down a stuck NCCL communicator: ncclCommAbort() → cudaStreamSynchronize() (NCCL upstream #829). This is the surface of the two drains with surviving logs.

In every case SLURM's SIGTERM → 30 s KillWait → SIGKILL queue undelivered; after 60 s the node drains. When the wedge is GPU-side, nvidia-smi --gpu-reset then also hangs (the process still holds the device), so recovery needs a reboot.

§2 — Evidence (validated)

  • Production logs — the two drains with surviving logs (jobs 1208980, 1209813) carry the identical signature: Future for ProcessGroup abort timed out after 600000 ms → JOB NOT ENDING WITH SIGNALS → Container … has N processes, giving up after 63 sec → drain.
  • Direct kernel-state capture — a separate-allocation observer recorded /proc/<pid>/stat + wchan for every rank through the kill window (the measurement never taken before). Across the instrumented runs — including the real production pipeline — the ranks were repeatedly caught in D-state in exactly the three driver surfaces in §1: cxiWaitEventWait (CXI network), d_alloc_parallel / folio_wait_bit_common (GPFS), and os_acquire_rwlock_write/read / os_acquire_semaphore / uvm_gpu_retain_by_uuid (NVIDIA driver) — the precise waits the production events hung in.
  • Upstream corroboration — NCCL #829 (abort → cudaStreamSynchronize D-state); NVIDIA open-gpu-kernel-modules #278 (os_acquire_semaphore deadlock → D-state); SchedMD docs (D-state cannot be signalled; UnkillableStepProgram; timeout cap 126 s, bug #11103).

§3 — Why it only sometimes drains

The drain requires the D-state to be permanent. On a healthy GPU the driver releases the lock within milliseconds — the wait is transient, the task returns to a killable state, and SIGKILL reaps it cleanly. Fourteen instrumented attempts on this node — eight synthetic (incl. the exact production watchdog → ncclCommAbort teardown path and direct driver-lock contention) plus six rapid kill→relaunch cycles of the real production pipeline (the single-user cascade) — produced hundreds of transient D-state samples across all three driver surfaces yet all exited cleanly; the node never drained. A permanent wait needs the GPU itself wedged: a kernel that never completes or a context corrupted by an earlier unclean event. The production drains were therefore a cascade — seeded by the 2026-05-26 concurrent cross-cgroup cuInit failure (Event 0) that degraded the device — where each subsequent job's NCCL teardown wedged permanently and incomplete recovery re-seeded the next. This is why a drain cannot be triggered from a clean single-tenant state, and why the fix targets recovery and prevention of the wedged-GPU precondition, not the many possible triggers.

§4 — Surgical fix (SDCC)

Two config lines make every future drain self-diagnosing and self-recovering; one epilog gate stops the cascade at its root.

  1. Set UnkillableStepProgram (currently (null)). A root script runs the instant a step is declared unkillable: capture /proc/<pid>/stack + wchan for the cgroup PIDs, nvidia-smi, dmesg | grep -iE 'NVRM|Xid', echo w > /proc/sysrq-trigger, then schedule a reboot. Turns a multi-hour manual drain into a logged, auto-recovered event — and gives the kernel stack we cannot capture as a normal user.
  2. Raise UnkillableStepTimeout 60 → 120 s (hard cap 126, SchedMD bug #11103). Legitimate multi-GPU NCCL teardown takes 30–60 s; 60 s tips healthy teardown into a needless drain.
  3. Epilog GPU-clean gate (prevents the cascade). After each GPU job, verify no compute process remains and the GPUs are healthy; if not, drain-with-reason rather than release a dirty node, and ensure clean GPUs before the next job starts. This stops a wedged context from propagating to the next job — the mechanism behind every cascade drain.

Lower-priority hardening (separate ticket): egress REJECT not DROP on betelgeuse (removes a non-GPU network D-state surface); investigate MPS/MIG or serialised cross-cgroup cuInit to eliminate the Event-0 seed; alert on DRAIN. Application-side hardening (cooperative STOP-FILE cancellation, three-layer sbatch time-limit defence, in-process encoders) is already in place and is not sufficient alone — it cannot reach a D-state task; the cluster-side fix above is required.
