§1 — What is deployed, and the one number we have

DeepSeek-V4.1-Flash serves on four H200 cards at TP4/EP4, port 18810, behind the router on 18802, with the launcher listing it. The deployment itself is settled and recorded in clive-global-endpoint-routing; this plan is about what it actually delivers under load.

The single measurement taken so far is a single-stream decode sweep, and it is the reason this plan exists:

Flat at 34.4 tok/s with a 131 ms time-to-first-token. The DeepSeek beta reported 300–507 tok/s, on their own serving stack. A single-stream figure and an aggregate figure are not comparable, which is precisely why §2 exists — but a 9× gap is large enough that it should not be assumed away as a concurrency artefact before it is measured.

Three candidate causes, in the order they are cheap to test: speculative decoding is off (§3), the MXFP4 experts run through a dequantisation path rather than native FP4 tensor cores because H200 is SM90, and the Engram tables are gathered from host memory rather than HBM. Only the first is a setting; the other two are properties of running this checkpoint on Hopper.

§2 — Concurrency sweep

Record decode tok/s, aggregate throughput, TTFT and p95 TTFT across a range of concurrencies against the live endpoint. imas-ambix agent bench already carries a concurrency category and writes JSON to ~/.local/share/ambix/bench/; use it rather than writing a new harness.

The pool is sized at 20,000,000 tokens, so KV capacity should not bind until concurrency times context approaches that. The scheduler caps are max_running_requests=256 and chunked_prefill_size=32768; the sweep should reach far enough to show whether the ceiling is the scheduler, the KV pool, or the GPUs.

Done when: a table of concurrency against per-stream and aggregate tok/s exists in the evidence record, the saturation point is named, and the binding constraint at saturation is identified by measurement rather than inference.

§3 — DSpark speculative decoding

The serve currently reports speculative_algorithm: None. This checkpoint ships DSpark, and the vendor's own four-GPU recipe enables it with --speculative-algorithm DSPARK --speculative-dspark-block-size 5. The V4-Flash profile in this repository already sets an equivalent under vLLM, so the omission here is an oversight rather than a decision.

Speculative decoding helps single-stream latency most and can cost throughput at high concurrency when acceptance is low, so it must be measured on both sides of the §2 sweep rather than enabled on principle.

Done when: single-stream and saturated throughput are measured with and without DSpark, and the profile carries whichever wins with the measurement recorded beside it.

§4 — Dogfood through clive workers

Synthetic benchmarks measure token rates; they do not measure whether the deployment is usable for the work it exists to do. Drive real agent workloads through clive against this endpoint and record what breaks.

Agent traffic differs from the benchmark in ways that matter: long and growing contexts rather than a fixed 12-token prompt, tool calls in a loop, structured output, and bursty concurrency. The tool-calling path has been verified once by hand — a call and its result round trip correctly — but never under sustained multi-turn load.

Done when: several clive workers have completed real tasks against the endpoint, with observed failure modes, context-growth behaviour and tool-call reliability recorded; and any defect found is either fixed or carried as a followup naming it.

§5 — Serving interpreter: split kt-kernel out, then move to 3.14

The repository targets Python 3.14 and Ruff formats to it, which rewrites exception tuples into PEP 758's unparenthesised form. The serving venv is 3.12, where that form is a SyntaxError. The repository's own guidance records this as having recurred three times; it recurred a fourth time on 2026-09-14 when a directory-scoped formatter run rewrote the vLLM middleware modules, which would have broken every vLLM serve at import.

Moving the serving environment to 3.14 removes the whole class rather than documenting it again. Upstream permits it: PyTorch publishes cp314 wheels, SGLang requires only >=3.10, and vLLM allows <3.15. The blocker is local — a 3.14 sync fails with:

all versions of kt-kernel have no wheels with a matching Python version tag (e.g., `cp314`)
hint: Wheels are available for `kt-kernel` (v0.7.0.post4) with ABI tag: `cp312`

kt-kernel belongs to KTransformers CPU offload, and SiteConfig._engine_key maps the ktransformers engine onto the sglang venv, so one environment must satisfy both. Plain SGLang serving does not need the kernel at all.

Done when: the decision below is locked, the split (or its alternative) is implemented, a 3.14 environment builds and passes its runtime verification, and no serving-loaded module fails to parse under the interpreter that will run it.
