§1 — What this plan does, and the constraint that shapes it

The local lane currently serves deepseek-v4-flash from a two-card vLLM process (job 1260660, TP=2, 512K context, port 18800), fronted by the ambix-router on port 18802 — the origin every clive consumer is pointed at. Two peer sessions (nova and imas-codex) put nine dispatched nodes through that lane on 2026-09-05 and both report it landing usable work. The lane is worth investing in, and it is running at a quarter of the card budget it was sized for.

This plan raises it to four cards with DSpark speculative decoding, adds the serving-time instrumentation both peers named as the lane's biggest blind spot, and retunes the local backend's routing configuration from what the two sessions actually measured.

The constraint: the router refuses duplicate model ids

The obvious way to satisfy "keep the two-card serve live until the four-card serve is healthy" is to start the second serve alongside the first. Done naively that takes the live lane down. imas_ambix/agent/router.py collects every reachable upstream that advertises the requested model id and then refuses when the count is not exactly one:

owners = [(catalog.upstream, card)
          for catalog in catalogs
          for card in catalog.cards
          if card["id"] == model_id]
if not owners:
    await self._json_error(send, 404, f"unknown model id: {model_id}")
    return
if len(owners) != 1:
    await self._json_error(send, 409, f"duplicate model id: {model_id}")
    return

Both profiles publish the same served_name — deepseek-v4-flash — precisely so a consumer never has to know which card count answered. That deliberate naming choice and this duplicate check are in direct conflict: the moment a second serve of the same release becomes reachable, every request through the router returns 409, including those the healthy two-card serve could have answered. The overlap the AGENTS.md deployment notes describe is therefore not currently executable.

So the ordering below is not ceremony. The router must learn a deterministic preference before a second serve exists, and the fact that _fetch_catalog only includes upstreams that actually answer /v1/models is what turns that preference into a health-gated cutover: a four-card engine still loading its weights is simply absent from the catalog, so traffic stays on two cards until the new process is genuinely answering.

What the two consumer sessions measured

Both peer reports are first-hand execution data from 2026-09-05, and they agree everywhere they overlap. Nine nodes total: five on nova (four landed, one live at the time of writing), three on imas-codex, all promoted, and zero corrective redispatches to a frontier lane. Every landed node passed its gate on the target surface and survived a hunk-by-hunk read. Two nodes corrected their coordinator's brief rather than executing it faithfully, and one declared its own headline measure vacuous instead of banking it.

The findings that bear on configuration:

  • Brief specificity, not task difficulty, is the governing variable. Both sessions state this independently and it is the single most useful result. A brief naming a field, a formula, a sign rule and two fixtures produced an edit at assistant turn 6, seventeen seconds in. A brief asking the worker to decide when it had measured enough produced no edit in forty minutes on the same model — and committed within minutes once the measurements were handed back to it as established fact.
  • Whole-context re-read per turn, with no prompt caching. Uncached input totals of 8M, 10M, 26M and 31M tokens on single nodes; imas-codex measured 19,974,934 input tokens with zero cache reads against 428,888 on a comparable codex node — roughly 46× the fresh input. This is the lane's cost story and §4 must establish whether it is a vLLM prefix-caching gap or only a usage-reporting gap.
  • Mid-flight throughput is unreadable. output_tokens: 0 on every per-message usage record; totals appear only in the terminal result record. Generation rate from those totals: 22–33 tok/s across both sessions. This is what §3 fixes.
  • The declared time budget is not enforced for this launch kind. Nodes with a 60 m budget ran 129 and 135 minutes with nothing stopping them; another overran 2400 s until killed. A coordinator cannot time-box this lane today.
  • Thinking dominates output — 83% of emitted characters on one node, above 95% on two others — and reasoning effort is declared rather than effective: the endpoint returns a thinking block at every budget including none.
  • Transcript volume is extreme — about 350 system stream records per assistant turn, 5–10 MB transcripts, 128k stream records on the 135-minute node.
  • Ledger cost is imputed ($52–$162 per node), which ranks the free lane as the most expensive one. A router reading cost inverts.
  • Not observed on any node: tool-call malformation, thinking-tag leakage into text, truncated output, refusal to write, long-context degradation. Peak per-turn input read was 356,574 tokens against an advertised 492,288 ceiling — 72%, never clamped.

§2 — Engine configuration: DSpark and the recipe flags

The profile at imas_ambix/agent/profiles/deepseek-v4-flash.toml already declares tensor_parallel = 4, gpus = 4, kv_cache_dtype = "fp8" and the deepseek_v4 tool-call and reasoning parsers. What it does not carry is DSpark, and several flags the vLLM recipe treats as standard for this model family. The engine schema in imas_ambix/agent/profile.py has no field for them, so they cannot be expressed in a profile at all today.

The upstream recipe for this checkpoint (recipes.vllm.ai, and the model card for the DSpark variant) gives this as the multi-GPU shape:

vllm serve deepseek-ai/DeepSeek-V4-Flash-0731 \
  --trust-remote-code --kv-cache-dtype fp8 --block-size 256 \
  --enable-expert-parallel --tensor-parallel-size N \
  --moe-backend auto \
  --tokenizer-mode deepseek_v4 \
  --tool-call-parser deepseek_v4 --enable-auto-tool-choice \
  --reasoning-parser deepseek_v4 \
  --attention_config.use_fp4_indexer_cache <arch-dependent> \
  --speculative-config '{"method":"dspark","num_speculative_tokens":K,
                         "draft_sample_method":"greedy"}'

DSpark is not a separate model. The DeepSeek model card is explicit: "It is the same checkpoint with an additional speculative decoding module attached." The fused release adds a dspark_* block to config.json, and the weights we already hold carry exactly that block. Nothing needs downloading; the module is loaded by naming the method.

Two parameters are genuinely uncertain and must be settled by measurement rather than by copying an example, because the published examples target different silicon:

  • num_speculative_tokens — the recipe's SM120 example uses 7 and states a floor of 5 with a direction to check the checkpoint. Our checkpoint declares dspark_block_size: 5. Start at 5, which the checkpoint itself names, and try 7 only if 5 loads and serves.
  • attention_config.use_fp4_indexer_cache — Blackwell-oriented; the SM120 recipe requires False and the H200 section does not specify it. Our cards are SM90. Leave it unset (engine default) unless a probe shows a measured win, and record which way it went.
  • draft_sample_method — the model card uses greedy, the SM120 recipe uses probabilistic. Default to greedy; it is the better fit for tool-calling and structured output, where draft acceptance matters more than sample diversity.

Prefix caching is in scope here and is the highest-value item in the plan. If vLLM automatic prefix caching is off, or is defeated by how the Anthropic surface assembles each turn, the lane is re-reading tens of millions of tokens per node for nothing. If it is on and only the usage reporting is wrong, the compute is already being saved and the fix belongs in §3. These are different defects with the same symptom, and the node must say which one it found.

Done when: the generated serve script for deepseek-v4-flash at --gpus 4 emits the DSpark speculative config and each flag above, proven by imas-ambix agent serve deepseek-v4-flash --gpus 4 --dry-run output captured to a file; new unit tests assert each emitted flag; and the whole-tree gate uv run --no-sync ruff check imas_ambix tests exits 0. The serving-interpreter grammar test must pass, because every module named here is imported on the compute node under Python 3.12.

§3 — Serving-time receipts

The user requirement is that tok/s and related metadata are recordable while models serve, so that experience receipts accumulate rather than being reconstructed afterwards. Both peer sessions independently report the same gap from the consumer side: throughput is unreadable mid-flight and only appears in a terminal record.

Substantial machinery already exists and must be reused rather than reimplemented. imas_ambix/agent/bench.py already carries a Prometheus text parser (_parse_prometheus_text), a speculative-decode counter snapshot (_spec_decode_snapshot, _scrape_spec_decode, _counter_delta, _per_position_delta, _spec_decode_window) and provenance capture (capture_provenance). What it does not have is a continuous sampler: it measures a benchmark window, not a serving lifetime.

The deliverable is a recorder that samples the live engine's /metrics on an interval and appends one row per sample to a durable, append-only receipts file, so that a serve's whole life is a readable record. Each row should carry at least: timestamp, job id, profile slug, served name, card count, generation and prompt throughput, running and waiting sequence counts, KV-cache utilisation, prefix-cache queries and hits (the §2 question in continuous form), and — because DSpark is the point of this plan — the speculative-decode acceptance counters per draft position, which is what tells us whether DSpark is actually earning its cards.

This node develops and verifies against the live two-card endpoint, which is already serving and must not be disturbed: scraping /metrics is a read. It must not submit, cancel, or restart any scheduler job — that authority belongs to §4 alone.

Done when: the recorder runs against http://98dci4-gpu-0003:18800/metrics for at least 60 seconds, and the captured receipts file is committed as evidence showing a monotonically advancing sample series with a non-null generation-throughput field and a prefix-cache hit-rate field; unit tests cover the parse and the row shape against a recorded fixture, not a live endpoint; the whole-tree ruff gate exits 0.

§4 — Router preference, bring-up, and health-gated cutover

This section is the operator work, and it carries the one irreversible action in the plan. It runs only after §2 and §3 have landed.

The router change comes first and is what makes the rest safe. Given more than one reachable upstream advertising the same model id, the router must select deterministically instead of returning 409. The preference should be the larger accelerator count, with the more recently started job breaking a tie; the ambix metadata block on each model card already carries accelerator_count, so the information is present without consulting the scheduler. A 409 should remain for the genuinely ambiguous case the preference cannot resolve.

Then, in order:

  1. Restart ambix-router so it runs the new preference logic while still resolving a single upstream. Verify the catalog still lists deepseek-v4-flash and that a one-token completion through port 18802 succeeds.
  2. Probe the card and core budget with srun --test-only --reservation=gpu_0003_grpA --account=grpa --gres=gpu:4 --cpus-per-task=12 --mem=300G true before submitting. Cores, not cards, are what bind on this node.
  3. Submit the four-card serve on port 18801 — 18800 is the live serve and 18802 is the router. Do not touch either.
  4. Wait for the four-card engine to answer /v1/models on 18801, then confirm through the router on 18802 that completions are being served by the four-card upstream.
  5. Record receipts from §3 against the four-card endpoint under a real agentic load, and compare decode throughput against the two-card baseline of 22–33 tok/s. Capture the DSpark acceptance counters — a speculative configuration that drafts and is never accepted is a regression wearing a speedup's clothes.
  6. Only then cancel job 1260660, returning two cards.

If the four-card serve fails to become healthy, stop and leave the two-card serve running. That is a successful outcome for this section, not a failure: the requirement is an overlap with a health gate, and a gate that never opens has done its job. Cancel the failed four-card job to return the cards and report what the engine said.

Done when: a completion issued to the router on port 18802 is demonstrably answered by the four-card upstream, evidenced by a captured /v1/models payload showing accelerator_count: 4 and a receipts sample from §3 taken against the four-card engine; the two-card job is cancelled and the card budget is back to four held.

§5 — Retune the local lane from measured experience

The host flight configuration at ~/.config/reckon/flight.yaml defines the clive backend with only launch, command, model, effort and alias. It is the least completely specified backend on the workstation and, by node count today, the highest-volume one. Both peer sessions converged on the same recommendations, which §1 records in full.

The changes to make, each traceable to a measurement rather than a preference: declare sandbox: worktree-full and session_reuse: true so the lane matches every other CLI backend; declare a time_budget longer than the metered lanes and annotate it as advisory, because it is demonstrably not enforced for this launch kind; do not make the launcher enforce it — that recommendation was withdrawn by the nova lead on the grounds that the two-hour walls were measured on the two-card deployment and are expected to move once four cards and DSpark are serving, so a fence calibrated on them would be calibrated on a configuration that no longer exists; leave effort pinned and record that it is not a calibration axis for this lane; and gate spec level so that exact is trusted unsupervised, guided is allowed only when the measurement is handed to the worker as established fact, and open never routes here.

This file is user data outside every repository, so it is written by the coordinator rather than a worker — reckon worker write paths are repository-scoped for every role.

Done when: reckon flight --project imas-ambix reports the new keys resolving from the host layer, and each change carries an inline comment naming the measurement behind it.

§ Decisions

Model deployment config is persisted as TOML profiles under imas_ambix/agent/profiles/ today, and the request named YAML. Keep TOML, or migrate the profile store?

Proceeding on TOML so the serve is not blocked behind a format migration. The reading that makes both statements true is that the request's "yaml files in this repo" refers to reckon's flight.yaml , which is genuinely YAML and is retuned in §5 — while the deployment profiles are the repo-persisted, CLI-managed store the request also describes, and those are TOML. A migration would touch nine profiles, the loader, and the tests, and would buy no capability.

The router returns 409 when two upstreams advertise one model id, which makes the documented overlap impossible. How should the cutover work?

Locked. A distinct served name would break the catalog's design promise that one release keeps one client-visible name across every card count, and would require every consumer to re-select. Stop-then-start abandons the overlap the request explicitly asked for and costs a hard outage across the weight-load window, which is minutes for a 284B checkpoint. The preference makes zero-downtime cutover a property of the system rather than a manual dance, and reuses the reachability check already in _fetch_catalog as the health gate.
