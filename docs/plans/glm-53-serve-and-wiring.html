§1 — Why this comes first

Every other item in this sprint is about serving more than one model, and none of them can be proven until a second model is actually listening. The router's acceptance test is that one origin lists two releases and routes each to the right engine; the launch surface's is that a picker shows two rows with honest topology labels. Both need this. So this plan is a prerequisite of the router rather than a consequence of it, and it is the one item that is ready to start with nothing outstanding.

It is also ready in the literal sense. The profile was corrected to name the artifacts actually published, the download completed on 2026-09-01, and both checkpoints are on disk:

§2 — Bringing it up beside DeepSeek

A second engine needs a second port, because one process serves one model and both default to the same one. The launch is therefore explicit about port as well as topology:

imas-ambix agent serve glm-5-3 --gpus 4 --cpus 12 --port 18801

No auth flag: an open endpoint is now the default. Cores are declared rather than derived — they do not follow the card count — and 12 is the profile's own figure for four cards, which leaves the reservation's shared pool usable by the physics jobs that run on this node. Probe it before committing, as with every serve here:

srun --test-only --partition=betelgeuse --reservation=gpu_0003_grpA \
     --account=grpa --gres=gpu:4 --cpus-per-task=12 --mem=320G --time=00:01:00 true

Reaching a ready state is not evidence that this engine works. The sparse-MLA attention kernel claims roughly 8 GiB per card lazily on the first real decode, so a launch that reports ready with a thin reserve dies on its first request — that is exactly how a sibling deployment failed after a clean startup. Validation is a real generation, and the context ceiling is read from the engine's own startup pool line rather than computed: this architecture replicates a compressed attention latent on every rank instead of sharding it, so more cards buy context only by shrinking weights per card, and arithmetic has already been wrong about the runtime overhead by about 12 GiB on a neighbouring variant.

§3 — Wiring it through to a consumer

A running engine nobody can select is not a served model. Four things must be true, and each has a distinct failure mode:

  • The catalog must carry this release with intact launch-owned metadata — accelerator family, a card count of 2, 4, 6 or 8, and checkpoint precision — because the launcher fails closed on an incompletely annotated entry rather than degrading. Note the precision differs by variant here (int4 against fp8), unlike DeepSeek where one checkpoint serves every width, so this is the first release that will exercise per-variant metadata.
  • The union — both releases at one origin — is verified in the router's plan, not here, and that is why this plan is its prerequisite rather than its consequence. Everything in this section is checkable against this engine's own port, so nothing here waits on the router; the router then cannot close until this engine exists to be listed beside the first.
  • The client-visible name is glm-5.3 — the profile's served name, not its slug, and the same name at every card count so a consumer never has to know which node size answered.
  • Tool calling and reasoning must actually work through the harness. This release uses different parsers from DeepSeek, and an agentic consumer is useless without tool calls. Verify a real tool-use round trip and a reasoning response against this engine specifically; do not carry the DeepSeek result over.

Once selectable, it becomes the second local release in the launch surface, which is what gives the alias mapping something to distribute: one local release for bulk and parallel work and a second for the other local slot, per clive-launch-modes.

§4 — Done-when

  • The four-card INT4 deployment serves on its own port beside the DeepSeek serve, sized from a scheduler probe, with 6 of 8 cards in use and the shared core pool not exhausted.
  • Its context ceiling is quoted from the engine's startup pool line, and a real generation succeeds — not merely a ready state.
  • A tool-use round trip and a reasoning response both succeed against this engine.
  • The release appears in the catalog with complete metadata and correct per-variant precision, and the generated launcher lists and selects it with no source change.
  • The eight-card FP8 deployment is measured once for single-model quality and explicitly recorded as an alternative to concurrency rather than a default.

§ Decisions

Is the second engine's port a fixed convention, or allocated per serve and discovered?

Recommendation: allocated and discovered. A fixed convention is simpler to type but becomes a second thing consumers learn and a collision waiting to happen once more than two engines run; the router already has to resolve upstreams dynamically, so discovery costs nothing extra and keeps the port an implementation detail behind one origin.

Is speculative decoding enabled for this release, or left off pending measurement?

Recommendation: measure first, and expect it to be unavailable. This checkpoint does quantize a draft head, but the engine could not construct a draft against a compressed-tensors mixture-of-experts on the neighbouring variant, and the same loader path applies. Where drafting did work it cost single-stream throughput at low concurrency, which is the regime an interactive consumer sits in.
