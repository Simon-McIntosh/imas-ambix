§1 — What forces the indirection

One vLLM process serves one model and binds one port. Every consumer-facing contract we have assumes the opposite. SiteConfig.global_origin is a single origin, and the generated clive launcher makes exactly one anonymous GET <origin>/v1/models request whose non-empty response it treats as the complete availability authority. That works while precisely one model is served and fails the moment a second one is, because the second model answers on a different port and therefore publishes a different catalog.

The documented claim that "a future catalog item with id: glm-5.3 is immediately selectable by --model glm-5.3 without a Clive source or deployment change" is true only if both releases appear in the same catalog. Nothing in the tree produces such a catalog today. That is the gap this plan closes, and it is the prerequisite for both downstream plans.

Two further problems resolve in the same component, which is why they are scoped here rather than separately:

  • Consumer metadata in the operator's job log. Prompts do not leak — vLLM 0.28 defaults enable_log_requests to false and a 2.7 MB live log contained zero request-body lines — but every consumer's IP, endpoint and status does, in the serve job's own stdout. With a router in front, the engine log records one client address and the router owns per-consumer accounting under its own retention policy.
  • A GPU node named in the client-facing URL. Resolved in §3: the origin stays on the GPU node deliberately, and the reasoning is recorded so it is not re-litigated.

§2 — Pass-through, not translation

Decision locked: no LiteLLM on the inference path. The measured reason is that every leg already speaks the same wire protocol, so there is nothing for a translating proxy to add and a great deal for it to lose. Probed against the live engine, vLLM exposes the complete Anthropic surface Claude Code drives:

PathResult
POST /v1/messages200; SSE with real thinking content blocks
POST /v1/messages/count_tokens200
POST /v1/messages with tools200
GET /v1/models200, carrying the launch-owned ambix metadata

A translating proxy would convert a native Anthropic request into OpenAI chat and the response back again, and that conversion is where thinking blocks, tool_use identifiers, cache_control and interleaved-thinking signatures are lost or mangled. The failure mode is not hypothetical: the previous proxy attempt died on a dialect mismatch, because LiteLLM's anthropic/ provider emits x-api-key and no Authorization header while the engine's key middleware accepts only Authorization: Bearer. A correct credential returned 401 on every request.

So the router dispatches and streams. Its whole contract is model id → (upstream base, auth header) plus byte-faithful streaming, which preserves the wire format by construction and has no dialect surface to get wrong. LiteLLM keeps its existing job on the genuinely polyglot path — the separate proxy already serving OpenRouter, Gemini and OpenAI routes on a login node — and the two are not merged.

§3 — Where it runs, and why the GPU node wins

The earlier recommendation was a pinned login node, on the reasoning that a client-facing URL should not name a GPU host that SLURM might reassign. Measurement retired that reasoning: sinfo -p betelgeuse returns exactly one node. The serve host does not move between relaunches, so the premise for relocating was wrong, and 98dci4-gpu-0003 is the more descriptive name of the two.

Decision locked: the router runs on the GPU node and the origin stays http://98dci4-gpu-0003:<port>. It keeps the client-facing URL stable across engine restarts and port changes, needs no second host to be healthy for local inference to work, and adds no network hop to the hot path.

The cost is real and measured. From inside a betelgeuse allocation:

Target from 98dci4-gpu-0003Reachability
api.anthropic.com:443blocked
1.1.1.1:443blocked
98dci4-srv-1006:18400 (login node)open

So a router here cannot reach a hosted provider directly. It can reach a login node, which has full egress, so a hosted leg remains available through one internal hop rather than being foreclosed. That keeps the locked origin compatible with the deferred work instead of trading it away.

Reachability of the origin itself is not in question: a standard compute node already reaches both the GPU node's serve port and the login node's proxy port, so consumers on login nodes and inside compute jobs are both served.

§4 — Resolving upstreams without hand-edited config

The router must learn where each engine is listening without a human editing a file, or it reintroduces by hand the coupling it exists to remove. The data already exists and needs no new mechanism: agent serve stamps the scheduler comment ambix-serve;port=<port>, and live discovery already reconstructs node, port, model id, card count, reported context and checkpoint precision from the scheduler plus an endpoint probe.

Two resolution sources, and the plan builds the second:

  • Scheduler discovery — reuse the existing path on a short TTL. Cheap, but it queries one user's queue, so a router run by one operator sees only that operator's serves.
  • A registration file per serve — the serve job writes its resolved identity to shared storage at startup and removes it on shutdown. User independent, survives a scheduler outage, and is the source the router should prefer. Build this one; keep scheduler discovery as the fallback that reconciles a stale file against reality.

The prerequisite defect here is already fixed: live discovery had been rejecting a healthy serve outright because the allocation parser anchored the resource name to the start of the field, and this scheduler reports the TRES form gres/gpu:2. Six spellings are now covered by a table test.

§5 — The union catalog

The router's GET /v1/models merges each upstream's catalog into one response, preserving the per-release ambix metadata block the launcher validates: accelerator family, an accelerator count restricted to 2, 4, 6 or 8, checkpoint precision, and the engine's own max_model_len. The launcher already fails closed on a duplicate, malformed or incompletely annotated catalog, and already renders a release-at-topology selector per item, so a correct union needs no launcher source change at all — which is the test that the indirection is faithful rather than merely functional.

Done-when for this section is exactly that: with two engines up, clive --list shows both releases with correct topology labels, and clive --model <either> reaches the right engine, using the launcher as currently generated.

§6 — Done-when

  • One origin serves a union catalog over two concurrently-running engines, with per-release ambix metadata intact and the engine-reported context preserved.
  • clive --list and clive --model <id> work against both releases with no change to the generated launcher.
  • Streaming is byte-faithful: an SSE response through the router carries the same event sequence and thinking/tool_use blocks as the same request made directly against the engine.
  • count_tokens and the OpenAI chat path both work through the router.
  • The engine's job log records one client address; per-consumer accounting lives in the router's own log.
  • An engine restart on a new port is picked up without editing router config or redeploying the launcher.

§ Decisions

Does the router translate protocols, or stream through?

Locked to pass-through. Every leg already speaks Anthropic /v1/messages — measured on the live engine, including SSE thinking blocks, count_tokens and tool definitions — so translation buys nothing and risks the exact class of failure that killed the previous proxy, where LiteLLM's anthropic/ provider sent x-api-key against a Bearer-only engine and a correct key 401'd.

Which host owns the client-facing origin?

Locked to the GPU node. betelgeuse is a single-node partition, so the serve host does not move and the argument for relocating to a login node fell away; the GPU host is also the better-named of the two. Accepted cost, measured: no outbound internet from there, so a hosted provider leg needs one hop through a login node.

Does the router resolve upstreams from a per-serve registration file, from scheduler discovery, or from both with the file preferred?

Locked to the recommendation on execution. The per-serve registration record is user-independent and survives a scheduler outage, while the scheduler discovery already in the tree reconciles a stale record against reality. Scheduler-only would inherit the one-operator limitation of a per-user queue query. The record never establishes availability on its own: a reader still qualifies it with an endpoint probe, which is what keeps a stale file from becoming a phantom upstream.
