§1 — The defect, and why it survives every review

A test that reads a constant out of the module it is testing and asserts a produced value equals it cannot fail on that constant's value. Change the constant and both sides move together; the test stays green and reports that the behaviour was checked. It is the test-suite form of the guard that disables itself to pass its own test — it certifies something, just not the thing its name claims.

This is not a hypothetical shape. It was found by a reviewer on the telemetry spine, in a module whose own six review rounds had not surfaced it, because every round read the module and its tests as a pair and the pair is internally consistent. That is the mechanism: a circular assertion is invisible to any reader who holds both sides at once, which is exactly what a focused review does. Only a check that compares the two sides mechanically sees it.

What was measured, and the number that was wrong

An earlier scan of this repository reported 210 sites. That figure counted any assert a == b in which either side referenced a symbol imported from imas_ambix, which sweeps in the two shapes that are the opposite of the defect: a chain that pins a literal somewhere along it, and a comparison whose other side is a written-out literal. Scanned again with those excluded:

Three shapes that look identical to a scanner and are not defects

Every one of these was found among the ten spine sites, so an allowlist is not a concession to legacy code — it is required for the guard to be correct on code written this week.

ShapeExampleWhy it is sound
Wiring derived["occupancy_target"] == LaneCapacity.OCCUPANCY_TARGET The claim is that the published field is fed by that constant, not that the constant holds a particular value. Pinning a number here would assert the wrong thing and would churn on every retune.
Pinned once, referenced after rows[0]["upstream"] == SELF_ANSWERED_UPSTREAM, where the same file elsewhere asserts SELF_ANSWERED_UPSTREAM == "(router)" The value is pinned exactly once, and every later use reads as prose. Repeating the literal at each site would be worse, not better.
Written-out literal _CARD_QUERY_FIELDS_LITERAL == node_probe.CARD_QUERY_FIELDS The left side is spelled out in the test file itself, so the comparison does pin the value. A scanner sees a Name on both sides and cannot tell.

The third shape is the one that decides the guard's architecture. Telling it apart from a genuine circular assertion needs the test module's own bindings resolved, not just the comparison node — so the check is a small AST pass over each test file, not a regular expression, and it must be written that way from the start.

§2 — The guard

Deliver one check that walks tests/, parses each test module, resolves which names it binds locally and which it imports from imas_ambix, and reports an assert whose equality chain is anchored to nothing: no literal anywhere in the chain, no side bound to a literal within the test module, and at least one side a bare reference into the package under test.

It carries an explicit allowlist keyed on file and symbol, with a required one-line reason per entry, so a wiring assertion is recorded as a decision rather than as an absence. An entry without a reason is a failure of the guard, not an exemption from it — the reason is the thing a later reader checks.

Done when: the guard runs from the repository root and exits 0 on an empty finding set; a test asserts it reports a deliberately planted circular assertion; a second test asserts it stays silent on each of the three sound shapes in §1, one case each; and the allowlist refuses an entry with no reason. The whole-tree lint gate stays green.

Not in scope: wiring it into CI. A guard that fires on 135 pre-existing sites cannot be made blocking on the day it lands, and making it blocking before §3 and §4 have run would force exactly the reflex this plan exists to prevent — silencing the check to get green.

§3 — Dispose of the spine modules' ten sites

Ten sites across test_lane.py (5), test_engine_metrics.py (2), test_node_probe.py (2) and test_request_receipts.py (1). Inspection while writing §1 suggests most are the sound shapes rather than defects, so the expected outcome here is mostly allowlist entries with reasons — and that is a real deliverable, because an unrecorded sound assertion is indistinguishable from an unnoticed circular one.

Each site is disposed of one of three ways, and the disposal is stated per site: pin the value with a literal; keep it and add an allowlist entry naming which of the three sound shapes it is; or delete it as carrying no claim. Every pinned site must be demonstrated by a mutation — change the constant in the module and show the named test reddens — because a site repaired without that demonstration has only been rewritten, not fixed.

Done when: the guard reports zero unallowlisted findings under those four files; every allowlist entry added carries its reason; every pinned site has a mutation receipt quoting the exact changed line and the test that failed; the focused suites pass and the whole-tree lint gate is green.

§4 — Dispose of the remaining tree

125 sites across 47 files once §3 has run. This section is partitioned by file rather than by subject, because the inventory the guard emits already exists and coverage is then checkable by arithmetic: each worker takes a disjoint set of test files, disposes of every finding in them, and a merge step verifies the tiling by count against the guard's own output. The heaviest files are the place to start — test_machine_artifact_arm.py and test_geometry_export.py carry 12 each, test_provenance.py 10, test_artifact_resolution.py 9.

The same three-way disposal and the same mutation requirement as §3 apply. Nothing here is urgent; it is the long tail, and it is sequenced last so the guard has been exercised on the spine before it is pointed at unfamiliar code.

Done when: the guard reports zero unallowlisted findings across tests/; the tiling is verified by count; and a decision is recorded on whether the guard becomes blocking in CI, which is the only point at which that question can be answered from evidence rather than from intent.

§ Decisions

Once the tree is clean, does the guard become a blocking CI check or stay an advisory report?

Deferred to §4 on purpose. Answering it now would be answering from intent; after the disposal the false-positive rate on real code is measured and the question has an evidenced answer.

Where does the allowlist live — beside the guard, or as a marker at each site?

An inline marker keeps the reason next to the code it explains, which is where a reader wants it; a central file makes the whole set of exemptions readable at once and is harder to add to casually. Settle this in §2 before any entry is written, because migrating entries afterwards is pure churn.
