Seeing what the map binds

JT-60SA Geometry and Signal Figures

The JT-60SA machine map (jt60sa-machine-map) has converted the facility's SELENE input decks into an IMAS machine description for each operating phase, and cached the first EDDB pulses, yet nothing of it has been drawn. This plan draws it: the poloidal cross-section of each phase with every conductor and sensor, what changes between OP1 and OP2, and the cached coil, plasma-current and flux-loop signals. The figures are evidence the map's census and convention work will read, and they run in their own session, independent of the map's build.

§2 — Geometry: each phase, and what changes between them

Two figures, rendered by imas-ink in its own style (lead ruling, 2026-10-06). A short script, scripts/figures_jt60sa_geometry.py, opens each phase of the store through the jt-60sa catalogue, which owns its addressing: load_packaged_machine_map("jt-60sa") gives the store root (description_store_root_path()), the layout and the phase maps, and NetCDFTransformEngine.open on that root and map returns the store whose path is the phase directory. It reads wall, pf_active and magnetics with imas.DBEntry, passes them to imas_ink.extract.extract_geometry and renders each phase with imas_ink.figures.geometry_figure_mpl into axes the script lays out, using the ax argument and the reference-outline line style that imas-ink's geometry-figure-vessel-units plan adds, since the figure today makes its own axes and has no second-outline style: axes off, equal aspect, imas-ink's default weights and greys, and no labels, legend or added colour. The first figure is OP1 and OP2 side by side on one shared viewport. The second overlays the two phases' first wall and vessel contours on one panel, the components that change at the OP1 to OP2 boundary, telling the phases apart by line style alone. The caption carries everything a reader needs to identify what is drawn: which panel is which phase, which contours are the first wall and which the vessel skins, that each coil rectangle is the outline of one of the 12 PF coils, the envelope imas-ink draws around the coil's current filaments (268 in all), that the cryostat-scale passive loop and the sensors EDDB acquires without a facility position are not drawn, and the counts. The script draws no element itself and holds no colour, label or style constant.

It waits on two landings: the machine map's wall rewrite, which writes each phase's first wall as a limiter unit and its vacuum vessel as an annular vessel unit from the inner and outer VV skins of coil_vv_OP{1,2}.dat (lead ruling, 2026-10-06; machine-map node jtmm-passive-cryostat-and-wall), and imas-ink's geometry-figure-vessel-units, which teaches it to draw vessel units and to compose two phases into one figure. Done-when: both figures are written as one SVG each, with no PNG twin, under docs/figures/jt60sa-geometry/ and embedded with a project-absolute src and a caption in the node's evidence fragment; the script prints, per phase, the counts it passed to imas-ink and those it drew (PF coils drawn and the filaments they enclose, first-wall and vessel contour points, flux loops, probes) and they match the store.

§3 — Signals: the cached pulses

Three figures, rendered by imas-ink's time_trace_figure_mpl from imas_ink.components.TimeSeries panels, in imas-ink's default style with nothing added to what it draws, from a short script, scripts/figures_jt60sa_signals.py, that draws nothing itself and holds no style constant. Each channel is read through a read_channel this section adds to imas_ambix/data/eddb.py beside write_channel, returning the same ChannelRecord (data, time base and the UNIT_ATTR unit) from channel_path and channel_time_path, so the cache keeps one owner for its read as for its write; the unit is named on the axis. Which channel to draw, and at what factor, comes from the packaged JT-60SA signal maps where they bind it: load_packaged_signal_map("jt-60sa", "pf_active") serves the MMSYS coil-current chain chosen for each PF coil and load_packaged_signal_map("jt-60sa", "magnetics") the PSRC plasma current, so the figure draws the served chain and applies its channel_factor rather than choosing again. The engine path those maps feed (ZarrTransformEngine, VirtualZarrView) returns values with no time base, though its VirtualArray.attrs carry the bound channel's target unit, which the figure takes from there; and the maps bind no flux loop. So read_channel supplies every channel's time base, and the unbound flux-loop channels whole with their EDDB unit; the section corrects eddb.py's module docstring, which says the cache needs no cache-specific reader, to name read_channel as the raw read beside the engine path. read_channel is the one public name the section adds to eddb, the read counterpart nothing there provides, and it retires nothing; a round-trip test in tests/data/test_eddb_cache.py writes a channel and reads it back. For E101154, the PF coil currents from MMSYS against time, and the plasma current from PSRC. Also for E101154, the flux loops, one panel per index holding the processed PSRC magFluxLp channel and the raw MDAC magFlxLp channel of the same index, the raw one in imas-ink's reference line style, through the multi-series panel imas-ink's geometry-figure-vessel-units plan adds (its §3), which is the raw-to-processed correspondence the map's census must settle, drawn rather than assumed. For C060033, the coil currents of the no-plasma commissioning record, the input the map's convention work uses. Where a channel's time base or unit differs from its neighbours, the figure says so rather than rescaling silently. The signals script is a second caller beside the geometry script because it reads the EDDB cache, not the description store; it adds one script with no command-line option and no public name, and retires nothing.

Done-when: the three figures are written as one SVG each, with no PNG twin, under docs/figures/jt60sa-signals/ and embedded in the node's evidence fragment, which the landing carries into this plan, with a project-absolute src and a caption naming the shot, the channels and their units; the script reads only the cache and prints, per figure, the channel names and units it drew.

§4 — imas-ink draws the wall's vessel units

This work moved to imas-ink's own plan, imas-ink:geometry-figure-vessel-units, because a project's work is written in its own repository; §2 waits on that plan, and this section is kept only as the record of why. imas-ink's extract_geometry gathers only wall.description_2d.limiter units (imas_ink/extract.py, _select_mobile_unit), so a vacuum vessel written to description_2d.vessel never reaches geometry_figure_mpl. The machine map now writes JT-60SA's vessel there, as an annular unit built from the inner and outer VV skins of coil_vv_OP{1,2}.dat. The lead ruled on 2026-10-06 that any drawing the figures lack is added to imas-ink, not ambix, so this section extends imas-ink in its own repository through the vessel owner it already has: extract_vessel_shells (imas_ink/three_d/walls.py:151) and its VesselShell type. That owner reads an annular unit's centreline (with thickness) or a plain outline, but not outline_inner and outline_outer, which is what the JT-60SA store writes (two closed 51-point skins, the same in both phases); the section adds that reading, one VesselShell per skin, ahead of the centreline path. extract_geometry then carries those shells on MachineGeometry in a field typed with the existing VesselShell, and geometry_figure_mpl draws them in imas-ink's ink style beside the limiter, adding a style constant only if the vessel needs a weight distinct from the wall. The 2D geometry has no vessel representation today, so the field retires nothing; it is the one public addition, reusing the type the 3D path already exports.

The done-when and its test live in that plan.

§ Decisions

Repository colour-role palette

The repository's first colour assignment: one role per component the JT-60SA figures draw (PF coils, OP1 vessel, OP2 vessel as lightness steps of one hue, wall, flux loops, pickup probes). Every candidate holds 3:1 against white, uses no red, and keeps colour-blind dE at or above 8 over all pairs. On 2026-10-06 the lead provisionally chose A from the first three and asked to see a wider range drawn on the geometry before locking.

The lead ruled on 2026-10-06 that JT-60SA figures render through imas-ink in its own style with no labels, so the repository keeps no palette of its own.

Who draws the JT-60SA figures

ambix had grown its own style module and hand-drawn painters; imas-ink already renders IMAS machine geometry and time traces, and nova's binding plot rules route every figure through the imas-ink style.

Rendering belongs to imas-ink; ambix keeps the data and a thin call. Any missing drawing is added to imas-ink.

Source of the JT-60SA wall and vessel contours

The SELENE deck gives the vessel only as filament rectangles; coil_vv_OP{1,2}.dat carries the first wall and the inner and outer VV skins as smooth contours, and the imas-codex graph lists further candidates on the JT-60SA host.

coil_vv already holds both phases' first wall and VV skins; the machine map writes them so imas-ink draws them with no figure code. Graph-listed sources were passed to the machine-map session for cross-checking.
