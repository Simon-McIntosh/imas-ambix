§1 — What moves, and why

Every Claude Code session on this workstation, fourteen of them across five zellij sessions (ambix, codex, efit, nova, reckon), runs on the login node 98dci4-srv-1006, together with its followers, dispatch shells and searches. On 2026-09-23/24 those processes contributed to a GPFS degradation that took the node to load 143. The evidence is in the research note login-node-storage-contention, whose §8 records the probes this design rests on. Reckon's a-cutover-is-measured-against-its-baseline §4 sets the topology: a zellij server in the fleet allocation's batch step, login nodes attaching only as viewers, and one SLURM step per session. This plan delivers that topology for the sessions themselves and the connection you use to reach them.

§2 — The connection: idempotent, and nobody remembers the job id

Landed in dotfiles 3cfd155 and imas-ambix a102bafc. A session is in fleet mode when its name is listed in ~/.config/cx/fleet-sessions, so sessions move one at a time and the others are untouched. For a fleet session, the login-side cx:

  1. Resolves the fleet from ~/.local/state/fleet/record.json, which the supervisor writes at start. It confirms the job with squeue and never trusts the record alone.
  2. Holds one only if none runs, by running imas-ambix agent fleet hold --submit under a lock in ~/.local/state/fleet/. If a submitted job is still pending, it waits for that job rather than submitting another, and shows the pending reason while it waits. Two terminals opening at once therefore produce one allocation.
  3. Cancels stale viewers by step id. Viewer steps are named cx-view-<session>, so one left behind by a dropped connection is found by name and cancelled by id, never matched by pattern.
  4. Attaches with srun --overlap --pty --jobid=<fleet> --job-name=cx-view-<session> fleet-attach <session>. The step asks the supervisor to start the session if it isn't running, then attaches to it.

Running cx twice attaches to the same server. A laptop that sleeps or an ssh connection that drops ends only the viewer step, and cx reattaches. If the allocation is re-held on another node, the record moves with it, so the fleet's job id is never typed or remembered.

On the node: fleet-supervisor is the batch step. It creates the runtime directory the node lacks and points XDG_RUNTIME_DIR at it, which puts zellij's sockets and Claude Code's messaging sockets there. It starts zellij servers on request, and on a reload request it re-executes itself in place, so a fix to it needs no new allocation. fleet-claude runs a Claude session as its own step, so SLURM removes whatever the session started when it ends. fleet-shell opens a shell inside the job.

Four defects the demonstration found, all fixed: (1) sbatch exports the submitting shell, so the zellij variables leaked into the batch step and zellij refused to create a session. (2) Submitted from inside a Claude session, the same export carried CLAUDE_CODE_CHILD_SESSION, which turned transcript saving off for the resumed session. It also carried the submitting session's messaging token. The supervisor and fleet-claude now drop every inherited ZELLIJ* and CLAUDE* variable. (3) zellij attach --create-background alone does not create a session in 0.45; it needs --create as well. (4) cx's background create passed CX_BACKGROUND=1 into the environment of every pane it made, so a later cx inside one exited silently. A peer's name is derived per process, so a moved session gets a new name: reckon-2f came back as reckon-a0.

§4 — ssh configuration: a fixed alias, not a rewritten one

Rewriting ~/.ssh/config on WSL and on the login node whenever the fleet moves is not needed, and it would be the wrong route in. An ssh session straight onto the node lands in the node's user.slice, outside the job, escaping both its limits and its cleanup (research note §8). The job id is already resolved on the login side, so a fixed alias is enough: Host fleet, with the same connection settings as iter, RequestTTY yes and RemoteCommand ~/.local/bin/fleet-shell. That gives you a shell inside the job, wherever the job currently runs, and never needs editing.

§5 — The fleet-wide move

Every session has confirmed it is at a clean stop and has stopped its followers. The move runs in one operation, because sessions on the two sides cannot message each other. For each zellij session:

  1. Inventory. ~/.claude/sessions/<pid>.json maps each live Claude process to its session id, directory and peer name. The process's environment gives its zellij session and pane.
  2. Stop, then resume. Each Claude process is stopped by pid, with its child tree listed first, before its session is resumed on the fleet: two processes must never write one transcript. On the fleet, the zellij session of the same name gets one tab per former pane, each running fleet-claude --resume <id> in that session's directory. Stopping the old login-node zellij server comes before creating its fleet namesake: zellij's resurrection cache is in the shared home, and two live servers must not write the same entry.
  3. Verify from the healthy path only. Every resumed session registers with its socket under the fleet runtime directory. Its pane shows its last pre-move turn. A fleet session lists the others as peers.
  4. This coordinating session moves last, by a script launched detached on the login node that stops it and resumes it on the fleet.
  5. Flip the sessions over by listing all five names in ~/.config/cx/fleet-sessions, so every Windows Terminal profile now lands on the fleet.

§6 — What must change elsewhere before the fleet carries dispatch

  • Workers must be launched through the supervisor (reckon). A worker whose srun client lives in the orchestrator's step is removed when that session ends. So dispatch must ask the supervisor to launch it from the batch step, which needs a spawn request. The same applies to per-project producers. reckon-c4 has recorded this on a-dispatch-returns-without-its-worker. Until it lands, full RESUME must not dispatch from fleet sessions.
  • One allocation. Reckon's placement record still names the older allocation, 1276262, whose batch step only sleeps. Reckon's re-hold path creates an allocation with salloc --no-shell, which has no batch step at all. Both must move to the supervisor-running allocation, and then 1276262 is retired.
  • Durable evidence paths. Gate logs cited from a session scratchpad under the runtime directory stop resolving once the session moves (reported by imas-ambix-b6, with thirteen promotions affected). Anything cited as evidence belongs on GPFS.
  • Image paste. The WSL clipboard bridge (port 2490) and the wsl reverse tunnel (port 2222) end at localhost on the login node. Fleet sessions cannot reach them, so the bridge needs a route from the node.
  • Shell configuration drift. The live ~/.bashrc is ahead of dotfiles' shell/bashrc (the TMPDIR fix, the clive path, the clipboard bridge) and is a plain file, not the symlink install.sh makes. Its uv wrapper was fixed today to skip injecting --no-sync when it is already given, a fix that exists only in the live file.
  • WSL's cx. Reaching a fleet session needs no change to the WSL copy. But cx sync from WSL copies it over ~/.local/bin/cx, now a symlink into dotfiles. So WSL must pull dotfiles before running cx sync, or its older copy overwrites the repository's.

§7 — Done when

A connection from WSL (ssh wsl, then cx iter fleet-demo) lands in the fleet session, and a second connection replaces the first without a doubled display. All fourteen sessions run on the fleet, each as its own step, each showing its last pre-move turn and listing the others as peers. The login node runs no Claude session of the fleet. Workers are dispatched through the supervisor before any fleet session dispatches.

§ Followups

What breaks when the ambix holder retires, checked in code

The decisions are locked in reckon and the code does not yet match them. Reckon HEAD keys the reservation record per project (2b0be9f8), not at the host layer, and no command adopts an already-held job. The imas-ambix record naming 1276262 was published by hand through publish_reservation. Reckon S21's the fleet shares one allocation owns closing that seam; nothing here can land before it does.

fleet status returns a false negative the moment the holder retires. It matches comment ambix-fleet on account iter, while reckon holds its allocation as job-name reckon-reservation with no comment at all (placement.py:52,150). So it prints “No fleet allocation is held” and exits 0 while one is held. No test catches it, because every fixture carries the token — the guard and its tests agree with each other and not with the world. Retire status with the holder, or repoint it at reckon's record.

Reckon ensure would resubmit the wrong shape. Its defaults are constants — partition all, 32 cores, 128G (placement.py:38-52) — against the locked rigel whole-node decision and ambix's SiteConfig.fleet_*. When 1276262 leaves, ensure resubmits its own shape unless it first learns the declared one.

There are now two allocations and they are not interchangeable. 1276262 holds reckon's workers; 1277272 is the ambix-fleet supervisor job hosting the new sessions, with its record at ~/.local/state/fleet/record.json. The unification target is the supervisor kind, so a reader of this plan should not assume the job id it names elsewhere is the one to unify.

Every placed step, and every session moved into either job, dies with that job. Drain and move before retiring anything; never cancel it while work runs there.

Nothing else breaks: the flight layer and its test carry no job id, and throttling.py with the end reading are login-node cgroup reads. Two pieces of plan text assume the ambix holder and need revisiting: the locked allocation-shape decision, and §6's “imas-ambix owns the node”.

Retire outright: fleet.py placement_argv and fleet place are shallow — tested, but nothing calls them since the shim was deleted and the flight layer stopped naming them. fleet hold is deep but redundant once ensure adopts.
