Changing the serving engine's settings today takes a seven-step manual procedure, the lane-cycle runbook: announce, pause the router, wait for the engine to drain, relaunch, wait for readiness, validate with a real completion, resume. The one command that looks like it does this, imas-ambix agent restart, does not: it cancels the serve and submits a new one with no pause, so requests in flight fail and the lane is down until the new engine is ready, which took 485 s from RUNNING on the last DSpark launch. This plan adds imas-ambix agent reload <slug>, which accepts the same settings options as restart and swaps the engine without losing a request.

The router already manages traffic, and an engine swap does not restart it. RouterApp._reachable_catalogs in imas_ambix/agent/router.py resolves upstreams on every request, with no cache. The resolver, _resolve_router_upstreams in imas_ambix/agent/cli.py, reads the serve registrations and the scheduler's live serve jobs, and keeps an engine only once its /v1/models probe reads ready. _preferred_owner then routes a model id to the widest engine, with the later start stamp breaking a tie. The router re-reads router-gate.json (width, pause, wait) at most once a second. So a newly ready engine receives the next request, and a cancelled one drops out of routing on the next request. What the router cannot do is the scheduler side: submit the replacement, decide when it is fit to take traffic, and cancel the job it replaces. That is the command this plan adds.

§1 — agent reload runs the paused cycle as one command

Add imas-ambix agent reload <slug>, with the options restart already takes (--gpus, --cpus, --port, --no-speculative, --dspark-block-size, --time, --auth, --api-key, --dry-run) plus --reason. Its orchestration lives in a new module, imas_ambix/agent/reload.py. That module takes the scheduler, the gate file, the lane reading and the validation request through small interfaces, so its tests drive every branch without SLURM or a live lane. The reload command in imas_ambix/agent/cli.py is a thin wrapper that builds the real implementations and reuses restart's profile resolution, port precedence and engine-environment check. It does not copy them.

The cycle, in order:

  1. Find the profile's running serve job by job name, exactly one, and save its batch script (scontrol write batch_script <id>) as the rollback. Zero or several matching jobs is a refusal that names them.
  2. Pause through the same function agent pause calls, with the reason given on the command line, and record when the pause took effect.
  3. Wait for the engine to drain. Proceed only on a lane reading that classify_reading calls measured with running at 0. A stale or unavailable reading is never a zero. If no such reading arrives within 10 minutes, resume and stop with nothing cancelled. Poll router_generation_gate.waiting while paused and keep the peak.
  4. Cancel the saved job by its id, never by name, wait for it to leave the queue, and submit the new serve script, generated as restart generates it.
  5. Wait for RUNNING, then for readiness, bounded at 15 minutes from RUNNING, not from submit. Then validate with a real completion against the new engine: 400 max_tokens, requiring usage.completion_tokens of at least 200 and a finish_reason of stop or length. An HTTP 200 alone is not validation, because the DSpark fused-MoE workspace is allocated at the first generation.
  6. If readiness or validation fails, cancel the new job by id, resubmit the saved batch script, and wait for that engine to answer the same validation.
  7. Resume, in a finally, so every path that paused also resumes, whether the new settings validated, the rollback served, or an exception was raised.
  8. Print the cycle and append one JSON line to lane-cycles.jsonl beside lane.json: pause start, pause end, peak held, the replaced and new job ids, the settings that changed, and the outcome (reloaded, rolled-back, aborted-before-cancel).

Bound the whole pause inside the runbook's 40 minutes, which leaves margin on the clients' 56-minute ride-out (11 attempts of 305 s), and bound it with two deadlines measured from the moment the pause took effect, because a rollback is a second launch inside the same pause. The new settings must validate by 22 minutes; past that the cycle rolls back without waiting out the readiness bound. That leaves 18 minutes for the rollback, which the 485 s readiness and the validation of the last DSpark launch fit inside. At 40 minutes the command resumes whatever state the engine is in, exits non-zero, and prints that the lane may have no serving engine, naming both job ids. It never holds the pause past the ceiling, because a held request that outlives the client's ride-out is lost, while a resumed one that finds no engine fails visibly. Announcing the cycle to the live coordinators stays a human or coordinator step, before the command runs.

Done when. uv run --no-sync pytest -p no:cacheprovider tests/test_agent_reload.py tests/test_agent_pause_cli.py tests/test_agent_dry_run.py -q passes on the fleet node. tests/test_agent_reload.py drives the cycle through fakes and asserts:

  • the success order: pause, a measured zero, cancel by id, submit, RUNNING, ready, validated, resume;
  • a readiness miss resubmits the saved batch script, validates it and resumes;
  • a completion under 200 tokens counts as a validation failure and rolls back;
  • a drain that never reaches a measured zero resumes and cancels nothing, and a stale or unavailable reading is never taken as a zero;
  • an exception raised at each step after the pause still resumes;
  • with a fake clock, new settings still unvalidated at 22 minutes roll back, and a rollback still unvalidated at 40 minutes resumes with a non-zero exit, so no path holds the pause past 40 minutes;
  • --dry-run prints the steps and the job id it would replace, and calls no cancel, no submit and no gate write.

The negative control is to delete the finally resume: the exception-path test then fails. The record is checked by a test that reads the appended line back. ops/lane-cycle/AGENTS.md replaces steps 2 to 6 with the command and keeps step 1, the announcement, and step 7, the record. The whole-tree lint gate uv run --no-sync ruff check imas_ambix tests exits 0, and tests/test_agent_serve_registry.py -k 'agent_package_modules_parse_with_serving_python' passes, because the router imports cli.py under the serving interpreter.

Placement and authority. Every test runs in place on the fleet node. The worker never pauses the real lane, submits or cancels a serve, or edits router-gate.json: those are operator actions. The first live reload is a coordinator inline exception under the runbook, recorded in this plan's evidence.

§2 — Overlap reload: start the replacement beside the old engine and route to it only after it has generated

A zero-wait swap was shown by hand on 2026-09-07: bring the new topology up on its own port while the old one serves, confirm the router prefers it, then stop the old. Two defects stop a command from doing this safely:

  • The router takes the new engine too early. The serve script writes its registration right after launching the engine (generate_serve_script in imas_ambix/agent/slurm.py, the registry write step), and the resolver routes to it as soon as /v1/models answers. That is before the first generation that allocates the DSpark workspace, so traffic can move to an engine that then fails.
  • Two copies of one profile carry the same job name. So agent shutdown would cancel both.

The work:

  1. A held registration. The registry gains a hold marker per job, written and removed by imas_ambix/agent/registry.py. _resolve_router_upstreams skips a held job on both of its paths: the registration path, and the scheduler-only path that adds live serve jobs without a registration. The router publishes "held_registrations": true in its lane snapshot, so a caller can tell whether the running router honours holds.
  2. agent reload --mode auto|overlap|pause, with auto the default. auto takes the overlap path only when two things hold: the lane document advertises held registrations, and the live ledger has room for a second copy of the serve's cards, cores and memory. The ledger is scontrol show node AllocTRES for cards and memory, and the gpu_0003_grpA core ledger as imas_ambix/agent/AGENTS.md §2 describes. Otherwise auto takes §1's paused cycle. overlap refuses when either condition fails.
  3. The overlap sequence:
    • Submit the replacement on a free port with its registration held. If it pends for more than 120 s, cancel it by id and fall back to the paused cycle under auto, or refuse under overlap.
    • Wait for readiness, bounded at 15 minutes from RUNNING.
    • Validate it with §1's completion, sent directly to its port.
    • Release the hold.
    • Confirm through the router's own /v1/models that the model now resolves to the new engine.
    • Cancel the old job by id, and republish the endpoint document as shutdown does.
    A failure before the release cancels the new job by id and leaves the old engine serving, with nothing paused.

Deploying it needs one router restart. The resolver runs inside the router process, so a hold is honoured only by a router started from the new code. That restart is a coordinator inline exception under the runbook's router-restart row: pause, drain to a measured zero, restart, confirm the pause survived, resume. Until then the lane document carries no held_registrations, and auto keeps choosing the paused cycle. That is the point of the advertisement.

Done when. uv run --no-sync pytest -p no:cacheprovider tests/test_agent_router_resolution.py tests/test_agent_reload_overlap.py tests/test_agent_reload.py -q passes on the fleet node, with these tests:

  • A held registration is absent from the resolved upstreams on the registration path, and a held job is absent on the scheduler-only path. Removing the skip on either path fails its test, which is the negative control.
  • auto picks the paused cycle when the lane document lacks held_registrations, and when the ledger lacks cards, cores or memory.
  • An overlap whose replacement fails validation cancels only the replacement's job id and leaves the old job running.
  • A successful overlap releases the hold before it cancels the old job, and cancels by id.

The imas_ambix/agent/AGENTS.md §3b rotation passage names the command in place of the manual sequence. Lint and the serving-interpreter parse test pass as in §1.

§3 — A router deploy drops the requests the router holds

Restarting the router loses every request in its FIFO, because the queue lives in the router's memory. That is why the runbook restarts the router only inside a pause, after the engine reads a measured zero, and why §2's deployment carries that same risk once. A lossless router deploy needs a handover. One way: start the new router on the same port with SO_REUSEPORT, close the old router's listener so new connections reach only the new one, and let the old router finish its in-flight and held requests before it exits. Two processes then each apply the gate width, so the handover window admits up to twice the width; that has to be bounded or shared before this is built. This section is deferred. Router code deploys are rare, the runbook's paused restart loses only what arrives in the swap instant, and engine reloads, §1 and §2, never restart the router. It becomes implementable when a router change has to land on a lane that cannot be held quiet, or when serving-across-servers moves the router off the engine node.
