§1 — What exists, and what it is recording

A serving recorder already runs with every serve. imas_ambix/agent/serving_receipts.py is launched from the serve's own SLURM script (slurm.py, the _RECEIPTS_PATH block), samples the engine's /metrics every five seconds, and appends one JSON row per sample to /work/projects/imas_gpu/agents/receipts/<slug>-<jobid>.jsonl. It starts immediately after the engine process so the startup window is captured, tolerates the engine not answering yet, and dies with the job. The architecture this plan needs is therefore already in place. What it records is not.

Measured on the running four-card DeepSeek-V4.1-Flash serve (job 1273253), 2026-09-18: fourteen of the recorder's twenty fields are null in every one of 13,791 rows.

The cause is a single defect with a long reach: the recorder reads metric names through imas_ambix.agent.bench, which knows only the vllm: namespace. This deployment serves under SGLang, whose series are named sglang:. Two gauges survive because their names happen to match; everything else silently records null. A reader that knows one engine family reports a healthy serve as absent, and nothing anywhere raises — the file grows at 8.7 MB per job-day and looks like a complete record.

The same defect has already been paid for twice. The workstation watcher gpu-watch carried its own independent scraper precisely because the canonical one was blind, and that scraper then had to learn both families by hand. It also grew its own parallel token ledger, its own price resolution and its own utilisation arithmetic — a second implementation of this record, kept on a login node, covering only the hours somebody happened to be watching. Metric-name knowledge living in two places is what let the two drift apart, and no amount of care in either copy fixes that.

Why the node is the right place to generate this

The recorder runs inside the serve's SLURM allocation, on the GPU node. Verified on that node: nvidia-smi, squeue and SQLite 3.46.1 are all present and are ordinary local calls there. Every hard problem the login-node watcher has hit this year dissolves at that location:

  • No srun --overlap step. The watcher spawns one sampler step per owned job per session to read nvidia-smi. Steps are a bounded per-job resource, and exhausting MaxStepCount locks --overlap out for the life of the job.
  • No orphaned samplers. Measured 2026-09-18: four sampler steps outlived their parent by three hours, reparented to init, still polling nvidia-smi once a second and each still holding a step against a job that had no idea they were there.
  • Continuous coverage. A login-node watcher observes only while someone is looking. Utilisation over a week or a month cannot be answered from it at all, and the honest response — declining to report a figure backed by a sliver of the period — is the current behaviour.

One limit is inherent and must be stated rather than designed around: the recorder sits inside the serve's cgroup, so its nvidia-smi sees the serve's cards. That is exactly the set the serving panel and the utilisation figure describe. The node-wide eight-card view remains a separate concern with its own sampler.

The shape being built

One generator on the node; one append-only record; readers derive and never probe the cluster themselves.

§2 — Teach the recorder both engine families

Extract the engine-family knowledge that is currently split between bench.py (vLLM names only) and the workstation watcher (both families, by hand) into one module that owns the mapping from a family's series names to canonical quantities. The recorder, bench, and every later reader resolve through it. This is the load-bearing change: without it the two implementations drift apart again, which is the mechanism that produced a 13,791-row record of nulls.

The canonical set must cover, for both sglang: and vllm:: requests running and queued; KV-pool occupancy; prompt, generation and cached token counters, with cached split by the tier that answered it; uncached prompt tokens; and the time-to-first-token and inter-token-latency histograms. Where a family exposes a quantity under a different decomposition — SGLang publishes cached tokens by cache_source and prefill work under prefill_effective_tokens_total — the module reconciles it to the canonical name rather than leaving the caller to know which engine it is talking to.

A quantity absent from a family must be recorded as absent and be distinguishable from a measured zero. The failure being repaired is exactly a null that reads as a reading, so the row schema carries presence, and the recorder never writes a field it did not observe.

Write paths. imas_ambix/agent/engine_metrics.py (new), imas_ambix/agent/serving_receipts.py, imas_ambix/agent/bench.py, tests/test_engine_metrics.py (new).

Done when a live scrape of the running SGLang serve populates every canonical field; a recorded fixture of vLLM output populates the same fields through the same code path; a family that genuinely lacks a quantity yields an absent field rather than a null or a zero; and uv run --no-sync ruff check imas_ambix tests exits 0.

§3 — Record the cards, the host and the node's job table

Add three local probes to the recorder's tick. All three are ordinary local calls at the node and need no SLURM step.

  • Cards — per-card utilisation, temperature, power draw, power cap, clocks and memory, from one nvidia-smi query, mapped to physical indices through SLURM_STEP_GPUS so a card is labelled by the number the node knows it by rather than by the step-relative ordering.
  • Host — CPU busy fraction from /proc/stat and memory from /proc/meminfo.
  • Node job table — squeue -w $(hostname), so what else was resident is part of the record and a later reader can explain a slow hour without re-deriving it from SLURM accounting.

The row shape changes with this section. Today's ReceiptRow is a flat dataclass of twenty fields, fourteen of them null; adding cards, host and jobs to a flat row makes it sixty. Rows instead carry versioned, sparse sections — engine, cards, host, jobs — each omitted entirely when its probe did not run, so an absent source costs no bytes and cannot be mistaken for a measurement. A schema version on every row is what lets the index in §5 ingest old and new files together.

Sampling is staggered rather than uniform: the engine scrape stays on the five-second tick, cards on the same tick (a single nvidia-smi call is cheap), and the job table at a much lower rate, because it changes on the scale of minutes and costs a SLURM RPC.

Write paths. imas_ambix/agent/node_probe.py (new), imas_ambix/agent/serving_receipts.py, tests/test_node_probe.py (new).

Done when a serve launched from the generated SLURM script writes rows carrying card, host and job sections; a probe that fails or is unavailable omits its section and the tick still completes; the recorder's added cost is under one percent of one core, measured on the node; and the whole-tree lint gate exits 0.

§4 — Tiered rotation and compaction

There is no rotation today: 44 files and 110 MB have accumulated, one per job, forever. Growth is 8.7 MB per job-day at five-second resolution, which is affordable now and is not a retention policy.

Compaction must be correct about what it is averaging. Cumulative counters compact by keeping the endpoint value, never by averaging — a mean of a monotonically rising counter is meaningless, and the integrals in §5 difference endpoints. Gauges and utilisations compact by a time-weighted mean, carrying the weight forward so a compacted row knows how much observation stands behind it. A compacted row that cannot say how many raw samples it represents cannot be integrated honestly at the next tier.

Compaction runs opportunistically inside the recorder, between samples, because the recorder is idle there and needs no separate supervision. It is also exposed as a subcommand so that a tier can be rebuilt, or caught up, while the serve is down. A compaction is idempotent and never deletes a source tier until its successor has been written and re-read.

Write paths. imas_ambix/agent/telemetry_store.py (new), imas_ambix/agent/serving_receipts.py, imas_ambix/agent/cli.py, tests/test_telemetry_store.py (new).

Done when a synthetic multi-day record compacts through all three tiers with counter endpoints preserved and gauge means time-weighted; compaction is idempotent under repeated runs; a crash mid-compaction loses no source data; the subcommand rebuilds a tier from its source; and the lint gate exits 0.

§5 — The reader index, and the watcher moves in

Readers derive; they do not probe. A reader builds a SQLite index on local disk by tailing the record files it has not yet ingested, tracked by path, inode and byte offset so a rolled or replaced file is detected rather than re-read or skipped. The index is disposable by construction: it is rebuilt from the JSONL on corruption, on a schema change, or on demand, and therefore can never itself be a data loss. This is why the durable record stays append-only JSONL — that is the shape that is correct on GPFS without locking, and SQLite's WAL mode is not available on a network filesystem.

With an index the ledger becomes a query rather than an arithmetic layer: period sums over differenced counter endpoints, and a time-weighted mean for utilisation. Both are already specified and tested in the workstation watcher and move across with it.

gpu-watch moves into this repository as imas-ambix agent watch, next to the producer it reads. Its panels are unchanged — the ranked layout, the bar-for-every-percentage rule, the ledger with its one earned rule. What changes underneath is that the serving figures, the serve's card readings and the whole ledger come from the record instead of from live probes, so the subcommand no longer spawns sampler steps for the serve's cards and no longer maintains a private ledger. The node-wide GPU panel keeps its own sampler, and that sampler gains the cleanup this repair proved it needed. The dotfiles repository keeps a thin launcher on PATH so the command name does not move.

Two behaviours must survive the move, because both were bought with measurement. Utilisation declines to report when too little of a period was observed, rather than passing off the watcher's habits as the deployment's load — with a continuous on-node recorder this will now almost always be satisfied, which is the point. And open-market cost is resolved against a provider's published rates per interval at the rate then in force, because the served model is priced by time of day and a period billed at one instant's rate is wrong by the peak-to-off-peak ratio.

Write paths. imas_ambix/agent/telemetry_index.py (new), imas_ambix/agent/watch.py (new — the ported watcher), imas_ambix/agent/cli.py, tests/test_telemetry_index.py (new), tests/test_watch_panel.py (new).

Done when imas-ambix agent watch renders every panel from the record; the index ingests incrementally across a rolled file and a restart without double-counting or gaps; a deleted index rebuilds to identical query results; the ledger's hour, day, week and month rows are all populated from a continuously recorded serve; the watcher spawns no sampler step for the serve's cards; and the lint gate exits 0.

§6 — Per-request receipts from the router

Aggregate gauges answer how the lane is behaving; they cannot attribute. The router is the only component that sees every call — it proxies each one and already carries per-request hooks — so request-level receipts belong to it and not to the serve.

One append-only row per completed request: timestamp, model, upstream chosen, prompt tokens, cached prompt tokens, completion tokens, time to first token, total duration, and the caller hint the router already derives. Written to its own stream, on its own rotation, under the same tiering rules, so the request record can be retained at a different depth from the sampled one.

This is what turns cost from a lane-wide estimate into an attributable figure: which workloads spent the tokens, what a given campaign cost, and which callers carry the prompts whose cache misses show up as prefill on the cards. It is deliberately the last section — it is the largest, it is a different producer, and every section before it is useful without it.

Volume must be bounded by design rather than by hope: at the observed request rate a full-fidelity row per call is small, but a pathological client can change that, so the writer samples above a configured rate and records the sampling fraction on the rows it keeps, so totals scale honestly.

Write paths. imas_ambix/agent/request_receipts.py (new), imas_ambix/agent/router.py, tests/test_request_receipts.py (new).

Done when every completed request through the router appears once in the stream; a failed or aborted request is recorded as such rather than dropped; the router's added per-request latency is under a millisecond at the p99, measured; sampling above the configured rate records its fraction; and the lint gate exits 0.

§ Decisions

Where does the durable record live, given a node-side writer, login-node readers, and GPFS?

SQLite's WAL mode does not work on a network filesystem and rollback-journal locking over GPFS carries a documented risk with a continuous writer. An append-only JSONL write of a short line is atomic and lock-free, so the durable record stays dumb and correct; the query layer becomes a local, disposable index that is rebuilt from source rather than recovered.

What does the recorder capture?

All four sources: repaired engine metrics, GPU cards, host CPU and memory with the node's job table, and per-request receipts from the router. The node makes the first three free, and the fourth is what makes cost attributable rather than lane-wide.

Where does the watcher live once it reads the record?

It moves next to the producer it reads. Duplicated metric-name knowledge across two repositories is the mechanism that produced a record of nulls; sharing one module is the repair, and it only works if both live together. dotfiles keeps a thin launcher so the command name does not move.

How long is telemetry kept, and at what resolution?

Five-second detail is wanted for the recent hours and is wasteful for a year. Tiering keeps the near past exact, costs a few megabytes for a year of trend, and is what finally gives the month-scale utilisation figure real coverage instead of a declined answer.

§ Followups

Land the telemetry spine — five nodes, §2 and §6 first
