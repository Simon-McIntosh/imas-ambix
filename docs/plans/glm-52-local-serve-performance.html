§1 — What this plan is for

Two deliverables. First, a GLM-5.2 serve that is actually fast on this node rather than merely running: the INT4 checkpoint on four H200 cards, coexisting with the two-card DeepSeek V4-Flash serve, with speculative decoding active. Second, throughput measurement that carries enough provenance to be worth keeping — today a saved benchmark records numbers but not the configuration that produced them, so a fast run and a slow one are indistinguishable after the fact.

The GPU-count-in-the-name question is settled and is not revisited here: a release is served under one client-visible model name, the profile slug names the checkpoint precision, and the card count is a launch flag. The two node sizes need genuinely different checkpoints, so they cannot collapse into one profile the way DeepSeek's two sizes do.

§2 — Serve bring-up: what the attempts established

Bring-up took several attempts because four independent constraints sit in series, and each one only becomes visible after the previous is satisfied. Three of the four are now settled facts about this hardware and engine, worth recording so they are not rediscovered.

Setting triedResultWhat it established
kv_cache_dtype = "fp8_e4m3" No valid attention backend GLM-5.2's sparse attention has no FP8 KV kernel in vLLM. Every candidate backend rejected it, each naming either sparse not supported or kv_cache_dtype not supported. The often-quoted FP8-KV throughput gain is an SGLang result and does not transfer to this engine.
kv_cache_dtype = "bf16" Rejected at argument parse The accepted spelling is bfloat16; bf16 is not in the engine's value list.
Draft model on the older engine Missing weight key Not a truncated download. The checkpoint is structurally complete and stores experts individually, while the older loader looked for a single fused tensor per layer. The newer loader rewrites the layer prefix and fuses the per-expert weights itself, so the checkpoint layout is the supported one.
Newer engine, older framework pin Sparse indexer refused to start The engine wheel is compiled against a newer framework ABI than the pin allowed, so its matrix-multiply extension could not load, and the sparse attention indexer depends on that extension. Advancing the pin resolves it; the CUDA 13 runtime the extension also needs is already present in the environment and already on the serve script's library path.

Why the order matters

Each constraint masks the next, which is why a single change never produced a working serve.

Integrity of the weights

The download job reported failure, so the weights were verified rather than assumed: all 83 shards of the main checkpoint parse as valid safetensors and every shard's declared tensor extent matches its file size exactly. The draft model likewise matches its index with no absent keys. The job's failure was raised after transfer, by an accelerated-download helper that is not installed; it did not truncate anything.

§3 — Measurement: what exists and what is missing

The benchmark harness itself is sound and needs no redesign. It already measures time to first token, decode rate, prefill rate, and aggregate throughput across concurrency levels, alongside retrieval, tool-calling, and reasoning checks, and it saves every run as JSON. What it does not do is record which configuration produced a number, which is precisely what is needed to compare node sizes or to judge real workload behaviour.

Run provenanceMissing Saved runs carry only the served model name. Precision, card count, parallel width, KV dtype, speculative settings, engine version and the scheduler job are all absent, so two runs cannot be attributed.

§4 — Work

Three strands, each owning a disjoint set of files so they can run at once, then a measurement pass once the serve is up.

  • Provenance and acceptance capture — record the serving configuration and engine version into every saved run, and poll the engine's metrics endpoint for draft-token acceptance so a degraded speculator is visible as a number rather than as unexplained slowness.
  • Comparison reporting — read two or more saved runs and render the differences, so a node-size or precision comparison is a command rather than a manual exercise.
  • Deployment notes — fold the established constraints in §2 into the serving guidance next to the code, including the naming convention and the framework pin requirement.
  • Measurement — once the serve answers, benchmark it and re-baseline DeepSeek on the same stack so the comparison is like-for-like.

§ Decisions

What distinguishes the two GLM profiles in their name?

Card count is a launch flag, as it already is for the DeepSeek serve, which holds two cards under its plain slug. The profiles differ because the checkpoints differ, so precision is the honest differentiator and the client-visible model name stays constant per release.

Which KV cache dtype for the INT4 serve?

Forced, not chosen: no FP8 KV kernel exists for this model's sparse attention in this engine. Revisit if a later engine adds one, since it would restore both throughput and KV capacity.

The status command reports zero serving while two serve jobs run, and flags every running job as a rejected serve candidate with 'unsupported or missing GPU allocation'. Reported by a peer session whose own serve was flagged, so it is not specific to one profile or card count; it appeared alongside the live-route discovery work. It matters because operators use this command to decide whether an endpoint is up.

Three findings the numbers force. Tensor-parallel width must divide 64 attention heads, so only 2, 4 and 8 cards are possible and 6 is not; GLM cannot run below 4 because its weights would need 218 GiB per card. Adding cards costs DeepSeek single-stream speed and buys KV capacity, 740k to 3.37M tokens. Disabling drafting on 8 cards raises single-stream 52 percent and collapses aggregate 16-fold, the two serve configurations differing in that one flag alone, so the setting is workload-dependent rather than simply on or off.

Two measurement defects were corrected rather than reported around. Concurrency workers generated 256 tokens, short enough that scheduler warm-up dominated and one deployment measured a higher aggregate at sixteen concurrent than at thirty-two; regenerated at 1024. The four-card context was sized from a single lucky launch: three launches of the identical configuration on clean cards returned pools of 6.4, 3.14 and 6.33 GiB, so 64K fails whenever the pool lands low and 32K is the figure that holds.
