§1 — What is wrong today

The interactive agent fleet runs on the login node 98dci4-srv-1006. Up to thirty clive sessions live there at once, and each one carries a reckon mcp and an imas-codex serve child, so the process count is roughly three times the session count. All of them share one control-group quota with every other thing the account runs on that host: editors, git, the docs server, the reverse tunnels and the zellij servers themselves.

That quota is four cores. It is set site-wide by /etc/systemd/system/user-.slice.d/10-defaults.conf as CPUQuota=400%, alongside MemoryMax=64G and MemorySwapMax=0. It is not a per-session budget and it does not grow with the number of sessions; thirty sessions divide the same four cores that one session would have had to itself.

The consequence is not a slow fleet but an unreliable one. Throttling does not kill a process directly, yet everything with a deadline fails around it: model context protocol startup handshakes, health probes, inter-process timeouts, and any watchdog that treats a missed heartbeat as a dead peer. A fleet that is starved of CPU looks exactly like a fleet that is intermittently broken.

First, the account has recorded oom_kill 529 in the slice's memory.events, all from a single runaway episode in which the control group's out-of-memory killer reclaimed by resident size and therefore selected the largest processes in the slice — the agent sessions and the multiplexer servers — rather than the small shells that were forking. Neither is caused by the CPU quota, but both are made more likely by a slice that is permanently at its ceiling, and neither can be diagnosed cleanly while the baseline is a starved machine.

Recommendation: rigel. It is the only partition that is simultaneously long-lived and genuinely unloaded. There is no sixty-four-core CPU node to take, and this is the one place the plan does not give the lead the number asked for. A rigel node is twenty-eight cores — two sockets of fourteen, hyperthreading off — with 128 GB, so holding one whole node yields twenty-eight, not sixty-four. The only sixty-four-core machine in the cluster is 98dci4-gpu-0003 itself, which is the node we are trying to stop competing with. The closest CPU alternative is vega at fifty-six cores and 512 GB, and vega is the worst-placed partition in the table right now: zero idle nodes, twenty-seven fully allocated, and forty-three draining. Two traps worth recording. rigel_debug contains zero nodes, so a job submitted there pends forever rather than failing; and every *_debug partition caps at one hour, which would destroy the fleet hourly and is therefore unusable for this purpose regardless of how idle it looks.

§4 — Where the fleet should sit

The fleet moves into a persistent single-node rigel allocation. The login node keeps what it is good at — terminals, git, editors, and the zellij clients the operator attaches with — and stops hosting the work. The GPU node keeps its sixty-four cores for serving the model rather than for orchestrating the clients that call it, which is the contention the lead identified.

The login node keeps only the zellij terminals and the job monitors that link to the compute. Nothing else runs there: no agent sessions, no model context protocol servers, no dispatch. That is the whole of its remaining job.

The catalog came back naming deepseek-v4.1-flash at a max_model_len of 512,000, which is the live lane rather than a cached document. Sub-two-millisecond connect times put the compute node and the GPU node on the same fabric, so the lane needs no tunnel, no forwarded port and no change to the origin the launcher already embeds. A session hosted on rigel reaches the H200 lane exactly as one on the login node does.

One operational detail surfaced by the same run: a job step on a compute node cannot write the login node's runtime directory and falls back with Unable to create TMPDIR [/run/user/39486]. The allocation must set TMPDIR explicitly, as the repository's compute guidance already requires.

Reaching the allocation is a solved problem on this cluster: the account already runs persistent jobs of exactly this shape, including codex-neo4j and codex-embed at four days of elapsed time and ambix-router at nearly two. With pam_slurm_adopt, an ssh connection to a node where the account holds an allocation is adopted into that job's control group, so the existing ssh and cx pattern carries over with a new host entry. The current cx titan entry is not that entry: titan is 98dci4-gpu-0002, a twenty-core GPU node hosting the graph and embedding services, and it is the wrong target for the fleet.

§5 — The risk this introduces, and why it is the whole design

SLURM on this cluster runs ProctrackType=proctrack/cgroup. Every process inside an allocation lives in the job's control group, and when the job ends — time limit, scancel, node drain, preemption — SLURM kills that entire group at once. Moving the fleet inside an allocation therefore creates a single event that can terminate every session simultaneously.

That matters more than usual here, because simultaneous whole-fleet loss is the symptom already under investigation on the login node. Today the zellij servers survive those events and the sessions can be resurrected; inside an allocation the servers would be in the control group too, and nothing would survive. The move must not be made in a way that converts a recoverable failure into an unrecoverable one.

Three consequences follow, and they constrain the implementation rather than merely warning about it. The allocation must be genuinely persistent and must not sit on a draining node. The operator needs a deliberate, visible signal when the allocation is approaching its end, because an agent fleet that vanishes without warning is the failure we are trying to remove. And session state that matters — plans, commits, manifests — must already be durable on shared storage before the control group is torn down, which is the existing commit-and-push discipline rather than anything new.

§6 — Which repository owns this

The work splits across two owners and the split is clean.

imas-ambix owns the node. This repository already coordinates the compute resources the lane depends on: the GPU server, the SLURM access patterns, the serving topology and the clive consumer surface, with the detail scoped under imas_ambix/agent/AGENTS.md. The allocation that hosts the fleet is another coordinated resource of the same kind, held beside the router and the model server, and the contention being resolved is between them. Acquiring, holding, monitoring and releasing the allocation belongs here.

reckon owns the dispatch pattern. Crew dispatch, worker placement, the run ledger and the worktree fleet are reckon's, and any change to how a worker is launched or where it lands is a change to that contract rather than to this one. If hosting the fleet in an allocation requires dispatch to learn a new placement, that is a dependency to raise in reckon, not a thing to implement here.

The first implementation step below is deliberately shaped to test whether such a change is needed at all. If the fleet can be hosted by moving where the operator attaches, with dispatch unchanged, then reckon needs nothing and the boundary never has to be crossed.

§7 — Implementation

Ordered so that the cheapest reversible step answers the most expensive open question first.

  1. Record the throttling baseline before anything moves. The figures in §2 are one reading; take a second across a normal working day so the comparison in step seven is against a range rather than a point. The recorder already on the login node supplies process counts and cpu.stat supplies the throttled fraction. Done when a baseline share is written into this plan.
  2. Ask the site why lingering is not holding. This is the only interim lever, because no user-space placement survives. The system journal shows the user manager being stopped and app.slice removed in the same teardown that stops the session scopes, so a transient user unit escapes one of the two units being stopped and not the other — the evidence, including the two services killed at status=143 each time, is in the session-scope teardown record. Lingering is enabled for this account and persisted on disk, and exists precisely to keep a user manager alive with no sessions open; it is not holding, and the teardown recurred twice inside five hours. Done when the site holds the journal extract and has either corrected the behaviour or confirmed it is expected — which decides whether the allocation is the only remedy or merely the robust one.
  3. Hold the interactive reservation on one whole rigel node. Twenty-eight cores, 128 GB, no time limit, not on a draining node, with TMPDIR set. Done when the job is running, an ssh connection lands in its control group, and the allocation survives an operator disconnect.
  4. Run one session there end to end before moving any others. A single zellij session inside the allocation, one clive worker, dispatching to the router as it does today. Done when a real task completes with the model reached over the network and no dependency on the login node beyond the terminal.
  5. Decide whether dispatch changes. From step four, record whether reckon crew dispatch placed work correctly with no modification. Done when the answer is written into this plan and, if it is no, a dependency plan is raised in reckon naming the specific contract that must change.
  6. Give the allocation a visible lifetime. A status surface the operator can read — remaining time, node, health — and a warning before it ends. Done when an operator can answer "is my fleet about to disappear" without running squeue by hand.
  7. Move the fleet and leave the login node thin. Done when the login slice's throttled fraction over a working day is materially below the measured baseline in §2, and that comparison is recorded here.

Step seven is the measure that decides whether this plan worked. The baseline is in §2 and it is a ratio, not an absolute: what must fall is throttled thread-time as a share of available capacity, sampled over a comparable working period.

The site request is written — the step is not closed

The deliverable of the second step is authored and validated: Site request — user lingering is not holding on 98dci4-srv-1006 is the send-ready text, carrying the journal extract that shows the teardown. No change required to the reckon crew dispatch contract: a worker is created as a child of the calling coordinator process, and reckon chooses no node, control group or scheduler affinity unless a backend declares one — while the declared-placement path that does exist already holds a single reservation and places workers into it as srun --overlap --jobid steps. The citations, the measurement that the path is present but unarmed in the live configuration, and the split between what the code settles and what an allocation forces an operator run to still show are in the cumulative evidence record.

§8 — The cheaper alternative that must be priced first

Before building any of §7, the site could be asked to raise CPUQuota for this account on the login node. It is a one-line change to a drop-in file against a whole migration, and if it were granted it would remove the measured throttling immediately.

It should be asked and it should not be waited for. It does not get the fleet off a shared interactive host, so it leaves the account exposed to every other tenant on that node and leaves the site's own guidance — that sustained work belongs on compute — unsatisfied. Treat a raised quota as relief while §7 proceeds, not as a substitute for it.

§ Decisions

Which partition hosts the fleet allocation?

Locked to rigel by the lead, conditional on free capacity, which the survey confirms: 51 of 61 nodes carry no allocation, idle load reads 0.00 to 0.14, there is no pending queue and nothing is draining. Reachability to the serving lane was then measured from a rigel node rather than assumed — see §4.

Does the whole fleet share one allocation, or does each lane hold its own?

Locked to one node, held whole, managed as an interactive reservation. The lead's figure of sixty-four cores is not available on any CPU partition: a whole rigel node is twenty-eight cores and 128 GB. vega is the only larger CPU node at fifty-six, and it is the most contended partition in the survey with zero idle nodes and forty-three draining, so it is not a candidate while rigel sits empty. If twenty-eight proves tight the escalation is to re-survey vega, not to assume it.

Do we raise a site request to increase the login-node CPUQuota in parallel with §7?

Declined by the lead. The fleet moves to an interactive reservation on compute, so the login node stops carrying the work rather than being granted a larger share of it. The login node keeps only the zellij terminals and the job monitors that link to the compute.

The subtle case is the whole point: this allocation is deliberately unbounded, so the scheduler reports its remaining time as the literal UNLIMITED. That token is not a duration — it maps to None, so it cannot be parsed as a number, compared against the warning threshold, or reported as expiring. A finite remainder below 30 minutes adds a warning line; an allocation with no wall clock never warns. Holding no allocation at all is reported in words at exit 0 rather than as an empty table.
