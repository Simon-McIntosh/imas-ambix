§1 — What is wrong today

The interactive agent fleet runs on the login node 98dci4-srv-1006. Up to thirty clive sessions live there at once, and each one carries a reckon mcp and an imas-codex serve child, so the process count is roughly three times the session count. All of them share one control-group quota with every other thing the account runs on that host: editors, git, the docs server, the reverse tunnels and the zellij servers themselves.

That quota is four cores. It is set site-wide by /etc/systemd/system/user-.slice.d/10-defaults.conf as CPUQuota=400%, alongside MemoryMax=64G and MemorySwapMax=0. It is not a per-session budget and it does not grow with the number of sessions; thirty sessions divide the same four cores that one session would have had to itself.

The consequence is not a slow fleet but an unreliable one. Throttling does not kill a process directly, yet everything with a deadline fails around it: model context protocol startup handshakes, health probes, inter-process timeouts, and any watchdog that treats a missed heartbeat as a dead peer. A fleet that is starved of CPU looks exactly like a fleet that is intermittently broken.

§4 — Where the fleet should sit

The fleet moves into a persistent single-node rigel allocation. The login node keeps what it is good at — terminals, git, editors, and the zellij clients the operator attaches with — and stops hosting the work. The GPU node keeps its sixty-four cores for serving the model rather than for orchestrating the clients that call it, which is the contention the lead identified.

§5 — The risk this introduces, and why it is the whole design

SLURM on this cluster runs ProctrackType=proctrack/cgroup. Every process inside an allocation lives in the job's control group, and when the job ends — time limit, scancel, node drain, preemption — SLURM kills that entire group at once. Moving the fleet inside an allocation therefore creates a single event that can terminate every session simultaneously.

That matters more than usual here, because simultaneous whole-fleet loss is the symptom already under investigation on the login node. Today the zellij servers survive those events and the sessions can be resurrected; inside an allocation the servers would be in the control group too, and nothing would survive. The move must not be made in a way that converts a recoverable failure into an unrecoverable one.

Three consequences follow, and they constrain the implementation rather than merely warning about it. The allocation must be genuinely persistent and must not sit on a draining node. The operator needs a deliberate, visible signal when the allocation is approaching its end, because an agent fleet that vanishes without warning is the failure we are trying to remove. And session state that matters — plans, commits, manifests — must already be durable on shared storage before the control group is torn down, which is the existing commit-and-push discipline rather than anything new.

§6 — Which repository owns this

The work splits across two owners and the split is clean.

imas-ambix owns the node. This repository already coordinates the compute resources the lane depends on: the GPU server, the SLURM access patterns, the serving topology and the clive consumer surface, with the detail scoped under imas_ambix/agent/AGENTS.md. The allocation that hosts the fleet is another coordinated resource of the same kind, held beside the router and the model server, and the contention being resolved is between them. Acquiring, holding, monitoring and releasing the allocation belongs here.

reckon owns the dispatch pattern. Crew dispatch, worker placement, the run ledger and the worktree fleet are reckon's, and any change to how a worker is launched or where it lands is a change to that contract rather than to this one. If hosting the fleet in an allocation requires dispatch to learn a new placement, that is a dependency to raise in reckon, not a thing to implement here.

The first implementation step below is deliberately shaped to test whether such a change is needed at all. If the fleet can be hosted by moving where the operator attaches, with dispatch unchanged, then reckon needs nothing and the boundary never has to be crossed.

§8 — The cheaper alternative that must be priced first

Before building any of §7, the site could be asked to raise CPUQuota for this account on the login node. It is a one-line change to a drop-in file against a whole migration, and if it were granted it would remove the measured throttling immediately.

It should be asked and it should not be waited for. It does not get the fleet off a shared interactive host, so it leaves the account exposed to every other tenant on that node and leaves the site's own guidance — that sustained work belongs on compute — unsatisfied. Treat a raised quota as relief while §7 proceeds, not as a substitute for it.

§ Decisions

Which partition hosts the fleet allocation?

Locked to rigel by the lead, conditional on free capacity, which the survey confirms: 51 of 61 nodes carry no allocation, idle load reads 0.00 to 0.14, there is no pending queue and nothing is draining. Reachability to the serving lane was then measured from a rigel node rather than assumed — see §4.

Does the whole fleet share one allocation, or does each lane hold its own?

Locked to one node, held whole, managed as an interactive reservation. The lead's figure of sixty-four cores is not available on any CPU partition: a whole rigel node is twenty-eight cores and 128 GB. vega is the only larger CPU node at fifty-six, and it is the most contended partition in the survey with zero idle nodes and forty-three draining, so it is not a candidate while rigel sits empty. If twenty-eight proves tight the escalation is to re-survey vega, not to assume it.

Do we raise a site request to increase the login-node CPUQuota in parallel with §7?

Declined by the lead. The fleet moves to an interactive reservation on compute, so the login node stops carrying the work rather than being granted a larger share of it. The login node keeps only the zellij terminals and the job monitors that link to the compute.
