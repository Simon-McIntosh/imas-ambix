§1 — Outcome and authority boundary

Replace Clive's single configured URL assumption with live discovery of this user's running Ambix serve jobs. A route becomes selectable only after its own /v1/models endpoint answers successfully; a SLURM allocation, listening socket, or configured profile alone is not availability. The launcher remains local-only by default and never falls back to an external provider when discovery is empty or a selected route fails.

The serving CLI owns job and endpoint facts; the generated launcher consumes those facts and sets the selected model and base URL for Claude Code or Codex. Discovery must support authenticated and keyless vLLM endpoints without printing credentials. It must not cancel, restart, or otherwise mutate serve jobs.

§2 — Dynamic discovery and topology-qualified selection

Build one structured discovery path from RUNNING SLURM jobs to probed endpoints. Each live entry carries the server-reported model id, compute node, actual port, GPU count, job id, and context metadata when reported. Extract launch-specific ports and GPU allocation from job state rather than assuming port 18800 or a profile's default card count.

Display DeepSeek and GLM routes with an explicit 2×, 4×, 6×, or 8× H200 topology beside the server-reported release name and endpoint. Topology is runtime presentation data, not a new profile slug, SLURM job name, or served-model identity. If more than one live route reports the same model id, its topology-qualified selector must choose the intended endpoint unambiguously.

Add a non-interactive listing mode and a deterministic selection contract. One live route may be selected automatically; several live routes are presented for interactive choice, while non-interactive use requires an unambiguous selector. Explicit URL/model overrides remain available but are probed before launch. The selected route supplies both model and endpoint to the child harness, so no stale models appear as available.

§3 — Family-independent launch, verification, and deployment

Derive availability from endpoint responses rather than a hard-coded DeepSeek or GLM release list. A future GLM-5.3 serve therefore appears automatically when its running endpoint reports glm-5.3, with the launch topology and endpoint that actually answered. Keep the direct-local no-fallback behavior and the explicit OpenRouter branch isolated from local discovery.

Cover job parsing, port and GPU extraction, authenticated and keyless probes, readiness filtering, selector ambiguity, topology labels, one-route auto-selection, multi-route selection, and propagation into both harness environments. Run the focused agent tests and the repository's whole-tree Ruff gate. Deploy only the repo-generated launcher, confirm the deployed bytes match imas-ambix agent clive --print, and exercise live listing against the current serve without exposing its key.

§ Decisions

What makes a local model available in Clive?

Only a successful live models response from the route itself; scheduler state alone is insufficient.

Where does the card-count distinction belong?

In the discovered route label and selector, while the served model remains the release identity reported by the engine.

How does Clive acquire future GLM releases?

Generically from live server metadata, so a GLM-5.3 endpoint requires no launcher source edit.
