The lead decided on 2026-10-23 that it serves DeepSeek-V4.1-Flash-1017 on all eight cards from day one. There is no bake-off before cutover. The other open models are downloaded as backups, to try later if wanted.

§2 — Review the model store on /work

/work/projects/imas_gpu/agents holds checkpoints accumulated over several serving plans: deepseek-v4-flash, deepseek-v4-flash-0731, deepseek-v4-1-flash, three GLM-5 releases with their int4 and W4A8 requantisations, kimi-k2-6, mimo-v2-5-pro, minimax-m2-7 and minimax-m3. Nothing records which are complete, which a profile still references, or which are superseded. This section produces that record. It reads the store and deletes nothing.

For each directory, the record gives:

  • its size on disk;
  • the Hugging Face repository and commit it was downloaded at, from its .cache/huggingface/download metadata;
  • whether every shard named by its index is present at the size the index or repository listing gives;
  • the first shard's SHA-256 against the repository's LFS hash at that commit;
  • which profile under imas_ambix/agent/profiles/ names it as its weights_slug, and when a receipt file last names it;
  • a recommendation of keep, backup or prune, with its reason.

Pruning is the lead's decision and is not taken here.

The B300 is declared in SiteConfig.servers, which serving-across-servers §3 landed. Its host name, partition, account and reservation are filled from the operator's answer at arrival (question b300-arrival-facts).

No new option. A configuration is a server and a card count, and both are already selectable. --server landed with serving-across-servers §3. --gpus selects one of the profile's gpu_variants through ModelProfile.for_gpus, which _scale_profile already applies on the serve and restart paths. So the three configurations are: no flags (h200-4x, which stays the profile's default); --server b300 --gpus 4; and --server b300 --gpus 8. Today for_gpus(gpus) looks up gpu_variants by card count alone. This section extends it to for_gpus(gpus, server=None): a variant keyed (server, gpus) wins over one keyed by gpus alone. _scale_profile passes the resolved server on both the serve and restart paths. That is an extension of the existing mapping, not a second one, and with server=None every existing lookup is unchanged. Until the B300's host facts are known (b300-arrival-facts), it is declared only in a test site configuration, through the same AMBIX_AGENT_SERVERS mechanism §3 landed. "The default from day one" means the B300 engine is launched as b300-8x; it does not change what a bare agent serve launches.

§5 — Measure the B300 on arrival

Launch b300-8x and measure it with the repository's own benchmark, imas-ambix agent bench. Its tool-call probe (run_tool_call_bench, now bench.check_tool_call after the rotation) runs first. Then its concurrency ladder (_run_concurrency) runs at --levels 1,2,4,8,16,32,64; the option already takes a custom ladder, so the extension to 64 needs no code. The ladder today sends one fixed one-sentence prompt (bench.py, inside _run_concurrency) and takes no prompt argument. This section adds a prompt-size option to _run_concurrency and the bench command, which sets the prompt length in tokens. The census docs/research/serving-capacity-and-b300-projection.html names (docs/figures/b300-serving-projection/census-1280470.json) holds summary quantiles, not per-request lengths. So each configuration is swept at its two receipts.job quantiles, prompt_median (118,490 tokens) and prompt_p90 (168,151 tokens), the prompt sizes our callers send. Aggregate and per-request tokens per second, time to first token, and the knee (the concurrency beyond which aggregate throughput gains less than 5%) are read from the ladder's results. bench_report has no knee reduction today (its reductions are describe_run and compare_runs), so this section adds one, bench_report.knee, beside them, tested where those reductions are tested, rather than computing it in the throughput document. The figure is drawn from that report. Repeat for b300-4x, so both configurations have a measured knee. The b300-8x knee becomes the engine's starting gate width.

The only H200 knee on record (width 10, in local-lane-throughput-against-occupancy.html) is a plateau in production router occupancy, found by a different rule and a different instrument. It is not comparable with a bench sweep, so it is quoted in the text as a reference with that caveat. It is not drawn on the B300 figure's axes.

  • tests/test_bench.py covers the prompt-size option and tests/agent/test_bench_report.py covers bench_report.knee.
  • The tool-call probes pass on b300-8x.
  • Negative control: a repeat of the 16-concurrent point must lie within 2.5% of the first, half the 5% gain that defines the knee, so the noise is smaller than the margin the knee is read from. If it does not, the whole sweep is rerun once. If the rerun's repeat is again outside 2.5%, the section reports the knee as unmeasured and does not set a gate width from it.

§6 — Cut over

The H200 keeps serving (lead, 2026-10-23). After cutover, the lane is two engines of one model: b300-8x and the H200's h200-4x. Today's routing would send every new key to the widest engine (_preferred_owner) and leave the H200 idle, so serving-across-servers §7 lands first. It places each new session on the engine with room and keeps the session there, so its prefix cache stays warm. Cutover then registers the b300-8x engine with the router and confirms both engines take work. This is a coordinator action under the lane-cycle runbook, and the router does not restart for it.

Done when.

  • endpoints.json lists the B300 engine with the 1017 release, and the router's catalog routes deepseek-v4.1-flash to it.
  • Over the first hour, the share of requests ending failed stays within one point of the H200's previous day, and the outcomes line shows no gate expiries above that day's level.
  • Negative control: before registration, a request routed by name is shown to land on the H200 engine. After it, the same request lands on the B300.

§7 — A bake-off, if one is wanted later

Deferred by the lead on 2026-10-23. If a backup model is to be judged against 1017 later, the method is this. Replay about 30 of our own promoted worker nodes, each graded by its own gate command, against each model through one provider path. Store the per-attempt records under the run's directory, and compare paired pass rates with a 95% bootstrap interval. The rule is fixed before results exist: switch only on a gain of at least 5 points with the interval excluding zero, at no less than half of 1017's throughput. The rule is shown to refuse a candidate whose interval includes zero. All four models are on OpenRouter, so this can run without the hardware.

§ Open questions

On arrival: the B300 node's host name, partition, account and reservation, and the CUDA driver version it ships with. §4 fills them into the server declaration, and the driver version bounds which SGLang builds can run.

After cutover, does the 4×H200 keep serving DeepSeek beside the B300, or return to FP64 physics and training? Keeping it adds roughly a fifth to the lane's capacity, but needs serving-across-servers §7 (session affinity, 5 h, elevated risk) and keeps those cards from physics work.

The H200 keeps serving DeepSeek beside the B300 (lead, 2026-10-23). §6 therefore waits on serving-across-servers §7 (session affinity across engines).
