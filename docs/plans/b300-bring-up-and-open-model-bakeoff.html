§1 — The question, and what is already known

An 8×B300 node arrives in about two weeks. Its host is in the same SLURM cluster, with /work mounted (answer of 2026-10-23). This plan has the hardware's first week spent measuring rather than downloading. Every candidate is downloaded, has a launcher, and has been scored on our own agentic work before the node is racked. The rule is set in advance: we switch only if a candidate beats the incumbent, DeepSeek-V4.1-Flash-1017, on our work by more than noise, at a throughput we can afford. The incumbent is chosen by the rotation plan.

What this already says: on the one independent agentic benchmark, GLM-5.3 leads 1017 by 7 points. MiMo ties it. Kimi K3 is far behind and is the largest by a wide margin. Each candidate costs 2.5 to 6.5 times 1017's active parameters per token, which is roughly the factor by which it serves fewer tokens per second on the same cards. A public benchmark is not our workload: Terminal-Bench measures terminal tasks under a generic harness, and our lane runs Claude Code workers on this repository's plans. So the deciding measurement is §3–§4 on our own nodes. Kimi K3 is still downloaded and launchable (§2, §5) so that the record is complete and the decision does not rest on one benchmark, but it is run in §4 only if the decision bakeoff-spend allows it.

§2 — Download the candidates

GLM-5.3 at FP8 is already on disk: /work/projects/imas_gpu/agents/glm-5-3/model, 704 GB. This section confirms it is the complete zai-org/GLM-5.3 release rather than a partial or requantised copy, and adds two profiles with pinned revisions:

  • kimi-k3: moonshotai/Kimi-K3, MXFP4, about 1.42 TiB;
  • mimo-v2-6-pro: whichever XiaomiMiMo/MiMo-V2.6-Pro-* variant (-RL or -MOPD) the model card names as the release for agentic use and SGLang's cookbook serves. The node records which, and why.

Both download through imas-ambix agent download <profile>, which runs as a resumable SLURM job. /work/projects has 286 TB free, against about 2.1 TB added here. The B300 launch topology is left to §5; this section's profiles carry identity and weights only.

Write paths. imas_ambix/agent/profiles/kimi-k3.toml (new), imas_ambix/agent/profiles/mimo-v2-6-pro.toml (new), tests/test_agent_candidate_profiles.py (new).

Done when.

  • Every shard of Kimi K3 and of the chosen MiMo variant is on disk, with size and SHA-256 matching the repository listing at the pinned commit. The comparison is recorded.
  • The GLM-5.3 directory's shard list and sizes match zai-org/GLM-5.3 at a named commit.
  • Negative control: the verification run against a copy of one shard with its last byte changed reports that shard as a mismatch.

§3 — A bake-off measured on our own work

The task set is real work this lane has already done. From the imas-ambix and reckon run ledgers, select 30 promoted implementation nodes that ran on the local lane, and stratify them across small, medium and large briefs. Each task is the node's brief, its base commit and its recorded gate command. A model attempts a task as a worker would: in a fresh detached worktree at the base commit, through Claude Code pointed at an Anthropic-compatible endpoint, with the node's write paths and time budget. Its result is graded by running the node's own gate command against the worktree it leaves.

Per attempt, the harness records:

  • gate pass or fail;
  • wall time;
  • input, cached and output tokens;
  • tool calls that failed to parse;
  • whether the worker stayed inside its write paths.

The endpoint is a parameter, so the same harness runs against the local lane, an OpenRouter model or a B300 engine.

The harness is validated now, at no metered cost, against the local lane's incumbent. Every one of the 30 tasks runs once there, which also gives 1017's baseline on our work once the rotation has landed.

Write paths. imas_ambix/agent/bakeoff/ (new), tests/test_agent_bakeoff.py (new), docs/research/open-model-bakeoff-tasks.html (new; the task list and how it was drawn).

Done when.

  • The task list of 30 nodes is committed with each node's run id, base commit and gate command, and the sampling rule is stated.
  • One full pass against the local lane completes, with a pass rate and a per-task record.
  • Each task's gate command is checked twice: it passes at the node's own promoted head and fails at its base commit. A task whose gate passes at its base cannot discriminate and is replaced.
  • Negative control: an endpoint that always returns an empty completion scores a pass rate of 0 with every attempt classified, never as an error that crashes the harness.

§4 — Run the candidates on our work

Run §3's 30 tasks, three attempts each, against 1017, GLM-5.3 and MiMo-V2.6-Pro, and against Kimi K3 if bakeoff-spend includes it. All models go through one provider path, so serving differences do not leak into the quality comparison. If the decision is OpenRouter, every model runs there, including 1017 (deepseek/deepseek-v4.1-flash-1017). The run is capped at the decision's budget and stops, with partial results recorded, when the cap is reached.

The comparison is paired by task: per-task pass rates, and the difference against 1017 with a 95% bootstrap interval over tasks. Tokens and wall time per passed task are reported beside the pass rate. A model that passes the same share of tasks but spends twice the tokens is not equal on our lane.

Write paths. docs/research/open-model-bakeoff-results.html (new), docs/figures/open-model-bakeoff (new).

Done when.

  • Every model in scope has 90 graded attempts, or the budget stop is recorded with the attempts completed.
  • The results document shows each model's pass rate and its paired difference against 1017 with the interval, and one figure of the per-task differences.
  • Negative control: the bootstrap is run once on 1017 against a copy of its own results, and its interval must contain zero.

§5 — Launchers for 8×B300

For each of 1017, GLM-5.3 FP8, MiMo-V2.6-Pro and Kimi K3, research and write down how it runs on eight B300 cards:

  • the engine (SGLang or vLLM) and the earliest version supporting both Blackwell (sm_100) and the model;
  • the container image or wheel set, pulled to /work so launch day needs no network;
  • tensor and expert parallelism;
  • KV-cache dtype (FP8 KV, which Hopper could not give GLM-5.3);
  • speculative decoding, which the capacity study found helps only at low concurrency;
  • the memory budget per card.

The B300 is declared in SiteConfig.servers, using the machinery serving-across-servers §3 landed. Its host name and reservation are filled from the operator's answer at arrival. Each profile gains a B300 topology, so imas-ambix agent serve <profile> --server b300 --dry-run prints a complete script today.

Write paths. imas_ambix/agent/profiles/deepseek-v4-1-flash.toml, imas_ambix/agent/profiles/glm-5-3.toml, imas_ambix/agent/profiles/kimi-k3.toml, imas_ambix/agent/profiles/mimo-v2-6-pro.toml, tests/test_agent_b300_launchers.py (new), docs/research/b300-launch-recipes.html (new).

Done when.

  • For each of the four models, --server b300 --dry-run prints a script naming an image or wheel present under /work, the weights directory, TP8, and the KV dtype. A test pins each script's placement and topology lines.
  • The recipes document cites, for each model, the engine release notes or cookbook page that the version choice rests on.
  • Negative control: asking for the B300 topology of a profile that has none refuses, naming the profiles that have one.

§6 — Throughput on the B300, on arrival

Serve each model in turn at TP8 on the B300 with §5's launcher, then sweep concurrency from 1 to 64 with prompts drawn from the receipts' measured prompt-size distribution, not the 128-token prompts the published benchmark used. Record aggregate tokens per second, tokens per second per request, time to first token, and the knee: the concurrency beyond which aggregate throughput gains less than 5%. The knee becomes the engine's starting gate width.

Write paths. docs/research/b300-throughput.html (new), docs/figures/b300-throughput (new).

Done when.

  • Each model has a sweep with its knee, and one figure with every model on shared axes.
  • Negative control: a repeat of 1017's sweep point at 16 concurrent requests lies within 10% of the first measurement, or the sweep is reported as noisy and repeated.

§7 — Decide what the B300 serves

The rule is stated before any result exists, so a result cannot shape it. A candidate replaces 1017 as the primary model only if both of these hold:

  • its paired pass-rate difference over 1017 on §4 is at least 5 percentage points, with the 95% interval excluding zero;
  • its measured B300 aggregate at the knee (§6) is at least half of 1017's.

If a candidate passes the first test but not the second, it is offered as a second model on half the node, routed by name. That choice goes to the lead and is not made automatically. If no candidate passes, 1017 serves the B300 alone and the H200 returns to physics. The outcome locks serving-across-servers' b300-role decision, with this plan's results document as its rationale.

Done when b300-role is locked, and its rationale cites §4's interval and §6's knee for every candidate.

§ Decisions

Where does §4 run, and on what budget?

All four models are listed on OpenRouter, so the quality bake-off can run this week on metered spend, leaving the B300's first week for throughput. Running it locally instead waits for the hardware and occupies it for several days. The order of magnitude, before §3 measures tokens per task: 30 tasks, 3 attempts and 3 to 4 models make 270 to 360 attempts, at very roughly $0.5 to $3 each with prompt caching.
