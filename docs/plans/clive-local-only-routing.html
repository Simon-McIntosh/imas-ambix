§1 — Symptom and reproduction

The shared SDCC launcher clive — published on PATH by the Clive/0.1.0 environment module, which symlinks /work/imas/opt/EasyBuild/software/Clive/0.1.0/bin/clive to /work/projects/imas_gpu/agents/clive — returns errors and then hangs. A launch with a non-interactive prompt produced no completion and was killed at the 180 s mark.

The served model is healthy. SLURM job 1252401 (deepseek-v4-flash) has been running 5 days on 98dci4-gpu-0003 in partition betelgeuse, and the endpoint answers correctly on both surfaces:

ProbeResult
GET /v1/models200 — one entry, deepseek-v4-flash, max_model_len 524288
POST /v1/messages with Authorization: Bearer <key>200 — "Hi! How can I help you today?"
claude -p against the endpoint with clive's direct-route env vars200 — replied OK

So the fault is not the model, not the GPU node, and not the vLLM server. It sits entirely in the routing layer that clive selects at launch.

§2 — Root cause

clive chooses between two routes at startup, and the selector is the mere readability of a personal key file:

if [[ -n "${OPENROUTER_API_KEY:-}" ]] || [[ -r "$HOME/.config/openrouter/key" ]]; then
    _HAVE_OR=true
fi

With no key, clive points Claude Code straight at the vLLM endpoint and everything works. With a key present, clive instead starts a per-user imas-ambix-llm.service LiteLLM proxy and points Claude Code at 127.0.0.1:18399. On that second route every one of the five picker slots is dead, from two independent causes.

Fault 1 — auth-header mismatch kills the default (local) model

The picker default is the haiku slot, which the proxy route maps to the local deepseek-v4-flash. In litellm_config.yaml that model is declared with LiteLLM's Anthropic-native provider — model: anthropic/<name> plus api_base — a form chosen deliberately so that cache_control survives. But that provider authenticates the Anthropic way. In litellm 1.80.13, AnthropicConfig.get_anthropic_headers builds exactly:

headers = {
    "anthropic-version": anthropic_version or "2023-06-01",
    "x-api-key": api_key,
    "accept": "application/json",
    "content-type": "application/json",
}

There is no Authorization header on that path. vLLM's API-key middleware only honours Authorization: Bearer. Probing the endpoint directly isolates the boundary unambiguously:

Header sent to POST /v1/messagesStatus
Authorization: Bearer <key>200
x-api-key: <key>401
no auth header401

Through the proxy the same request returns {"error":"Unauthorized"} … Received Model Group=deepseek-v4-flash with code 401. The credential itself is fine: the systemd env helper writes a correct 43-character AMBIX_LOCAL_KEY into $XDG_RUNTIME_DIR/imas-ambix-llm.env, byte-for-byte what the same extraction yields when run by hand. The key is right; the header carrying it is wrong.

Fault 2 — the OpenRouter key's spend cap is exhausted

All four or-* slots return 403 with "Key limit exceeded (total limit)" — or-opus-4.8 and or-sonnet-4.6 as an Anthropic permission_error, or-gpt-5.5 and or-glm-5.2 as a LiteLLM APIError. This is account state, not a code defect, but it means the four remaining picker entries were dead alongside the default.

The design defect behind both

Neither fault would have taken down the shared launcher had the launcher not silently rerouted itself. Three properties combined to make this a production outage on a shared tool:

  • An implicit, invisible route switch. Nothing the user typed selected the proxy. Merely owning a file at ~/.config/openrouter/key — possibly created months earlier for an unrelated purpose — moved every request onto a different transport with different auth semantics.
  • The failure is invisible to anyone who cannot reproduce it. Users without a key were unaffected, so the outage looked intermittent and user-specific rather than systematic.
  • A shared cluster launcher acquired a personal-billing dependency. A tool whose purpose is to expose the local H200 model to SDCC users routed its default model through a third-party proxy and made it contingent on a personal OpenRouter account's remaining credit.

The generator is confirmed authoritative, so the bug is in committed source rather than a hand-edit of the deployed copy: imas-ambix agent clive --print is byte-identical to /work/projects/imas_gpu/agents/clive. Every fix below is therefore a version-tracked change to imas_ambix/agent/ followed by a re-deploy.

§3 — Decision: clive is DSv4-only

Locked by owner directive: the shared SDCC clive serves the local model and nothing else. It must not be OpenRouter-accessible. This is not a workaround for the exhausted key — it is the correct boundary for a cluster-wide launcher, and it resolves Fault 1 and Fault 2 together by deleting the route on which both occur.

Consequences that follow directly:

  • The five-slot picker collapses to one model. Every tier alias points at the served local model, as the working no-key route already does.
  • The LiteLLM proxy has no remaining consumer in clive. Its generators, its deploy entries, its /work artifacts and the per-user systemd unit all become dead surface and are removed rather than left dormant — a dormant OpenRouter route in a group-shared directory is precisely what this decision excludes.
  • ~/.config/openrouter/key stops having any effect on clive. No env var and no file changes its routing.

A separate, private, non-deployed launcher for a key-holder's own OpenRouter use is out of scope here and must not live in the group-shared agents directory.

§ Decisions

Should the shared SDCC clive keep any OpenRouter capability?

Owner directive: clive is for DSv4, the local model, and the SDCC-public version must not be OpenRouter-accessible. Removal — rather than an opt-in flag or repairing the proxy's auth header — is what makes that boundary real: a dormant route in a group-shared directory is still an OpenRouter surface, and it keeps a cluster launcher's default model contingent on a personal third-party account's credit.

How should clive authenticate to the local vLLM endpoint?

Directly, with ANTHROPIC_AUTH_TOKEN , which Claude Code sends as Authorization: Bearer — the only scheme vLLM's api-key middleware accepts, verified 200 against 401 for x-api-key . Removing the proxy removes the mismatch at its source rather than patching a header override into a gateway that no longer has a purpose.
