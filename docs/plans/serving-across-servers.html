§1 — What assumes one server today

The local lane is one engine: DeepSeek-V4.1-Flash on four H200 cards of 98dci4-gpu-0003, behind the router at 98dci4-gpu-0003:18802. An 8×B300 server is planned. The B300 projection puts it at four to six times today's serve for the same model, and its §8 names what the router needs for a second server: a gate for each upstream, and session affinity when one model runs on both. This plan carries that design, and the watch tools that show it, from the router outwards.

Some of the system already handles several servers. Each serve writes a registration that names its host, port, model and accelerators. The router resolves upstreams from those registrations on any host and routes each request by the model it names. Every request row in requests.jsonl names the engine that served it (upstream) and the session and run that sent it. Recorder rows carry the hostname, served model and job id. Reckon lets each backend declare its own lane_document.

Nine places still assume a single server. Each is a defect only once a second server exists, and each needs a different fix:

§2 — The shape: servers, engines, pools, and one owner per figure

Four words are used throughout, each for one unit:

TermIsThe unit of
ServerA physical host: 98dci4-gpu-0003 today, the B300 host later Cards, power, temperature, host CPU and memory, SLURM jobs, the recorder
EngineOne serve: a model at a topology on a server, at one port. Its id is <host short name>:<port>, such as gpu-0003:18810 KV pool, throughput knee, gate width, live counters
PoolEvery engine serving one model id. Usually one engine. What a client names; the admission figures reckon dispatches against; price and cost
RouterThe one origin every consumer holds Catalog, routing, one gate per engine, the request record

Consumers keep one address. A request names a model; the router resolves the model to its pool, picks an engine (§7 when the pool has more than one), and waits at that engine's gate (§4). Each pool publishes one lane document in today's shape (§5), so reckon dispatches against the pool its worker's model belongs to. lane.json stays the default pool's document, so reckon keeps working unchanged.

Every figure has one owner, and the split follows what a figure describes. The serve grid in gpu-watch today mixes the engine (throughput, cache, KV pool), the router (gate, queue, headroom) and the cards (temperature, power) in one table. That works for one server. With two, an engine's figures have no single machine to sit under, and the router's queue sits on no machine at all. So the service figures move to llm-watch: engines, gates, pools, callers, traffic history and cost. gpu-watch keeps the machines: cards, host, temperature and power, and jobs. It also gains one identity row per engine (model, cards, port) so a reader can still tell which cards serve what. This answers whether the model performance figures move: they all do, and the serving-figures-home decision records the choice.

Both tools keep the serve panel's visual grammar unchanged:

  • the seven-column grid, with the first column 13 characters wide and the rest 12;
  • bands of a label row over a value row, separated by weight rather than rules;
  • every percentage drawn as a filled bar beside its figure;
  • health shown as colour ramps;
  • one stale mark on a header rather than on every row.

The tools render published sources and compute nothing a publisher already computes.

§3 — Servers are declared once

SiteConfig gains a servers list. Each entry has:

  • a name and host;
  • its SLURM partition, account and reservation;
  • its accelerator family and card count;
  • the per-card power cap;
  • the reservation groups its job table labels (the A and B groups on 98dci4-gpu-0003).

When no list is configured, today's flat fields become the single entry for 98dci4-gpu-0003, so an existing configuration resolves unchanged.

imas-ambix agent serve <profile> --server <name> places a serve, and registrations carry the server name. endpoints.json gains a servers array listing each server's name, host, accelerators and engines. Readers outside the package, such as gpu-watch and reckon, read servers from that document and never from the site configuration.

The servers array is written by the existing owner, registry.build_endpoint_document, never by a second registry. Its model-id dedup (keep the later job for a model) becomes a dedup on engine id (<host short name>:<port>). That way, two engines serving one model both appear in endpoints as well as in servers, while a restarted job on the same engine still replaces its predecessor.

Done when.

  • With no servers configured, imas-ambix agent serve deepseek-v4-1-flash --dry-run prints a script byte-identical to the one the plan's base revision prints.
  • A test configuration with two servers produces scripts carrying each server's own partition, reservation and account.
  • endpoints.json written from a two-server registration set lists both servers, with each engine under its own server.
  • Negative control: --server naming an undeclared server exits non-zero, names the declared servers, and writes no script.

§4 — One gate per engine

Each engine gets its own _GenerationGate: its own queue, width, width controller and admission ledger. An engine's controller is fed only by that engine's lane reading, because the throughput knee is a property of the engine's hardware and configuration. A B300 engine held to the H200 width of 12 would run at an eighth of its projected width. The router resolves model, pool and engine before queueing, so a request waits only at its own engine's gate.

The gate control file keeps today's flat keys as the defaults for every engine. An engines map keyed by engine id overrides width, wait and pause for one engine. A top-level paused still pauses every engine, so the lane-cycle runbook keeps working as written. A gate-expiry row keeps the (router) upstream sentinel and gains the id of the engine whose gate it waited at.

Queue order within each gate is not decided here. It belongs to the queue-order decision in local-lane-admission-control, and every gate applies whichever order that decision locks. Until it locks, each gate keeps today's first-come, first-served order, so this section does not wait on it.

Done when.

  • A router test with two fake upstreams of widths 2 and 4 sends six concurrent requests to each. Admission timestamps show each gate admitting up to its own width, and a full gate on one engine never delays a request bound for the other.
  • A throughput reading from one engine moves that engine's width and leaves the other engine's width unchanged.
  • A gate expiry on one engine writes a row naming that engine.
  • The existing router admission and gate tests pass unchanged against a one-engine router.
  • Negative control: a top-level pause holds new requests on both engines, and a pause in the engines map holds only its own engine.

§5 — One lane document per pool, and lane.json stays the default pool

Each engine has its own reading loop, which fetches that engine's metrics into that engine's own window. One composer runs once per publishing tick, after the readings. The composer is RouterApp._publish_lane itself, rewritten to iterate the engines instead of reading upstreams[0]. Today there is a second writer of lane.json: the imas-ambix agent lane command (cli.py), whose --submit form runs a long-lived refresher job (generate_lane_refresher_script). This section retires that writer. Before it does, the node searches the reckon, dotfiles and imas-ambix trees and the scheduler's running job names for the command and the refresher, and records what it found. After this section, no function but the composer writes a lane document. A test asserts it by searching the package for calls to both functions that write one: lane.write_lane_document and lane.write_unavailable_document. The lane command calls the second on its unavailable path, so a guard covering only the first would pass while the refresher kept overwriting lane.json. The done-when gains a bullet for the retirement: the caller search is recorded, the command and its refresher are removed, and the search test finds no writer outside the composer. It writes the default pool's document at lane.json and every other pool's document at lanes/<model id>.json, from the latest reading of each engine. The default pool is never written a second time under lanes/, so no two files carry the same fields. The lanes index maps the default model to lane.json itself. So every document has exactly one writer, even when a pool spans engines. A pool document has today's lane.json shape:

  • One engine: every field is that engine's own, with an unchanged meaning.
  • Several engines:
    • counts and capacities sum: running, waiting, pool tokens, the concurrent-request ceiling, headroom, the gate's width, in-flight and waiting counts, and worker slots;
    • the aggregate token rate sums;
    • per-request figures (mean context, rate per request) are weighted by each engine's running count;
    • an engines array carries each engine's own reading and gate.

lane.json is the default pool's document (the model SiteConfig.preferred_release_id names, else the only pool) plus a lanes index mapping each model to its document and engines. A reckon backend for a second model sets lane_document to that model's file, so model-level routing needs no reckon code change. The lanes index is an added key, so a reader of today's shape is unaffected. The lane document's versioned schema belongs to local-lane-admission-control, which this plan is sequenced after. If that schema has landed when this section runs, this section bumps its version. If it has not, the schema takes the lanes key in when it lands.

Done when.

  • From one engine's fixture readings, a golden test shows lane.json carrying the same keys and values the base revision publishes, plus the lanes index, plus the schema version where this section bumps it. No other key is added or dropped.
  • A two-pool fixture writes two pool documents, and lane.json equals the default pool's document plus the index.
  • The second writer is retired. The node's search of the reckon, dotfiles and imas-ambix trees and of the scheduler's running job names for the lane command and its refresher is recorded. The command and generate_lane_refresher_script are removed. A test finds no call to write_lane_document or write_unavailable_document outside RouterApp._publish_lane.
  • reckon's reader, reckon.crew.lane_document.read_lane_document, resolves every field from a pool document exactly as it does from today's lane.json. This runs as a contract test where reckon is importable, and is skipped with its reason printed where it is not.
  • Negative control: with one engine stopped, its pool document reads unavailable, while the other pool's document stays measured and fresh.

§6 — Live figures and the ledger are per engine

The live block chooses the newest raw receipt for each serve, keyed on hostname, served model and job id, among files written within the lane's shelf life. It produces one live entry per engine, joined to the engine through its registration. The period ledger gains one set of rows per model, each priced at that model's own rate, plus a total across models. The ledger's storage and pricing stay with serving-record-warehouse; this section only keys them by model.

Done when.

  • Two recorder files from two serves in a fixture yield two live entries, each with its own counters.
  • A recorder file whose last row is older than the shelf life yields no live entry.
  • A two-model ledger fixture prices each model at its own rate, and the total equals the sum of the two.
  • Negative control: a malformed tail on one engine's file makes that engine's live entry unavailable, with a reason, and leaves the other engine's entry intact.

§7 — One model on more than one engine

This section runs only if the b300-role decision puts a model on both servers. Until then, every pool has one engine and routing by model id needs nothing new.

Within a pool, a request is keyed by the session it declares (x-reckon-session), else its run (x-reckon-run-id), else its caller host. Routing then follows these rules:

  • When two engines of the model run on the same server, the one _preferred_owner ranks first (wider, then newer) is current, and the other is draining. A draining engine takes no new keys. The keys already pinned to it stay until they expire or fail over. This is today's rotation rule, applied per server.
  • A key's first request goes to the current engine with the fewest pinned keys per unit of gate width, skipping engines whose gate is paused. Ties go to the wider engine. Placement therefore spreads sessions in proportion to width, whatever load each engine happens to carry at the moment of placement.
  • Later requests with the same key stay on that engine.
  • A key moves only when its engine's gate is paused, the engine is gone, or its queue wait passes a bound (30 s by default, set in the control file).
  • A pin expires after 180 s idle, the router's existing working horizon.

Each request row records why it went where it did: pinned, placed or failed-over.

The reason is the prefix cache. The projection study measured 96.8% of prompt tokens served from cache. A turn sent to the other engine prefills about 120,000 tokens instead of about 3,700: roughly 12 s on H200 and 2 s on B300.

Done when.

  • In a two-engine pool, fifty requests from one session all land on one engine.
  • With widths 4 and 12, sixteen sessions placed one after another split within one session of 1:3.
  • Pausing the pinned engine sends that session's next request to the other engine, recorded as failed-over.
  • In a rotation overlap on one server, every new key goes to the new engine. The fixture has the old engine at width 4 and idle, and the new one at width 12 carrying one request. Keys already pinned to the old engine stay there.
  • The existing rotation tests for _preferred_owner pass.
  • Negative control: with the wait bound at 0 s, a full engine's sessions fail over; with no bound set, none fail over while their engine serves.

§8 — The llm-watch document

One builder produces the document that the view renders and llm-watch --json prints. It reads only published sources: endpoints.json, the lane documents, the tail of the router's request record, the recorder receipts and watch.json. That builder already exists and is extended, not rebuilt. live_panel.live_panel composes the live, lane and callers blocks, and watch.live_document serves it. That chain is what agent watch --json --live prints and what dotfiles gpu-watch renders its serve panel from today. llm-watch --json prints the same function's output. lane_callers.py stays where it is and gains the account and project levels. No second builder or alias layer is written, so agent watch --json --live keeps working unchanged until §11 retires the flag.

Write paths. imas_ambix/agent/lane_callers.py, imas_ambix/agent/live_panel.py, tests/test_lane_callers.py, tests/test_live_panel.py.

Callers are grouped by account, then by project, from identity the caller reports. The callers block carries two levels. accounts has one entry per account: the number of sessions and runs, held, held per run, mean gate wait, and its share of the gate. Requests that reported no account are totalled under a single unattributed entry, which lists the hosts they came from. projects has one entry per (account, project): the number of sessions and runs, held, held per run, and mean gate wait. The per-session list stays as it is, with each entry gaining account and project. Both new fields come from the request record (§13), and the builder copies them without inferring anything. The accounts' held figures sum to the block's held, and an account's projects sum to that account's held.

The contract with §13 is two optional row keys. The builder reads row.get("account") and row.get("project") from each request-record row. A row without them is unattributed, and so is every row written before §13 deploys. §8's fixtures carry the two keys by hand, so §8 does not wait for §13 to land, and neither section invents a name the other has not stated. When an account is reported without a project, the project reads unattributed within that account.

This deletes the inference the dotfiles watcher does today. Its _Resolver searches the viewer's own ~/.claude/projects for a session transcript (about 2 s on GPFS), matches reckon session names against <project>-YYYYMMDD, and runs reverse DNS and squeue on the caller's host. Its answers depend on who is viewing. It cannot attribute another account's sessions, and it marks ? on a session named any other way. On 2026-10-22, s21-nova, one of the viewer's own coordinators, was marked ? because of this. None of that machinery carries over.

The only differences allowed are the added accounts and projects levels and the per-session account and project keys.
  • The document is built for one engine. Per-engine entries, and each caller's held figures split by engine, are §14's, because their shape is the pool document §5 and §6 publish.
  • History bins over a fixture with a known request schedule match occupancy computed by hand.

  • On a fixture of two accounts, three projects and one unattributed host, the accounts' held figures sum to the block's held within 0.01, and each account's projects sum to its held within 0.01. Rows with no account land in unattributed and carry their hosts.
  • No code under imas_ambix/ reads ~/.claude/projects, runs squeue or does a reverse DNS lookup to name a caller.
  • Negative control: a fixture row whose account is absent, on a host where only one account holds SLURM jobs, still lands in unattributed and is never assigned to that account.

§10 — gpu-watch shows the machines

gpu-watch drops the serve panel, the callers table and the ledger. For each server declared in endpoints.json it shows:

  • the card table (utilisation and memory, now and mean);
  • host CPU and memory;
  • a conditions line (°C mean, °C max, kW, percentage of cap) moved from the serve grid;
  • the SLURM job table;
  • one dim row per engine on that server, naming its model, cards and port. This row gives identity only, with no performance figures, and points to llm-watch.

--server NAME limits the view to one server; the default shows all of them, stacked. Reservation-group labels come from the server's declaration instead of constants.

watch-home is locked to both-in-imas-ambix, so:

  • gpu-watch's renderer moves into imas_ambix/agent/gpu_watch/;
  • the on-node readings come from node_probe.NodeProbe (read_cards, read_host, read_jobs), the reader the recorder and the retention pass already use. It is extended with a streaming entry point that one long-lived SLURM step runs on the node. The dotfiles _gpu_sample.py is deleted rather than moved, so cgroup and SLURM_STEP_GPUS handling has one owner;
  • it shares one style module with llm-watch;
  • dotfiles bin/gpu-watch becomes a launcher.

Who writes what. Workers cannot write dotfiles, so this section is split. The worker node writes only inside imas-ambix: the package, the NodeProbe streaming entry point, the console scripts and the tests. The coordinator does the dotfiles half at landing, as it has done for every gpu-watch change so far. It replaces bin/gpu-watch and adds bin/llm-watch as launchers that exec the console scripts, deletes bin/_gpu_sample.py and bin/_gpu_watch_test.py, and commits that in the dotfiles repository. The done-when's symbol check runs against both imas_ambix/agent/gpu_watch/ and dotfiles bin/gpu-watch, the second after that commit. A serve-panel symbol or hard-coded node name in either place fails it.

Done when.

  • A two-server test configuration renders two stacked blocks.

§11 — Rollout, and who does each step

  1. No service impact. On today's single engine, the sections still to land are §6, the rest of §9 (retiring agent watch's text view, and the ten-minute live run) and §10, and any worker node can build them. §3, §8, §13 and §9's view have landed; their landing comments are the record. The coordinator regenerates the installed clive script now that §13 has landed. Until step 2 deploys §13's router change, every live caller reads unattributed in llm-watch's accounts table.

§13 — Callers report their account and project

Why the account cannot be shown today. The router's request record holds the peer address, the user agent, and the two identities reckon dispatch reports in headers: x-reckon-run-id and x-reckon-session (request_receipts.identity_from_headers). Every caller authenticates with one shared key, so nothing in the record names an account or a project. The callers table in dotfiles gpu-watch therefore guesses them on the viewer's side, from the viewer's own transcripts and from squeue on the caller's host. Any figure that is a total per account is impossible until the account is reported at the source.

The caller reports it, and the router copies it.

  • clive (clive.py, the generated wrapper) appends two lines to ANTHROPIC_CUSTOM_HEADERS before it execs claude: X-Ambix-Account: $(id -un), and X-Ambix-Project: followed by the base name of the main checkout. That name comes from the parent of git rev-parse --path-format=absolute --git-common-dir, so a reckon worktree reports its repository rather than its node directory. Outside a repository it falls back to the base name of the working directory. reckon's dispatch already composes the variable for every worker it launches, writing the run and session headers in dispatch_launch._worker_runtime_environment. clive does not compose it a second time. It appends a line only when the inherited value carries no header of that name, and it never rewrites or reorders what it inherited. clive is the writer here because it is the one launcher both a dispatched local-lane worker and an interactive session pass through, and it is in this repository. Making reckon's dispatch the writer for every backend is the proposal under Left to reckon below. Once reckon writes the headers, clive's absent-only rule leaves them alone. Every local-lane worker launches through clive, as does every interactive clive session, so both are covered without a change to reckon.
  • The record. request_receipts.py gains ACCOUNT_HEADER = "x-ambix-account" and PROJECT_HEADER = "x-ambix-project", read under the same rules as the existing tokens (_identity_token). RequestReceipt gains account and project, each null unless reported. The router passes both through at its two call sites of identity_from_headers. The router infers neither field.

Trust. The headers are self-reported, just as the session header is. That is enough to attribute load on a cluster whose users share one key. It is not enough to enforce a share, and the docstrings say so. Per-account keys would be needed to enforce one, and that is out of scope here.

Deployment. The router change takes effect at the next lane cycle under ops/lane-cycle/AGENTS.md, which is operator work. The clive change takes effect once the coordinator regenerates the installed clive script. Until then, new rows read unattributed, which is the truth about them.

Left to reckon. A worker dispatched on a non-clive lane, codex or another tool, stays unattributed. Making reckon dispatch send X-Ambix-Account for every backend is proposed to reckon as a followup, not changed here.

§16 — A router restart drops nothing

The gap. A router restart is cheap for the engine, which keeps running and is rediscovered from its registration. It is not cheap for the router's own memory. While admission is paused, the requests of workers already running wait in the generation gate's in-memory FIFO. At shutdown, RouterApp's lifespan handler cancels the lane publisher, closes the upstream session and closes the receipt sink, but answers none of those waiters. They die with the process as dropped connections, not as the 529 Retry-After that every client retries cleanly. ops/lane-cycle/AGENTS.md records this as the one cost of a router restart, and §11 and §15 each need at least one.

The fix. lifespan.shutdown is too late. uvicorn reaches it only after it has waited timeout_graceful_shutdown on open connections and cancelled them, and with that setting unset, which is how the router launches today, it waits forever. So the release runs when the shutdown signal arrives. The router installs a handler that, on SIGTERM or SIGINT, makes the gate stop admitting and answer every waiter with the same 529 overloaded_error and Retry-After the wait bound already produces. Only then does it hand over to uvicorn's own shutdown. The router's launch also sets timeout_graceful_shutdown, so the wait that follows is bounded. The lifespan handler keeps its existing cleanup. Each is recorded as a gate expiry with a reason naming the shutdown. Requests already relaying are given a bounded grace to finish, set by uvicorn's timeout_graceful_shutdown and defaulting to 30 s, and are recorded as cut if they outlast it. With this, the restart sequence of hold dispatch, pause, restart and resume loses no request that reached the router.

Write paths. imas_ambix/agent/router.py, imas_ambix/agent/request_receipts.py, tests/test_agent_router_gate.py, tests/test_agent_router_service.py.

§ Decisions

What does the B300 server serve first?

The projection study recommends different models on different servers at first: model-level routing needs nothing new, and every prefix cache stays warm. A second copy of the H200 model needs §7's session affinity. Splitting the node runs DeepSeek on four B300 cards and GLM-5.3 at FP8 on the other four, which also needs §7.

The lead's decision of 2026-10-23: the B300 serves DeepSeek-V4.1-Flash-1017, the H200 lane's own model after its rotation, on all eight cards from day one, with no bake-off first. The independent evidence supports it. 1017 ties GLM-5.3 and MiMo-V2.6-Pro on the Artificial Analysis index (45 against 45 and 46), and GLM-5.3 leads it by 7 points on Vals' Terminal-Bench 4.0. But 1017 runs 16B active parameters against their roughly 40B, so it serves about two to three times the tokens per card. The other models are downloaded as backups (b300-bring-up-and-open-model-bakeoff §3). Whether the H200 keeps serving beside the B300, which is the only case that needs §7, is that plan's open question h200-role.

Where do the two watch tools live?

Recommended: both in imas-ambix, sharing one style module and tested with the rest of the package, with dotfiles keeping two launchers. Workers cannot write to dotfiles, so gpu-watch changes have always landed through the coordinator, and gpu-watch has no tests. Keeping gpu-watch in dotfiles means the style helpers exist twice.

Both tools live in imas-ambix as console scripts that share one style module and are tested with the package. dotfiles keeps two thin launchers so the command names stay on PATH. The cost of the alternative was measured: dotfiles gpu-watch grew to 1,819 untested lines. Its serve panel, ledger, lane availability and callers table all landed after serve-telemetry-spine §5 had declared the watcher moved, because the lead watches gpu-watch and workers cannot write dotfiles. The review of 2026-09-21 raised the unthinned launcher, finding f9ff54483cc, and that finding stayed open for a month. Accepted cost: the on-node sampler moves into the package too, and gpu-watch gains the package's dependencies.

Where do the model performance figures live?

Recommended: llm-watch only. With several servers, an engine's figures have no single machine to sit under, and the router's queue sits on no machine. gpu-watch keeps one identity row per engine so cards can still be matched to what they serve.

The lead's ruling of 2026-10-22 is that the running-workers listing and every LLM-specific figure leave gpu-watch for a redesigned llm-watch. gpu-watch keeps the machines, plus one dim identity row per engine so cards can be matched to what they serve. A one-row performance summary in gpu-watch would recreate the mixed panel this split removes.
