JT-60SA Tokamap From Generated Maps

The lead asked on 2026-10-09 for a working prototype of the whole chain, from discovery to a tokamap directory. The tokamap must carry both the machine description and the signal mappings, with the signal mappings at draft. The work is split between two repositories, and each runs in its own session:

  • imas-codex discovers signals and generates mappings from facility signals to Data Dictionary paths. Its plan, imas-codex:generated-map-handoff, exports them in one hand-off document per facility, defined in that plan.
  • imas-ambix owns the machine description, which is its catalogue built from the SELENE deck. It resolves each draft signal to its probe or coil index, checks rules against data, and writes the tokamap directory and the IDS.

The two sessions coordinate by message.

The lead also ruled that a map is never promoted by default without a validation step. In imas-ambix this means two things:

  • a rule built from an imas-codex mapping carries the validation state draft, and the tokamap comment carries that state;
  • such a rule becomes corpus-validated only through imas-ambix's existing checks against pulse data.

The exporter already exists: imas_ambix/data/tokamap_export.py export_tokamap_directory, with tests in tests/data/test_tokamap_export.py, but no command calls it.

A probe on 2026-10-09 ran it on maps/jt-60sa/machine_map.json and the four signal maps in maps/jt-60sa/maps/. Its output carries both halves. Machine-description entries such as b_field_pol_probe[#]/length read /work/projects/imas_gpu/jt60sa/machine_description/OP2/magnetics.nc. Signal entries such as b_field_pol_probe[#]/field/data read MDAC magPbTC10.

It refused correctly on one point. Two of the 432 catalogue bindings target magnetics/b_field_pol_probe/poloidal_angle, which is COCOS-dependent, and the JT-60SA catalogue declares source_cocos: 0. The JT-60SA COCOS is undetermined: the plasma current has been seen with one polarity only, and the handedness is undeclared. Declaring it is jt60sa-machine-map's work, not this plan's.

With those two held out, the probe wrote 6 groups, 2 shot partitions (100001 and 101174), 12 mappings.json files and 70 entries.

§1 — A command that exports a machine's tokamap

Add imas-ambix maps tokamap MACHINE --out DIR to the existing maps group in imas_ambix/maps_cli.py. It loads the machine's catalogue with imas_alambic.machine_map.load_machine_map and its signal maps with imas_alambic.signal_map.load_signal_map, then calls export_tokamap_directory. It prints the group, partition and entry counts, split between machine-description entries and signal entries.

An undeclared source COCOS is still a refusal by default. Add one opt-in keyword to export_tokamap_directory itself, exposed as --withhold-undeclared-cocos. It skips each binding or rule that targets a COCOS-dependent path while its source COCOS is undeclared, and records that item in the returned TokamapExport under a new field such as withheld, with its name, target path and reason. The command prints every withheld item. No entry is ever written with an assumed factor. Extend the exporter itself rather than filtering the catalogue outside it.

The probe also exposed a silent defect that §1 must fix first. _leaf_mappings keys each entry by its tokamap path, in which every structure array is written [#], and keeps only the first rule for a key. So the 17 pickup-probe rules collapse into one entry, b_field_pol_probe[#]/field/data, which reads magPbTC10. The magnetics leaf holds 11 keys for 45 signal rules, and a reader would give every probe probe 10's signal.

The tokamap schema is installed at .venv/lib/python3.14/site-packages/tokamap/schemas/mappings.schema.json. Its DATA_SOURCE entries take args, scale, offset and slice, and the schema also defines DIMENSION, EXPR and CUSTOM. Find out from the tokamap package how an entry under a [#] key selects its source per index, and emit every rule addressably. If tokamap cannot express a case, the export refuses and names it. Two rules must never collapse silently into one.

Validate every written file with tokamap's own validator, tokamap.validator.

Run the command for jt-60sa with the flag. Write the output to /work/projects/imas_gpu/jt60sa/tokamap/hand-built/, which is the reference that §3 compares against. That directory is data and is not committed.

§2 — Import imas-codex's generated mappings as a draft signal map

Add draft to the validation-state vocabulary, _VALIDATION_STATES in packages/imas-alambic/src/imas_alambic/machine_map.py. Then add a reader in a new module, imas_ambix/data/generated_mapping_import.py. It turns one imas-codex hand-off document into a draft SignalMap per IDS.

For each hand-off row, the reader fills source_group, source_array, units, target_path and transformation from the row. It sets validation_state to draft, and its evidence names the imas-codex mapping id, its status and the row's own evidence.

target_index comes from imas-ambix's machine description, not from the hand-off. The reader resolves it by matching the row's member_identifier and source_array through the catalogue's sensor_identity_rules to a machine-description element. It must not read the index from the hand-built signal maps, because §3 compares against those, and taking indices from them would make the comparison circular.

A row the identity rules do not resolve, and every unexpanded row, is reported with its reason, never guessed. Those gaps define what the hand-off contract still has to carry.

Build and test against imas-codex's committed fixture, tests/fixtures/mapping_handoff_example.json from imas-codex:generated-map-handoff §1. Copy it here as tests/fixtures/mapping_handoff_example.json.
