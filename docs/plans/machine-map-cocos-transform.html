§1 — A name map is not a transform

The landed machine map binds each source array to a Data Dictionary path, its units, and a sign convention. That is a semantic name map: it says what a channel means and where it goes. It does not say what has to happen to the value on the way, and for a large class of DD fields something does.

Coordinate and sign conventions (COCOS) fix the handedness of (R, φ, Z), the sign of poloidal flux relative to plasma current, and the direction of the poloidal angle. A quantity written under one convention and read under another differs by a sign, or by a factor of 2π, or by both. The Data Dictionary declares which of its fields are convention-dependent and how each transforms — so the target path itself tells us a transform is required. Binding a COCOS-dependent field without applying its transform is a silent sign error, not a missing feature.

In magnetics alone the DD marks 17 COCOS-dependent fields across six transformation classes, and the machine map already binds targets in three of them:

Probe orientation angles are the immediate exposure: they are machine description, the map binds them, and they are convention-dependent. A wrong poloidal-angle sign rotates a probe's sensitivity direction, which corrupts every magnetic reconstruction built on it without ever failing a schema check.

§2 — Identify MAST's convention, do not assume it

Two prior results frame this and neither settles it. The MAST → IMAS COCOS evaluation found the MAST-only chain sign-sound and self-consistent, and explicitly identified the unwired IMAS ingestion seam as a latent risk where COCOS-11 (axis = flux-minimum for Ip > 0) disagrees with the pipeline's working convention (axis = flux-maximum). The transform engine is now that seam. The COCOS-17 hardening plan shipped a DD 4.1.1 / COCOS-17 contract with imas_ambix/cocos.py carrying require_canonical_contract, canonical_factor and mast_angle_to_canonical — machinery to build on, and evidence that the target convention is already decided.

What is not established is MAST's source convention as a COCOS number, derived from the data rather than inferred from the fact that the internal chain is self-consistent. A self-consistent chain is consistent in some convention; it does not name which. The Sauter and Medvedev coefficients — σBp, σRφZ, σρθφ and the eBp 2π exponent — are what turn an observed set of relative signs into a convention number, and they are also what generate the transform to COCOS-17 once the number is known.

§3 — Prove it on real data, both current signs

The determination must be an assertion against measured MAST data, not a documentation reading, and it must hold for both signs of plasma current. This is the part that makes the result trustworthy: several of the Sauter sign relations involve the product of a convention coefficient with sgn(Ip), so a single-polarity test cannot separate a convention error from a current-sign error. They are only distinguishable when the same relation is checked at both polarities, where a genuine convention holds and a mistaken one flips.

MAST ran both polarities, so a cohort is available. The check needs, per shot, the relative signs of plasma current, toroidal field, poloidal flux and the poloidal-angle direction, read from the level-2 store through the existing loaders and compared against what each candidate COCOS predicts. A convention survives only if it predicts every observed relative sign at both polarities.

Deliberate negative outcome to allow for: the observed signs may match no single COCOS. That is a real possible finding — a facility store assembled over decades can be internally consistent without being COCOS-expressible — and it must be recorded as such rather than rounded to the nearest convention. If it happens, the transform declaration becomes an explicit per-quantity sign table with its evidence, which is honest, whereas a mislabelled convention number is a trap for the next machine.

§4 — Where the transform lives

The transform belongs in the engine, driven by declarations in the map, for the same reason the engine is format-scoped rather than machine-scoped: the DD's transformation class is a property of the target path, and the source convention is a property of the machine, so the pair determines the factor without any machine-specific code.

Concretely, a binding declares its source convention and the engine looks up the target path's transformation class from the DD, then applies the Sauter factor for source → COCOS-17. A binding whose target is COCOS-dependent and whose source convention is undeclared must fail loudly rather than pass the value through: silent identity is exactly how a sign error survives to a reconstruction.

Done-when: MAST's source convention identified as a COCOS number or explicitly recorded as not COCOS-expressible, asserted against real level-2 data for both current polarities with the per-quantity sign table printed; the Sauter coefficient set for that convention and the derived factors to COCOS-17 committed as data, not prose; the transform applied in the engine for every COCOS-dependent target the catalog binds, with an undeclared source convention on a COCOS-dependent target failing loudly; and a round-trip test asserting that emitting through the engine and transforming back recovers the source values, run over shots of both polarities.

§ Decisions

Where is a machine's source COCOS convention declared — once per machine, or per binding?

A source convention is a property of the machine's store, so declaring it per binding would repeat one value across 254 declarations and invite exactly the drift the declarative catalog exists to prevent — that rules out per-binding. It is not declared once and made immutable either, because this sprint's own evidence shows why: the convention determination allowed for the real possibility that a facility store assembled over decades matches no single COCOS, and a store carrying one subsystem in a different convention is the same phenomenon at smaller scale. Per-machine with an optional per-binding override expresses the common case once and keeps the exception representable without a schema change. The engine currently defaults the value to the measured COCOS-4 for backward-compatible catalog calls, which is a shim rather than a declaration; locking this moves the declaration into the machine map where it is data.

TOKAMAP ASSESSED (github.com/ukaea/tokamap, UKAEA, MIT, 1 star, 2 open issues, last updated 2026-03-20): NOT a suitable substrate for these mappings, on three concrete grounds. FIRST and decisive, its schema offers exactly the two options this plan's sibling locked AGAINST: map_type EXPR carries an arbitrary expression language (example: expr 'pi * r^2' with named parameters) and map_type CUSTOM carries arbitrary code hooks (example: library 'custom', function 'dot_product', with inputs). The map-expressiveness decision chose range-scoped-maps over conditional-schema and over map-plus-code; tokamap is both rejected options at once, and the rejection rested on measurement — the declared ranges partition the corpus exactly, so no conditional is needed. SECOND, its five map types (DIMENSION, VALUE, DATA_SOURCE, EXPR, CUSTOM) carry NO units, NO sign convention, NO coordinate convention, NO Data Dictionary paths and no validity ranges in the example mappings; it is domain-agnostic by design, whereas the value of our catalog is precisely its domain semantics — DD target path, observed source unit, sign convention, transformation class, binding role, source rank, drive topology and circuit joins. THIRD, it does not address COCOS at all, so it cannot help with the question this plan exists to answer. The owner's read is right: it is closer to an external write and organisation layer, standardising how a mapping directory is structured and validated rather than what a mapping MEANS. One convergent detail worth noting as mild independent support: its example mappings live in numbered partition directories, which echoes range partitioning.
