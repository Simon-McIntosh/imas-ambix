§1 — Why this is separate from the bring-up

The four-card GLM release now serves coherently and calls tools correctly, so the engine works. What this plan covers is narrower and was only observable because it works: two defects in how that engine's reasoning and tool parsers frame their output. Both were measured against a live, healthy endpoint rather than inferred, and neither blocks serving — which is exactly why they belong here rather than holding up a bring-up that has shipped.

§2 — A closing think marker leaks into tool responses

A tool-use response that carries no thinking block still emits the literal closing marker of the reasoning parser in its adjacent text. A consumer reading that text sees a stray token that belongs to a block which was never opened. The reasoning parser and the tool parser are configured independently for this release, so the fix is a question of which one owns suppressing the marker when no thought was produced.

§3 — Reasoning consumes the whole output budget

A reasoning request spent its entire 512-token cap inside the thinking block and emitted no separate final text block before the response ended. The answer was correct and the thinking block was real, so nothing is broken; but a consumer asking a question and reading only the text block would receive nothing. Either the reservation must be split so a final block is always reachable, or the caller must be told that this release answers inside its thought for short budgets.

The launcher's per-release budgeting, which now derives an output reservation from the selected card's own context, is the natural place for a split to live if that is the chosen shape.

§4 — Done-when

  • A tool response carrying no thinking block contains no closing reasoning marker, asserted against a live engine rather than a fixture.
  • A reasoning request at a realistic output budget produces both a thinking block and a non-empty final text block, or the launcher states the behaviour at selection time so a consumer is not surprised by it.
  • Neither change alters tool-call correctness or coherence, re-checked by the same probes that proved them.

§ Decisions

Does the reasoning parser suppress its closing marker when no thought was produced, or does the tool path strip it?

Recommendation: the reasoning parser, because it is the component that owns the marker and the only one that knows whether a block was opened. Stripping downstream would leave every other consumer of that engine seeing the same stray token.

§ Followups

Both were observed on the live four-card release during its coherence proof, so both are reproducible against a running endpoint rather than needing a fixture. The stray closing marker appears in tool responses that carry no thinking block; the reasoning cap is consumed inside the thought so no separate final text block is emitted.
