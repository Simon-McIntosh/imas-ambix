§1 — Why this plan exists at all, which is the part worth reading

This work was already written down. It sat as followup f-dsc-003 on dsv41-flash-serve-characterisation, a plan whose status is done at an implementation fraction of 1.0 — and a followup on a completed plan is not tracked work, it is hidden work. Reckon excludes a completed plan from pending_work, from ready_now, and from every open path, so the row rendered on its own page, satisfied every continuation check, and appeared nowhere a human or an agent looks to decide what to do next. Measured on 2026-09-18: the project reported 27 plans in pending_work and the owning plan was not among them.

It had also acquired a second layer of invisibility. Its own text says it is "gated on the kt-kernel-split decision" — and that decision was locked on 2026-09-14, choice separate-ktransformers-env. So the row announced a blocker that had already been removed four days earlier, and nothing re-reads a gate clause once its decision lands. A reader skimming for actionable work would have skipped it twice: once because its plan was finished, once because it said it was blocked.

This plan exists so that neither is true any longer. It owns the work; its own lifecycle is what makes the work visible.

§2 — The constraint is local, and it is one wheel

Nothing upstream prevents the serving stack from running on the current interpreter. The floor is set by a single dependency that publishes no build for it, and which happens to share an environment with the engine that does the serving.

ComponentInterpreter it allowsWhere the limit comes from
PyTorchcurrentupstream, no local constraint
SGLangcurrentupstream, no local constraint
vLLMcurrentupstream, no local constraint
kt-kernel3.12 onlypublishes cp312 wheels and no others

Because the ktransformers engine shares the SGLang environment, that single row governs the whole serve. A sync to the current interpreter fails today, not because the serving stack cannot run there, but because one accelerator kernel sharing the environment cannot.

§3 — What this actually costs, which is a defect class rather than a defect

The repository formats its sources to the syntax of the interpreter the project targets. The serving environment parses them with an older one. So every time the formatter emits syntax the serving interpreter predates, something that was correct in the repository fails in the serve — and this has now happened four separate times.

That is the argument for doing the work: each individual occurrence looks like a small, quickly-fixed breakage, which is exactly why the underlying cause has survived four of them. Repairing the fifth instance costs less than this plan; removing the class is what this plan buys, and the class will keep producing instances at whatever rate the formatter advances.

The remedy follows directly from §2. The kernel does not need to share an environment with the engine — it needs to be reachable by it. Splitting them lets the serving environment follow the repository while the kernel stays on the interpreter its only published wheels support.

§4 — This needs a lane window, and that is the lead's to give

Rebuilding the serving environment stops the lane. That lane is not idle infrastructure: measured on 2026-09-18 it was carrying 32 concurrent requests at zero headroom, serving worker fleets belonging to four separate coordinators across the nova, imas-efit, imas-codex and imas-ambix projects. Taking it down is an irreversible action on shared infrastructure with an outward-facing effect on peers who did not ask for it, so it is not something an agent schedules on its own initiative.

This plan therefore carried no sprint membership for as long as no window existed — explicit backlog rather than work left unscheduled by omission. That membership has now been granted, but scheduling it does not authorise taking the lane: the two are separate permissions and only the first has been given. The standing rule that a serving lane is never hard-stopped still governs the rebuild — the window is a drain to a genuine zero held across samples, then the rebuild, and a drain that has not reached zero is not a window however long it has been waited on.

§5 — Done-when

  • The accelerator kernel resolves from its own environment, and the serving environment no longer contains it.
  • The serving environment syncs on the interpreter the repository targets, and the sync is reproducible from the project files after removing the environment entirely.
  • A source file carrying syntax the previous serving interpreter could not parse is imported successfully by the serve, which is the direct measure of the defect class being gone rather than a proxy for it.
  • A real generation succeeds against the rebuilt serve — a readiness probe is not the measure — and the lane document reports a measured state afterwards.
  • The rebuild is recorded with the lane's drained-to-zero evidence beside it, so the next window can be planned from what this one measured.
