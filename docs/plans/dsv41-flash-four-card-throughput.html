The cumulative-ratio trap is in the code, not only in the reading. imas_ambix/agent/serving_receipts.py computes prefix_cache_hit_rate as a lifetime ratio and assigns that same cumulative value to every emitted row, and a test codifies the behaviour. On two controlled snapshots differing by +2,000 queries and +1,800 hits — an interval truth of 0.9000 — the recorder reports 0.8253. That is the instrument four sessions read. Two operational findings that change the swap procedure. agent serve exposes no pool-size option, so agent serve deepseek-v4-1-flash cannot by itself produce the 14,999,808 pool §3 requires — the pool must become an explicit, reviewable setting rather than a hand-edit at serve time. And the survey reported that the standing lane refresher is a separate ambix-lane SLURM job which a profile shutdown will not stop, so two refreshers would race and re-publish the retired origin. That second finding is wrong for the running system, and the correction follows.

Correction — the lane document is published by the router, so the swap is simpler than the survey said. There is no ambix-lane job in squeue, yet lane.json is rewritten every thirty seconds. RouterApp carries an internal publish task on a thirty-second interval, and its own comment gives the reason it was moved there: a separate job "spent a core of a 30-core GPU reservation on one HTTP read every thirty seconds, while a peer's GPU work pended on Resources with two cards idle". The router "already survives serve rotations", and its resolver is a supplier invoked afresh on every resolution, so it re-reads the endpoint document rather than caching an upstream. Leave the router running through the swap — job 1271309 — and the lane reading follows the new serve within one interval.

Both mechanisms are real, which is the accurate version of this and corrects a first attempt at the correction. generate_lane_refresher_script is still in slurm.py and is reachable: agent lane --submit --refresh N calls it and submits a standing ambix-lane job. It is a supported path, not dead code. An earlier note here said nothing called it and that it should be deleted; that was wrong, and deleting it would have removed a live CLI feature.

So the codebase carries two publication mechanisms whose docstrings argue against each other, and the one in use is not the one that argues hardest. slurm.py makes the case for a separate job in exactly the terms the survey reported; router.py makes the opposite case, cites the reservation core the separate job wasted, and is what actually runs. The survey asked what the source says publishes the lane and got a true answer about the mechanism that is available rather than the one that is running — an aimed-instrument error, not carelessness, and one the source invites.

The swap-time consequence is a precondition, not a deletion. The scout's race is real but conditional: it needs an ambix-lane job to exist, and none does. So before the swap, require squeue to show no ambix-lane job, and if one has appeared, stop it by its exact id — never with --all, which would take the serving jobs too. Leave the router alone either way.

Done when: the receipts recorder emits per-interval query and hit deltas and an interval ratio alongside the retained cumulative fields, with the 0.9000 case as a test; a collector joins real clive stream evidence to receipt intervals and bins per-worker decode and prefill rate by width, refusing synthetic benchmark records; and the 14,999,808 pool is selectable through a reviewable setting. These are what make §3's done-when measurable at all.

§3 — The one thing that was never measured

The retired plan's §4 was to drive real agent traffic through V4.1 with clive workers. It was closed unrun, correctly, because the serve had been taken down by then. It is the only section of that plan that did not land, and it is the only measurement that could overturn the close.

The reason it matters is specific rather than hopeful. This lane's throughput problem is not decode — it is that the prefix cache returns 25.7% where multi-turn agent traffic should approach 90%, so roughly three quarters of every prompt is recomputed, and that recomputation is what evicts the next session's prefix. Turnover is pool ÷ prefill rate: about 165 seconds on V4-Flash's 2.8M pool, which is inside a worker's think-and-tool gap, so a prefix is often gone before its own next turn arrives.

V4.1's pool is 5.3× larger. At the same prefill rate that is roughly 880 seconds of prefix survival instead of 165 — comfortably beyond an agent turn gap. If the hit rate rises accordingly, prefill volume falls, and per-worker decode under real load rises toward the idle rate rather than collapsing to a seventh of it.

So the genuine question is a trade with a measured cost and an unmeasured benefit: V4.1 gives up 2.5× on raw decode and buys 5.3× on pool. On real agent traffic, which wins? V4-Flash keeps 86.6 unloaded and delivers 6.9–10.1 loaded; if V4.1 keeps a larger fraction of its 34.4, it could deliver more under load while being far worse on paper.

Done when: real clive workers have run sustained multi-turn work against a V4.1 serve, with per-worker decode binned by concurrency and the prefill rate recorded beside it, and a windowed internal prefix-cache hit rate taken as a distribution of per-interval deltas at a stated concurrency — not a cumulative ratio, which has misled four sessions on this lane. The comparison bins are V4-Flash at 27.0% and 10.1 tok/s for 10–14 concurrent, and 26.3% and 6.9 tok/s for 15–19.

§3a — The two arms must run the same traffic, and that has to be arranged in advance

§3 compares a V4-Flash arm and a V4.1 arm. If each arm improvises its own workload, the comparison measures the workload rather than the serve — and nothing above says otherwise, which is how this would have been missed. The measured problem on this lane is prefix reuse, and prefix reuse is a property of the prompts: two task sets with different context growth or different repetition produce different hit rates on an identical engine. The arms are hours apart and on different checkpoints, so the only thing that can hold the workload constant is a recorded artifact.

The V4-Flash arm therefore produces two deliverables, and the second is a prerequisite rather than a courtesy: the measurement, and a replayable task set — the concrete agent tasks, their order, their concurrency schedule, and the seed or fixture that makes the sequence reproducible. The V4.1 arm replays that artifact rather than authoring its own, and records that it did so. A V4.1 arm that cannot name the artifact it replayed has not produced a comparison.

The generator is real clive sessions — multi-turn, real tool calls, real context growth. It is explicitly not agent bench, whose prompt is a fixed single turn that barely touches the KV pool and is the exact shape §2 warns must not be compared against real traffic. The fleet runs inside one SLURM allocation on a *_debug partition, never on the login node.

One run, three results. The V4-Flash arm is also the post-measurement of the pre-registered draft-group veto test, whose baseline was taken with DSpark enabled and whose current serve has it disabled. The same windowed, width-binned instrument answers both questions, so the arm is dispatched once and reports the veto verdict against its own pre-registered bands alongside the comparison numbers.

§4 — Two structural handicaps, and whether either is removable

The retired plan named three candidate causes for 34.4 tok/s against the 300–507 the vendor reports on their own stack. One has since been settled — DSpark cannot start. The other two are properties of this checkpoint on Hopper rather than settings, and they bound how much §3 can possibly recover:

  • MXFP4 experts dequantise rather than using native FP4 tensor cores, because H200 is SM90 and FP4 silicon arrived with Blackwell. Not removable on this hardware at all.
  • Engram tables gathered from host memory rather than HBM. The tables are 196.6B parameters at FP8, about 183 GiB. Four cards hold 561 GB against a 511 GB checkpoint, so they cannot be resident; eight cards at 1128 GB could. This is the concrete content of "needs eight cards", and it is the one handicap that a topology change would remove.

✓ landed 2026-09-15 The third possibility is closed: the image carries the fix. Read from the SIF's own SquashFS source rather than the mutable tag — engine commit da64c5cb, SWA_WINDOW = 128 with PAGE_INDEX_ALIGNED_SIZE = 64 giving a derived prefill row width of 128 and zero occurrences of 1152 in the builder. §8a — How to prove a bind-mounted kernel patch is in the compiled artifact

This is the measure that binds, and it is written down because two weaker versions of it were accepted first. The subject is a one-line patch to a JIT-compiled CUDA header bind-mounted over the container's copy. The failure mode is specific: a patch present in the file and absent from the compiled kernel looks identical to a working patch from every angle except the one that matters, and the defect it exists to prevent is silent KV-cache corruption under load — nothing crashes to tell you.

First rejected version: show the patched file is bound and the diff is one line. Satisfiable while the kernel never recompiles. It asserts about the source, and the source is not what runs.

Second rejected version: bind a deliberately broken copy and show the compile fails naming that file. Better — it proves the bind reaches the compiler — but only on a cold cache. It does not exclude a warm cache populated before the bind existed, where the patched source is read and a stale artifact is used regardless.

Third rejected version, and the instructive one: using one persistent cache directory, compile unpatched to artifact A, bind the patch, compile to artifact B, and require B ≠ A. This has a hole that is invisible until named: "different" is also what a non-reproducible build produces. Embedded timestamps, absolute paths or a build id make every compile differ, so B ≠ A passes without the cache having been consulted at all, and the check reports success for a reason unrelated to its claim.

The rule the third version violates, stated generally because the control is only its instance. Ask what a check does on the worst input it could receive, not the expected one. If the answer is "passes, and more emphatically", the check is measuring its own form rather than its subject. That is a worse failure than a check that cannot fire and than one that fires wrongly, because its pass probability rises with the severity of the condition it exists to detect — it grows more convincing as it grows more vacuous, so the evidence feels strongest exactly where it is worth least. A compiler embedding a timestamp is the ideal subject for an artifact-inequality measure and the one it can say nothing about.

The measure, with the control that closes it — one extra compile:

StepArtifactRequirementWhat it establishes
compile unpatchedA—baseline
compile unpatched againA′A = A′the control: output is reproducible, so a later difference is attributable
bind patch, compileBB ≠ Athe measure: the bind reached the compiled artifact

Without the middle step, B ≠ A is consistent with both "the patch was compiled" and "this compiler never emits the same bytes twice". With it, the inequality can only come from the patch.

And A ≠ A′ is not a failed run — it is the finding. A non-reproducible artifact means no patch can ever be proven present by comparing artifacts, so verification must move to something derived from the source rather than from artifact identity: a symbol, a constant, or an instruction sequence the patch changes. Record that outcome as the result rather than retrying for a pass.

Two acceptable answers on the cache, and the second is better for the fleet. If the cache key derives from a hash of the source, the cache is content-addressed, a changed source can never hit a stale entry, and demonstrating the key derivation settles the question outright. If it does not, the bind is unsafe as a standing configuration and a fresh cache directory per launch becomes part of the deliverable — not a workaround to remember, because a rule with no check is how this class of defect returns.

§ Decisions

Is the 80 / 50 tok/s target per worker or per card?

Locked on the plan's own argument, which needs no measurement: per worker is the unit every baseline in this repository is expressed in, it is what a worker experiences, and per-card decode is not a quantity the engine reports because a single request is served by all four cards at once. The consequence is accepted rather than worked around — the 50 tok/s loaded target is above V4.1's measured 34.4 tok/s idle ceiling, so V4.1 cannot reach the target on four cards. Section 5 already provides for this: the live comparison is against V4-Flash's loaded per-worker figures, and beating those without reaching 50 is a real outcome. Reading the target per card would let a synthetic aggregate clear a bar no worker ever experiences.

Given §2, is §3 worth the lane downtime and a 511 GB checkpoint?

The lead authorised taking the four-card DSv4 serve down to serve this variant, which settles the lane-downtime half. Two facts found while scoping move the cost and the value in the same direction. The 511 GB download is already paid: the checkpoint is resident at /work/projects/imas_gpu/agents/deepseek-v4-1-flash, 476 GiB, with a committed serve profile beside it. And the competing explanation for this lane's prefix hit rate has just been eliminated on the live serve — the draft-group veto test reads 28.8 percent, inside its own pre-registered no-veto band of 17-40 and nowhere near the 88.9-100 a gating veto predicted. Removing the drafter did not move the hit rate, so pool turnover is the leading remaining candidate, and pool size is precisely what section 3 varies.
