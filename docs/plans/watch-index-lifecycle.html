§1 — What the two services were doing to GPFS, measured

On 2026-10-23 the reckon storage session found ambix-watch-publisher to be the largest load on GPFS on this workstation. It was reading about 49 GB a minute (about 800 MB/s), against about 1.6 GB a minute for every reckon monitor process combined. It had run like this for 2 days 8 hours, which plausibly explains mmfsd sitting near 150% CPU and plan writes taking over two minutes. Its sibling ambix-ingest was reading another 2.8 GB a minute. Both run as declared services of the fleet supervisor on 98dci4-clu-2068 (job 1291586), from ~/.config/fleet/services.json.

What the publisher does each iteration, and why it never rested:

  • It writes a 9–12 KB document from an 8.66 GB database on GPFS. ~/.cache/ambix/watch-index.sqlite3 sits in the home directory, which is GPFS. Its service log shows compute_seconds of 1,241 to 1,306 s for each of the last five cycles against a 300 s cadence, so it computed continuously. It ran at 71% of a core.
  • Each gauge read scans the whole table. TelemetryIndex.time_weighted_mean computes LAG/LEAD window functions over every row of sample: its only filter is ts_epoch IS NOT NULL, and the window bounds are applied after the scan. watch_document calls it once per card for each of the four ledger periods (1 hour, 1 day, 1 week, 1 month), which is up to 32 full scans per publication.
  • The fix was already planned and never built. On 2026-10-15, serving-record-warehouse §24 accepted the remaining whole-table scan as owned by the hourly rollup in its followup f-srw-020. That rollup was never dispatched. Meanwhile the cycle grew with the table: 78 s on 2026-10-02, 529–612 s on 2026-10-18, and 1,306 s on 2026-10-23.

What the ingest does each tick, and why it reads gigabytes to take in kilobytes:

  • Every 60 s, each grown file is read twice in full. For a file that grew, _was_rewritten hashes the whole consumed prefix to prove the file was not rewritten. _resume then reads that same prefix again (head = handle.read(start)) to seed the next digest. The cost grows with the file's size, not with what was appended.
  • The live serve's raw record is one 1.02 GB file, and its minute tier is 0.29 GB. Both are deepseek-v4-1-flash-1280470*.jsonl. They have not rolled daily, because serving-record-warehouse §21's daily roll takes effect only at the next serve restart. Two reads of 1.31 GB a minute is about 2.6 GB a minute, which matches the 2.8 GB a minute the storage session measured. One tick takes in about 50 KB.

§2 — The design: authority on GPFS, derived state on the node, one writer

The system has one authority: the receipts on GPFS, which the recorder appends to and nothing else writes. Everything else is derived from them and can be rebuilt. Each artefact therefore gets a place, a lifecycle and a deletion rule that follow from which of the two it is.

Five rules follow from that split, and every section below implements one of them:

  • An ingest tick costs the bytes it takes in (§3), not the size of the file they were appended to.
  • The derived index lives on the node, not on GPFS (§4). Its readers and its writer are on the fleet node, so every page it serves from GPFS is a remote read for no reason.
  • A read costs its window, not the history (§5). A period is a sum of whole hours from a rollup plus raw samples at its two edges.
  • One process owns the index (§6). The ingest is the only writer, and it publishes the document itself, so there is no second long-lived process, connection or lock contender.
  • Nothing useful is deleted. The only deletion of authority remains retire-raw's compaction-proven path. Logs and the old index are compressed into an archive rather than removed, and each archive is verified byte-identical before its original goes (§7). Pruning raw samples from the index is deferred to §9 until a rebuild has proven it loses nothing.

Why local disk and not /dev/shm. Both are node-local and both vanish with the allocation, so neither is more durable than the other. They differ in what they cost the fleet:

  • /dev/shm is memory. On this node it is a 63 GB tmpfs inside the 120 GB allocation that every orchestrator and worker shares. Its pages are charged as memory and cannot be evicted under pressure, so an 8.66 GB index that grows would hold that memory permanently.
  • Node-local /tmp is a 232 GB disk with 214 GB free. The kernel page cache keeps the hot pages in memory anyway and releases them when workers need the room.
  • After §5 the hot working set is the rollup table and the recent edge hours, which is small.

Why WAL. SQLite's write-ahead log lets readers proceed while the writer commits, which removes the database is locked class of failure. SQLite documents WAL as unsafe on network filesystems, and that is why it could not be used while the index lived on GPFS. On local disk it is the correct mode. §4 refuses WAL on a path whose filesystem is a network type, so a misconfigured path fails loudly rather than corrupting the index.

§3 — An ingest tick reads the bytes it takes in

The ingest keeps one running hashlib.sha256 object per source in memory across ticks. A tick updates it with the appended bytes only, so the stored prefix_sha stays the exact digest of the consumed region without re-reading it. Proving that the old bytes are unchanged is then split into two checks:

  • Every tick, for a source whose size or mtime has changed: a bounded probe. A source whose size and mtime match its recorded row is skipped without being opened, as today, since 106 of 108 files are unchanged on a typical tick. The one exception is a source whose content has changed since its last whole-prefix verification and whose verification has come due. That source is verified at the first tick after the interval, whether or not it changed on that tick, so a rewrite never escapes by happening before the interval. A closed file that has been fully verified since its last change is never opened again. For a changed source, the tick compares digests of the first 64 KiB of the file and of the 64 KiB before the recorded offset, which the index stores at consume time. It also checks that the size is not below the offset, that the inode is the same and that mtime has not gone backwards.
  • On a slower cadence: the whole-prefix digest, re-verified per source at most once per FULL_IDENTITY_INTERVAL (default 3,600 s). The process also builds each source's hash state once at start-up, with a full read that doubles as that verification.

The trade is stated in the decision below. A rewrite in place that touches neither probe window is detected within an hour, rather than within a tick. Receipts are append-only by contract, and no writer other than the recorder has ever touched one.

Write scope: imas_ambix/agent/telemetry_index.py (the source read path: _resume, _was_rewritten, _digest_of and the source columns they need), tests/test_telemetry_index.py.

Done when:

  • After every tick the stored prefix_sha equals sha256(file[:offset]) exactly.
  • The negative controls are each detected at the stated time:
    • a rewrite inside the head probe window, on the next tick;

§4 — The index lives on node-local disk, with compressed snapshots on GPFS

A new module, imas_ambix/agent/index_placement.py, owns where the index is and how it survives a node:

  • Resolve the path in this order:
    1. $AMBIX_WATCH_INDEX, when set;
    2. $FLEET_RUNTIME_DIR/ambix/watch-index.sqlite3, when the fleet runtime directory exists on a local filesystem;
    3. otherwise none.
    The agent watch command, run where no local index resolves, prints the published watch.json with its published_at instead of deriving anything. It never opens a GPFS copy of the index.
  • Journal mode: set PRAGMA journal_mode=WAL on open, and refuse when statfs reports a network filesystem type (GPFS, NFS, Lustre).
  • Snapshot once a day:
    1. copy the index with SQLite's online backup API to a temporary file on local disk;
    2. compress it with zstd (the standard library's compression.zstd);
    3. write it atomically as ~/.local/state/ambix/index-snapshots/watch-index-<UTC stamp>.sqlite3.zst;
    4. verify it by decompressing it and running PRAGMA quick_check;
    5. only then delete snapshots beyond the newest three verified ones.
  • Restore at ingest start, when the local index is missing:
    1. decompress the newest verified snapshot;
    2. if there is none, start empty, which is today's cold-build path;
    3. in either case, let the ingest catch up from each source's recorded offset. That catch-up is idempotent because samples are unique on (host, boot, inode, offset).
  • Wiring: the resolver replaces DEFAULT_INDEX_PATH (watch.py:91), which is today the one declaration of where the index lives. Every place that restates it calls the resolver instead, so no fallback can reach the GPFS path:
    • the two Path(index_path or DEFAULT_INDEX_PATH) fallbacks in watch.py;
    • the three --index help strings in cli.py;
    • the ingest command's own resolution.
    The argparse entry point in telemetry_ingest.py requires --index, so it never resolves a default, and it is left as it is.
  • The snapshot schedule is a closure that the ingest command in cli.py passes as the loop's on_tick. The closure captures the TelemetryIndex the command opened, and its docstring says so. The hook keeps its TickReport signature, and telemetry_ingest.py is not touched.
  • The public surface is one resolver in place of one constant. The network-filesystem refusal is an error the resolver raises, not a new option. The resolution order is an environment override, then a node-local root. That order follows the shape of imas_ambix/gs/artifact_resolution.py, which owns a different artefact (machine bundles) and is not extended.

Write scope: imas_ambix/agent/index_placement.py (new), tests/test_index_placement.py (new), imas_ambix/agent/cli.py, imas_ambix/agent/watch.py.

§5 — Watch reads hourly rollups: a read costs its window

This section takes over f-srw-020 from serving-record-warehouse unchanged in intent. One index rebuild introduces two things:

  • a name and kind dictionary, so that measurement carries integer keys instead of repeated strings;
  • an hourly rollup that the ingest maintains for each source (host, boot_id, inode), measurement and hour. Each rollup row carries:
    • the counter difference within the hour's counter runs;
    • the gauge's time integral;
    • the coverage seconds.

This rollup is not a second copy of the compaction tiers in telemetry_store.py. Those tiers, raw, minute and hour, are per receipt file, and the index already reads only the finest tier offered for each job. The rollup's axis is per source, per measurement and per hour. It carries gauge time integrals and coverage, which a file-level tier does not carry. The rollup reads samples the index already holds, and it does not replace any tier.

A period sums its whole hours from the rollup and reads raw samples only for the partial hours at its two edges. Every remaining raw-sample query is bounded to its window plus each source's last sample before the window, and all cards of one period are read in one statement rather than one statement per card.

Write scope: imas_ambix/agent/telemetry_index.py, imas_ambix/agent/watch.py, tests/test_telemetry_index.py, tests/test_agent_telemetry_watch.py. §6 — The ingest publishes the watch document, and the standalone publisher is retired

The ingest command composes publication into its on_tick hook:

  • When at least --publish-every seconds (default 300) have passed since the last publication attempt, successful or failed, it publishes. A failing derivation is therefore retried at the publication cadence, not on every 60 s tick, and the previous file keeps its published_at, which shows how old it is. It publishes by calling watch_publish.one_iteration with the resolved index path. That function already implements the whole contract: an atomic write through os.replace, published_at and compute_seconds at top level, mode 0644, one flushed line, and a failure leaving the previous file byte-identical. Nothing in it is re-implemented, so the contract keeps one owner.
  • A failed publication never fails the tick.
  • publish-watch keeps --once for manual use and loses its loop. This narrows the interface to one standing process.

The published document's path keeps one declaration. §4 added PUBLISHED_WATCH_PATH in watch.py beside watch_publish.DEFAULT_OUTPUT, and this section makes one of them refer to the other, so the reader and the producer cannot drift apart.

§10 — A schema change rebuilds the index instead of crash-looping the ingest

§5 made TelemetryIndex refuse an index without the name dictionary (the measurement dictionary requires an index rebuild). Nothing in the ingest command answers that refusal, so two ordinary events crash-loop the service under its supervisor:

  • Any restart of the running ingest. It still holds pre-§5 code in memory, and the editable install already serves §5, so a restart for any reason, a fleet-node failure included, opens the old-schema live index and raises.
  • A start with no local index. index_placement.restore_index decompresses the newest snapshot without checking its schema. Today the only snapshot was written by pre-§5 code, so the restored index is refused the same way.

The index holds nothing the receipts do not, so the correct answer to an incompatible schema is a rebuild from the receipts, never an exit:

  • The ingest command, finding an index that requires a rebuild, rebuilds it from the record directory with TelemetryIndex.rebuild into a sibling path. It moves the result into place only once the rebuild completes, prints one line naming the rebuild and its duration, and then runs the loop.
  • restore_index skips a snapshot whose schema the current code would refuse. It prints the skip, and falls back to the next snapshot or to the rebuild path. An incompatible snapshot is never deleted.

§9 — Raw samples age out of the index once rollups carry them (deferred)

Once §5 has landed, raw sample rows older than a horizon serve only edge hours that no period reaches. The horizon would be 35 days, covering the one-month period plus its edges. Removing those rows loses nothing, because the receipts and their compacted tiers on GPFS remain the authority. That is true only if a rebuild from the receipts reproduces the pruned hours' rollups exactly. This section is deferred until §8's breakdown says how much the pruning would recover, and until that reproduction is measured.

§ Decisions

Where does the live index live?

The two node-local choices are equally ephemeral. /dev/shm charges every page to the memory of the allocation every orchestrator and worker shares, and cannot release it under pressure. Local disk plus the page cache gives the same hot-read speed and lets the kernel evict. GPFS is what this plan exists to leave. The choice can be revised by the lead; it is one resolver.

How often is a source's whole consumed prefix re-verified?

Every tick re-reading the whole prefix costs about 2.6 GB of GPFS reads a minute today, and that cost grows with every file. The bounded probe still catches truncation, replacement and any change at the head or at the read point on the next tick. A rewrite confined to the middle of a file, which no writer has ever made, is caught within the interval. The interval is one constant.
