Day, week and month are the same number. The month row claims coverage 122× longer than the measurement history behind it. A reader takes it for a month of traffic; it is three hours of one serve.

Three independent causes, all of which must be fixed

A counter span has no concept of a serve. counter_span differences the last reading at or before each bound and refuses only when the two belong to different (host, boot). Every serve restarts its counters from zero, and many serves share one boot, so within a boot it will happily difference across job boundaries.

Coverage and totals are drawn from different populations. Coverage counts samples present in the window; totals come from one contiguous counter run. Nothing requires them to describe the same interval, and above they differ by two orders of magnitude.

The record speaks two vocabularies and the reader knows one. 256,424 rows carry these quantities under flat names written by an earlier recorder; 2,170 carry them under engine.*. A reader asking only for the new name sees three hours of a fifteen-day record and reports it as the whole.

§2 — What the store must be

The receipts are the record and are never rewritten. The recorder appends; nothing else writes to a receipts file. Every correction, re-keying or backfill happens in the store, which is derived. A store that edits its own source cannot be rebuilt from it, and rebuildability is the property that makes every other repair safe.

The store persists and is rebuildable, and those are different requirements. It survives across runs and accumulates, so the ordinary cost of reading is an append of what is new rather than a re-read of everything. And it can be discarded and reconstructed from the receipts alone, so no fact exists only inside it. A rebuild must produce a store equal to the appended one; that equality is a test, not an aspiration.

Ingest is idempotent and resumable. A file already read to a given offset is resumed from that offset, a file re-read from the start inserts nothing new, and a file that rolled or was compressed is recognised as the same source rather than as a new one. The existing index already keys a sample on (host, boot_id, inode, offset), which is the right shape; what is missing is that nothing runs it on a schedule and nothing keeps it.

Retention compacts, it does not delete. Raw rows roll into the minute and hour tiers the store already defines, and the tiers are what answer long windows. Compaction is the reason a month query does not scan a month of five-second samples, and it must never be the reason a month of history stops existing.

§3 — The aggregation rule the reporter got wrong

A cumulative counter is one serve's, over one boot, on one host. So the only correct way to total a window is to partition it into contiguous counter runs, difference within each run, and sum the results. A run ends at a serve restart, a reboot, a host change, or any gap the record cannot bridge.

Two figures must then be reported together and must describe the same thing: the total, and the union of the runs that contributed to it. Where that union is shorter than the requested window, the report says so rather than printing the window's length beside a partial total. A window the record cannot cover yields a partial figure that announces itself, or no figure — never a full-looking one.

This is the same rule the spine already applies twice, at counter_span across hosts and at _prefix_hit_rate across serves, and it is stated here once because it was rediscovered as a defect three separate times.

§4 — Per-model and per-caller, and the honest limit on "user"

The serve recorder answers per model already: every row carries served_name, profile_slug, gpus and the seven settings the engine reports. Several models serving at once are several recorders writing several files, which the store ingests as distinct sources. Nothing new is needed for that dimension beyond keying on it.

Per-caller is a different matter, and the data does not yet exist. The router's RequestReceipt carries the right fields — model, prompt, cached and completion tokens, time to first token, duration, status, and a sampling fraction — but two facts block it:

  • No request receipt has ever been written. The running router started 2026-09-16 22:30:08; the receipt sink was wired into it 2026-09-18 19:39:08, one day and twenty-one hours later, and corrected through 2026-09-21. The process serving today predates its own recorder, so the stream does not exist on disk.
  • caller_hint is not an identity. It is "{host}:{port}|{user-agent[:32]}", and the client port changes per connection. Its own docstring says it identifies a calling process "well enough to group its own turns". Counting distinct values counts connections. Dropping the port leaves a host, which on a login node is every session at once.

That second fact is not a prediction — it was measured as an outage. A per-consumer admission filter keyed on exactly this pair, client host joined with user-agent, lived in the router until 2026-09-14. Every harness process on one login node resolved to a single bucket, so a whole fleet shared six request slots: 402 of 1,075 requests refused over one afternoon, 37.4%, 252 of them queue timeouts burning thirty seconds each, while the engine sat at 0.0% KV occupancy. Host and user-agent are therefore refuted as a caller identity by measurement, not merely judged inadequate.

The channel already exists, and it already carries a constant

The reason per-caller attribution is cheap rather than expensive is that nothing new has to be transported. Every session already sends an identity field on every request: the generated launcher sets ANTHROPIC_AUTH_TOKEN to the fixed string clive-no-auth — its own comment says the value is non-secret and exists only because the client configuration requires the variable — and the router forwards every header it receives except host, content-length and transfer-encoding. So the field arrives, is relayed, and identifies nothing, because it is the same string for every caller.

Making it carry an identity is a launcher change and a recording change. The launcher knows what the router cannot see — which consumer, which session, which worker node, which project — and stamping that is what removes the per-connection port problem at its source: the identity comes from the client, not from the socket. An unknown header is ignored by the engine downstream, so a declared field costs the serve nothing.

What this buys is attribution of workload, not authentication of a principal, and the report must say so in its own output. Any client can claim any value, and on this workstation every process runs as the same OS user, so a column headed user would be false in two separate ways. The honest column is caller: which consumer, session or worker spent the tokens. That answers utilisation and engagement per consumer, which is what the question is actually for; it does not answer who a person is, and nothing recorded here can.

§5 — Who runs the ingest, and why it is not the recorder

The ingest belongs to neither the recorder nor the watcher, and the reasons are measured rather than stylistic.

Not the recorder. It runs inside the serve's allocation, lives and dies with that job, and sees only its own file. A store fed by the recorder would exist once per serve and vanish with it, which is the present defect restated. The recorder also already costs 4.25% of a core at its five-second cadence, measured, and it is the one process whose failure stops the record being written at all.

Not the watcher. It is an interactive reader. Making a person's report the thing that maintains the store means the store is current only as often as someone looks, the first look after a quiet week pays for the week, and two people looking at once contend on one file. The warehouse must be current for a reader who has not run yet.

A separate ingest, scheduled, owning the store alone. One writer, many readers. It scans the receipts directory, appends what is new from each source at its recorded offset, compacts what has aged past the raw tier, and exits. A watcher then only reads. This also matches how the record already behaves: receipts accumulate on shared storage whether or not anyone is watching, and the store should too.

Its cadence is a decision recorded below. Its placement is not: it reads shared GPFS and writes a store, needs no GPU and no serve, and must not run on the login node when the corpus is large — so a short scheduled CPU job, with the login node acceptable only while the whole scan stays under the seconds-scale bound the repository sets for interactive work.

Placement decided by the lead, 2026-10-01

The ingest is a standing loop, not a pass that exits: imas-ambix agent ingest runs one tick every 60 s and never stops on its own. The fleet allocation's supervisor starts it and keeps it running. That is the batch step of the CPU fleet job, which already owns the node sampler and every agent session. It is not a SLURM job on the GPU server's reservation, which spends a CPU slot beside the serve for work that needs no GPU. A recorded steady tick costs 0.29 s, so the loop holds about 0.5% of one core. It ends with the fleet allocation and starts again when the allocation does.

  • Who changes what. The fleet supervisor belongs to reckon. Reckon gains a generic way to start declared standing services, the same way it starts the node sampler. imas-ambix declares the ingest as one such service.
  • What leaves the repository. The ingest's SLURM service generator and its --submit and --dry-run options are removed, because a second, unused placement invites the wrong deploy.
  • What readers do once it runs. agent watch opens the index read-only and never ingests on a read. That is what removes the cold catch-up that took over 300 s on 2026-09-29.

Readings settled after the read-back. This placement replaces the placement paragraph above it, which proposed a short scheduled job.

  • The ingest is never submitted to SLURM, on any partition. It runs only as a process inside the fleet allocation.
  • The supervisor relaunches it whenever it exits, with a backoff of 5 s doubling to 300 s that resets after 10 minutes of steady running. It never kills a long tick for being slow, because a catch-up after a requeue can take 862 s.
  • The service declaration lives in ~/.config/fleet/services.json, and the mechanism lives in reckon. No launcher is written in imas-ambix.
  • It needs no allocation or memory reservation of its own, because it runs inside the fleet allocation.
  • The 5 s figure compared above is the ingest command's former default. Its default is now 60 s.
  • "Read-only" means a read-only handle. With no index, agent watch says so and creates none. A stale index is read as it is, and its last-ingest time is shown.

§6 — Queries the store must answer

Each of these is a gate, and each must state the coverage behind its answer under the §3 rule:

  • Aggregate tokens in, cached and out over any window, including windows spanning many serves and the whole record.
  • The same, split per model, for several models served concurrently.
  • The same, split per caller process, with the identity limit of §4 stated in the output rather than in a comment.
  • Throughput and utilisation over a window, derived from totals and the covered union rather than from the window's nominal length.
  • Cache hit rate per model, from the family-correct source, over a window the record actually covers.
  • A window the record cannot cover, answered as partial-with-coverage or declined — never as a full figure. This is the gate that would have caught today's month row.

The relay restart, and why it is not the serve

The relay and the model serve are two different SLURM jobs, and only one of them is untouchable. This is the fact that makes the restart cheap, and it is worth stating because the two are reached at one address and are easily spoken of as one thing:

Restarting the relay does not touch the model, does not unload a checkpoint, and does not surrender a card. Its node had 35 of 64 CPUs and 745 GB of memory free inside the group reservation when this was written, so the resubmit is granted immediately rather than queued.

What it does cost is every request in flight at that instant, and that is the whole cost. The relay is the fixed address every consumer holds, so the zero-downtime rotation that works for a serve — bring the new one up on its own port, let traffic move on health, stop the old one — has no analogue here. There is no second address to move to. The lane carried nine running requests when this was measured; the restart therefore waits for a genuine zero rather than a quiet-looking moment, the same rule that governs stopping a serve.

Sequence it last among the recording changes, and do it once. Each restart costs another set of in-flight turns, so the receipt must be carrying every field it is going to carry before the relay is cycled — including the declared caller identity, which is why that node runs first. Restarting now would start a stream that a second restart would then have to supersede, and a record that changes shape mid-stream is precisely what §1 measures the cost of.

§9 — The cost figure a reader sees is the realistic third-party price

What the cost column is for. It answers one question: what would this traffic have cost if a third-party provider had served the same model instead of our local lane? Both surfaces answer it wrongly today. imas-ambix agent watch and ~/.local/bin/gpu-watch each price a period through ledger_cost. That function bills our own cached input at the provider's cache-read rate and only the remainder at the prompt rate. Our cache hit rate runs 0.95, peaking at 0.9985, so the figure printed today sits at the low end of what a provider would really charge: it assumes the provider would also have given us our own cache.

Why our hit rate cannot transfer. We run one large, persistent radix cache. It holds long agent prefixes indefinitely and is shared by the whole fleet. A hosted endpoint serving the same model routes each request across replicas and providers, expires cached prefixes after minutes, and shares nothing between our sessions. A provider would bill most of what we serve from cache as fresh input, and the provider's prompt rate is roughly fifty times its cache-read rate. On agent traffic like ours, our hit rate will run far above anything a moving endpoint can reach, so our measured rate is the wrong input to the counterfactual.

What is displayed: the estimate, and only the estimate. Every surface that prints a cost prints exactly one cost figure, the best-effort estimate. It is computed from the price row that match_price already resolves for the served model from the cached provider price table. Each interval of the period is priced at the rate in force at that interval (price_at), as the watch command already prices a period today. With h the estimated third-party cache hit rate, it is:

h × input tokens × cache-read rate + (1 − h) × input tokens × prompt rate + output tokens × completion rate

Our own cached token count does not enter the formula. No minimum and no maximum is printed beside the estimate. The own-cache figure (what ledger_cost computes today) and the no-cache figure are not computed anywhere in the production path and not printed anywhere; only the tests compute them. Neither answers the question, and a band invites the reader to pick an endpoint. The coordinator comment on the counterfactual describes a band reported beside the estimate; that band is superseded by this paragraph at the lead's direction. Beside the figure, a short label gives h as a percentage, which of the three sources below it came from, and that source's citation: the measuring endpoint and date, the receipt window, or the provider page and date.

Where the estimated rate comes from, in order of preference.

  1. Measured on a third-party endpoint. A response from a hosted provider reports the cached share of its prompt tokens in its usage block. The measurement comes from agent turns that clive's OpenRouter opt-in lane sent to the same model, or from a deliberate re-send of recorded agent turns through that lane; either way the measurement covers at least fifty responses. h is the cached prompt tokens summed over those responses divided by the prompt tokens summed over them. It is the grounded figure, and once one has been obtained and recorded it wins.
  2. Derived from our own request timing. Once request receipts exist (after the relay restart in §7), compute it from the receipts without sending anything. For each caller, a request counts as a hit when the same caller's previous request to the same model arrived within the provider's published cache lifetime. The lifetime is timed from that previous request, so a prefix that keeps being re-sent stays cached; a gap of exactly the lifetime counts as a miss. h is the hit requests' prompt tokens over all prompt tokens.
  3. A published provider figure, with its provider page and date, used only until one of the two above has been obtained and recorded. The first node obtains a measurement whenever clive's OpenRouter opt-in lane can serve the model. It records a published figure only when the lane cannot, and says why in the record.

The estimate is recorded as one small JSON record of its own: h, the source kind, the citation and the observation time. It is kept beside the provider price table but never inside it, because that table is re-fetched and overwritten on its refresh interval. The watch command reads the record through one function in imas_ambix/agent/watch.py, and it is never a constant repeated inside two tools. Moving gpu-watch onto that function is the work of the separate gpu-watch consolidation followup, not of this section, so gpu-watch inherits the figure there rather than by a second implementation.

§8 — Compaction must integrate, not drop

Retiring raw is only safe once a coarser row carries what the raw rows carried in aggregate. It does not. Measured 2026-09-23 by compacting two serves that restart inside one minute of one boot:

One minute, one boot, a restart between two serves.
raw rows incompacted row out
job 1001, counter 1,000,000 then 1,500,000one row: job 1002, counter 20,000
job 1002, counter 0 then 20,000

The first serve's closing value is gone, and with it every token it served in that window. That is not a loss of time resolution, which is the only loss retention is meant to cost. It is a lost integral, and a retention policy built on the belief that tiers keep the integrals would delete the sole record of that traffic.

The cause is that a run is defined twice

The reader ends a run at a change of host, boot or job, or at any counter that fails to advance. The writer groups only by host and boot. Two definitions of one object, one in the compactor and one in the query, free to drift — and the drift is what discards the endpoint: a window holding two serves keeps the later job as its identity and the later value as its counter.

One predicate, shared by both. That is the repair at the root; everything below follows from it and none of it is sound without it.

What a compacted row has to carry

A row must never span a run boundary. Key the stride by job as well as host and boot, and split it wherever a counter fails to advance. Then identity is constant by construction, counters are monotonic within the row, and a window containing a restart yields two rows rather than one — which is correct, because it was two things.

A counter carries its opening as well as its closing. Today only the closing survives, so a row's own contribution cannot be read without its neighbours. With both, the advance is exact and local, and differencing across windows still works.

An observed count belongs to each leaf, not to the row. The row already carries observed.samples and observed.seconds, which is the honest denominator for the row. But a gauge null in nine of twelve samples has a mean resting on three, and the row cannot currently say so — the same absent-versus-zero distinction, one level down.

Where a peak is the quantity, a mean is not sufficient. An hour at 40% mean occupancy is consistent with a flat 40% and with a spike to 100%, and only one of those is a capacity problem. Carry the extremes for the leaves whose peaks are read that way.

The equality that licenses deletion

For any window, the partitioned total over the compacted rows equals the total over the raw rows they replace. Asserted across a restart, across a null-rich stretch, and through the tier chain, so that compacting raw to minute to hour agrees with compacting raw straight to hour. Until that equality is a test, deleting raw destroys measurements the tiers do not preserve, and the deletion cannot be undone.

The order is therefore: share the predicate, split the strides, carry the openings and the per-leaf counts, assert the equality, and only then retire anything. The first four are worth doing whether or not retention follows, because the minute and hour tiers are wrong today: every week or month window answered from them under-reports across every restart, which is the honesty this plan exists to establish.

One adjacent finding, because it has the same shape and will confuse this work if left unstated: the index ingests raw and compacted files into one sample table and no query distinguishes them. Its key_kind column names how a host and boot were resolved, not which tier a row came from. A reader asking for a window that both a raw file and its minute compaction cover is answered from both.

Retention, authorised by the lead on 2026-10-01

The lead has authorised deleting raw serving receipts. Deletion cannot be undone, so these rules bind every node that deletes, and they run in this order.

  1. The index reads one tier per job first. For each serve job, the index ingests exactly one of its files: the raw file when it exists, otherwise the minute tier, otherwise the hour tier. A window that a raw file and its compaction both cover is then counted once. When a raw file is later deleted, the index moves to that job's minute tier, and the totals do not change.
  2. Tiers are rebuilt from raw before anything is deleted. Every job's minute and hour files are regenerated from its raw file under the current compaction code, so each compacted row declares its per-leaf counts. The rebuild is checked per job: the partitioned totals of generation, prompt and uncached prompt tokens from raw, from minute and from hour must be equal.
  3. What may be deleted. A raw receipt file (<job>.jsonl) is eligible only if all three hold: its serve job is not running, its last row is more than 14 days old, and its rebuilt tiers passed the check in rule 2. Compacted tier files and the router's request receipts are never deleted. Neither is the file of a running job, whatever its age.
  4. How it is deleted. One command lists every eligible file before anything is removed: the job, the last row's time, the size and the check result. A second run with an explicit apply flag deletes exactly that list and prints each file as it removes it. The live sessions are told before the apply run.

Readings settled after the read-back. These govern wherever the rules above leave room.

  • Order. Rule 1 is merged and running in the ingest before any file is deleted. Rules 2 and 3 apply job by job: a job's raw file may be deleted once that job's own rebuild has passed. No global rebuild-everything gate is needed.
  • Which compaction code. "Current" means the corrected compaction now on main: one shared run predicate, strides split at a job change, openings carried through the tiers, and per-leaf counts and peak extremes. A rebuild under that code is what makes each row declare its counts.
  • The check is per window, not per job total. For every UTC hour the job spans, and for each of generation, prompt and uncached-prompt tokens, the partitioned total from raw, from minute and from hour must be equal exactly. A job fails if any one window or any one counter differs.
  • Which file the index reads. A raw file present on disk is the one the index reads, including a running job's growing file. A job with none of its three files has no data, and coverage reports its window as uncovered.
  • "Not running." The job id appears in no squeue state for the account, and the raw file has not been modified in the last 24 hours. Either sign of life makes the file ineligible.
  • "Older than 14 days." Measured from the timestamp of the file's last parseable row, not from its modification time.
  • The listing. For each eligible file it prints the job, the last row's time, the size, and the three totals per counter with pass or fail.
  • The listing is frozen. The listing run writes a manifest of the eligible files: path, size, SHA-256 and last row time. The apply run takes that manifest and deletes exactly its files. Before deleting each one, it confirms the file is still eligible and its SHA-256 is unchanged. A file that fails either test is skipped and reported, never deleted.
  • Who tells the sessions. The coordinator messages the live sessions before the apply run. The tool neither notifies anyone nor waits for acknowledgement.
  • An empty or unreadable raw file counts as absent. A raw file with no parseable row does not stop the fall-through, so the index reads that job's minute tier.
  • The re-check clock cannot add files. A file older than 14 days at listing is older still at apply. The apply re-check can only drop a file, never add one.
  • Request receipts means the router's request files: requests.jsonl and its rotations under ~/public/imas-ambix/. The retention command never opens the directory those live in.
  • squeue knows only live jobs. A job that has ended is absent from it. That is the intended reading: absence from squeue, together with 24 hours without a write, is the definition of not running.

§10 — gpu-watch reads the recorder: one source for every serving figure

What is wrong. gpu-watch lives in the dotfiles repository at bin/gpu-watch. It still computes every serving figure itself. It keeps a private ledger at ~/.cache/gpu-watch/serve-ledger.jsonl, scrapes the serve over HTTP, fetches its own OpenRouter price table, and carries its own copies of ledger_cost, match_price and price_at. imas-ambix agent watch derives the same quantities from the recorder's receipts. So the two tools can print different tokens, different cost and different utilisation for the same period, and a fix to one never reaches the other. The §9 cost estimate reaches only the repository command until this section lands.

What moves. Every serving-derived panel of gpu-watch gets its figures from imas-ambix agent watch --json and only renders them: the serve panel, the period ledger, and its cost column. gpu-watch's private ledger file, its ledger writer, its price fetch and its own ledger_cost, match_price, price_at and ledger_integrate are deleted. After this section, no serving figure is computed in the dotfiles repository. Consuming the JSON document rather than importing the package keeps gpu-watch a standalone script, and it makes the document the single contract between the two.

What does not move. gpu-watch is also an overview of the whole accelerator node, and the recorder cannot replace that half. The recorder sees only the cards inside its own serve's allocation; the other reservation group's cards and jobs are invisible to it. These stay exactly as they are:

  • the per-card utilisation and memory bars over a rolling window
  • the node-wide job table from squeue, covering every user and both reservation groups
  • host load
  • the one-second live mode

Where the two tools differ today. agent watch is a one-shot render: the serve rail, the serve's card readings from the receipts, and the period ledger with cost. It has no live mode, no window argument, no view of the other group's cards, and no job table. It covers the serving half of gpu-watch, not the node half. Its --record help text also still names ~/.local/share/ambix/receipts as the default. That was the stale default 48dea5e0 removed, so the help now contradicts the behaviour.

§ Decisions

What identifies a caller, given that caller_hint carries a per-connection port and the lane is keyless by default?

The channel already exists and already carries a value on every request, which was not known when the options were written. The generated launcher sets ANTHROPIC_AUTH_TOKEN to the fixed string clive-no-auth on every session, because the harness requires the variable to be set, and the router forwards every header it receives except host, content-length and transfer-encoding. So a client-declared identity needs no new transport, no key management and no change to the keyless posture: the launcher stamps what only it knows -- which consumer, which session, which worker node -- and the router records it. What it buys is attribution of workload, not authentication of a principal: any client can claim any value, and on a single-user workstation the OS user is the same for all of them, so the report must say caller and never user. The alternative that would authenticate, a key per consumer, ends the keyless lane for every consumer to gain a distinction nothing here needs. The two rejected options are refuted rather than merely dispreferred: host-only and the process hint were both tried as an admission key in the router until 2026-09-14, and every harness process on one login node collapsed into a single bucket -- 402 of 1,075 requests refused, 37.4%, while the engine sat at 0.0% KV occupancy.

How often does the scheduled ingest run?

Lead decision 2026-10-01: a standing loop at a 60 s cadence, started and kept alive by the fleet allocation's supervisor on the CPU fleet node, not a SLURM job on the GPU server's reservation. The recorded steady pass is 0.29 s, so a 60 s cadence costs about 0.5% of one core, keeps the ledger at most a minute stale, and stats the receipts directory twelve times less often than the 5 s default would.

How does gpu-watch get agent watch's period ledger without a 48 s read?

After reading stored timestamps, agent watch --json still takes about 48 s on the 4.8 GB index, because the week and month periods aggregate every raw sample. gpu-watch runs on the login node and cannot pay that per refresh.

Lead decision 2026-10-02. Publishing from the fleet node unblocks gpu-watch now, with a small change deployed before any rollup exists, and puts the 48 s computation on the fleet allocation instead of the login node. The rollups are the durable fix. They are a schema addition, so they are built in the same single index rebuild that also introduces the name/kind dictionary: one rebuild event producing both. That dictionary was recommended for f-srw-014 by the index-size breakdown (comment c-srw-index-size-breakdown-2026-10-02). The work is in f-srw-019 (publisher) and f-srw-020 (rollups with the dictionary).

How does the retention check treat hours in which no tier holds the counters?

Old-format receipt rows carry throughput rates and no cumulative token counters. compare_tiers counts an hour absent in every tier as a disagreement, so job 1273253 (115 such hours, 14 covered hours all equal) and the 19 pure old-format files can never become eligible.

Lead decision 2026-10-02. When no tier carries a counter in a given hour, there is nothing to verify, so that hour-and-counter pair is skipped rather than counted as a disagreement. The rows for the hour may still exist; what is absent is the counter. A file with no compared pair at all would be deleted on no evidence, so at least one compared pair is required. Hybrid files such as 1273253 become eligible when every compared pair agrees, and the 19 pure old-format files are kept. The exact rule, with absent, compared and agrees defined, is f-srw-018.

The aggregation rule is now in the store rather than in the reporter: TelemetryIndex.partitioned_total(name, start, end) partitions a window into contiguous counter runs, differences inside each run, sums the results, and returns the union of the contributing runs' spans as the coverage beside that total. watch._span and watch.period_row both read through it, so no period figure is a single outermost difference taken across a serve restart any more.
