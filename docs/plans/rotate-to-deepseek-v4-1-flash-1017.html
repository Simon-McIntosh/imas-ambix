§1 — Why rotate, and the evidence

The lane serves deepseek-ai/DeepSeek-V4.1-Flash, downloaded on 2026-09-14 to /work/projects/imas_gpu/agents/deepseek-v4-1-flash/model. On 2026-10-17 DeepSeek published deepseek-ai/DeepSeek-V4.1-Flash-1017 (commit 1bae0e1088993b9b82de08f59de5be5a34e42170) and switched its own API to it. It is a weights-only update: the same deepseek_v41 model type, 48 safetensors shards and 510.3 GB, against our local copy's 48 shards and 510.3 GB.

Independent measurements agree with the vendor's claim:

Two caveats are carried forward rather than dismissed. 1017 is verbose: Artificial Analysis counted 210M output tokens on its index against a median of 140M. One review also rates its reliability 3/5. A user report says it keeps the earlier tool-call pattern while using about 20% fewer tokens at each reasoning effort, but no source tested our parsers. That is why §3 exists.

§2 — Download the 1017 release into its own directory

The release lands in its own directory, deepseek-v4-1-flash-1017, for the reason the profile already gives: a shared directory would leave one release's shards beside the other's index, with no record of which checkpoint a run loaded. The profile deepseek-v4-1-flash gains a revision field pinning the commit above. Its hf_repo, weights_slug and revision name the 1017 release, and served_name stays deepseek-v4.1-flash (decision served-name). The September directory is kept until §5 has held for a week, as the rollback target.

Changing the profile does not touch the running serve. It is read only at launch, and nothing relaunches until §5. The download runs through imas-ambix agent download deepseek-v4-1-flash as a SLURM job, which resumes if cut, and the generator passes the pinned revision to the Hugging Face client.

§3 — The relaunch validates a tool call, not only a completion

imas-ambix agent restart already restores the saved script when the new engine fails readiness or a real completion. A completion is the wrong test for this rotation. The 1017 model card ships its prompt encoding as encoding/encoding.py and points production use to deepseek-recipe, with no Jinja template. Every worker on the lane makes tool calls. A release that completes text but returns tool calls our parser cannot read would pass validation and then fail every worker.

The validation step gains two probes, each sent to the new engine before it serves work. In the pause path that is before resume. In the overlap path it is before the held replacement is admitted to routing, so a failing probe leaves the old serve routed and cancels the replacement:

  • Tool call. A chat request offering one tool must come back as a parsed tool_calls entry with arguments that parse as JSON.
  • Anthropic dialect. The same tool call made through the dialect clive uses must return a tool_use block.

A probe for reasoning leaking into tool arguments is deliberately not added. The a-tool-call-carries-no-model-markup plan records that today's engine still leaks in some calls, so such a probe would fail its own positive control. That plan owns the probe and adds it to this validation once its fix lands.

Any probe failing restores the saved script and resumes, exactly as a failed completion does today. Before pausing anything, restart also runs a weights preflight: the profile's weights directory must hold model.safetensors.index.json and every shard it names. If not, the restart refuses and the lane is never paused. The preflight runs in a real restart and in --dry-run, which prints its verdict and never touches the lane.

No new module. The OpenAI-dialect probe already exists: bench.py's tool_use category offers the get_weather function through _chat(..., tools=...) and checks that tool_calls is non-empty and its arguments parse (bench.py:1280–1326). That check is factored into one public function, bench.check_tool_call, which both the bench and the restart validation call. The Anthropic-dialect check is added beside it as bench.check_tool_use. The restart wires both into the validate callback that run_reload and run_overlap already take (cli.py:2641). The new public surface is these two functions and the preflight. Nothing is retired, because the bench keeps its behaviour through the same function.

Write paths. imas_ambix/agent/cli.py (the restart validation and preflight), imas_ambix/agent/bench.py, tests/test_bench.py, tests/test_agent_restart_validation.py (new).

Done when.

  • Both probes pass against today's served engine through the router, run once from the fleet node, as the positive control on known-good weights. The log is committed at docs/evidence/fragments/rotate-to-deepseek-v4-1-flash-1017/serve-probe-positive-control.log.

§4 — Record which release answered

The served name stays deepseek-v4.1-flash through the rotation, so the name no longer says which weights answered. Two records carry it instead. The field is named checkpoint, because "release" already means two other things in this subsystem: registry.release_registration clears a held allocation, and clive's release id names a served endpoint.

  • Now. The serve's registration carries checkpoint: <hf_repo>@<revision>, written by the serve job from its profile at start, and endpoints.json publishes it on the engine's entry.
  • History. A registration is one file per job, rewritten in place and deleted when the job ends, so it cannot answer what served last week. The recorder's per-job file can. Each row already carries a serve_config section read from the engine. That section gains the engine's own reported model_path, and since every checkpoint has its own directory, every row then records the checkpoint that produced it. Each row also carries its job_id and timestamp, so the record says which checkpoint a job ran and when. This section deliberately adds no receipt-to-checkpoint join. A receipt's upstream is only node:port, which the pause path reuses and the overlap path duplicates on one host, so a correct join needs the router to record the serving job. That is a router change for the reader that first needs it, not part of this rotation.

A registration written before this section reads checkpoint: null, which a reader reports as unknown and never guesses. The new surface is one field on the registration and the endpoint, and one key in serve_config. Nothing is retired. No router change is needed.

Write paths. imas_ambix/agent/registry.py, imas_ambix/agent/slurm.py, imas_ambix/agent/serving_receipts.py, tests/test_agent_serve_registry.py, tests/test_agent_endpoint_discovery.py, tests/test_agent_serving_receipts.py.

Done when.

  • A registration written by a generated serve script carries the profile's hf_repo@revision as checkpoint, and endpoints.json publishes it on the engine's entry.
  • A recorder row built from a fixture engine report carries serve_config.model_path exactly as the engine reported it. An engine that reports none leaves the key absent rather than empty.
  • A registration with no checkpoint key is read as null and the document still builds.
  • Negative control: a profile with no revision writes <hf_repo>@unpinned, never a commit read from the downloaded directory's cache.

§5 — The rotation itself

An engine relaunch under the lane-cycle runbook (ops/lane-cycle/AGENTS.md), run by the coordinator as a reported inline exception. A cycle is an operational action on a shared service, so it is never a worker node. The router does not restart: an engine relaunch drops nothing, because in-flight requests finish and later arrivals wait in the router's FIFO. The steps:

agent restart chooses between two paths (--mode auto, its default; see hot-reload-the-serve), and this rotation accepts either:

  • Overlap. When the node has room for a second four-card serve, the replacement launches beside the running one. It is held out of routing until it has generated and passed §3's probes, then takes new work while the old one drains. Nothing pauses.
  • Pause. Otherwise the gate pauses, the engine drains to a measured zero, the serve is replaced, and the probes run before resume, inside the runbook's 40-minute bound.

The H200 node's other four cards are often allocated to another reservation group, so a pause is the likely path. The command's output names the path it took.

  1. Announce to the live coordinators, with the bound: no pause if overlap is chosen, and a pause of at most 40 minutes otherwise.
  2. From the main checkout, run imas-ambix agent restart deepseek-v4-1-flash --reason "rotate to V4.1-Flash-1017".
  3. Record in the landing record the path taken and its figures. For a pause: start, end, peak held and final failures. For an overlap: when the replacement was admitted to routing, and when the old serve drained.
  4. Watch the first hour of receipts. The failed-request share and the gate-expiry count must stay at the previous day's levels.

Rollback is the same command with the profile pointed back at the September directory, which §2 keeps for a week.

Done when.

  • endpoints.json shows the engine's checkpoint as deepseek-ai/DeepSeek-V4.1-Flash-1017@1bae0e10…, the recorder's newest row shows serve_config.model_path under deepseek-v4-1-flash-1017, and /v1/models still lists deepseek-v4.1-flash.
  • A reckon worker dispatched on the local lane after the cycle completes its node and promotes.
  • Over the first hour, the share of requests ending failed stays within one percentage point of the same hour the previous day.
  • Before the cycle, imas-ambix agent restart deepseek-v4-1-flash --dry-run prints the preflight's verdict as passing on the 1017 directory. §3 makes the preflight run in a dry run too.
  • Negative control: immediately before the cycle, the same --dry-run is run against a copy of the profile whose weights slug names an empty directory. It must print the preflight refusing, naming the missing index. A dry run skips the running-job check and never touches the lane, so this exercises the real path.

§6 — Is 1017 better on our work?

Public benchmarks put 1017 ahead of the September weights: +12 points on Vals' Terminal-Bench 4.0, and +6 on the Artificial Analysis index. Whether that holds on this lane's own work is a separate fact, and the lead asked for it to be measured. Every local-lane run is attributable to one checkpoint by the swap boundary, 2026-10-23T20:14:30Z, recorded in lane-cycles.jsonl with the two serve jobs it separated: 1280470 served the September weights, and 1294597 serves 1017. The recorder's model_path key cannot attribute the before window, because it only exists since §4 landed. That makes a before/after comparison free.

The comparison. Every clive-backend implementation run in every mounted project's ledger (~/Code/*/docs/state/*/runs/*.json) is split by dispatch time into a before window and an after window of equal length on each side of the boundary. Only records whose ledger role is implement are counted. That field separates review, test, investigate and documentation runs exactly, whereas the node-name prefix review-of- misses 1,136 of 2,739 review runs. Runs whose attempts straddle the boundary are excluded. Per window it reports:

  • promotion rate;
  • first-attempt gate pass rate;
  • the share of runs needing a repair or resume round;
  • mean independent-review score per dimension;
  • wall time per promoted run;
  • input, cached and output tokens per promoted run, joined from the request record by run id;
  • the share of requests that failed or aborted.

Each difference gets a 95% bootstrap interval over runs. The work mix shifts between windows, and the comparison says so: it reports the project mix of each window and repeats the main figures restricted to the projects present in both. Its verdict is one of four: better, no detectable difference, worse, or insufficient data. The last is returned whenever the positive control below fails. A paired comparison on identical tasks is the deferred bake-off (b300-bring-up-and-open-model-bakeoff §7). This section names it as the next step if the verdict is no detectable difference.

Write paths. docs/research/deepseek-1017-on-our-work.html (new), docs/figures/deepseek-1017-on-our-work (new). The analysis runs as a script recorded under docs/evidence/fragments/rotate-to-deepseek-v4-1-flash-1017/.

Done when.

  • The research document gives both windows' bounds, run counts and project mix, every metric above with its interval, and the verdict, with one figure of the per-metric differences.
  • The analysis script and its log are committed, and rerunning it reproduces the document's numbers.
  • Positive control, before any verdict: each window holds at least 30 runs, its run count matches an independent count of ledger files whose dispatched_at falls in the window, and the token join to the request record succeeds for at least 90% of runs. If any of these fails, the verdict is insufficient data, never no detectable difference.
  • Negative control: the same analysis with the boundary moved to a point inside the before window, splitting September runs from September runs, must pass the positive control and report no detectable difference on the promotion and first-attempt rates.

§ Decisions

Under what name is 1017 served?

Keeping the name means clive, every reckon backend and the price table keep working with no change at cutover. A new name would have to change in all of them in the same cycle, or workers fail. The cost is that the name alone no longer identifies the weights, so §4 records the release on the registration and in the endpoint document.
