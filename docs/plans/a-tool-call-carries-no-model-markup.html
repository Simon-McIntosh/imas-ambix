§1 — The defect, measured

Some tool calls from the local lane (clive, serving deepseek-v4.1-flash) reach the Claude Code worker with the model's own tool-call markup inside an argument. Reckon's figure-review evaluation on 2026-10-22 found it in run r-20261022T124012688022-clive-judges-pair-fig-01. The run's first Read carried a file_path that began with the right directory and then continued as ... followed by <｜DSML｜ calls> and <｜DSML｜ invoke name="Bash">. The model had emitted a second tool call, and it arrived as text inside the first call's argument instead of as a second call. The harness answered File does not exist. Nothing reported a parse failure, and the run went on to make a correct Read.

The census is ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/census.py. It counts a tool call when its tool_use input contains the markup token <｜DSML｜, the opening of a DSML block. A search that merely names the format does not write that token, and runs belonging to this plan are excluded, since they handle the markup on purpose. Run over clive runs launched from 2026-10-20T00:00Z to 2026-10-22T19:00Z (log ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/census-baseline.log), it found 20 of 93,565 tool calls in 1,383 runs: 10 Bash, 6 Edit and 4 Read, one in each of 20 runs. The rate is low, but every occurrence is silent, and it can turn a correct action into a failed one or, for Bash and Edit, into a different action. A second defect appeared beside it: in r-20261022T125056443470-clive-judges-pair-fig-07 a Read path was truncated to a literal .... That one carries no markup and may have a different cause.

The serve leaves parsing to the engine: [engine.parsers] tool_call = "auto" in imas_ambix/agent/profiles/deepseek-v4-1-flash.toml, which the engine resolves to deepseekv41. The profile records one correct tool-calling round trip as verification, which a single call cannot show to be false for this case.

§2 — Find the layer the markup survives

Why. The local lane points Claude Code straight at the routing origin (imas_ambix/agent/clive.py, ANTHROPIC_BASE_URL="$GLOBAL_ORIGIN"), and the router relays each response body chunk unchanged (RouterApp._relay in imas_ambix/agent/router.py); the LiteLLM proxy rendered by litellm_config.py serves only clive's hybrid branch. deepseek-v4.1-flash is served by SGLang (type = "sglang" in its profile, launched from the container /work/projects/imas_gpu/containers/sglang-dev-dsv41.sif), and SGLang takes no middleware, so imas-ambix's OrphanThinkMarkerMiddleware, which only the vLLM launch adds, is not on this path. That leaves two places the markup can survive, each needing a different fix. SGLang's DeepSeek-V4.1 tool-call parser, which [engine.parsers] tool_call = "auto" resolves to, can leave a second call's markup inside the first call's argument. Or the model itself can write the markup into a string argument, where no parser is wrong to leave it.

Change. The primary instrument is deterministic. The investigation runs SGLang's DeepSeek-V4.1 tool-call parser, the class under /sgl-workspace/sglang/python/sglang/srt/function_call/ in /work/projects/imas_gpu/containers/sglang-dev-dsv41.sif, offline on raw completion text written in the model's DSML format. The parser has two entry points, and the serve uses the second: detect_and_parse parses a whole completion, while parse_streaming_increment parses it chunk by chunk through its own buffer, and Claude Code consumes the serve as a stream, so the argument a worker received is the concatenation of the deltas the streaming path emitted. It feeds the parser cases built from what the leaked calls show: two well-formed calls in one completion; a second call that begins before the first call's argument closes; a call whose argument string contains the opening token. Each case goes through detect_and_parse whole, and through parse_streaming_increment under several chunkings: one character at a time; a cut at every position inside the opening token <｜DSML｜; and cuts at the token boundaries of the serve's own tokenizer, /work/projects/imas_gpu/agents/deepseek-v4-1-flash/model/tokenizer.json. It records, for each entry point and chunking, which inputs yield a call whose argument carries the token. It then classifies each leaked call §1's census names. The receipts hold no response body, so the completion the model actually emitted cannot be recovered, and attribution to one call is a consistency claim; the report says so. From the delivered argument in the run's stream.jsonl it builds one candidate completion for each shape that could have produced it: (a) two well-formed calls, the argument up to the opening token as the first and the text from the token onward as a second, closed DSML call block; (b) a first call whose argument is never closed before the second call's opening token, which is the delivered text written verbatim in DSML; (c) one call whose closed string argument contains the markup. It runs every candidate through both entry points under every chunking and records which shapes reproduce the delivered argument. Under the DSML grammar a parser that keeps the markup inside the argument for shape (b) or (c) is correct, because the model's output put it there; for shape (a) it is a parser defect. Because the request receipts hold no response body (RequestReceipt in imas_ambix/agent/request_receipts.py), and a leak occurs about once in 4,700 calls, a live replay is a supplement and not the evidence: where it is run, up to twenty samples a call for at least three leaked calls, its outcome is reported. It confirms with one traced response that the router relays the body unchanged. Each parser input and its output is saved as a replayable fixture under ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/fixtures/, for the leaking cases and for three clean ones; §3 replays those fixtures.

Write paths: ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/report.md, ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/fixtures/.

Done when the report lists every leaked call §1's census finds over its baseline window by run and tool, the twenty in ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/census-baseline.log, and reports any later ones separately. It shows the parser run: the container and the parser class and file it imported, each input case, and, for detect_and_parse and for each chunking through parse_streaming_increment, the parsed calls it returned, quoted, with the streamed argument deltas concatenated. For every leaked call, it quotes the candidate completions it built and states which shapes reproduce the delivered argument, through which entry point and chunking. It names one origin, as a consistency claim over the leaked calls. The origin is the parser when a shape-(a) completion reproduces a delivered argument through either entry point under any chunking: that is a demonstrated parser defect whose output matches the leak, and the report names the entry point and the chunking. The origin is the model when no shape-(a) completion reproduces any delivered argument: the report then names, for each leaked call, whether shape (b), shape (c) or both reproduce it, because §3 chooses between recovery in the parser and a guard on delivery according to that shape. It reports any replay outcomes and the router check. ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/fixtures/ holds each parser input and output, for the leaking cases and three clean ones. It also says whether the truncated-path case in fig-07 shares that origin; if it does not, §4 holds it. Every log is written under the run directory, starts with its revision and the literal command, and ends in EXIT=. Negative control: three clean completions, each with one well-formed call, parse to that one call with no token in its argument, through both entry points under every chunking.

§3 — Stop the markup at the layer that leaks it

Why. §2 found that the model writes the markup and the parser delivers it correctly, so no parser change can remove it. The one layer every local-lane response passes through is the router (RouterApp._relay in imas_ambix/agent/router.py), and it already has both halves of a guard. It reads every SSE line before forwarding it (StreamAccounting.feed in imas_ambix/agent/request_receipts.py). And its operator cut already ends a stream in a close form that a streaming client retries, which keeps the turn alive. A leak occurs about once in 4,700 calls, so a retried turn almost always samples a clean call. Work that legitimately mentions the markup must still pass: this plan's own census and fixtures quote the bare token. So the guard matches a structural opening, the token followed by a tag name, and not the token alone.

Change. A new module, imas_ambix/agent/tool_input_markup.py, owns the guard's logic: the matcher for a structural DSML opening (the token <｜DSML｜, optional whitespace, then calls, invoke or parameter), and a per-response watch. The watch accumulates each tool_use content block's input_json_delta text, so it catches an opening split across deltas or across relayed chunks, and it reports when a block's input carries one. It matches against the accumulated input with JSON string escapes decoded, so an opening the serve writes as \u003c or \uff5c is matched too. StreamAccounting (imas_ambix/agent/request_receipts.py) stays the relay's only SSE line parser: it hands each event record it decodes to the watch it holds, so the guard adds no second line split, oversize-line rule or JSON-decoding stance. RouterApp._relay reads the watch's verdict after each feed and before it forwards the chunk. On a firing it forwards nothing more. The relay's way of ending a stream so a streaming client retries it, today written inline in the operator cut's close branch, is factored into one helper that both the cut and the guard call. The guard always takes the close form, whatever the gate's cut_form setting and whether or not the relay was armed by watch_cut, because its purpose is a retried turn and the cut setting governs cuts only. The receipt records the request as STATUS_ABORTED, as a cut does, so no receipt reader counts a new status. Each firing and each pass-through appends one JSON line to tool-input-markup.jsonl beside the request receipts, in the directory the router's receipt sink writes. The line names the time, the request-body digest, the matched opening and whether it was a firing or a pass-through, and it is what a census counts. A random leak almost never recurs when the turn is sampled again, but a deliberate quote does: this plan's own fixtures carry structural openings. So the guard stops a given request at most once. It keeps the digests of the request bodies it stopped in the last hour. When an identical request body produces a structural opening again, the relay forwards that response untouched and logs it as a pass-through. A turn that must quote the markup therefore costs one retry, never a livelock. The guard covers streamed responses, which is how Claude Code requests a turn; a non-streaming response passes unguarded, and the node names that limit in its report.

Done when unit tests for tool_input_markup.py show the matcher firing on every structural opening and on one split at each byte position across two deltas, and not firing on the bare token without a tag name. Relay tests extending tests/test_agent_router_cut.py and tests/test_agent_router.py drive RouterApp._relay against a fake upstream that streams each leaked fixture in ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/fixtures/ as the serve would: the tool input split into input_json_delta events at the fixture's tokenizer-boundary cuts and at every cut inside the opening token. For every leaked fixture, the client receives no content_block_stop for the block carrying the opening and no message_stop, so the tool call is never completed. The stream ends through the shared ending helper, and the receipt reads STATUS_ABORTED. The existing cut tests pass unchanged through the factored helper. A relay test sends one request body twice against an upstream that streams a structural opening both times: the first response is stopped, the second is forwarded byte-identical and logged as a pass-through, and a different request body producing the same opening is stopped again. The three clean fixtures, and three streams whose tool input quotes the bare token without a tag name, relay byte-identical to the relay without the guard. A population pass imports the matcher from tool_input_markup.py and the run walk from ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/census.py, so neither is written twice. It renders every clive tool input in §1's baseline window (the 93,565 calls that census reads) as input_json_delta events and runs the watch over them. Its log, under ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/, lists every firing by run and tool. It fires on exactly the twenty leaked calls, all of which carry a structural opening, and any firing outside them is listed separately with the text that matched. Before the relay tests are built, one real stream captured from the serve through the router, a tool_use whose input holds < and a non-ASCII character, is saved as a fixture and shows how the serve encodes them. The relay tests stream the leaked fixtures in that encoding, and one test streams them JSON-escaped. Tests and the population pass run on the fleet node in place, the population pass in the foreground. Negative control: with the watch's verdict ignored by the relay, every leaked-stream test fails, because the client receives the block's content_block_stop.

§5 — The guard runs on the serving router

Why. The guard protects nothing until the router serving the local lane runs it. That router serves every session on the workstation, so restarting it interrupts all of them. The restart is the lead's decision, not a node's.

Change. Once the lead has restarted the serving router on a revision that carries §3, a node confirms that the running router holds the guard: the module the serving process imported carries the guard's symbol. It then counts the guard live: census.py over clive runs launched after the restart, and the receipts' guard status over the same window.

Done when ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/census.py, run over at least 300 clive runs launched after the restart, finds no leaked call, and its log is recorded beside the baseline. At the baseline rate those runs would carry about four leaked calls. The report gives, from the router's per-firing log lines over the same window, the number of firings and of pass-throughs. A firing is recorded on its receipt as an ordinary abort, so the log line is the only source that tells it apart. For each firing, the report says whether the retried turn went on to complete. Negative control: the same census over the 300 clive runs launched before the restart finds at least one leaked call.

§6 — Reasoning text that reaches an executed argument

Why. In §2's resumed run, the model wrote its reasoning prose as a Bash call's command, and the shell ran it. The > characters in the prose created two empty files in the worktree. §3's guard matches DSML structure, which reasoning prose does not carry, so a prose leak would pass it, and in a command argument it executes.

Change. An investigation measures how often the model's reasoning text reaches a tool argument, over §1's baseline window, with two candidate signatures: a tool input containing </think>, and a Bash command that bash -n rejects. For each signature it counts the firings by run and tool, quotes three examples, and counts the overlap with the twenty structural leaks. It then states whether that signature is narrow enough for a guard to match, with its firings outside the leaks quoted.

Done when ~/.config/reckon/crew/reports/imas-ambix/a-tool-call-carries-no-model-markup/reasoning-leak.md gives, for each signature, its firing count over the 1,383 baseline runs by run and tool, three quoted examples, its overlap with the twenty leaked calls, and a stated verdict on whether a guard can match it. The known prose call in r-20261023T000714944866-dsml-markup-leak-origin (its resume-1.jsonl, the Bash call whose command begins with reasoning text) is counted for this check, though census runs normally exclude this plan's nodes. Every log is written under the run directory, starts with its revision and the literal command, and ends in EXIT=. Positive control: at least one signature flags the known prose call; a signature that misses it is reported as missing it.
