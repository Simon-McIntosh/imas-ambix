Second machine on the declared-map substrate

JT-60SA Machine Map for Equilibrium Reconstruction

MAST is read through a declared machine map and a format-scoped transform engine. JT-60SA is the next machine on the left of that diagram: author its map, prove its conventions against data, and serve its pulses through the same engines. The driving use case is equilibrium reconstruction — recover the SELENE equilibrium from mapped coil currents and magnetics — because it exercises every one of the five first-pass IDSs and gives a comparator that cannot be satisfied by a map that is merely well-formed.

§1 — The map lives in ambix; codex supplies discovery and evidence

Two repositories could hold a JT-60SA map, and both already carry part of the answer. imas-codex has a JT-60SA facility configuration, an EDAS/EDDB signal scanner that enumerates the self-describing catalogue over ssh (eddbreadCatTable, eddbreadTable), wiki-site adapters for the Naka TWiki (manuals, the discharge-parameter handbook, equilibrium-code pages), and an LLM pipeline that proposes IMASMapping nodes with typed MappingEvidence. imas-ambix has the executable half: a LinkML machine-map schema with no conditional or code-hook slot, range-scoped maps selected by shot, two store engines (zarr, netCDF) that apply any map, a compiled affine signal map with COCOS factors resolved at the read boundary, a lazy transform-aware view over immutable arrays, and an evidence-based convention scorer. MAST runs through all of it today with 254 bindings; DIII-D has a one-binding source-only map.

The division is already written into ambix: the signal-map module states that discovery systems may produce a large evidence graph, that the ambix runtime does not query that graph, and that it loads a reviewed, content-addressed distillation instead. The north star makes the same split load-bearing — machine identity enters only through the shipped description and the deterministic forwards, and every learned component is geometry-conditioned by construction. A map is therefore part of the physics substrate the estimator ships with, not a discovery artefact.

Decision proposed and argued here, locked below: JT-60SA maps are persisted in ambix as packaged, versioned documents under imas_ambix/data/machine_maps/jt-60sa.json (description bindings) and imas_ambix/data/maps/jt-60sa/<system>.json (pulse signal maps), each carrying evidence receipts that point back at codex graph nodes, handbook pages and PIDs. Codex remains the place where candidates are discovered, where the handbook and PID tables are indexed, and where an LLM proposal is scored; it does not become the runtime authority for what a channel means. Nova stays machine-agnostic: it consumes the DD-shaped output in COCOS 17 through its existing IDS readers (nova.imas.machine, nova.imas.equilibrium) and carries no JT-60SA module — the earlier nova/projects/JT-60SA scripts were already moved out into the standalone nakamap package in October 2024, which is exactly the boundary this plan keeps.

§2 — Map schema: the ambix contract, with a tokamap export

UKAEA's tokamap is the community interchange format for IMAS mappings: a mappings.cfg.json with metadata, groups (one per IDS) and shot partitions selected by MAX_BELOW, MIN_ABOVE, EXACT or CLOSEST; a globals.json of templated constants; and per-group mappings.json keyed by DD path with five map types — VALUE, DIMENSION, DATA_SOURCE (with args, offset, scale, slice), EXPR and CUSTOM. It is executed by libtokamap and UDA's JSON mapping plugin, and the MAST mappings use it with Inja templating ({{ at(flux_loop_names, indices.0) }}) and bare scale factors ("SCALE": -1.0 on flux_loop[#]/flux).

The comparison below is why tokamap is a target of this plan rather than its source of truth. Everything the ambix schema was built to make structural — a declared source unit beside the target unit, a named sign convention instead of a bare -1.0, a machine-wide source COCOS with per-binding override, a validation state and evidence string per binding, source qualifications for arrays that exist but cannot be bound, and range-scoped selection with no conditional — has no slot in tokamap. A tokamap file can be generated from an ambix map losslessly in the forward direction (unit factor × sign × COCOS factor collapse into scale; DD-path keys and partitions are mechanical), but the reverse loses the provenance and the convention claims this plan exists to prove.

The rule is a declared store layout. A store declared per-shot keeps today's behaviour: open resolves {root}/{int(shot)} and reads one {binding}.nc per binding. §5 — Pulse bindings and the EDDB census

The pulse signal maps bind EDDB channels to DD leaves with a compiled affine transform. They are read by the loader that reads MAST's, imas_ambix/data/signal_map.py load_packaged_signal_map(machine, system), which resolves PACKAGED_MAP_ROOT/<machine>/<system>.json and refuses a file whose declared machine and system differ from the path; jt-60sa already matches its component pattern, so the JT-60SA maps add files and no loader. Known from the commissioning-shot tables: MMSYS/cur{CS1..CS4,EF1..EF6}{HiTe,LKAT} in A are the pf_active circuit currents, with the two chains recorded as ranked sources rather than silently preferring one; MMSYS/cur1TFLKAT and cur2TFLKAT are the TF current; PSRC/Ip is the plasma current for magnetics/ip/data, in A (measured 2026-10-06 on E101154: unit attribute A, peak 9.99e5 A, so the unit factor is 1; the commissioning tables' kA reading was wrong). What is not yet known is where the raw flux loops and pickup coils live for a plasma shot and how many there are — the candidates are MDAC (264 channels, the magnetic data-acquisition controller), PSRC (312 channels) and MAG on an E-shot — and whether EDDB exposes them as separate dnames or as multi-channel arrays.

§6 — Prove the conventions: vacuum shots, COCOS scoring, DD unit checks

A map that binds names is not yet a transform; MAST taught that the convention must be identified from data and proved for both current signs rather than asserted. JT-60SA offers a cleaner instrument than MAST had: the C-series commissioning shots drive the superconducting coils with no plasma, so every loop flux and probe field is a deterministic function of the measured coil currents and the declared geometry. The prediction comes from ambix's own forward model, the one the §7 reconstruction's vacuum term and MAST's vacuum-stratum validation already use, so the §6 verdicts and the §7 residual share one operator. imas_ambix/gs/operator.py build_operator assembles the geometry-only Green's matrices from the §4 description's geometry, and ForwardOperator.vacuum_prediction gives the PF-only loop flux and probe field for a vector of coil currents. The coil currents reach the operator's G_pf columns through ForwardOperator.assemble_pf_currents, unchanged. It reads each conductor's declared drive channel, which build_operator takes from the geometry's conductors, and MAST's label-to-amc table is only the fallback for geometry that declares none. So the JT-60SA catalogue declares the MMSYS coil-current channels as its coils' drive, and no placement step is added. Nova's Biot–Savart operators are not a second forward model here. Comparison against the measured channel fixes, per channel, the loop sign, the probe sensitive axis, the unit factor and whether the declared position is consistent — exactly the adjudication that settled MAST's nineteen disputed loop positions. The probe sensitive axis it fixes is what lets the 17 stored probe poloidal_angle values, which §4 records as a source qualification, be bound. That binding needs three changes, and §6 owns all three. First, a pol_angle_like transformation class in the COCOS factor table. The table lives in nova (nova/io/cocos.py TRANSFORMATIONS), and imas_ambix/cocos.py canonical_factor only delegates to it, so the class is added in nova, through a node in nova's own repository, and ambix keeps delegating rather than growing a second table. It is a generic COCOS transformation that any machine's probe angle needs, so it is not the JT-60SA-specific addition to nova that §7 rules out. That class carries only the COCOS-digit factor. Whether a source's angle runs opposite to DDv4's is a separate fact, and the binding already has the slot for it: sign_convention negate or identity, set from §6's measurement. Ambix holds two directed-angle helpers in imas_ambix/cocos.py. project_poloidal_field is in use (the forward operator, imas_ambix/gs/operator.py, projects predicted fields with it), so the vacuum prediction reuses it unchanged. mast_angle_to_canonical has no production caller (its only caller is its own test in tests/test_cocos.py, which retires with it), and the negation it hard-codes is what a binding's sign_convention negate expresses, so §6 retires it. The interface account: nova gains one transformation class, and ambix retires one public definition and adds none. Second, an emit path that lets a description binding whose sense §6 has now measured stop being unknown-unvalidated. Third, the angle reaches the geometry table through the selector §4 built rather than a parallel read: imas_ambix/data/description_reader.py read_geometry_table applies nothing for probe_angle_source description today, so that branch fills each probe's angle from the emitted poloidal_angle, beside the acquisition-address branch's _supply_declared_probe_angles. geometry_adapter._b_probes keeps building probes without an angle, and the catalogue's declared source decides who supplies it. Each JT-60SA verdict is recorded as MAST's are, as a FluxLoopPositionDeclaration over the shot range it was measured on, undecided verdicts included, and read back through MachineMapCatalog.flux_loop_positions_for, so the reader stays machine-agnostic. A channel whose vacuum prediction does not track its measurement with slope near one is left unknown-unvalidated and reported, never forced.

The COCOS of the source is then identified rather than assumed. For the raw side, the sign products that the Sauter and Medvedev coefficients constrain are read from plasma shots: Ip against the sign of poloidal flux change at the loops, toroidal field polarity from the TF current, the handedness implied by q from FAME. That computation already has an owner, imas_ambix/data/cocos_convention.py: its score_convention, score_conventions and surviving_conventions take any cohort of ShotSignObservation, with the MAST table only as the default, and format_sign_report writes the sign report this section's done-when names, so JT-60SA supplies an observation cohort to it rather than a second scorer. The EDDB cache is a {shot}.zarr/{category}/{dname} store that the zarr engine already reads as {source_group}/{source_array}, so the §5 JT-60SA bindings serve it, and MAST's catalogue reproduces today's reads. No parallel EDDB observation reader is added. For the equilibrium side, the SELENE and FAME outputs are scored on the convention scorer's tests (edge-minus-axis flux sense, flux-per-radian versus total flux by integrating the Grad–Shafranov current, q sign). The shipped entry point, imas_ambix/challenge/convention.py measure_diiid_convention, reads the DIII-D challenge corpus's own keys and accepts no SELENE or FAME record; the reusable part is its Grad–Shafranov current integral, _integrated_current. §6 therefore generalises the entry point to take an equilibrium record through a loader, with the DIII-D corpus as its first loader and SELENE and FAME as the next, rather than writing a second scorer. §7 — Equilibrium: FAME scalars first, SELENE maps second, then the reconstruction gate

The equilibrium IDS is mapped in two rungs. The first binds the FAME real-time scalars — plasma current, poloidal and toroidal beta, normalised beta, internal inductance, axis position, X-point height, strike-point angles, boundary gaps, Bt·R — to equilibrium/time_slice/global_quantities and boundary leaves and to vacuum_toroidal_field. These are time series in EDDB, so they ride the §3 path unchanged. The second rung reaches the offline SELENE equilibria: the server holds the SELENE sources, the equilibrium database client (client_eqdbms) and the FAME reader (eqdbget), and the Code TWiki documents the equilibrium codes. That rung needs a reader for the EQDB record (psi on its grid, boundary, p′ and FF′ or their profiles) wrapped in the same remote-extractor contract, and a COCOS verdict from §6 before any map is written into profiles_2d/psi. The EQDB read extends the §3 extractor rather than sitting beside it, but its request and record are not channels. ChannelRequest names (shot, category, dname) and the batch carries (channel, time) arrays, while an EQDB request names a shot and an equilibrium record, and its answer is psi on a two-dimensional grid with its boundary and profiles. So imas_ambix/data/eddb_remote.py gains one request type and one record type for EQDB beside ChannelRequest and ChannelRecord, rather than widening the channel types. RemoteEddbExtractor dispatches on the request type and keeps what is not channel-shaped: the per-request refusal contract, and the niced, module-loaded remote command over SshTransport. encode_batch and decode_batch gain the EQDB record's framing beside the channel framing, and the remote side calls eqdbget through the EQDB client rather than eddb_pwrapper. The two new public types are the section's interface addition; they retire nothing, because no equilibrium-database request type exists. The fields of the EQDB record are settled with the open question eqdb-reader. Its records land in the same store, owned by imas_ambix/data/eddb.py: write_channel writes only a (channel, time) array with a sibling time vector, and an EQDB record is psi on a two-dimensional grid with its boundary and profiles, so eddb.py gains a grid record writer beside write_channel under the same {shot}.zarr/{category}/{name} layout and the same refuse-to-overwrite rule, rather than a second store over JT60SA_ROOT. The two writers must share the store's invariants, and today two of them are inline statements in write_channel's body, not code a second writer could call: the pulse group's EDDB_TOKEN_ATTR token match and the overwrite refusal. So the node that adds the grid writer first extracts them from write_channel into private helpers in eddb.py: one that opens a pulse group and enforces its EDDB token, and one that refuses an existing record. write_channel then calls them, with its tests unchanged, and the grid writer calls the same helpers with _channel_present, so the token and overwrite contract has one implementation and cannot drift between the two writers. That writer's array layout waits on the open question eqdb-reader, which settles the record shape. It retires nothing, because no equilibrium-database reader exists in ambix.

The reconstruction gate is what makes the map honest. The spine reads JT-60SA geometry through gs/artifact_resolution.py with a JT-60SA pin rather than through a second resolver, so resolve_machine_description gains a machine to resolve: its pins, today the single PINNED_SEMANTIC_IDENTITY, PINNED_PHYSICAL_DIGEST and PINNED_REGISTRY_DIGEST constants, become a table keyed by machine, and author_pinned_description, which hard-imports nova.imas.mast_geometry, takes each machine's authoring route from that table. The selection path is pinned to MAST as well: gs/machine_selection.py ArtifactMachineSelector.select resolves a shot through gs/machine_identity.py identity_for_shot, whose default_registry is nova's MAST geometry registry, and reads channels with read_acquisition_channels at its default machine. The selector therefore takes the machine from the catalogue the shot belongs to and passes it to the identity registry, the pin table and the acquisition read, rather than JT-60SA growing a selector of its own. No file maps a shot to a catalogue today, and a JT-60SA pulse integer (E101173 is 101173) cannot be told from another machine's shot number by value, so the machine is never inferred: the frozen shot set declares it. The machine-map registry cannot own that route, because a catalogue's ranges are scoped to its own machine and overlap across machines (DIII-D's one map spans 0–2147483647, covering every MAST and JT-60SA integer), so map_for_shot can only run after a catalogue is chosen, and every non-benchmark read already names its machine by calling load_packaged_machine_map(machine) before transform_machine_description. The benchmark shot set is where a bare shot first enters, so it declares the machine there. That set has one owner, imas_ambix/spine_bench/shots.py, whose BenchShot carries shot_id, role and, since 2026-10-05 (jtmm-shotset-machine), machine, which MAST's six shots declare as mast; its resolve_shotset_version already compares (machine, shot_id, role), and scripts/spine_benchmark.py already requires --machine with --shots, with no default, so a list of bare shot ids is never read as MAST by accident. Those landed and retire nothing beyond the implicit MAST default. What remains for this section is the JT-60SA frozen set, a second named set in that module with its own version label, so a JT-60SA shot whose digits coincide with a MAST id can never be stamped under the MAST label; it is drawn from the 2023 OP1 shots on which SELENE ran. The selector reads the machine from that declaration, and identity_for_shot, which takes a registry rather than a machine, is handed the registry for the declared machine instead of default_registry's MAST one. § Decisions

Where are JT-60SA → IMAS maps persisted?

Codex has traditionally generated the facility and DD knowledge graph; ambix holds the executable machine-map substrate that MAST already runs through.

Lead's choice 2026-10-05. Ambix already serves MAST through a declared machine map (254 bindings), two store engines and a compiled affine signal map, and its runtime never queries the discovery graph by design, so JT-60SA maps are packaged, versioned ambix documents with evidence receipts pointing at codex graph nodes. Rejected: IMASMapping nodes in the codex graph (a live graph and a tunnel at every read) and a separate mapping repository (a third repo that defers the units/sign/COCOS schema question).

Is the map authored in the ambix LinkML schema or natively in tokamap?

Tokamap is the UKAEA/UDA interchange format; it has no slot for units, sign convention, COCOS, validation state or evidence.

Lead's choice 2026-10-05. Tokamap has no slot for units, sign convention, COCOS, validation state or evidence, only a bare scale, so it cannot carry the claims this plan proves; the forward collapse of unit, sign and COCOS factors into scale is lossless and the reverse is not. Author in the ambix LinkML schema and emit a tokamap directory that passes tokamap-validator for UDA and UKAEA consumers. Rejected: tokamap native with custom keys, invisible to libtokamap and unvalidated.

How does the SELENE deck reach the transform engine?

The deck is a static per-phase text file; the engine registry varies by store format.

Lead's choice 2026-10-05. The SELENE deck is a static per-phase text file read twice a campaign, so there is no per-shot cost to amortise with a new engine; convert coil_vv_OP1/OP2.dat once with the nakamap logic into IDS netCDF carrying the deck hash and converter commit as the receipt, read by the existing netCDF engine.
