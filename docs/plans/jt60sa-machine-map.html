Second machine on the declared-map substrate

JT-60SA Machine Map for Equilibrium Reconstruction

MAST is read through a declared machine map and a format-scoped transform engine. JT-60SA is the next machine on the left of that diagram: author its map, prove its conventions against data, and serve its pulses through the same engines. The driving use case is equilibrium reconstruction — recover the SELENE equilibrium from mapped coil currents and magnetics — because it exercises every one of the five first-pass IDSs and gives a comparator that cannot be satisfied by a map that is merely well-formed.

§1 — The map lives in ambix; codex supplies discovery and evidence

Two repositories could hold a JT-60SA map, and both already carry part of the answer. imas-codex has a JT-60SA facility configuration, an EDAS/EDDB signal scanner that enumerates the self-describing catalogue over ssh (eddbreadCatTable, eddbreadTable), wiki-site adapters for the Naka TWiki (manuals, the discharge-parameter handbook, equilibrium-code pages), and an LLM pipeline that proposes IMASMapping nodes with typed MappingEvidence. imas-ambix has the executable half: a LinkML machine-map schema with no conditional or code-hook slot, range-scoped maps selected by shot, two store engines (zarr, netCDF) that apply any map, a compiled affine signal map with COCOS factors resolved at the read boundary, a lazy transform-aware view over immutable arrays, and an evidence-based convention scorer. MAST runs through all of it today with 254 bindings; DIII-D has a one-binding source-only map.

The division is already written into ambix: the signal-map module states that discovery systems may produce a large evidence graph, that the ambix runtime does not query that graph, and that it loads a reviewed, content-addressed distillation instead. The north star makes the same split load-bearing — machine identity enters only through the shipped description and the deterministic forwards, and every learned component is geometry-conditioned by construction. A map is therefore part of the physics substrate the estimator ships with, not a discovery artefact.

Decision proposed and argued here, locked below: JT-60SA maps are persisted in ambix as packaged, versioned documents under imas_ambix/data/machine_maps/jt-60sa.json (description bindings) and imas_ambix/data/maps/jt-60sa/<system>.json (pulse signal maps), each carrying evidence receipts that point back at codex graph nodes, handbook pages and PIDs. Codex remains the place where candidates are discovered, where the handbook and PID tables are indexed, and where an LLM proposal is scored; it does not become the runtime authority for what a channel means. Nova stays machine-agnostic: it consumes the DD-shaped output in COCOS 17 through its existing IDS readers (nova.imas.machine, nova.imas.equilibrium) and carries no JT-60SA module — the earlier nova/projects/JT-60SA scripts were already moved out into the standalone nakamap package in October 2024, which is exactly the boundary this plan keeps.

§2 — Map schema: the ambix contract, with a tokamap export

UKAEA's tokamap is the community interchange format for IMAS mappings: a mappings.cfg.json with metadata, groups (one per IDS) and shot partitions selected by MAX_BELOW, MIN_ABOVE, EXACT or CLOSEST; a globals.json of templated constants; and per-group mappings.json keyed by DD path with five map types — VALUE, DIMENSION, DATA_SOURCE (with args, offset, scale, slice), EXPR and CUSTOM. It is executed by libtokamap and UDA's JSON mapping plugin, and the MAST mappings use it with Inja templating ({{ at(flux_loop_names, indices.0) }}) and bare scale factors ("SCALE": -1.0 on flux_loop[#]/flux).

The comparison below is why tokamap is a target of this plan rather than its source of truth. Everything the ambix schema was built to make structural — a declared source unit beside the target unit, a named sign convention instead of a bare -1.0, a machine-wide source COCOS with per-binding override, a validation state and evidence string per binding, source qualifications for arrays that exist but cannot be bound, and range-scoped selection with no conditional — has no slot in tokamap. A tokamap file can be generated from an ambix map losslessly in the forward direction (unit factor × sign × COCOS factor collapse into scale; DD-path keys and partitions are mechanical), but the reverse loses the provenance and the convention claims this plan exists to prove.
