Second machine on the declared-map substrate

JT-60SA Machine Map for Equilibrium Reconstruction

MAST is read through a declared machine map and a format-scoped transform engine. JT-60SA is the next machine on the left of that diagram: author its map, prove its conventions against data, and serve its pulses through the same engines. The driving use case is equilibrium reconstruction — recover the SELENE equilibrium from mapped coil currents and magnetics — because it exercises every one of the five first-pass IDSs and gives a comparator that cannot be satisfied by a map that is merely well-formed.

§1 — The map lives in ambix; codex supplies discovery and evidence

Two repositories could hold a JT-60SA map, and both already carry part of the answer. imas-codex has a JT-60SA facility configuration, an EDAS/EDDB signal scanner that enumerates the self-describing catalogue over ssh (eddbreadCatTable, eddbreadTable), wiki-site adapters for the Naka TWiki (manuals, the discharge-parameter handbook, equilibrium-code pages), and an LLM pipeline that proposes IMASMapping nodes with typed MappingEvidence. imas-ambix has the executable half: a LinkML machine-map schema with no conditional or code-hook slot, range-scoped maps selected by shot, two store engines (zarr, netCDF) that apply any map, a compiled affine signal map with COCOS factors resolved at the read boundary, a lazy transform-aware view over immutable arrays, and an evidence-based convention scorer. MAST runs through all of it today with 254 bindings; DIII-D has a one-binding source-only map.

The division is already written into ambix: the signal-map module states that discovery systems may produce a large evidence graph, that the ambix runtime does not query that graph, and that it loads a reviewed, content-addressed distillation instead. The north star makes the same split load-bearing — machine identity enters only through the shipped description and the deterministic forwards, and every learned component is geometry-conditioned by construction. A map is therefore part of the physics substrate the estimator ships with, not a discovery artefact.

Decision proposed and argued here, locked below: JT-60SA maps are persisted in ambix as packaged, versioned documents under imas_ambix/data/machine_maps/jt-60sa.json (description bindings) and imas_ambix/data/maps/jt-60sa/<system>.json (pulse signal maps), each carrying evidence receipts that point back at codex graph nodes, handbook pages and PIDs. Codex remains the place where candidates are discovered, where the handbook and PID tables are indexed, and where an LLM proposal is scored; it does not become the runtime authority for what a channel means. Nova stays machine-agnostic: it consumes the DD-shaped output in COCOS 17 through its existing IDS readers (nova.imas.machine, nova.imas.equilibrium) and carries no JT-60SA module — the earlier nova/projects/JT-60SA scripts were already moved out into the standalone nakamap package in October 2024, which is exactly the boundary this plan keeps.

§2 — Map schema: the ambix contract, with a tokamap export

UKAEA's tokamap is the community interchange format for IMAS mappings: a mappings.cfg.json with metadata, groups (one per IDS) and shot partitions selected by MAX_BELOW, MIN_ABOVE, EXACT or CLOSEST; a globals.json of templated constants; and per-group mappings.json keyed by DD path with five map types — VALUE, DIMENSION, DATA_SOURCE (with args, offset, scale, slice), EXPR and CUSTOM. It is executed by libtokamap and UDA's JSON mapping plugin, and the MAST mappings use it with Inja templating ({{ at(flux_loop_names, indices.0) }}) and bare scale factors ("SCALE": -1.0 on flux_loop[#]/flux).

The comparison below is why tokamap is a target of this plan rather than its source of truth. Everything the ambix schema was built to make structural — a declared source unit beside the target unit, a named sign convention instead of a bare -1.0, a machine-wide source COCOS with per-binding override, a validation state and evidence string per binding, source qualifications for arrays that exist but cannot be bound, and range-scoped selection with no conditional — has no slot in tokamap. A tokamap file can be generated from an ambix map losslessly in the forward direction (unit factor × sign × COCOS factor collapse into scale; DD-path keys and partitions are mechanical), but the reverse loses the provenance and the convention claims this plan exists to prove.

It retires nothing, because ambix has no exporter, and it is kept out of the loaders because they read the ambix schema and must not learn tokamap's.

§3 — Access path: EDDB over ssh, an on-demand cache, a lazy view

The authorised data path is the EDDB C library through its Python wrapper on the Naka analysis server (/analysis/src/eddb/eddb_pwrapper.py, /analysis/lib/libeddb.so), reached as ssh jt-60sa (nakasvr26). Measured 2026-10-05 from this workstation: the catalogue answers with 73 categories; the current shot is a coil-commissioning pulse (C-series); category MMSYS carries every CS, EF and TF coil current in amperes from two independent measurement chains (HiTec and LKAT), PSRC carries the plasma-shape-reconstruction inputs and outputs including Ip in kA, FAME carries one hundred real-time equilibrium scalars, and MAG on the commissioning shot carries only MHD fluctuation channels. The ssh link to IFERC dropped mid-session and stayed down, so the raw flux-loop and pickup-coil census on an OP2 E-shot is an open item (§5) rather than a finding.

Transforming on the fly from nakasvr26 therefore means two tiers, not one. The remote extractor is a stdlib-plus-wrapper script executed over ssh, niced, that takes a batch of (shot, category, dname) requests on stdin and streams compact binary arrays back. That is the shape codex's remote layer already uses for enumeration (imas_codex/remote/scripts/enumerate_edas.py run through executor.py and ssh_worker.py, with the msgpack array format in serialization.py). Ambix owns its own extractor rather than importing that layer or extracting a shared remote core from it. Importing it would make imas-codex, with its graph, LLM and tool-installation dependencies, a dependency of every ambix read, which the map-persistence decision rules out. And the extractor needs a small part of that layer: one ssh process per batch, one remote script read from stdin and numpy arrays back, with no session pool, host registry or tool installer, because the ssh control master in the user config already amortises session setup and the cache means a shot is fetched once. Codex stays the reference for the EDDB call shapes (enumerate_edas.py and imas-codex:jt60sa-eddb-census), not a code dependency. A second facility needing remote execution in ambix is the point at which a shared core becomes the cheaper path, and that is decided then, in its own plan. The extractor's public surface is one batch-fetch function and one cache writer; it retires nothing, because ambix has no remote reader today. The on-demand cache lands only the channels the map binds, for the shots a run asks for, as {shot}.zarr/{category}/{dname} with the EDDB unit string, channel count and sequence number as attributes, in raw units and raw sign, written on first fetch and never rewritten. It is not a copy of the EDDB: about 230 first-pass channels cost roughly 1.4 GB per shot at full rate or 150 MB windowed to the plasma phase (one coil-current record is 740,900 points, 5.9 MB), so a frozen 20-shot benchmark set is 3 to 28 GB under a size cap, pre-warmed only for that set. The lazy view is the existing VirtualZarrView: listing and metadata read no chunks, and a slice applies the compiled affine transform to only the returned chunk. The zarr engine then serves JT-60SA with no new engine, which is the test that the architecture scales the way its own plan claimed.

Done-when: a cold fetch of one OP2 shot's first-pass signals completes through the extractor in a single ssh session; a warm read of the same signals through the view touches no network; and the extractor's wall time per signal and bytes per signal are recorded in the evidence so the cache for a shot set is sized rather than guessed. The cache root is declared once, as JT60SA_ROOT in imas_ambix/data/paths.py beside the MAST MIRROR_ROOT, because that module is the single owner of mirror paths and every reader and writer imports from it. Its value is /work/projects/imas_gpu/jt60sa, on GPFS beside the MAST store, so every ITER session and worker reads the same bytes (decision below). The cache is a second transport beside the FAIR-MAST mirror, not an extension of it, and it keys a pulse the way the rest of ambix does. EDDB names a pulse by a series letter and six digits (E101173 for an experiment, a C-series token for a commissioning pulse), while the catalogue's shot ranges and both engines' {shot} paths are integers. The cache therefore stores a pulse under the integer of its six digits and records the full EDDB token on the pulse group; a write whose token differs from the one already recorded there is refused, so two series sharing a number fail loudly instead of sharing a store. The census records whether the C and E series overlap at all. imas_ambix/data/manifest.py and the ambix data manifest and download commands in imas_ambix/data/cli.py plan and run bulk whole-shot copies from S3 through s5cmd, selected from a parquet shot index, while this cache fetches named channels over ssh only when a run asks for them. It therefore shares the path owner and the zarr layout the engine reads, takes none of the manifest or download machinery, and adds no ambix data command.

§4 — Machine description: the SELENE deck is the source

The JT-60SA conductor and sensor geometry already exists on this workstation as the SELENE input decks coil_vv_OP1.dat and coil_vv_OP2.dat with per-phase loop, probe and vessel-contour tables, and the nakamap package has one-shot scripts that turn them into pf_active, pf_passive, wall and magnetics IDS netCDF files (jt60sa_md_OP1.nc, jt60sa_md_OP2.nc). That work is the seed, not the deliverable: it is imperative, carries no provenance beyond the file name, hard-codes the phase, and its comment still names the wrong machine.

The source of truth is the facility's SELENE PSRC run tree (decision below). Measured 2026-10-05 by jtmm-geometry-source: the workstation decks coil_vv_OP1.dat and coil_vv_OP2.dat are byte-identical to the copies in the lead's analysis-server home, both arrived in a OneDrive bundle dated 2024-10-21, and the OP1 deck is element-for-element identical (largest difference 0.0) to /analysis/src/SAselene_v2.0_forPSRC/RUN/EQSLE.DATA, the input the facility's plasma-shape reconstruction runs on (2020-12-14), whose fort.96 carries 27 flux-loop and 17 probe positions. The lead's own extraction (jt-60sa:~/work/efit_jt60sa/extract_jt60sa.py, 2026-04-27) reads the same two files. Between OP1 and OP2 the PF coils, flux loops and probes are identical; only the vessel changes, from 120 filaments at 7.76e-7 Ω·m to 98 at 7.20e-7 Ω·m, with the wall contours. The nakamap IDS files are not sources: they are DD 3.42 fragments labelled SST-1, with no provenance, and their magnetics IDS stores the probe coordinates in flux_loop (5.09 m from the true loop positions).

A read-only search, run as ssh -F ~/.ssh/config jt-60sa under nice -n 19 with every find bounded by timeout 180 and -maxdepth 5 over /analysis/src and /analysis/lib only, looks for four things. First, SELENE, PSRC, FAME and EQDB trees newer than SAselene_v2.0_forPSRC. Second, any sensor table holding 34 flux loops or 23 probes or naming magFluxLp and magPbTC, compared with fort.96 to 1e-6 m. Third, the sensor-position or calibration parameters EDDB carries as one-point data for PSRC and MDAC on E101173, read with eddbreadOne and never as time series. Fourth, a 98-filament OP2 vessel block or a TF table, compared with coil_vv_OP2.dat. It is done when the loop and probe count of every sensor table found is tabulated with its agreement to fort.96, and a facility file is named for magnetics, OP2 pf_passive and tf, or the search states plainly that none exists inside its bounds.

The converter reads the facility file, records its path and sha256 as the receipt, and treats the OneDrive deck as a verified mirror rather than as the source. The lead ruled that JT-60SA geometry is committed to the repository as MAST's is in mast.json, so supplements and directional vacuum verdicts carry their coordinates inline; EDDB values never enter the repository.

This section rebinds that content as a range-scoped machine map: one binding set per operating phase, with the OP1→OP2 boundary expressed as a shot range exactly as MAST's two geometry transitions are, and every emitted conductor element, loop position and probe position carrying a binding whose evidence names the deck line range and the deck's hash. pf_active coils (CS1–4, EF1–6, FPPC upper and lower) emit rectangular elements with positive turns and circuit direction in pf_active/circuit/connections, following the rule the MAST map settled — direction lives in the circuit, not in signed turns. pf_passive vessel filaments carry resistivity so the loop resistance is derived, not asserted. The tf IDS is populated from the deck's TF description with tf/coil/current bound to the MMSYS TF current and tf/b_field_phi_vacuum_r derived from it and the turn count, so the one COCOS-dependent tf field is produced by a declared relation rather than a guess. Magnetics geometry (loop positions, probe positions and directed probe angles) is bound from the deck's sensor tables, with the probe angle marked unknown-unvalidated until §6 settles its sense against vacuum data.

Whether the deck itself gets a store engine, or is converted once into an IDS netCDF with a recorded receipt that the existing netCDF engine reads, is a decision below; the recommendation is the receipt, because a static per-phase description has no per-shot access cost to amortise. The existing engine does not yet read such a file: NetCDFTransformEngine.open resolves {store_root}/{shot}/ and reads one {binding}.nc per binding, a per-pulse layout that suits MAST, whose geometry is written into every pulse, but would force a copy of a static description for every JT-60SA shot. §4 therefore extends that engine, rather than adding one, so a store can be addressed by the map a shot selects. The converted description is one IDS netCDF per IDS per phase under JT60SA_ROOT/machine_description/. Being static over a map's shot range is a property of how the engine addresses the store, not a new catalogue slot: description values reach the DD through ordinary bindings to that netCDF, and a value it cannot carry goes in the slots the schema already has for static description, DescriptionSupplement (with its point_flux_loops and polygon_sections) and StructureAssembly, used as mast.json uses them, each entry's evidence naming the deck path, sha256 and line range. That netCDF is the source layer, the counterpart of MAST's level-2 store that the transform engine reads, and not a second machine-description artifact store. The spine reads geometry through imas_ambix/gs/artifact_resolution.py, whose content-addressed store (publish_object, resolve_machine_description, a pinned semantic identity) holds MAST's single pinned description and is consumed by gs/machine_selection.py select_machine. The JT-60SA artifact the spine needs is authored from this source and published through that owner with a pin of its own (§7); the deck receipt is the field provenance that artifact's semantic identity covers. The catalogue gains the slots this addressing needs, under the §2 slot rule: the description's store format and store root, named through paths.py, and the source of directed probe angles, so load_machine_map's fixed key set grows by named structure rather than by machine. The extension point is imas_ambix/data/description_reader.py read_geometry_table, the sole acquisition route from catalogue to geometry table, which today resolves one fixed store format and root and supplies MAST's probe angles under a machine == "mast" branch. JT-60SA reaches the kernel through it, with the store format, root and probe-angle source resolved from the catalogue rather than from the machine name, so that branch is retired, not joined by a second. Done-when: transform_machine_description emits a JT-60SA description for one OP1 and one OP2 shot through one code path, read_geometry_table and geometry_table_from_description build a GeometryTable from it with zero machine-name branches, and the three identity assertions (determinism, partition consistency, visible change at the OP1/OP2 boundary) pass. Those are the assertions imas_ambix/data/description_identity.py already proves for MAST's two geometry transitions (machine_description_bytes, geometry_description_for_transition, description_field_changes), extended to the JT-60SA phases rather than rewritten.

§5 — Pulse bindings and the EDDB census

The pulse signal maps bind EDDB channels to DD leaves with a compiled affine transform. Known from the commissioning-shot tables: MMSYS/cur{CS1..CS4,EF1..EF6}{HiTe,LKAT} in A are the pf_active circuit currents, with the two chains recorded as ranked sources rather than silently preferring one; MMSYS/cur1TFLKAT and cur2TFLKAT are the TF current; PSRC/Ip in kA is the plasma current for magnetics/ip/data with a declared unit factor of 1000. What is not yet known is where the raw flux loops and pickup coils live for a plasma shot and how many there are — the candidates are MDAC (264 channels, the magnetic data-acquisition controller), PSRC (312 channels) and MAG on an E-shot — and whether EDDB exposes them as separate dnames or as multi-channel arrays.

The first node of this section is therefore a census, not a map: enumerate every category table for the latest OP2 E-shot, record name, class, unit, description, channel count and shot validity, record the PID of every one-point datum, and run the codex EDAS scanner from the workstation so the same catalogue lands in the graph as FacilitySignal nodes beside the handbook pages it already holds; publish the join as evidence. Only then are the magnetics bindings written, with sign_convention: unknown-unvalidated on every signed quantity until §6 replaces it. Unit strings in EDDB are free text (KA, DEG, T.m, deg. C); the census produces the normalisation table that maps each to a DD unit, checked with the imas-cx server's path and unit tools, and a string that cannot be normalised blocks its binding rather than defaulting.

Done-when: every first-pass DD leaf for pf_active currents, tf current, magnetics ip, flux loops and poloidal probes has either an executable binding or a source qualification naming why not, and the signal map compiles to one affine operation per channel with no string lookup in the chunk loop.

§6 — Prove the conventions: vacuum shots, COCOS scoring, DD unit checks

A map that binds names is not yet a transform; MAST taught that the convention must be identified from data and proved for both current signs rather than asserted. JT-60SA offers a cleaner instrument than MAST had: the C-series commissioning shots drive the superconducting coils with no plasma, so every loop flux and probe field is a deterministic function of the measured coil currents and the declared geometry. Nova's Biot–Savart operators predict both from the §4 description; comparison against the measured channel fixes, per channel, the loop sign, the probe sensitive axis, the unit factor and whether the declared position is consistent — exactly the adjudication that settled MAST's nineteen disputed loop positions. Each JT-60SA verdict is recorded as MAST's are, as a FluxLoopPositionDeclaration over the shot range it was measured on, undecided verdicts included, and read back through MachineMapCatalog.flux_loop_positions_for, so the reader stays machine-agnostic. A channel whose vacuum prediction does not track its measurement with slope near one is left unknown-unvalidated and reported, never forced.

The COCOS of the source is then identified rather than assumed. For the raw side, the sign products that the Sauter and Medvedev coefficients constrain are read from plasma shots: Ip against the sign of poloidal flux change at the loops, toroidal field polarity from the TF current, the handedness implied by q from FAME. That computation already has an owner, imas_ambix/data/cocos_convention.py: its score_convention, score_conventions and surviving_conventions take any cohort of ShotSignObservation, with the MAST table only as the default, and format_sign_report writes the sign report this section's done-when names, so JT-60SA supplies an observation cohort to it rather than a second scorer. For the equilibrium side, the SELENE and FAME outputs are scored on the convention scorer's tests (edge-minus-axis flux sense, flux-per-radian versus total flux by integrating the Grad–Shafranov current, q sign). The shipped entry point, imas_ambix/challenge/convention.py measure_diiid_convention, reads the DIII-D challenge corpus's own keys and accepts no SELENE or FAME record; the reusable part is its Grad–Shafranov current integral, _integrated_current. §6 therefore generalises the entry point to take an equilibrium record through a loader, with the DIII-D corpus as its first loader and SELENE and FAME as the next, rather than writing a second scorer. Because _integrated_current and _axis_and_boundary read DIII-D corpus keys (efit_grid_R, efit_psirz, efit_z_axis) directly, the loader boundary is a record contract with canonical keys for the grid, psi, axis and boundary, which the DIII-D loader maps onto and the kernel reads, so the kernel is reused rather than rewritten. The result sets source_cocos in the catalogue and the per-binding overrides where SELENE and the raw acquisition differ. Target convention is fixed: DD 4 in COCOS 17, and the engine applies the Sauter transform to each of the DD's COCOS-dependent leaves — seventeen in magnetics, three in pf_active, one in tf, one hundred and fifty-one in equilibrium — by the DD's own transformation table, not by a hand list.

Done-when: a sign report over at least three vacuum shots and three plasma shots, with both TF polarities if the campaign offers them, that names the identified source COCOS, the per-channel vacuum slope and correlation, and every channel left unvalidated with its reason; and a unit audit in which every binding's source and target units resolve through the DD unit vocabulary with the derived factor asserted against one hand-computed value per unit pair.

§7 — Equilibrium: FAME scalars first, SELENE maps second, then the reconstruction gate

The equilibrium IDS is mapped in two rungs. The first binds the FAME real-time scalars — plasma current, poloidal and toroidal beta, normalised beta, internal inductance, axis position, X-point height, strike-point angles, boundary gaps, Bt·R — to equilibrium/time_slice/global_quantities and boundary leaves and to vacuum_toroidal_field. These are time series in EDDB, so they ride the §3 path unchanged. The second rung reaches the offline SELENE equilibria: the server holds the SELENE sources, the equilibrium database client (client_eqdbms) and the FAME reader (eqdbget), and the Code TWiki documents the equilibrium codes. That rung needs a reader for the EQDB record (psi on its grid, boundary, p′ and FF′ or their profiles) wrapped in the same remote-extractor contract, and a COCOS verdict from §6 before any map is written into profiles_2d/psi. The EQDB reader adds one remote script and one fetch entry beside the §3 extractor's, using its transport and cache rather than a second path; it retires nothing, because no equilibrium-database reader exists in ambix.

The reconstruction gate is what makes the map honest. Using only the mapped pf_active, pf_passive, tf and magnetics data, the ambix physics spine (greens-matvec, with grid-delstar as the check), reading JT-60SA geometry through gs/artifact_resolution.py with a JT-60SA pin rather than a second resolver (so resolve_machine_description gains a machine to resolve, and how the artifact is authored from the §4 source without a JT-60SA module in nova is settled in this section), recovers the equilibrium for a frozen set of OP2 shots and is compared against SELENE on the quantities SELENE reports: boundary distance, axis position, Ip, q95, and the whitened magnetics residual. This is the MAST benchmark pattern with SELENE in EFIT's seat, and it is scored by the owner of that pattern: imas_ambix/eval/efit_referee.py judge_geometry already scores model geometry against an injected reference equilibrium into a GeometryVerdict (boundary RMS, axis position, q), so §7 adds a SELENE reference loader and its firewall tier to it instead of a parallel comparator. GeometryVerdict scores axis, X-point and boundary RMS only. The whitened magnetics residual already has its owner in the spine benchmark (imas_ambix/spine_bench/runner.py _magnetics_residual, written into the stamped record), so it is read from the stamp; q95 and Ip have no owner that scores them against a reference, so they are added to judge_geometry as verdict components rather than scored beside it. Nova consumes the emitted IDSs through its existing readers; nothing JT-60SA-specific is added to nova, which is the transfer claim of the north star exercised on a second machine without waiting for the sealed DIII-D rehearsal.

Done-when: a stamped spine-benchmark record for a JT-60SA shot set with the comparator named as SELENE, boundary RMS distance and whitened magnetics residual reported per shot, and the comparison run on a SLURM compute node with the machine/env block recorded. The first stamp is a baseline, not a pass mark: the number it reports is what later map corrections are judged against.

§8 — Execution order

  1. Lock the three placement decisions below (map location, schema versus tokamap, description source). The JT-60SA catalogue first lands with the §4 description bindings rather than as an empty scaffold: load_machine_map refuses a catalogue whose binding_sets or whose set's bindings is empty, and that refusal is kept because a map that silently binds nothing is the failure it exists to stop.
  2. Build the remote extractor and the mirror writer (§3); fetch one C-shot and one E-shot; record timing and sizes.
  3. Run the EDDB census on the E-shot (§5); join to handbook and PID evidence in codex; publish the normalisation table.
  4. Rebind the SELENE deck as range-scoped description bindings (§4); build the geometry table; pass the identity assertions.
  5. Vacuum-shot adjudication and COCOS identification (§6); replace every unknown-unvalidated that the data settles.
  6. FAME scalar bindings, then the EQDB reader and SELENE map bindings (§7).
  7. Stamp the reconstruction baseline on the spine with SELENE as comparator (§7); export tokamap and validate it (§2).

Items 2 and 3 are blocked only by the IFERC link being up; everything in item 4 can proceed from the local decks while it is down. Heavy gates — the census over all categories, the vacuum adjudication, the spine stamp — run on SLURM compute, never the login node.

§ Decisions

Where are JT-60SA → IMAS maps persisted?

Codex has traditionally generated the facility and DD knowledge graph; ambix holds the executable machine-map substrate that MAST already runs through.

Lead's choice 2026-10-05. Ambix already serves MAST through a declared machine map (254 bindings), two store engines and a compiled affine signal map, and its runtime never queries the discovery graph by design, so JT-60SA maps are packaged, versioned ambix documents with evidence receipts pointing at codex graph nodes. Rejected: IMASMapping nodes in the codex graph (a live graph and a tunnel at every read) and a separate mapping repository (a third repo that defers the units/sign/COCOS schema question).

Is the map authored in the ambix LinkML schema or natively in tokamap?

Tokamap is the UKAEA/UDA interchange format; it has no slot for units, sign convention, COCOS, validation state or evidence.

Lead's choice 2026-10-05. Tokamap has no slot for units, sign convention, COCOS, validation state or evidence, only a bare scale, so it cannot carry the claims this plan proves; the forward collapse of unit, sign and COCOS factors into scale is lossless and the reverse is not. Author in the ambix LinkML schema and emit a tokamap directory that passes tokamap-validator for UDA and UKAEA consumers. Rejected: tokamap native with custom keys, invisible to libtokamap and unvalidated.

How does the SELENE deck reach the transform engine?

The deck is a static per-phase text file; the engine registry varies by store format.

Lead's choice 2026-10-05. The SELENE deck is a static per-phase text file read twice a campaign, so there is no per-shot cost to amortise with a new engine; convert coil_vv_OP1/OP2.dat once with the nakamap logic into IDS netCDF carrying the deck hash and converter commit as the receipt, read by the existing netCDF engine. Rejected: a dedicated deck store engine, one more engine for a format with no access cost.

Where does the immutable EDDB mirror live?

Lead's choice 2026-10-05, after the store was re-stated as an on-demand cache of only the channels the map binds for the shots a run asks for, never a copy of the EDDB (about 230 first-pass channels, 1.4 GB per shot at full rate or 150 MB windowed; a frozen 20-shot set is 3 to 28 GB under a size cap). It lives on GPFS under /work/projects/imas_gpu/jt60sa beside the MAST store so every ITER session and worker reads the same bytes and the benchmark is reproducible offline. Rejected: in-memory only (re-pulls gigabytes per benchmark run through the laptop hop) and node-local /tmp (invisible to other sessions, gone with the allocation).

Is the codex graph used for JT-60SA evidence served locally or through the ITER tunnel?

Measured 2026-10-05: the ITER graph runs as a SLURM job but the forward tunnel on port 17687 is in a restart loop; a local Neo4j instance is running but rejects both the configured and its own launch credential; the local embedding server is not running and the workstation has no usable GPU.

Lead's choice 2026-10-05. The ITER graph (SLURM job codex-neo4j on gpu-0002, beside the embedding server) already holds the 4,476 JT-60SA wiki pages, is direct from ITER where the work moves, and reaches the workstation through the codex tunnel on 17687 now that the supervisor's connection grace is fixed. Rejected: a local per-facility graph, which needs a credential reset on the local Neo4j, a local embedding server without a usable GPU and a sync discipline back to ITER.

May JT-60SA geometry be committed to the public repository?

The machine-map schema carries static description values and vacuum-verdict coordinates inline in the packaged JSON, as mast.json does for open FAIR-MAST data; imas-ambix and its upstream are public.

Lead's choice 2026-10-05: JT-60SA geometry is committed like MAST's, after checking whether the SELENE decks are the best single source given the further .dat files, processing scripts and IMAS IDS data in the lead's analysis-server home, per phase because OP1 and OP2 are different configurations. EDDB signal values never enter the repository. Rejected: GPFS-only coordinates (a schema extension to reference netCDF values) and a private package (reopens the map-location decision).

Which source is the single source of truth for JT-60SA geometry?

Measured 2026-10-05 by jtmm-geometry-source: the OneDrive decks coil_vv_OP1/OP2.dat are byte-identical on both hosts and the OP1 deck equals /analysis/src/SAselene_v2.0_forPSRC/RUN/EQSLE.DATA to 0.0; the nakamap IDS files are DD 3.42 SST-labelled fragments whose magnetics IDS stores probe coordinates as flux loops; fort.96 holds 27 loops and 17 probes against 34 and 23 acquired in EDDB.

Lead's choice 2026-10-05. The facility file the plasma-shape reconstruction runs on is upstream of the decks, which match it to 0.0 for OP1, and using SELENE's own input keeps geometry out of the SELENE comparison in s7. pf_active, tf and wall are built now and OP2 pf_passive from coil_vv_OP2.dat provisionally; magnetics waits for the bounded /analysis/src sensor search because fort.96 covers 27 of 34 loops and 17 of 23 probes. Rejected: building everything from the OneDrive decks (ships an incomplete sensor set as authoritative) and building nothing until the search (holds geometry the facility file already settles).

§ Open questions

Which EDDB category carries the raw flux-loop and pickup-coil channels on a plasma shot (MDAC, PSRC or MAG), and are they separate names or multi-channel arrays?

Measured 2026-10-05 on E101173, the newest E-shot the catalogue lists: the equilibrium magnetics live in PSRC as one name per channel — 34 flux loops magFluxLp1..34 in Wb, 23 poloidal probes magPbTC1..23, 10 calibrated partial fluxes calFP1..10, the surface flux calFX, diamagnetic loops corDmagL1 and the calS1 surface integrals, with per-channel abnormality flags and calIp in kA; MDAC adds four vessel Rogowski coils curAVVRC1..4 for Ip, 41 halo-current Rogowski coils, one-turn voltage and the raw coil-current observations oCS1Cur..oEF6Cur, oTFCur; MAG holds only MHD fluctuation probes; MMSYS holds the coil and TF currents from two chains plus coil voltages; FAME holds 100 real-time equilibrium scalars (axis, boundary gaps, q, beta, li, volumes). The census log is the first node's input and is not yet persisted as evidence.

Does the codex graph hold the JT-60SA data handbook with each signal linked to its PID, so the census can join channels to handbook entries?

Partly. Measured 2026-10-05 against the ITER graph once the tunnel was repaired: the JT-60SA facility carries 4,476 wiki pages, 8,465 wiki chunks, 1,049 documents and 8,324 facility paths, including the JT-60SA Data Handbook and Discharge Parameter Handbook pages and the EDDB API manuals. The handbook is an index into per-database tables (EDDB, UDDB, PMDB, EQDB, FAME, LCDB, MBDB) served by CGI; those tables were ingested as one-chunk wrappers, so the per-category signal lists are not in the graph. No FacilitySignal, DataAccess, SignalSource or IMASMapping node exists for JT-60SA and no node carries a PID property: the EDAS scanner has never been run. In EDDB a PID No. is a nine-character key (four digits then five characters) for discharge one-point and condition data, read through eddbreadOne and eddbreadPara; time-series channels are keyed by category and data name. The census therefore joins through the EDDB catalogue itself and records PIDs for the one-point data, and the graph is populated by running the scanner from the workstation.

Is there a Python or C entry point to the SELENE equilibrium database (eqdbms, eqdbget) that the remote extractor can call without a Fortran build, and what grid and profile set does an EQDB record carry? The Code TWiki in the graph documents the EQDBMS library under /analysis/lib/eqdbms in 129×129 and 1025×1025 mesh variants, consumed by EQREAD, EQFAME, SELENE, SETEQU and FBEQU, and an EquilibriumDBFAME page; a Python wrapper was not found on the server before the IFERC link dropped.
