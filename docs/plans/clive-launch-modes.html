§1 — The default is local-only, and that is load-bearing

The shared launcher's value is that a consumer needs nothing: no repository, no virtual environment, no credential, no scheduler access. Every route that reaches off-cluster erodes that, and one particular way of eroding it has already caused an outage. A route selected by nothing the user typed — merely whether a personal credential file happened to be readable — silently made the launcher's default model hostage to one person's account balance, and holders of that file got five dead picker slots while everyone else got the working route.

So local-only remains the default and stays the route that needs no argument. Anything hosted is reached only by an explicit, named mode. This plan does not relax that; it names the mode and builds the surface around it.

§2 — Naming the mode

--claude is unavailable: the launcher already uses it for the harness axis, opposite --codex. A model-scope flag must not collide with that, and --anthropic was rejected. The remaining question is whether the scope axis is a boolean opt-in or a named mode with values.

Recommendation: a --mode axis with local as the default. One axis is self-documenting, lets a cautious caller state the default explicitly rather than trusting it, and leaves room for a third value later without a second boolean. The open question is what to call the non-default value; the candidates and their arguments are in the decision block, with tiered recommended because it names the working pattern rather than the vendor — cheap local models carrying bulk and parallel work, a frontier model reserved for adjudication.

Whatever is chosen, the mode must not silently change which model answers by default. Selecting a mode adds rows to the picker and changes what the alias slots map to; it never redirects an unqualified request off-cluster.

§3 — Two mechanisms, two jobs

The harness offers two ways to present models, and they are not interchangeable. Both were measured against the live engine rather than read from documentation.

Alias slots decide dispatch. The four ANTHROPIC_DEFAULT_<ALIAS>_MODEL variables map each alias onto a concrete model id, and that mapping is what a delegated worker resolves through. With two slots pointed at the local release and one at a deliberately invalid id:

The invalid slot failing is the informative half: it proves each alias resolves through its own slot rather than through a shared default, so different aliases can carry genuinely different models. This is the whole mechanism behind §4.

Curated picker rows decide presentation. A settings key accepts an ordered list of rows, each with its own model id, label and description, and a flag that replaces the built-in lineup rather than appending to it. Rows are not capped at the number of alias slots and an unrecognised model id is accepted as-is, so this is how two local releases get honest side-by-side labels (2×H200, 512k context against 4×H200) instead of being squeezed into alias names that mean something else. It is honoured from managed settings, from --settings, and from user settings, but not from a project checkout, and the highest-precedence source that defines it wins outright with no merging across sources.

Crucially, picker rows do not create aliases. A row is a thing a human can select; it is not a name a delegated worker can be sent to. Both mechanisms are therefore needed, and confusing them would produce a beautiful picker whose models no worker can be dispatched onto.

An arbitrary local id also works as a direct selection: a headless run against the live endpoint reported the correct 524,288-token window and named the local release as the model used, emitting an unrecognised-model telemetry line without blocking. One limit on the evidence: the settings file was accepted without error, but a non-interactive run cannot show the rows rendering, so an interactive confirmation is a done-when item rather than a claim.

Each slot and the curated rows additionally accept a supported-capabilities declaration. The launcher currently sets none, which leaves the harness guessing what a local release supports; declaring them is in scope here.

§4 — Dispatching work onto a local worker

The capability the lead asked for — a session that can be told to send work to local workers and knows what to do — decomposes into routing and knowledge, and only the second needs building.

Routing already works, by §3: because a delegated worker's model is requested by alias, mapping an alias to a local release sends every worker requested under that alias to the local engine, while another alias keeps a frontier model for the coordinator. No harness change is involved.

Knowledge is the gap. A session has no way to know which alias is local, what it costs, or what belongs there. The coordinator skill already handles this for its own dispatch path, routing every delegated node through a configured local backend alias when asked; what is missing is the same statement for ordinary delegation. The launcher is the right place to inject it, because it is the only component that knows the mapping it just created, and it already has a precedent for passing session-scoped settings. Scope here: state which alias is local, what its context and topology are, and the division of labour — bulk, parallel and mechanical work local; adjudication and physics-critical judgement on the frontier slot.

§5 — The hosted leg, and why it is deferred

Deferred by the lead, and there is a measured constraint the deferral must carry forward. The origin is locked to the GPU node, which has no outbound internet: from inside a betelgeuse allocation both api.anthropic.com:443 and 1.1.1.1:443 are blocked, while a login node's proxy port is reachable. A hosted leg is therefore not foreclosed but is not free either — it needs one internal hop through a login node.

Two properties to preserve when it lands. The hop must carry the caller's own credential rather than storing one, so a shared component never holds anyone's key. And catalog failure must continue to stop before the hosted leg is considered, so a local outage never silently promotes a metered route.

§6 — Done-when

  • An unqualified launch serves local models only, and no readable credential anywhere on the system changes that.
  • The mode axis is named, documented in --help, and fenced by a test that an unqualified launch and an explicitly-local launch produce identical environments.
  • Curated rows present each local release with its real topology and context, and the rows are confirmed rendering in an interactive session, not merely accepted.
  • Supported capabilities are declared for every slot the launcher sets.
  • A delegated worker requested under the local alias is observed running on the local engine, and the session is told which alias that is without being asked.

§ Decisions

Is model scope a named --mode axis with a default of local , or a single boolean opt-in flag over a local default?

Recommendation: the mode axis. It is self-documenting, lets a caller assert the default rather than trust it, and extends to a third value without adding a second boolean. A boolean is shorter to type but says nothing about what the default was.

What is the non-default mode value called — the one that adds the hosted frontier models to the local lineup?

Recommendation: tiered . It names the working pattern — cheap local models for bulk and parallel work, a frontier model for adjudication — which is the reason to select it, and it reads correctly for a lineup that is still mostly local. hosted is the most literal description of what is added but misreads as only hosted. mixed and hybrid are accurate and vague: they say two kinds are present without saying which or why.

Which alias slot carries the local release in the mode that includes hosted models?

Recommendation: sonnet for the primary local release, leaving haiku for the second one. The bulk-worker alias should be the one a delegating session reaches for by habit, and the smallest alias also feeds background harness traffic that a large local model serves expensively.

§ Followups

Name the mode axis, then build the picker and capability declarations

Two naming decisions gate the CLI surface and are the lead's to make: whether model scope is a --mode axis or a boolean opt-in, and what the non-default value is called (tiered recommended, because it names the working pattern rather than the vendor). Everything else is buildable now against the local-only default: curated picker rows with real topology labels, supported-capability declarations for every slot the launcher sets, and the session-scoped statement of which alias is local. Alias-resolution behaviour is already measured, so worker dispatch needs no harness change. The one unverified item is that curated rows actually render — confirm interactively, since a headless run cannot show a picker.
