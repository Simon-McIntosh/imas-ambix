Run the map where the data lives

JT-60SA Facility Mint: Public Engine, Private Maps

The machine map (jt60sa-machine-map) turns JT-60SA data into IDS paths, and jt60sa-pulse-ids §1 adds the writer that mints a pulse. Both run here, reading EDDB over ssh into a cache. This plan moves the mint to the facility. A slim public engine, imas-alambic, loads a private JT-60SA map bundle that it finds by machine name, and reads EDDB locally on the analysis server. The lead settled the route on 2026-10-06. The engine is a uv workspace member of this repository. The maps are authored in a private GitHub repository and stored as private GHCR artifacts, which this machine relays to the server. The install starts as an editable checkout on the analysis server, to test, and moves to a wheel.

§1 — Move the JT-60SA maps into a private bundle

The data-load code is in imas_ambix/data/. eddb_remote.py sends a batch of EDDB channel requests down one ssh session to the analysis server, whose remote half runs on the server's Python 3.12 with only the standard library, numpy and eddb_pwrapper. eddb.py owns the cache under /work/projects/imas_gpu/jt60sa/{shot}.zarr. signal_map.py and virtual_zarr.py apply the pulse maps over that cache, and transform_engine.py with machine_map.py serves the machine description through the catalogue. The maps are package data beside that code: imas_ambix/data/machine_maps/jt-60sa.json and imas_ambix/data/maps/jt-60sa/{pf_active,tf,magnetics}.json, found through PACKAGED_MACHINE_MAP_ROOT and PACKAGED_MAP_ROOT. Both GitHub remotes of this repository, the origin fork and upstream, are public, and the JT-60SA maps and their evidence fragments are pushed to origin. The description store and the SELENE deck copies it is built from live only under /work/projects/imas_gpu/jt60sa/, never in git.

The lead chose a private bundle (map-privacy, map-source, public-history). Three things move to a new private repository, Simon-McIntosh/imas-alambic-jt60sa, laid out as the bundle that §3 defines: the JT-60SA catalogue, its signal maps, and the description store (827 kB under /work/projects/imas_gpu/jt60sa/machine_description/). That repository is registered as a reckon project, so later map edits dispatch there. Each bundle version is pushed with oras as an OCI artifact to the private package ghcr.io/simon-mcintosh/imas-alambic-jt60sa, tagged with the bundle version and tagged again with the source commit. Afterwards the public tree carries no JT-60SA map. The engine's own tests use synthetic maps. Ambix tests that need the real JT-60SA maps resolve the bundle through §3's search path; when it is absent they skip with a stated reason, which is what public CI sees. The 12 earlier commits on origin that carry the maps stay as they are, because the lead chose not to rewrite history; upstream never had them. The evidence fragments and figures under docs/ are outside this move, and the open decision evidence-privacy covers them.

The move needs §2's bundle discovery, so that ambix still finds the maps. It also changes where the jt60sa-machine-map plan edits them. So it lands only when that plan has no run in flight on the map files, and that plan's later sections edit the private repository instead. Done-when: git ls-files imas_ambix | grep -i jt-60sa returns nothing on main. oras manifest fetch ghcr.io/simon-mcintosh/imas-alambic-jt60sa:<version> succeeds with the gh token and is refused without one. With the pulled bundle on the search path, the ambix tests that cover the JT-60SA maps add no failures against the stated base; without it, they skip with the stated reason.

§2 — imas-alambic: the slim engine as a workspace member

ambix declares 33 runtime dependencies, including torch, lightning, transformers, jax and torax, and none of them is needed to mint. The mint needs imas-python, numpy, the netCDF and Zarr readers, and the COCOS factors, which ambix takes from nova (imas_ambix/cocos.py canonical_factor delegates to nova.io.cocos). This section makes the engine its own distribution. It is imas-alambic, a uv workspace member at packages/imas-alambic/, with import package imas_alambic. It declares requires-python = ">=3.12", because the analysis server runs Python 3.12.9 while ambix requires 3.14. Its version has the root's owner: dynamic = ["version"] with hatch-vcs reading this repository's git tags (raw-options pointing at the repository root), never a static number.

The engine takes the map schema (machine_maps/schema.yaml), machine_map.py, signal_map.py, transform_engine.py, virtual_zarr.py, eddb.py, eddb_remote.py and the COCOS layer in imas_ambix/cocos.py. Each is moved rather than copied: ambix imports it from imas_alambic, and imas-ambix depends on imas-alambic through a workspace source. The map files stay with ambix, and so do the roots that point at them. PACKAGED_MACHINE_MAP_ROOT (machine_map.py:24) and PACKAGED_MAP_ROOT (signal_map.py:43) are module constants inside the files that move, and about ninety call sites, most of them tests, reach the maps through them. So the bundle discovery below lands in the same change as the move. Giving every call site a root argument now, only to take it away again, would churn the same ninety lines twice. The engine carries code and schema, never map data. Its runtime dependencies are numpy, imas-python, zarr, pyyaml and nova-cocos. The COCOS factors come from nova-cocos (nova:cocos-standalone-distribution §1) because nova itself requires Python 3.14 and cannot install on the server, and the plan allows no second factor table. Every ambix import of nova.io.cocos switches to nova_cocos in the same change, which frees nova to drop the re-export.

load_machine_map(path) and load_signal_map(path) already accept any file, so a private bundle needs no new format, only a way to be found. The by-name resolvers already exist, and each refuses an unknown name: load_packaged_machine_map(machine) (machine_map.py:1623), load_packaged_signal_map(machine, system) (signal_map.py:631) and resolve_description_store_root(name) (machine_map.py:118). This section generalises those three in place to search an ordered set of bundles, rather than adding a resolver beside them. Each keeps one owner, and every caller moves with it if its name changes to say what it now does.

A bundle is a directory holding a bundle.json beside the layout ambix already packages: machine_maps/<machine>.json, maps/<machine>/<ids>.json and machine_description/<machine>/. bundle.json gives the name, the version, the machines, and the bundle's named store roots, relative to the bundle. Bundles are found in two ways, because there are two kinds:

  • An installed package registers its bundle under the entry-point group imas_alambic.bundles. This is how ambix exposes its packaged maps (MAST, DIII-D, and JT-60SA until §1 moves them) and the store-root names that paths.py owns. So the engine ships no maps of its own, and paths.py stays the owner of ambix's on-disk layout.
  • A directory that is not a Python package, such as the bundle relayed from GHCR, is named in IMAS_ALAMBIC_MAP_PATH.

Those two retire the engine's own reading of the module-level packaged roots, and the getattr lookup against ambix's paths module, which the engine cannot import. The constants themselves move to ambix's paths.py as the address of ambix's own bundle. The sites that read them directly keep doing so through paths.py: spine_bench/transform_geometry_source.py:31,362 and tests/data/test_jt60sa_signal_maps.py:24,38. LINKML_SCHEMA_PATH moves with the schema, so tests/data/test_machine_map.py:202,1704,1724, which reach mast.json through LINKML_SCHEMA_PATH.parent, read it from ambix's map root instead. The nova.io.cocos importers that stay in ambix switch to nova_cocos in the same change: data/cocos_convention.py:26, challenge/convention.py:28 and tests/data/test_cocos_convention.py:11. The repository already has one by-name description resolver, gs/artifact_resolution.py resolve_machine_description, with AMBIX_MACHINE_ARTIFACT_CACHE and AMBIX_MACHINE_ARTIFACT_DIGEST. It is not this resolver's owner. It locates a nova-authored solver artifact addressed by manifest digest and semantic pin, re-authors that artifact through nova when it is absent, and imports nova, which cannot install at the facility. The bundle resolver instead locates authored map files and their description store by machine name. The two stay separate, and neither reads the other's variables. A machine found in two bundles raises the existing MachineMapError naming both, rather than one silently shadowing the other. The same directory reached by both routes counts as one bundle. No new refusal family is added. Inside a worktree, the shared environment carries ambix's entry points only as of its last sync. So the node's gate runs ambix's map tests with IMAS_ALAMBIC_MAP_PATH naming the worktree's imas_ambix/data, and the entry point is proved by the integration run after the merge, with the environment synced and the variable unset.

The interface account: §2 adds no command and no refusal family, and its environment variable and entry-point group are accounted for above. Its only new public surface is the distribution itself, which exists because imas-ambix cannot install on the facility's Python. The engine gains one console script, imas-alambic, and it gains it only with the mint. jt60sa-pulse-ids §1 adds mint_pulse in imas_ambix/data/pulse_mint.py and a mint command in imas_ambix/data/cli.py as the facility's entry point. That entry point works at the facility only once it lives in the engine. So the first section to find both pulse_mint.py and imas-alambic on main moves the function to imas_alambic.pulse_mint and the command to imas-alambic mint, and retires imas-ambix data mint. That section is §2 if the writer has landed when §2 is cut, otherwise §6. The engine's CLI is that one command plus --version, written with click as ambix's data CLI is.

Done-when: uv build --package imas-alambic writes a pure-Python wheel whose Version equals a root build's at the same commit. In a clean uv venv --python 3.12 environment, that wheel installs with its declared dependencies (nova-cocos from its own built wheel), python -c "import imas_alambic, nova_cocos" succeeds, and the engine's own tests, on synthetic maps, pass. When §2 moved the mint, imas-alambic mint --help also runs there. Every call site of the by-name loaders changes only its import. A synthetic bundle directory on IMAS_ALAMBIC_MAP_PATH resolves by name, and a machine present in two bundles raises MachineMapError naming both. Ambix's tests that cover the moved modules and its packaged maps add no failures against the stated base. After the merge and a sync, with IMAS_ALAMBIC_MAP_PATH unset, the same tests resolve MAST, DIII-D and JT-60SA through ambix's entry point. uv run --no-sync ruff check imas_ambix tests packages exits 0.

§3 — A local EDDB read on the analysis server

On the analysis server the EDDB read runs locally instead of over ssh, and the reader stays the one REMOTE_SCRIPT (eddb_remote.py:373). The ssh hop is not part of the Transport seam (eddb_remote.py:153). RemoteEddbExtractor._argv() (eddb_remote.py:322) builds it into the argv, putting ssh_command in front of a module-load shell string. Meanwhile SshTransport.run is a plain subprocess runner over whatever argv it receives. The local transport is therefore that same runner fed a local argv. Today _argv() returns the ssh prefix plus one shell string from _remote_shell_command() (eddb_remote.py:305), which cannot run without a remote login shell. So both are changed: with an empty ssh_command, _argv() composes nice -n 19 <python> -c REMOTE_SCRIPT as a list, with no ssh prefix and no module shell, because the venv's own Python already has numpy. The module-load string stays only on the ssh route. No new Transport class is added. SshTransport is renamed to say it runs a subprocess, and every caller moves with it. The envelope and decode_batch are shared, and no reader is extracted or duplicated.

Done-when: a stand-in eddb_pwrapper on the script's path returns recorded arrays for E101154's pf_active channels. Through it, the local transport returns ChannelRecords whose arrays equal the stand-in's bit for bit, decoded by the same decode_batch the ssh route uses. Mint equivalence waits for the writer and is §6's measure.

§ Decisions

Do the JT-60SA maps and their evidence stay in the public imas-ambix repository?

Lead, 2026-10-06: the JT-60SA maps are stored in a private GHCR and leave the public repository.

How does the map reach the facility?

Lead, 2026-10-06: install the light mapper on JT-60SA, preferably by wheel, starting with an editable checkout there to test.

What is the slim engine called?

imas- prefix with an ambix-lineage name; ambix (ἄμβιξ) became al-anbīq, then alambic / alembic.

Lead, 2026-10-06: imas-alambic, the French form of the still that ambix became; import name imas_alambic avoids SQLAlchemy's alembic. Free on PyPI and GitHub.

Where does the engine's code live?

Lead, 2026-10-06: packages/imas-alambic/ in this repository; one plan system, atomic data-layer changes; splittable later with history.

Where are the JT-60SA maps authored, with GHCR as their store?

Lead, 2026-10-06: map edits keep git diffs and reviews; GHCR holds the versioned artifacts the install consumes.

What happens to the 12 origin commits that carry the maps?

Lead, 2026-10-06: remove the maps from main going forward; no force-push. upstream never carried them.

How do the private maps reach the analysis server?

Lead, 2026-10-06: no GitHub credential is placed on a facility machine.

Do the JT-60SA evidence fragments and signal figures under docs/ stay public?

They are records of the jt60sa-machine-map and jt60sa-geometry-and-signal-figures plans and are served on the public Pages dashboard; moving them breaks those plans' evidence anchors.
