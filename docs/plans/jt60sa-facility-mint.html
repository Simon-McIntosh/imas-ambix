JT-60SA Facility Mint: Public Engine, Private Maps

The machine map (jt60sa-machine-map) turns JT-60SA data into IDS paths, and jt60sa-pulse-ids §1 adds the writer that mints a pulse. Both run here, reading EDDB over ssh into a cache. This plan moves the mint to the facility. A slim public engine, imas-alambic, loads a private JT-60SA map bundle that it finds by machine name, and reads EDDB locally on the analysis server. The lead settled the route on 2026-10-06. The engine is a uv workspace member of this repository. The maps are one flat bundle, edited in place under /work/projects/imas_gpu/jt60sa/maps/ and released as private GHCR artifacts, which this machine relays to the server. There is no private git repository. The install starts as an editable checkout on the analysis server, to test, and moves to a wheel.

IMASDB/
├── bin/imas-alambic          launcher

§15 — Write fetches a pulse it has not cached

§6 runs imas-alambic write 101154 at the facility, where the EDDB cache is empty. write_pulse refuses a pulse with no cache (shot ... has no EDDB cache), and nothing in the engine calls eddb.fetch_channels. So the writer the settings call "on-demand" cannot yet fetch anything, and §6 would stop at its first step. Development never met this, because the /work cache already holds the OP1 shots.

Before writing, write builds the channel requests its signal maps declare for the pulse. It passes them to fetch_channels, which skips anything already cached, so a cached pulse makes no transport call. Refused channels stay reported, as they are today. The transport is one setting owned by settings.py, eddb_host, set by --eddb-host or IMAS_ALAMBIC_EDDB_HOST. It has a flag and a variable like every other setting since §8, so config can report its source. Nothing is retired: the extractor's ssh_command parameter stays, and the setting only chooses what is passed to it. eddb_remote.py keeps owning how the ssh route is spelled. It gains one function that composes the ssh command for a host, keeping -F ~/.ssh/config and the remote module-load shell. DEFAULT_SSH_COMMAND becomes that function applied to jt-60sa. Unset keeps today's default, ssh to jt-60sa, so this checkout does not change. A host name composes the ssh route to that host. The value local gives an empty ssh_command: the local transport from §3. The facility launcher written by install/imasdb.sh exports IMAS_ALAMBIC_EDDB_HOST=local beside IMAS_ALAMBIC_HOME, because EDDB is on that machine. The installer's own SSH_HOST names the server it installs onto, which is a different job, and stays. imas-alambic config prints the setting with its source.

§ Decisions

Do the JT-60SA maps and their evidence stay in the public imas-ambix repository?

Lead, 2026-10-06: the JT-60SA maps are stored in a private GHCR and leave the public repository.

How does the map reach the facility?

Lead, 2026-10-06: install the light mapper on JT-60SA, preferably by wheel, starting with an editable checkout there to test.

What is the slim engine called?

imas- prefix with an ambix-lineage name; ambix (ἄμβιξ) became al-anbīq, then alambic / alembic.

Lead, 2026-10-06: imas-alambic, the French form of the still that ambix became; import name imas_alambic avoids SQLAlchemy's alembic. Free on PyPI and GitHub.

Where does the engine's code live?

Lead, 2026-10-06: packages/imas-alambic/ in this repository; one plan system, atomic data-layer changes; splittable later with history.

Where are the JT-60SA maps authored, with GHCR as their store?

Lead, 2026-10-07, revising the earlier private-repo choice: GHCR alone protects the maps; there is no private git repository. The flat bundle is edited under /work/projects/imas_gpu/jt60sa/maps/ and each released version is pushed to private GHCR; the immutable tags are the history.

What happens to the 12 origin commits that carry the maps?

Lead, 2026-10-06: remove the maps from main going forward; no force-push. upstream never carried them.

How do the private maps reach the analysis server?

Lead, 2026-10-06: no GitHub credential is placed on a facility machine.

Do the JT-60SA evidence fragments and signal figures under docs/ stay public?

They are records of the jt60sa-machine-map and jt60sa-geometry-and-signal-figures plans and are served on the public Pages dashboard; moving them breaks those plans' evidence anchors.

Lead, 2026-10-07, revising the earlier move-private choice: JT-60SA evidence fragments, landed records and figures stay in docs/ with their normal content, because that feedback is wanted. Only the maps are private, in GHCR. GitHub Pages stays off.

What is the engine's one command called?

The lead's ruling of 2026-10-07: the command writes a shot's IDSs, so it is write; mint suggested currency, map is the package's core noun, and convert is imas-python's DD conversion.

How do facility users run the engine?

Lead, 2026-10-07: replace source env.sh. The tool environment and a uv-managed Python 3.12 live in IMASDB/tools; the launcher IMASDB/bin/imas-alambic clears PYTHONPATH and sets IMAS_ALAMBIC_HOME. Other users need neither uv (there is no uv module on the server) nor the python module.

Where does the facility's IMAS folder live?

Lead, 2026-10-07: under /home/SharedFolder, the facility's shared area, in the account-named directory its README requires, with mode 1755. Named IMASDB; no machine level, because the folder serves one machine.

How are written IDSs laid out?

Lead, 2026-10-07: the folder is named ids, not data, because the maps are data too. Files are flat <pulse>_<run>.nc, so each file names itself and other names can sit beside it. Each run file carries every machine-description IDS of the shot's operating phase, alongside the served signals.

Where do the facility's defaults come from?

Lead, 2026-10-07: a facility folder serves one machine, so no install, path or package names it. Defaults derive from IMAS_ALAMBIC_HOME, which the launcher sets, and the machine is inferred from the one reachable bundle. The install-time option is the folder given to the install command. No site package, so no token is needed to install.

How is a facility bundle laid out?

Lead, 2026-10-07: the machine is named once, in bundle.json. Ambix's in-repo data keeps the multi-machine layout.
