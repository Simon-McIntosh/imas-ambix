Run the map where the data lives

JT-60SA Facility Mint: Public Engine, Private Maps

The machine map (jt60sa-machine-map) turns JT-60SA data into IDS paths, and jt60sa-pulse-ids §1 adds the writer that mints a pulse. Both run here, reading EDDB over ssh into a cache. The lead asked whether a public wheel could load a private map file so that, run at JT-60SA, it mints IDSs by itself. This plan answers yes, conditionally, and lays out the route: a slim public engine, a private map bundle it finds by machine name, and an in-process EDDB read on the facility's analysis server. Nothing here starts until the lead has decided where the JT-60SA maps may live and whether to install at the facility.

§1 — Where the maps and the data-load code live today

The data-load code is in imas_ambix/data/. eddb_remote.py sends a batch of EDDB channel requests down one ssh session to the analysis server, whose remote half runs on the server's Python 3.12 with only the standard library, numpy and eddb_pwrapper. eddb.py owns the cache under /work/projects/imas_gpu/jt60sa/{shot}.zarr. signal_map.py and virtual_zarr.py apply the pulse maps over that cache, and transform_engine.py with machine_map.py serves the machine description through the catalogue. The maps are package data beside that code: imas_ambix/data/machine_maps/jt-60sa.json and imas_ambix/data/maps/jt-60sa/{pf_active,tf,magnetics}.json, found through PACKAGED_MACHINE_MAP_ROOT and PACKAGED_MAP_ROOT. Both GitHub remotes of this repository, the origin fork and upstream, are public, and the JT-60SA maps and their evidence fragments are pushed to origin. The description store and the SELENE deck copies it is built from live only under /work/projects/imas_gpu/jt60sa/, never in git.

This section settles the decision map-privacy. If the maps are to be private, it moves them and their evidence fragments into a private bundle repository, leaves the engine's tests running on synthetic maps, and records what remains in the public history, which a move does not erase. Rewriting that history needs the lead's explicit approval and is not assumed. Done-when: the decision is locked, and the repository matches it.

§2 — A slim public engine

ambix declares 33 runtime dependencies, including torch, lightning, transformers, jax and torax, and none of them is needed to mint. The mint needs imas-python, numpy, the netCDF and Zarr readers, and the COCOS factors, which ambix takes from nova (imas_ambix/cocos.py canonical_factor delegates to nova.io.cocos). This section makes the engine installable on its own: the map schemas, the transform engine, the signal-map compiler, the mint writer and its command, as a distribution whose dependencies are those few. The COCOS factors come from nova as today, so either nova's COCOS module installs without the rest of nova, or the dependency is named and justified; a second factor table in the engine is not an option. Done-when: the slim distribution installs into a clean Python 3.12 environment with numpy and imas-python alone, and the jt60sa-pulse-ids §1 mint test passes against it.

§3 — Private maps by name, and an in-process EDDB read

load_machine_map(path) and load_signal_map(path) already accept any file, so a private bundle needs no new format, only a way to be found. The mint resolves a machine's catalogue, signal maps and description store from a declared search path or an entry-point group that a private bundle package registers, with the packaged maps as the fallback. A machine found in two places is refused rather than one silently shadowing the other. On the analysis server the EDDB read runs in process through eddb_pwrapper instead of over ssh. That is a second transport beside the ssh one, and the code the remote script already runs, not a second reader. Done-when: with a bundle on the search path and the in-process transport given a recorded EDDB response, the mint writes the same IDSs as the ssh route for E101154, byte for byte.

§4 — Install at the facility, or export tokamap maps instead

Two routes reach the facility. The first installs the slim engine and the private bundle in the analysis server's Python 3.12 environment, and mints there. The second installs nothing: imas_ambix/data/tokamap_export.py already writes a catalogue as a tokamap mapping directory, exact in value but lossy in provenance, which libtokamap and UDA consumers read. That route serves the facility only if JT-60SA exposes its data through UDA. The decision facility-install chooses between them. Installing on a facility server is an outward-facing action, taken only with the lead's explicit go-ahead and under the standing rule of light load on that server. Done-when: the chosen route mints or serves E101154 at the facility, and its IDSs match the ones minted here.
