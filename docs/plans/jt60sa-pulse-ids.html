From data load to IDS write, and a pulse you can watch

JT-60SA Pulse IDSs and Equilibrium Animation

The JT-60SA machine map (jt60sa-machine-map) holds the transformation from facility data to IDS paths: a catalogue that serves the machine description of each operating phase, and signal maps that carry EDDB channels to coil currents, the TF current and the plasma current. Nothing yet writes a pulse. This plan mints one, E101154 (OP1, plasma current near 1 MA), as IDSs on disk, then animates it from those IDSs alone. Each frame shows the flux surfaces, the separatrix, the O-point, the X-points and the strike points over the wall, the vessel and the coil outlines, drawn by imas-ink. Running the same mint at the facility is planned separately, in jt60sa-facility-mint.

§1 — Mint a pulse: one writer from data load to IDS write

Two halves of the transformation exist and nothing joins them. The static half is the catalogue imas_ambix/data/machine_maps/jt-60sa.json, served through imas_ambix/data/transform_engine.py StoreEngine: it emits the five description IDSs (pf_active, pf_passive, wall, magnetics, tf) of the phase a shot falls in, from the store under /work/projects/imas_gpu/jt60sa/machine_description/{OP1,OP2}. The dynamic half is the signal maps imas_ambix/data/maps/jt-60sa/{pf_active,tf,magnetics}.json, which imas_ambix/data/virtual_zarr.py VirtualZarrView applies over the EDDB cache /work/projects/imas_gpu/jt60sa/{shot}.zarr, producing arrays for the reconstruction spine. The mint takes the description IDSs for the shot's phase, writes into them the time-dependent quantities the signal maps serve (each PF coil's current, the TF coil current, magnetics/ip), and writes one DD 4.1.1 netCDF file per IDS under /work/projects/imas_gpu/jt60sa/ids/{shot}/, the layout the description store already uses.

The writer extends the two owners rather than adding a third path: the description comes from StoreEngine and the samples from the compiled signal map, so a unit, sign or COCOS factor is applied in exactly the place it is applied today. A signal the maps block (the second TF chain, the PF chains the cached shots do not corroborate) is not written. ids_properties.homogeneous_time is 1 only when every signal written into that IDS shares one time base, and otherwise 0 with each signal carrying its own time vector. The entry point is a mint command beside the existing ones in imas_ambix/data/cli.py, taking the machine and the shot.

Done-when: imas-ambix data mint --machine jt-60sa --shot 101154 writes pf_active, pf_passive, wall, magnetics and tf for E101154, and a test reads each back through imas.DBEntry at DD 4.1.1. In that test the 12 coils' currents equal the compiled signal map applied to the cached channels sample for sample, magnetics/ip peaks near 1 MA, and the static geometry equals the OP1 description byte for byte. Minting a shot with no cache refuses and names the missing cache. The mint reads only the cache and the store and never contacts the JT-60SA server.

§2 — The equilibrium IDS, with its topology

The animation draws equilibria, and the machine map's §7 owns mapping them: its second rung reads SELENE's equilibria from the facility's equilibrium database (EQDB) and maps psi on its grid, the boundary and the profiles into equilibrium, after §6 has fixed the source COCOS from data. This section does not read EQDB itself. It waits on that rung and mints E101154's equilibria through the same writer as §1, so the equilibrium joins the other five IDSs in /work/projects/imas_gpu/jt60sa/ids/101154/.

imas-ink renders topology and never computes it, so the minted IDS must carry it in the fields imas-ink reads (imas_ink/extract.py extract_slice): psi on profiles_2d[0] with its grid.dim1 and grid.dim2; global_quantities.psi_axis, psi_boundary, ip and magnetic_axis, which is the O-point; boundary.outline; each X-point in constraints.x_point[].position_reconstructed; and each strike point in constraints.strike_point[].position_reconstructed. Where the EQDB record already carries the X-points and strike points, the map binds them. Where it does not, they are computed from the mapped psi and the coil_vv first wall by nova's equilibrium topology (nova/equilibrium), which owns separatrix and X-point finding, rather than by a new finder in ambix. The decision topology-source settles which, once the machine map's open question eqdb-reader fixes the record's fields.

Done-when: E101154's minted equilibrium reads back through imas.DBEntry at DD 4.1.1 with one time slice per SELENE record. For every diverted slice, a test asserts at least one X-point inside the vessel, two strike points within 1 cm of the first wall, and an O-point inside the last closed surface. For every slice, the psi at the reported O-point and X-point matches psi_axis and psi_boundary within 1 % of their difference. imas_ink.extract.extract_slice reads every slice without falling back to an empty field.

§3 — What imas-ink provides, and what it must add

imas-ink already draws most of what the animation needs, and by the lead's figure-owner ruling every JT-60SA figure renders through it, in its own style and without labels. imas_ink.animate.animate_pulse(eq_ids, geom) iterates an equilibrium IDS's time slices, renders each with imas_ink.figures.equilibrium_figure_mpl and encodes a GIF. That figure layers flux contours, the separatrix, the O-point, X-point markers, divertor legs and strike points over geometry_figure_mpl: the wall outline, coil outlines, probes and flux loops. imas_ink.extract.extract_geometry(wall, pf_active, magnetics) builds that geometry from IDSs. Coils are drawn as outlines; the animation carries no coil-current shading, by the lead's decision animation-content.

Two things are missing for JT-60SA, and both belong to imas-ink, not ambix. First, the vessel: the minted wall carries the vacuum vessel as an annular unit (description_2d/vessel/unit/annular/outline_inner and outline_outer), which imas-ink does not draw yet. imas-ink's own plan imas-ink:geometry-figure-vessel-units owns that, and §4 waits on it. Second, animate_pulse does not pass equilibrium_figure_mpl's show_probes and show_flux_loops through, so the animation cannot leave the 17 probes and 27 flux loops out of an equilibrium frame. If the lead keeps sensors out of the animation, that pass-through is a node in imas-ink's repository, recorded on its plan, never a wrapper in ambix. This section is complete when both needs are recorded on imas-ink's plan and the decision animation-sensors is locked.

§4 — The E101154 animation, from IDSs alone

A short script, scripts/jt60sa_pulse_animation.py, opens only the minted IDSs in /work/projects/imas_gpu/jt60sa/ids/101154/, builds the geometry with extract_geometry from wall, pf_active and magnetics, and calls animate_pulse on equilibrium. It draws nothing itself and holds no style constant, so a rendering change is an imas-ink change. The GIF is written to docs/figures/jt60sa-pulse/E101154.gif; it is raster by nature, so no SVG twin is written.

Done-when: the GIF exists with one frame per equilibrium time slice. The script refuses if any input is not a minted IDS, so no frame reads the cache, the store or EQDB directly. The evidence fragment docs/evidence/fragments/jt60sa-pulse-ids/ embeds the GIF and records its frame count, its time range and, per frame, the number of X-points and strike points drawn. The lead has looked at it.

§ Decisions

What does each frame of the pulse animation show?

The lead's ruling: flux surfaces with every topological feature (X-points, O-points, strike points); shading coils by current was rejected as decoration that carries no equilibrium information.

May nodes read SELENE equilibria from EQDB on the JT-60SA server?

Authorised by the lead for light load, searches included, provided the server is not hit hard: each record is fetched once into the cache and never refetched for timing.
