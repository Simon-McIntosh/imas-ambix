§1 — A reader per machine does not scale; a map per machine does

Machine-specific readers put the same three concerns — where the bytes live, what the channels mean, and how to reshape them — into one module per machine, so every new machine re-derives all three and every store change is edited in as many places as there are machines. The alternative separates them: a machine map declares what a machine's channels mean, and a transform engine, written once per store format, applies any map. Adding a machine becomes authoring a map. Adding a store becomes writing one engine. Neither costs the other anything.

§2 — What a map declares, and what it must not become

A map binds each machine channel to its Data Dictionary path, its units and sign convention, and the source location in the store. It is declarative and validated against a LinkML schema, following the precedent already in-house for diagnostic corrections.

The risk worth naming up front: maps that need conditionals — "this channel means one thing before shot N and another after" — stop being data and become a small language, and small languages in schemas are worse than code. This is not hypothetical here, because geometry genuinely changes across and within campaigns. The design rule is therefore that a map is valid for a stated shot range, and change is expressed by having more than one map, never by a conditional inside one. If that rule proves insufficient, the finding is that maps need code beside them, and it should be recorded rather than absorbed by complicating the schema.

§4 — Identity, without a global digest

A machine that changes has no single identity, so asserting "same machine" globally is the wrong test and is what made the previous digest scheme need repeated cutovers. Three assertions replace it, all of which survive a machine whose geometry moves:

  • Determinism — the same inputs produce byte-identical description output.
  • Partition consistency — every shot declaring a given description version carries an identical description, and the versions partition the corpus at the declared transitions.
  • Visible change — a transition produces an inspectable diff rather than one description silently smeared across a boundary.

Vendoring follows from this: the description is embedded in the experimental dataset and is authoritative for reads, so a pulse is self-contained and portable in the way IMAS semantics already assume; the bare description store is the production and distribution library, not a validation oracle to compare against.

§5 — Scope boundary

This plan produces machine description only. equilibrium and every other processed or code-output quantity that a result is compared against belongs to the targets builder, not here — mixing a reconstruction into the description is exactly the leak the geometry module's static-versus-reconstructed discriminator exists to prevent.

§6 — The adapter the reader clause actually needs

The transform emits a collection of arrays; the 41 legacy call sites consume a GeometryTable. Nothing bridges the two, and that single missing piece — not the engines, not the schema — is what blocks §5's reader clause. The bridge must be machine-neutral, or it reintroduces exactly the per-machine reader this plan exists to remove.

Two constraints make this harder than a data-shape conversion, and both are measured rather than anticipated. The catalog is not description-complete: probe poloidal angle is unbound, passive conductors have no binding set at all, and turn weighting, circuit topology and channel drive have no declaration in the schema. And a description-content change already moved the frozen spine metric by 3.2%, inside the 7.93% source-cutover budget but well outside the 1% same-source budget — so parity has to be demonstrated, not assumed.

The sequence the audit recommends, in order, each rung gated on the one before:

  1. Complete the DD representability corrections, then bind the missing description fields and the drive topology — passive conductors, turns_with_sign, poloidal angle, circuit identity.
  2. Build the generic table adapter, with no machine-name branch.
  3. Compare adapter and legacy tables on one representative from each of the 11 MAST ranges, requiring exact arrays, ordering, counts, derived mappings, filament reductions and signature keys.
  4. Compare build_operator channel order, Green's columns, grid and limiter masks, and cache keys.
  5. Add a transform-backed benchmark geometry source and run the frozen clean CPU stamp under same-source parity tolerances.
  6. Migrate the 41 readers by seam, keeping a compatibility facade until the reader census reaches zero.
  7. Remove the raw reader only once table and operator parity are exact and the frozen benchmark is green.

Done-when: the adapter reproduces the legacy table byte-for-byte on one representative per transition range including the setup signature key; the frozen spine stamp run through a transform-backed geometry source sits inside the same-source budget; and the census of modules invoking a legacy description-read API reaches zero.

§ Decisions

When a channel's meaning changes mid-corpus, does the map stay purely declarative with one map per shot range, or does the schema grow conditional expressions?

The transitions partition the corpus exactly with no gap and no overlap, so shot range alone expresses every observed change and no conditional is needed. What the evidence refutes is not the design rule but the assumption that campaign is the natural range: 10 of 11 boundaries fall strictly inside campaign M5, so the rule holds at the cost of more maps than campaigns. Locked on the §3 measurement rather than on the plan's stated preference.
