§1 — The training path is the constraint, so it sets the format

Every other consideration about where data lives — semantics, portability, publishability — is affordable only if the store keeps four H200s fed. That is the specific question this plan answers, and it is deliberately narrower than "which format is nicest": what read rate does each candidate deliver into the training loop, and where does it starve the device? A format that loses on this measurement does not get to win on elegance.

The two access patterns are not the same problem and must not be pooled into one verdict. Static machine description is read once per run and turned into geometry; its cost is amortised to nothing and almost any format is acceptable. Experimental data is streamed, sliced and shuffled for the whole of training; its cost is paid continuously. The working hypothesis is therefore that the answer differs between them, and that a single store for both is a compromise neither needs.

One measurement discipline is inherited rather than invented. fast_loader.py already carries a correction where a plan claimed 660 kHz for xma against a real 5 kHz, because the array length was read as a rate. Every number this plan produces is a measured throughput with its wall clock and its sample count stated, never a size divided by an assumption.

§2 — Arms

Three storage arms, measured on identical payloads:

ArmWhat it isWhy it is in
IMAS-netCDF imas-python's netCDF backend, written and read through DBEntry Access-Layer compliant by construction; the only arm that publishes as real IMAS data without a further step
zarr + DD-path metadata The incumbent zarr store, with each array carrying its Data Dictionary path and units as attributes Tests whether DD semantics are separable from the IMAS container — vocabulary without the I/O
native level-2 The existing MAST level-2 form as read today The incumbent baseline; a new format must beat what is already running

Four access patterns per arm: whole-description static load; single-shot multi-signal slice; N-shot batch stream at training batch size; and random access across the corpus. Plus one transport comparison — live transfer against a mapped data entry already on disk — which belongs here rather than with the transform engine, because a measurement split across two plans stops being comparable.

§4 — Deliverable

One proposal naming a storage format for machine description and a storage format for experimental data separately, each defended by measured rates, together with the cross-over points where the ranking changes and an explicit finding on what the IMAS shape costs as storage versus what it costs as interchange. Those are different questions and the proposal must answer both.

Done-when: all three arms measured across the four access patterns and the transport comparison, on one node class, with throughput, wall clock and sample counts recorded per run to named on-disk logs; the IDSTensorizer subclassing seam verified or refuted with the code path stated; a proposal recorded as an evidence document naming both formats with the numbers that decide them; and the two format decisions below locked or explicitly left to the owner with the evidence attached.
