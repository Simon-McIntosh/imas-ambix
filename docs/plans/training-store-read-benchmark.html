§1 — The training path is the constraint, so it sets the format

Every other consideration about where data lives — semantics, portability, publishability — is affordable only if the store keeps four H200s fed. That is the specific question this plan answers, and it is deliberately narrower than "which format is nicest": what read rate does each candidate deliver into the training loop, and where does it starve the device? A format that loses on this measurement does not get to win on elegance.

The two access patterns are not the same problem and must not be pooled into one verdict. Static machine description is read once per run and turned into geometry; its cost is amortised to nothing and almost any format is acceptable. Experimental data is streamed, sliced and shuffled for the whole of training; its cost is paid continuously. The working hypothesis is therefore that the answer differs between them, and that a single store for both is a compromise neither needs.

One measurement discipline is inherited rather than invented. fast_loader.py already carries a correction where a plan claimed 660 kHz for xma against a real 5 kHz, because the array length was read as a rate. Every number this plan produces is a measured throughput with its wall clock and its sample count stated, never a size divided by an assumption.

§ Decisions

Which format stores the experimental data that feeds GPU training?

Decided on the measurement rather than on preference. DD-annotated zarr reads 9.02-10.28x faster than native level-2 and about 3.2x faster than IMAS-netCDF, at every one of 12 scale/batch grid points over a 64x payload range, with 0 crossings on either axis. Experimental data is the pattern whose cost is paid continuously for the whole of training, so the read-rate term dominates and nothing else measured competes with it. The DD-path and units attributes ride along at no measured cost, so DD vocabulary is retained without the IMAS container. Evidence: docs/evidence/archive/training-store-read-benchmark-landed.html#s2 and #s2-crossover.

Which format stores the machine description, given it is read once per run and then turned into geometry?

LEFT TO THE OWNER with the evidence attached, as §4 permits. Read rate does not decide this: description is read once per run and amortises to nothing (whole-load 0.0202s zarr vs 0.2073s native, immaterial against a training run), so every arm is fast enough and the choice turns on publishability rather than performance. Trade-offs measured: IMAS-netCDF is Access-Layer compliant by construction and publishable as real IMAS data with no conversion project, but costs a four-method compatibility shim while the project stays on imas-python 2.2.0; zarr+DD paths give one store technology and one engine across both access patterns but need a conversion step to publish; both keeps netCDF as the published form and zarr as the working form, and the shared IDSTensorizer base means the two writers share the DD shape rules rather than duplicating them. Supporting finding: the IMAS shape costs about 3.2x as STORAGE but approximately nothing as INTERCHANGE, because the DD tensorization logic is reusable by subclass into a non-IMAS container — IMAS semantics and the IMAS container are separable and only the container is expensive. Evidence: docs/evidence/archive/training-store-read-benchmark-landed.html#s4.
