SDCC ticket — CUDA-runtime init failure on 98dci4-gpu-0003, 2026-05-26. Node recovered after reboot; superseded by the 2026-05-27 drain RCA (rca-node-drain-2026-05-27).

Symptom

Every CUDA-driver call inside a Group A allocation failed with cuInit() rc = 3 (CUDA_ERROR_NOT_INITIALIZED), reproducible from pure C with no PyTorch. nvidia-smi / NVML kept working — only the CUDA runtime/driver API path was broken. Node then went DOWN+DRAIN+NOT_RESPONDING.

Minimal repro (pure C, no torch)

sbatch --partition=betelgeuse --reservation=gpu_0003_grpA --account=grpa \
       --gres=gpu:1 --cpus-per-task=1 --mem=4G --time=00:02:00 --wrap='
cat > /tmp/t.c <<EOF
#include <stdio.h>
#include <dlfcn.h>
int main(){ void*h=dlopen("libcuda.so.1",RTLD_NOW);
  int(*cuInit)(unsigned)=dlsym(h,"cuInit");
  printf("cuInit rc=%d\n",cuInit(0)); return 0; }
EOF
gcc /tmp/t.c -o /tmp/t -ldl && /tmp/t'

Expected cuInit rc=0; observed cuInit rc=3.

Hypothesised cause

Driver/cgroup state degraded after concurrent Group A + Group B activity — the failure began when Group B job 1208566 (murawan) started, the only concurrent change. Group A lost CUDA-runtime access while keeping NVML. Looks like a driver state machine wedged between two cgroup contexts on the same physical device.

Proposed fix (in order)

  1. nvidia-smi --gpu-reset while no jobs run.
  2. Reload nvidia modules (rmmod nvidia_uvm nvidia_modeset nvidia + modprobe) after draining.
  3. Reboot the node if module reload isn't feasible.

Follow-up question for SDCC: does the SLURM gres cgroup plugin correctly isolate CUDA/UVM/NVRM state between concurrent Group A and Group B jobs? If Group B can wedge Group A's CUDA path, the device-cgroup isolation may need a kernel-module config tweak.
