§1 — What this records

The deepseek-v4-1-flash profile renders a serve script for three configurations: the H200 four-card default, and a B300 server at four and at eight cards. The Blackwell configurations are selected by agent serve deepseek-v4-1-flash --server b300 --gpus 4|8, resolved through ModelProfile.server_gpu_variants — a section keyed by the site-declared server name and then by card count.

This document records, for each Blackwell setting, the source it rests on. It exists because a launch topology that was reasoned about and one that was scaled proportionally from a different generation of silicon look identical in a generated script, and the second kind fails on the model's own startup path rather than at review time.

The distinction that matters throughout: settings that follow from the checkpoints and the kernels have a source and are stated as such; settings that follow from measured device memory have one source only on Hopper, and are marked unverified here rather than transferred silently.

§3 — The Blackwell image, and why it is the local one

A Blackwell serve needs an engine whose kernels were built for sm_100 and whose model registry knows deepseek_v41. Those are two different facts about two different artifacts, and the second is the scarcer one.

  • Registry support. The SGLang release that carries the deepseek_v41 model module and the DSPARK draft path is the build already pinned for this checkpoint; the install notes describe the release channel but do not by itself guarantee a given build was compiled for a given architecture (SGLang install). Treating "pip install sglang" as an answer is how a serve reaches the node, loads the model, and only then discovers the draft path is absent.
  • Architecture. The pinned container /work/projects/imas_gpu/containers/sglang-dev-dsv41.sif was inspected directly, and its torch build publishes ['sm_75', 'sm_80', 'sm_86', 'sm_90', 'sm_100', 'sm_120'] — sm_100 present. The inspection is the evidence; a version string is not.
  • Kernels that are not prebuilt. The container's sgl-kernel is JIT-compiled per device through tvm-ffi, resolved under ~/.cache/tvm-ffi at flashinfer 0.6.18, so a Blackwell device compiles its own variants rather than depending on a prebuilt sm_100 wheel that may not exist.
  • The one CUDA patch the serve binds. The generated script binds imas_ambix/agent/kernel_patches/…/main_norm_rope.cuh into the container. It is generic CUDA for the normalisation and rotary step, carries no architecture guard, and so compiles on Blackwell unchanged — which is why no second patch was written for this launch.

The script therefore names an image that exists under /work and needs no network at launch, which is the requirement a launch from this node has.

§4 — Topology, KV dtype and the MoE runner

The vLLM recipe for this checkpoint publishes a Blackwell section that names, per SKU, exactly the choices a Hopper-scaled launch would get wrong (vLLM recipe, DeepSeek-V4.1-Flash). vLLM and SGLang are different engines with different kernels, so the recipe is used here for what is a property of the checkpoint and the silicon rather than a property of vLLM's flags:

  • Parallel shape. Blackwell uses TP2 with FLASHINFER_MLA_SPARSE_DSV41 and Engram CPU offload, and data+expert parallel at the hardware's own GPU count — DEP8 on B200/B300 nodes, DEP4 on GB200/GB300 trays. On these profiles the parallel width equals the card count (TP4/EP4 on four cards, TP8/EP8 on eight), which is the Blackwell expert-parallel arrangement rather than a rescale of the Hopper TP4.
  • KV dtype. Both Blackwell configurations set --kv-cache-dtype fp8, and the indexer dtype to mxfp4. SGLang's spelling of the same choice is fp8_e4m3, which is what the variants declare; the container's flashinfer build is the current one, so the FP8 KV path is available. Rollback: if the model's startup rejects an FP8 KV entry on this engine, the variants fall back to the profile's bf16 default, at half the tokens per byte of pool.
  • MoE runner. The Hopper path names flashinfer_mxfp4 — a deliberate choice for MXFP4 routed experts on SM90. On Blackwell the recipe's expert-parallel arrangement runs its MoE through deep_gemm's fused mega-MoE kernel, so a backend named for the SM90 flashinfer path is the wrong pin to inherit: the variants declare auto and let the engine select for the silicon it is on. This is the setting to confirm in the first launch's startup log, because auto resolves to a concrete backend and only the log says which.

§5 — Context, pool and the running-request bound

Three numbers, three different kinds of evidence, and they must not be confused.

  • Context 524,288. The Hopper path is capped at 262,144 by the decode-indexer cost on SM90 — a hardware limit, stated in the profile's own tuning comments. That cap does not travel to a compute capability without SM90's indexer. 512K also sits above the largest per-turn input ever measured from a worker on this lane, 356,574 tokens, so it covers observed agent traffic with room rather than being chosen as a round number.
  • Pool 4,000,000 / 8,000,000 tokens. Device memory is 288 GB per B300 card against 140.4 GB per H200, so the pool the Hopper path runs at (max_total_tokens = 4000000 at four cards) fits on four B300 cards with the checkpoint's resident weights and Engram tables on-device, and doubles with the card count. The pool is declared rather than auto-sized for the reason the profile gives on Hopper: a lazily allocated fused-MoE workspace lives outside the memory fraction, so an auto-sized pool is a bet against a concurrency-dependent allocation.
  • Running bound 48 at eight cards, 24 at four. The Hopper path's own bound is 36, which is a per-profile scheduler ceiling rather than a measured capacity; the Blackwell bound is instead scaled from the one throughput knee on record for this lane: width 10 at four H200 cards, and the capacity study's projection that a B300 node carries 3.9–6.3× the H200 four-card capacity (serving capacity and the B300 projection; device figures compared in H200/B300 performance). 10 × 3.9 ≈ 39 and 10 × 6.3 = 63, so the eight-card starting width of 48 sits inside that bracket rather than at either end of it; the four-card variant is half the width of the eight-card one because the pool it draws on is half the size. This is a starting gate width: it is a launch bound to be measured against the engine's own counters, not a capacity finding.
  • CUDA-graph batch equals the running bound. Decode capture is sized to the widest batch the scheduler will admit, so a request admitted outside a captured shape falls back to the eager path — the profile's Hopper comment records that shape of cost.

§6 — Speculative decoding and the caches

  • DSpark depth 5. The recipe states DSpark "still drafts 5 tokens per round" on this checkpoint, and that DSpark is the only speculative method it supports (the MTP module was dropped). The Hopper profile's 3 was chosen by a live A/B on real traffic on that topology; the Blackwell variants start at the recipe's stated depth and are to be re-tested the same way rather than inheriting a measurement taken at a different width.
  • Hierarchical cache off. On Hopper the host cache earns its place by holding prefixes the device pool would otherwise recompute. On eight B300 cards the device pool is 8,000,000 tokens against a measured working set in the tens of thousands per session, so there is little to evict to the host, while the feature keeps a second index and moves prefixes over the host link. It is switched on again only against a reading that shows the device pool evicting.
  • Engram host table off. On Hopper the 183.1 GiB of Engram tables are moved to pinned host RAM because four 140.4 GB cards cannot hold them beside the resident weights. 8 × 288 GB = 2.3 TB against a 511 GB on-device footprint, so the offload buys nothing and costs UVA reads on every token. The variants set SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=0.

§7 — What is carried over rather than sourced, and what to measure first

One setting has no Blackwell source and is carried over deliberately, said so in the profile, and should be re-measured at bring-up:

  • mem_fraction_static = 0.85 — the profile default, inherited by both Blackwell variants. The figure comes from a Hopper measurement: at 0.92 the fused-MoE workspace, allocated lazily outside the fraction, died at 256 concurrent while the KV pool sat at 3–7% occupancy; at 0.85 the same requests ran 1.7× faster and the pool still held 2,200,283 tokens. Neither the workspace size nor the split has been measured on Blackwell, and the Hopper numbers cannot be rescaled into one: the workspace is an SM90 kernel-batch allocation. Hold 0.85 as a conservative start, then read free device memory after a real multi-hundred-token generation — not after startup, because the allocation is lazy — before moving it in either direction.
  • SLURM cores are not scaled from cards — cores are the scarce reserved resource on the Hopper node — so the Blackwell variants declare the same 12/16 core counts as the equivalent Hopper widths. The B300 node's own reservation core count is an arrival fact that has not been read, and the number to use is whatever the live ledger shows.

Nothing above claims a B300 serve has run. The first real launch should validate three things in order: the engine's startup reports sm_100 kernels rather than a fallback, a multi-hundred-token completion succeeds (which is when the fused-MoE workspace actually allocates), and the engine's KV occupancy at the declared gate width matches the pool this document computes.
