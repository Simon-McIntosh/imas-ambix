This request was written on 2026-09-21 to ask the site why the login node's user manager was being stopped, and it was never sent. Retirement note — never sent, cause found on our side

Never sent. Nothing in §1 reached the site, and neither ask in it is outstanding: no logind journal read was requested, and no group membership was asked for. The account is in none of adm, systemd-journal or wheel today, exactly as §4 records.

The cause was a reckon test fixture, not a lingering defect. A session-scoped test fixture, written to stop finished workers, passed a process id taken from a /proc scan or a run record straight into os.killpg. Such a pid can report a process group it does not lead, and a reported group of 1 makes killpg a signal to every process the caller may signal — across every control group and every login session on the host, which is why a stop written for one worker took the whole session slice with it, the user manager included. The fixture's own measurement recorded three instrumented processes in three unrelated control groups and three unrelated process groups signalled within eighty microseconds of each other from one pytest process, with si_code reporting a deliberate kill; no signal to a single group can do that. Corrected in reckon commit 586a1ac6 on 2026-09-20 15:06:18 CEST (a worker signal reaches the worker, never the whole account): signal_worker now reserves the group signal for a process that leads its own group, which is true of anything started detached on purpose, and signals anything else alone. The investigation this request was built on is the session-scope teardown record, whose outcome section carries the same finding.

The evidence that it is over. Measured on the login node 2026-09-22 20:30 CEST: loginctl show-user mcintos -p Linger returns Linger=yes, and systemctl show user@39486.service reports ActiveState=active continuously since 2026-09-20 15:34:42 CEST — an unbroken interval of about two days and five hours, with 14 sessions held for the account at the reading, against a record in which the same teardown recurred twice inside five hours and five times inside three days. /var/lib/systemd/linger/mcintos is still present, root-owned, written 2026-08-08 17:07.

What this document is now. The text below is the request as written, kept as the record of the evidence it assembled and of the exclusions in §2 and §4 — those measurements stood, and what they established was that the failure was one of lifetime rather than of allocation. The fleet-hosting plan's move onto a scheduler allocation is unaffected by this retirement and rests on the throttling evidence, not on this defect.

§1 — The request

The text below was written on 2026-09-21 as the send-ready request. It was not sent (see the retirement note above).

Two asks, both answerable by whoever can read the system journal on 98dci4-srv-1006.

  1. Read the logind journal for 02:31:11 on 2026-09-20 and tell us what stopped the user manager. The account is mcintos, UID 39486; the unit is user@39486.service. The sequence to look for is the Exit the Session teardown quoted in §2 — we need the unit that issued the stop and the trigger it acted on. The same read answers a second question: how often this has happened since 2026-08-10, which journalctl -u user@39486.service --since "2026-08-10" | grep "Exit the Session" returns directly.
  2. Add the account to a group that can read that journal — adm, systemd-journal or wheel — so the next occurrence can be read directly rather than through a request. We are in none of them today, and that is verified rather than assumed: on the login node, journalctl -u user@39486.service prints No journal files were opened due to insufficient permissions and exits 1.

What this request is not. It is not a request for a larger share of the login node's processor time, and we are not attributing the teardown to resource contention — §4 records the counters that exclude that. The failure is one of lifetime, not of allocation: a user manager that lingering exists to keep alive was stopped.

§2 — The teardown the journal records

The system journal shows a complete teardown of the user, performed by systemd itself — not a session scope ending on its own, and not third-party software. Reproduced from the record of the 02:31:11 event on 2026-09-20, where systemd[2817083] is the account's user manager:

systemd[2817083]: Activating special unit Exit the Session...
systemd[2817083]: Stopping reckon plan server...
systemd[2817083]: Stopping IMAS Codex LiteLLM Proxy...
systemd[2817083]: imas-codex-llm.service: Main process exited, code=exited, status=143/n/a
systemd[2817083]: Removed slice User Core Session Slice.
systemd[2817083]: Removed slice User Application Slice.
systemd[2817083]: Reached target Exit the Session.
systemd[1]:      user@39486.service: Deactivated successfully.
systemd[1]:      Starting User Manager for UID 39486...        <- 1-2 seconds later

Two units are stopped, not one. The live session scopes are torn down first, taking every process started through those connections; then the user manager itself is stopped, which removes app.slice and session.slice and kills the services inside them. That is what the one-second gap between SIGTERM and SIGHUP in §3 was recording. The two long-running services in app.slice — the reckon plan server and the IMAS Codex LiteLLM proxy (imas-codex-llm.service) — are killed with status=143 in the same teardown, and 143 is SIGTERM: imas-codex-llm.service: Main process exited, code=exited, status=143/n/a, with Removed slice User Application Slice immediately after it. Lingering then brings the user manager back one to two seconds later, which is why its active-enter timestamp always sits just after the event:

session-*.scope     KillSignal=15 (SIGTERM)   SendSIGHUP=yes   KillMode=control-group
user@39486.service  ActiveEnterTimestamp = Sun 2026-09-20 02:31:12 CEST

The teardown is not a one-off. The same stop was read twice in a five-hour window on 2026-09-18:

The same teardown appears twice in a five-hour window on 2026-09-18, at 00:57:08 and at 05:46:41.

That is what makes it a standing defect rather than a single event, and it is the recurrence the whole-fleet symptom follows: agents that were born in the scopes being stopped die with them, and the ones that survive are simply the ones whose scopes were already abandoned and therefore never signalled.

The five recorded occurrences

§3 — What was recorded live at the last occurrence

A signal canary — a shell that traps every catchable signal, logs which one arrived and deliberately does not die — was running in three multiplexer panes at 02:31:11 on 2026-09-20: one in an attached session and two in a session with no client attached at all. All three logged the same pair, within one millisecond of each other:

02:31:11.782  marker(3559642) received SIGTERM      <- unattached session
02:31:11.782  marker(3559640) received SIGTERM      <- unattached session
02:31:11.783  marker(293705)  received SIGTERM      <- attached session
02:31:12.785  marker(3559642) received SIGHUP
02:31:12.785  marker(3559640) received SIGHUP
02:31:12.785  marker(293705)  received SIGHUP

SIGTERM, then SIGHUP 1.003 seconds later, to all three. Two of the panes were in a session nobody was looking at, which rules out a terminal hangup reaching a foreground job. The scope configuration in §2 produces exactly this pair: KillSignal=15 with SendSIGHUP=yes, delivered under KillMode=control-group, so the signal goes to every process in the scope's control group rather than to a foreground process group or down a terminal.

A second instrument sampling process topology every five seconds recorded nine processes dying at that instant, three of them agent workers that were fully detached — parent 1, own session id, no controlling terminal. Detachment in the process sense (setsid, nohup, start_new_session=True) does not move a process out of the systemd control group it was started in, which is why processes with no controlling terminal died here.

§4 — What we have already checked, so the site does not have to

  • Lingering is enabled and persisted. loginctl show-user mcintos -p Linger returns Linger=yes, and /var/lib/systemd/linger/mcintos exists — root-owned, written 2026-08-08 17:07. A user manager is observed being restarted under it after each stop.
  • The journal is unreadable to us — No journal files were opened due to insufficient permissions, exit 1. This is why §1 asks for a read and for group membership.
  • Not memory. At the instant of the kill the control group showed memory.current 6.38 GB of a 64 GB cap and pids.current 101, and the oom_kill counter is byte-identical before and after the event.
  • Not processor-time throttling. Throttling stalls a process; it never signals one.
  • Not our load. Fewer than five agent processes were running when the 02:31:11 event fired, and the memory and task counters agree.
  • Not a host change. systemd 252-14.el9_2.3 was installed 2025-04-02 and logind.conf has not been touched since 2023-07-17; the node has been up since 2026-08-08 with no reboot. The behaviour is not new.
  • Not a visible reaper. No entry in /etc/cron.d, no logind idle action, no system timer anywhere near the event — the signal lands 0.78 s after the final logout, not on a schedule. No pam_exec hook on session close and no cleanup script that signals user processes.
  • What remained open when this was written was who issued the stop. Four of the account's scopes currently read SubState=abandoned and two of them hold multiplexer servers that have run for days, so an abandoned scope is plainly survivable and the difference between the scopes that died and the ones that did not is not visible from user space. The system journal names the caller; on this host it is readable only by adm, systemd-journal or wheel. That question has since been answered without the journal — the caller was this account's own test fixture, which is the retirement note above; the exclusion work in this section is what left the account's own tooling as the remaining candidate.

§5 — What an answer changes on our side

The answer arrived from this side, not from the site (retirement note above), so neither branch below arose: the manager is not being stopped, and the login node's failure was never one of lifetime. The branches are kept as written because they are what the request would have decided.

Either outcome is useful. If the behaviour is corrected, a long-lived agent process can stay on the login node, and moving the work onto compute becomes the robust choice rather than the only one. If the site confirms the stop is expected, we treat the login node as a host where a long-lived process cannot be kept alive and move the fleet into a scheduler allocation, whose control group is owned by the node daemon and sits outside the login manager's session lifecycle entirely.

We are instrumenting our side meanwhile rather than waiting: a probe that blocks the signals and reads the kernel's own sender information (si_code, sender pid and uid) is armed in three different control groups, so the next occurrence names the sender instead of describing it. That probe answers the same question at the next failure; the journal read answers it today.
