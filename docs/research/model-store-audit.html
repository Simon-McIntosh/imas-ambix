Model store audit — what /work/projects/imas_gpu/agents actually holds

Thirteen checkpoint directories carry 7.21 TB of weights accumulated across several serving plans. Nothing recorded which were complete, which a profile still resolves to, or which are superseded. This is that record. Nothing was deleted and nothing was modified: every figure below comes from a read-only walk on 2026-10-26.

What the store holds

  • 13 directories under /work/projects/imas_gpu/agents hold a model/ subdirectory. Together they are 7.21 TB apparent size, of which 7.21 TB is the weights themselves.
  • 12 of 13 directories carry a shard set that matches their repository's file listing at the commit the download recorded — every shard the index names is present, at the size the repository gives it. One, glm-5-3-w4a8, is present and self-consistent but cannot be checked against its repository, because that repository refuses an anonymous listing.
  • 12 of 13 first shards hash to the repository's LFS object at that commit. The thirteenth is the same glm-5-3-w4a8, for the same reason.
  • Two further directories, glm-5-2-4x and glm-5-3-int4, hold a download cache and no model/ directory. They are not in the table below; see the two cache-only directories.

How each figure was produced

The audit is one script with three phases, committed beside this document as model-store-audit.py. Its whole output is the log model-store-audit.log.

PhaseWhereCommand
fetch login node (needs outbound network) python3 -I model-store-audit.py fetch --out <run>/audit — reads each directory's .cache/hub/models--<org>--<name>/refs/main for the repository and commit, falls back to model/.cache/huggingface/download/*.metadata (line 1 is the commit), then downloads https://huggingface.co/api/models/<repo>/tree/<commit>?recursive=1, which gives every file's byte size and its LFS sha256.
audit compute node (never the login node) python3 -I model-store-audit.py audit --trees <run>/audit --out <run>/audit/report.json — du -sb for sizes, model.safetensors.index.json's weight_map for the shard list, stat for each shard's size against the listing, hashlib.sha256 over the first shard, the profile loader for weights_slug, and each receipt's header line for the served serve_config.model_path.
control compute node python3 -I model-store-audit.py control --trees <run>/audit --dir mimo-v2-5-pro --scratch <tmp>/control --out <run>/audit/control.json — the negative control, below.

Sizes are apparent bytes (du -sb), not allocated blocks, so they are comparable with the repository's own file sizes. Profile is the profile whose weights_directory_slug — a declared model.weights_slug, else the profile's own slug — names that directory, with a card-count variant shown as slug@Ngpu. Last receipt is the newest receipt whose header line names that directory, by serve_config.model_path where the receipt carries one — that is the directory a serve actually loaded, a stronger statement than the profile name. Only the newest receipts carry model_path; where it is absent the receipt is attributed by profile and marked by profile only.

Controls

Positive control — the September V4.1-Flash directory

The row the plan fixes as the control reads as required. deepseek-v4-1-flash is deepseek-ai/DeepSeek-V4.1-Flash at commit dba1be0a40aa45a94ad051997016db3960a90277, and its first shard hashes to 886aebdafa08cc27bbae2165ed35bdfe0de9370bf88c1411283c155c6ae4ff89, identical to the repository's LFS object at that commit. The figure below is the audit's own line for it, not a transcription:

Negative control — an index naming a shard that is absent

The completeness check was run against a scratch copy of one checkpoint's index — the smallest shard set in the store, mimo-v2-5-pro, 34 shards — in two arms. Both arms hold the real index and reach the real shards by symlink; the short arm is missing the first shard entirely, which is the state a download stopped one shard early leaves behind. Run on 2026-10-26:

full arm complete=True missing=0 size_mismatch=0
short arm complete=False missing=1 size_mismatch=0
CONTROL PASS

The check therefore reports incomplete when a shard the index names is not there, and complete when the same tree is whole. Without the full arm a check that simply always said incomplete would pass the short arm too.

What the audit found beyond the row values

  • An index's own total_size is not a completeness instrument. For minimax-m2-7 the index declares 480.8 GB of tensor data while the 125 shards it names resolve to 230.1 GB, both locally and in the repository's listing at that commit. For minimax-m3 the split is 869.2 GB declared against 854.2 GB of shards, again identical on both sides. In both cases the local tree and the repository agree exactly — so the check that matters is the named shard set present at the listed sizes, and comparing a directory's byte total against the index's total_size would have reported two complete checkpoints as truncated. Their shard-name suffixes overstate the set the same way: model-00000-of-00130.safetensors is the first of 125 files, not of 130.
  • One repository cannot be reached, so one directory's provenance stops at what was recorded locally. glm-5-3-w4a8 records camel-ai/GLM-5.3-W4A8 at 9ad5642de554 in its hub cache, and the download metadata agrees, but huggingface.co/api/models/camel-ai/GLM-5.3-W4A8 answers HTTP 401 without a credential. Its 141 shards are all present and its index is self-consistent; its sizes and hash are unverified because there is nothing to verify them against.
  • The rotation already moved the profile off its rollback directory. deepseek-v4-1-flash.toml now declares weights_slug = "deepseek-v4-1-flash-1017", so no profile resolves to deepseek-v4-1-flash any more, and no receipt names its serve_config.model_path — yet that directory is the rollback target the rotation keeps for a week, and it is also this document's positive control. Both facts make it the one unreferenced directory that must not be pruned on the strength of being unreferenced.
  • One directory is genuinely superseded. deepseek-v4-flash (159.6 GB, 46 shards, June revision) is named by no profile, because deepseek-v4-flash.toml declares weights_slug = "deepseek-v4-flash-0731". Nothing has served it since: the last receipt under the deepseek-v4-flash profile is dated 2026-09-15, and no receipt names this directory's model_path at all. It is complete and downloadable, which is what makes it the cheapest prune.
  • Receipts name a directory, and only DeepSeek has any. The 117 receipt files carry profile_slug in their header and serve_config.model_path in the same line; the second is the directory the engine loaded. Every receipt in the store belongs to a DeepSeek profile, so the GLM, Kimi, MiMo and MiniMax rows have no receipt at all — an absence of recording, not evidence the checkpoint was never served.

Recommendations, and the space behind them

Eleven directories are keep: each is the checkpoint a profile resolves to, and each is complete with a verified hash. One is backup: glm-5-3-w4a8 is the four-card GLM-5.3 default and exists on this store alone, so its 399.8 GB is the only copy of a checkpoint its repository will not serve anonymously. One is prune: deepseek-v4-flash, at 159.6 GB, superseded by -0731 and named by no profile. Pruning it, and the two cache-only directories, would return about 160 GB of the 7.21 TB.

Pruning is the lead's decision and is not taken here. The recommendation that needs a decision sooner than pruning is the backup: a checkpoint whose only copy is on this filesystem and whose upstream refuses an anonymous listing has no path back if this copy is lost.
