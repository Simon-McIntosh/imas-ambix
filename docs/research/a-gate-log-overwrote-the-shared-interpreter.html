§1 — Summary

On 2026-11-16 at 06:04:54 CET a reckon worker submitted a gate job whose wrapper script was called with one positional argument missing. The wrapper took the path of the worktree's Python as its log file and opened it for writing. That path is a symlink chain ending at the Python 3.14.2 binary that uv installs once per user, so the redirect replaced the interpreter with a 765-byte gate log. Every running Python process on that interpreter, on every node, died within about a minute. The fleet supervisor was one of them, and fleet job 1313886 ended at 06:05:16.

Slurm recorded the job as OUT_OF_MEMORY. That label is misleading: it comes from 125 out-of-memory kills accumulated over the job's 2.7 days, not from the final minute. Memory pressure on the fleet node is real and is described in §5, but it did not cause this failure.

The interpreter was restored at 06:53 CET with uv python install --reinstall 3.14.2. The work that reckon owns is in §6: nothing in the current design stops the same single mistake from doing the same damage again.

This record lives in imas-ambix because the session that diagnosed the failure could write only here. The mechanisms that need changing are reckon's.

§3 — Mechanism

The wrapper is a script the worker wrote for its own gates. It takes four positional arguments and checks none of them:

TREE="$1"
REVISION="$2"
LOG="$3"
PYTHON="$4"
shift 4
cd "$TREE" || exit 97
COMMAND="env -u SLURM_JOB_ID PYTHONPATH=. $PYTHON -m pytest -p no:cacheprovider -q $*"
{
  echo "# revision: $REVISION"
  ...
} > "$LOG"

The failing call left out the revision:

sbatch --wait -p all_debug -J rvq-gate-delivered -t 00:30:00 \
  -o "$RUN/slurm-delivered-gate.out" \
  "$RUN/arm.sh" "$WT" "$RUN/head-gate-delivered.log" "$PY" \
  tests/test_run_verbs_share_one_identity_grammar.py

Every argument therefore moved one place to the left.

VariableIntendedReceived
TREEthe worktreethe worktree
REVISIONa committhe log path
LOGthe log path<worktree>/.venv/bin/python
PYTHON<worktree>/.venv/bin/pythonthe test file

The redirect > "$LOG" followed three symlinks to one regular file:

<worktree>/.venv
  -> ~/Code/reckon/.venv                       (worktree provisioning)
~/Code/reckon/.venv/bin/python
  -> ~/.local/share/uv/python/cpython-3.14.2-linux-x86_64-gnu/bin/python3.14
                                               (uv's per-user install)

The file that replaced the interpreter is the wrapper's own log. It names the job and the shifted arguments, which is how the cause was identified:

# revision: ~/.config/reckon/crew/runs/r-20261115T224629880489-qwnw-red-file-run-verbs-share-one-identity-grammar/head-gate-delivered.log
# tree: ~/Code/.reckon-worktrees/reckon-c8f839407e49/8e41a6d3-.../qwnw-red-file-run-verbs-share-one-identity-grammar
# host: 98dci4-clu-3141.iter.org partition all_debug job 1319167
# command: env -u SLURM_JOB_ID PYTHONPATH=. tests/test_run_verbs_share_one_identity_grammar.py -m pytest -p no:cacheprovider -q
env: 'tests/test_run_verbs_share_one_identity_grammar.py': Permission denied
EXIT=126

Three properties of the environment turned one wrong argument into a workstation-wide outage.

  • The interpreter was writable by its owner. uv installs it mode 755, so an ordinary redirect by the same user succeeds.
  • GPFS does not refuse a write to a running executable from another node. On a local filesystem the truncation would have failed with "text file busy". Here it succeeded, and processes that had the binary mapped were killed when they next touched a page of it. A monitor on the login node exited 135, which is SIGBUS.
  • One file serves four projects. The reckon, imas-ambix, nova and power_convertor environments all resolve to this binary. imas-codex (3.12) and imas-efit (3.13) do not, and were unaffected.

§6 — What would stop a repeat

The failure needed a wrong argument, a writable interpreter and a path from a worktree to that interpreter. Removing any one of them is enough. The outcomes below are ordered by how much of the exposure each removes.

OutcomeOwnerWhat it coversHow to tell it holds
A redirect onto an installed interpreter is refused.the user's environmentEvery writer under this account, on every node, including Slurm jobs.: > ~/Code/reckon/.venv/bin/python fails with "Permission denied" and reckon --version still answers.
A worker, and any job it submits, cannot write the shared environment or uv's install tree.reckonThe path used here. The current write fence mounts ~/.claude read-only around a worker launch; it does not cover ~/.local/share/uv or a main checkout's .venv, and it does not follow the worker into an sbatch job, which is where this write happened.The call in §3, replayed from a worker's worktree both directly and through sbatch, leaves the interpreter's size and mtime unchanged.
A gate's log path cannot be a path the gate did not create.reckonThe wrong-argument class. Each worker writing its own wrapper means each worker can repeat this mistake.A gate invoked with an existing executable as its log path exits non-zero and writes nothing to it.
The sessions outlive the supervisor's interpreter.reckonThe blast radius. The batch step is the Python supervisor, started from the checkout's .venv. When it died, Slurm ended the job and cancelled the 21 remaining steps with SIGTERM four seconds later, taking five zellij servers and 15 orchestrator conversations that do not themselves run on Python.Killing the supervisor process on a rehearsal fleet leaves the zellij servers and their panes running.
A run launched on a node that no longer holds the fleet is classified as stopped.reckonRecovery after any lost node. The new station, on 98dci4-clu-3026, read the 22 runs launched on 98dci4-clu-2001 as working with "process liveness is unknown" and resumable: false, because it cannot inspect another host. The fleet record already says that job is gone, so nothing recovers them without a coordinator.A live pointer whose launcher_host belongs to a fleet job the scheduler no longer runs reads as resumable within one station tick.
A hold that fails says why.dotfiles (cx)Diagnosis time, not the failure.With reckon unrunnable, cx prints the hold command's own error.

The first outcome was not in place when this record was written. The interim form is chmod a-w on each ~/.local/share/uv/python/cpython-*/bin/python3.*; it has to be repeated whenever uv installs a new interpreter, so it is a stopgap and the second outcome is the durable one.

The negative control for the second and third outcomes is the incident itself: the three-argument call in §3 must fail without changing the file it names.

§7 — A second analysis, checked against the record

A session that did not know about the overwrite analysed the same failure and concluded that the fleet ran out of memory. Its conclusion about the trigger is wrong, and most of its findings about load are right. Each was checked against the health series and the 115 process tables the supervisor saved.

The ingest leak was a defect in this repository and is fixed (commit 1d1f9089). A daily snapshot holds a second copy of the watch index, about 5 GB, in a scratch directory beside it on the node's local disk. The directory is removed when the pass ends normally. The supervisor stops and restarts the ingest service whenever its code moves, which happened about every twenty minutes overnight, and a process stopped mid-snapshot left its copy behind. Scratch directories now carry the pid that made them, and the ingest command removes any whose process has gone before it starts.

The analysis's recommendations stand on their own evidence, apart from the first, which is done: a memory limit per declared service, the three control processes' memory use, admission that responds to memory pressure, health samples written from outside the job, tests kept off the fleet node, a watch on local /tmp, and session scratch moved off /dev/shm. None of them would have prevented this failure. All of them describe a node that was killed 125 times in under three days.
