JT-60SA • discovery → mappings → IDS

From signal discovery to pulse IDS

imas-codex proposes source-to-IDS mappings; imas-ambix combines them with the SELENE-derived machine description and writes an indexed tokamap. The generated examples here come from the committed contract fixture, so their draft state is a demonstration of the hand-off contract, not a validated JT-60SA map.

Two repositories, one hand-off

imas-codex inventories facility signals, groups candidates and emits a hand-off JSON document with proposed Data Dictionary paths. Its companion discovery and mapping report explains the candidate and mapping evidence. imas-ambix owns the machine catalogue and signal rules, resolves each hand-off member against the machine description, exports the tokamap and supplies the slim imas-alambic IDS writer.

The fixture under tests/fixtures/mapping_handoff_example.json contains two IDS groups, four signals and one unexpanded flux-loop source. Each signal carries a source id, source group and array, member identifier, target path, units, transform, confidence and evidence. A generated status is not a validation verdict.

The whole chain

The import matches member_identifier to the machine description’s ordered members. Probe magPbTC10 becomes b_field_pol_probe[9]/field/data; CS1 current becomes coil[0]/current/data. The index comes from the catalogue order, not hand-off row order. The draft rules retain validation_state=draft and the imas-codex mapping identity in their tokamap comments.

The fixture export in /work/projects/imas_gpu/jt60sa/tokamap/draft-fixture/ has six IDS groups across two phase partitions, twelve mappings.json files and 70 entries: 50 description entries and 20 signal entries. The two generated IDS groups replace the covered hand-built signal maps with four draft rules in each partition. Its one unexpanded flux-loop source remains explicit because no FacilitySignal member is linked.

  globals.json; mappings.cfg.json
  magnetics/{100001,101174}/{globals,mappings}.json
  pf_active/{100001,101174}/{globals,mappings}.json

imas-ambix maps tokamap jt-60sa --out /work/projects/imas_gpu/jt60sa/tokamap/draft-fixture/ --draft-signals tests/fixtures/mapping_handoff_example.json is the fixture-driven export command. A real generated hand-off, when available under /work/projects/imas_gpu/jt60sa/handoff/, replaces that input for the next iteration.

Writing one pulse

The current bundle carries phase descriptions at maps/jt-60sa/machine_description/OP1/*.nc and OP2/*.nc; the catalogue records the converter source /work/projects/imas_gpu/jt60sa/machine_description/, which is absent on this host. The shared legacy HDF5 description at ~/public/imasdb/jt-60sa_md/ also exists, but the current writer reads the bundle’s phase netCDF files. The phase is selected from the shot and machine catalogue.

imas-alambic write E101154 --machine jt-60sa --maps maps/jt-60sa   --out ~/public/imasdb/jt-60sa/

The CLI uses a flag, then its IMAS_ALAMBIC_* environment variable, then IMAS_ALAMBIC_HOME or bundle store role, then the default where applicable. pulse_writer.write_pulse fetches mapped EDDB channels, opens the shot cache through VirtualZarrView, reads channels with read_channel, copies phase description IDSs and fills served time-dependent leaves. pulse_path names {out_root}/{pulse}_{run}.nc; for this command it is ~/public/imasdb/jt-60sa/101154_0.nc. The alternative root /work/projects/imas_gpu/jt60sa/ids/ already holds pulse netCDF files. The WriteReceipt records the path, phase, IDSs, leaves and excluded signals; the CLI prints a summary, while the Python return carries the detailed receipt.
