§1 — Outcome, stated first

The reported symptoms were not reproduced on a throwaway session, and the cause is therefore not named from this reproduction. With a Claude Code byte-stream pane holding a 60,000-line transcript, at the fleet config, a client attach renders in 153 ms at scroll_buffer_size 10000 and 175 ms at 50000; a resize to 80 columns renders in 434 ms and 418 ms respectively. The plain-shell negative control, identical in every other respect, measured 153 ms attach and 439 ms resize. The probe server logged no did not complete within 1s line in any run.

Two conclusions follow, and neither supports the working hypothesis. First, neither attach nor resize stalls at either scrollback setting: every render completes in under half a second against a one-second stall threshold. Second, the scrollback size is not a driver — the two scroll_buffer_size settings render in the same time and send the client the same 16,213 bytes on attach, which is the viewport alone. The control does not separate from the Claude Code pane in time either, so on this payload the scrollback content is not what a render costs.

This contradicts the resize-storm hypothesis the plan recorded. The negative result is the finding: at these scales a 50,000-line scrollback adds nothing measurable to an attach or a resize. The one positive lead the live log offers points elsewhere entirely: the action that stalls live is a literal no-op, so the second is the router blocking rather than work being done — see §7.

§2 — What was measured

Method: one throwaway session per scenario, created on the fleet node 98dci4-clu-2058 (job 1277272) under a private ZELLIJ_SOCKET_DIR, using the fleet config with only scroll_buffer_size and scrollback_lines_to_serialize changed. The pane payload is a recorded Claude Code terminal byte stream (script -q -c 'claude -p …' recorded on the node), cycled to 60,000 lines. A client is driven from a Python pty harness that answers the terminal queries zellij issues; render completion is the moment the client's output falls quiet for 500 ms after the bytes begin. The probe server's own log is counted before and after each run.

§3 — The second client at a different size

A second client attaching at 80 columns while a first is attached at 100 columns caused the first client to receive exactly one full-screen clear (ESC[2J), six cursor-home moves and 20,235 bytes in the ten-second window — a single coherent repaint, not a redraw storm. The probe server logged no stall during it.

The tab bar's own row cannot be read from this capture, and this is stated rather than guessed: the session name appears zero times in the first client's stream, because the fleet config sets hide_session_name true, and the tab bar is a plugin whose frame is composed by cursor addressing, not as text. So on this evidence a disappearing or duplicated tab-bar row is neither confirmed nor excluded. Confirming it needs a screen renderer over the same capture, which the capture is sufficient for and this node did not run. Raw evidence: docs/figures/fleet-view-rendering/evidence-probe/first-client-diffsize.bin. Superseded by §8, which runs that renderer and reads the row.

§4 — Duplicated lines

Not established. The duplicate-line question is whether a width mismatch between a live Claude Code TUI and its pane duplicates lines. This probe substituted a recorded byte stream replayed into a shell pane, so the pane was never a live Claude Code TUI negotiating its own width, and the condition was not exercised. Nothing here should be read as evidence either way. Answered in §8, which resizes a live pane and renders both widths.

§5 — Two harness defects, recorded because they cost the first two runs

Both were found by insisting on a positive control rather than trusting a plausible number, and both are worth knowing for any future probe or for fleet_connect.

A session created with -s and -l does not exist. zellij -s NAME -l LAYOUT attach --create-background exits 0, prints There is no active session!, and creates nothing. Every later zellij attach NAME then returns the literal 48–52 bytes No session with the name 'NAME' found!. Because the harness bounded its read at the first byte, that error string was the measurement: a uniform 94–106 ms across every scenario, including the control, which is exactly the shape of a plausible result. The working form is a positional name, zellij attach --create-background NAME, with the pane added afterwards by zellij run. Reproduction: docs/figures/fleet-view-rendering/probe/create-cc-10000.out, which carries the string There is no active session! from that create under the failing form, and the rendering counter-example is the same scenario under run5.sh in docs/figures/fleet-view-rendering/probe/.

A dumb pty must answer the terminal's queries. A zellij client emits its setup, then blocks on the device-attributes query ESC[c and renders nothing until it is answered. A harness that only reads sees about 48 bytes and no screen. Answering ESC[c (and the cursor-position, colour and keyboard-protocol queries) unblocks it. This is a property of the harness, not of zellij: every real terminal answers automatically.

§6 — Scope and cleanup

No live session was attached, resized or killed. Every probe session was created, used and removed by name under a private socket directory, and zellij delete-session removed its resurrection entry — ~/.cache/zellij holds no directory named for a probe session. Afterwards zellij ls on the fleet socket dir /tmp/39486-fleet/zellij reports three live sessions, fleet-demo, ambix-fleet and reckon-fleet, plus six (EXITED - attach to resurrect) entries (reckon, nova, efit, codex, ambix, iter). The exited entries are the resurrection records under ~/.cache/zellij, which zellij ls merges into every listing regardless of socket directory; they are not files on this socket dir and none is a probe session. No probe process survives either: no process on the node carries a probe session name or a probe command line, and the throwaway tree under /tmp is gone.

§7 — What would name the cause

The reproduction did not meet the symptom, so the next step is to change the reproduction rather than to re-run it. Three concrete paths, in the order I would try them: (1) drive a live Claude Code TUI in the pane rather than replaying a live recording, since the reported garbling and duplicated lines are reported for panes whose application owns the width; (2) render the existing captures through a VT parser and diff consecutive frames, which settles the tab-bar row and any duplicated line directly from bytes already on disk; (3) reproduce the known event instead of a synthetic one.

That third path is worth stating precisely, because the log already constrains it and the constraint is not what the working hypothesis predicted. The 33 stall lines are all Action NoOp did not complete within 1s timeout — a no-op taking a second, which is only possible if the router is not running, so the time is not the action's cost. They begin at 22:23:05, 8.85 s after the second new tab was created: the log shows PtyInstruction::NewTab … tab 5 at 22:22:26.055 and … tab 6 at 22:22:56.655, two tabs opened exactly 30 s apart, which is the shape of a client re-attach replacing its view. The stalls then recur intermittently for seven minutes forty-three seconds and stop. On this evidence the thing to reproduce is a second client attaching into a session that already has tabs open, and the question to ask is what the route loop is blocked on — not what a scrollback costs. Set against that, the NoOp action itself and the scrollback size are both red herrings, and §2 says the same from the other direction.

§8 — The three questions this note left open, answered

This section answers the three questions §3, §4 and §7 named as open, by running the probes they asked for: a second client at a different size attaching to a throwaway session that already holds four tabs, a VT renderer over the captured stream, and a live Claude Code pane resized between two widths. Every scenario also counts the stall lines in the same server log immediately before and after it, and every run added zero.

(a) A second client at a different size, four tabs, and the one-tab control. The second client attached at 60 columns to a session whose first client sat at 100. In every scenario the stall-line count read 33 before and 33 after — no stall was added by an attach or a resize, four tabs or one. Timings, from the client's own quiet period: with four tabs the first attach took 159 ms, the second 307 ms (11,501 bytes), and a later resize of the first client 100→80 columns 12 ms (8,738 bytes), with exactly one full-screen clear delivered to the first client. The one-tab control — the negative control this node declared — reproduced the earlier probe's attach figures: attach 163 ms against the declared 150–175 ms band, second attach 225 ms, server error false. Its 13 ms resize is not a reproduction of the earlier probe's 418–439 ms resize column, because the two probes time a resize differently: the earlier probe waits for a 500 ms quiet period after the bytes begin, while this one reads the client's own quiet period. The comparison holds within each probe — under this method a live Claude Code pane reflowed in 3,756 ms at 100→70 columns against 12–13 ms for a shell pane resized the same way. The four-tab figures are therefore not an artefact of the harness.

One ordering of the four-tab case kills the server, and the ordering is the variable. Opened before any client attached, four tabs leave the server unable to size them: its log shows Failed to apply layout: Not enough room for panes for the very first tab at 02:51:58, again for each new tab, and then Panic occurred … failed to attach client 2 to tab with index 3 at 02:52:05.667, followed by router and wasm panics. The second client received Error occurred in server:. Opened while a client is attached, the same four tabs are clean. A tab created with no client has no usable size, and the failure surfaces when the next client attaches — not when the tabs are created and not from the second attach alone. This is a different failure from the 33 recorded stalls and emits no stall line at all. Verbatim log excerpt: docs/figures/fleet-view-rendering/evidence-second-client/4tab-pre-server-panic.txt; per-run timings in docs/figures/fleet-view-rendering/evidence-second-client/*.marks.json; figure: .

(b) The tab-bar row, rendered. The four-tab capture was fed to a VT emulator (pyte) and the top row read at both moments. Before the second attach the tab bar reads Zellij … Tab #1 … t2 … t3 … t4 … +; after it reads the same with a focus marker added to the newly focused tab. The row is neither dropped nor duplicated — the only change is that marker. Rendered text with the row in place: docs/figures/fleet-view-rendering/evidence-second-client/4tab-attached.screen.before.txt and ….after.txt.

(c) A live pane resized between two widths. A live Claude Code pane on the local lane was attached at 100 columns (147 ms) and resized to 70 columns, which reflowed the pane in 3,756 ms and 10,247 bytes. The rendered screen holds zero duplicated content rows at both widths: the only repeated adjacent rows are the pane's own vertical frame borders, which are identical by construction. Screens: docs/figures/fleet-view-rendering/evidence-second-client/live.before.txt and live.after.txt. Two harness facts are recorded because they cost runs: a pane launched in a folder claude has not been trusted in shows its trust prompt instead of the TUI, so the resize is measured over a dialog rather than over the live screen; and a custom API-key value in the environment raises claude's API-key prompt, which does the same. Launching with no key variable and the local lane's model name reaches the TUI directly. The driver, the renderer and the plot script are under docs/figures/fleet-view-rendering/probe-second-client/.

§ Followups

Render the two-client capture through a VT parser

A VT parser over docs/figures/fleet-view-rendering/evidence-probe/first-client-diffsize.bin yields the tab-bar row as text and settles whether a second attach at a different size duplicates or drops it. The capture is sufficient; only the renderer is missing.

Probe the reconnect path, not the attach path

All 33 recorded stalls follow the creation of two tabs 30 s apart (22:22:26 and 22:22:56) and are all Action NoOp — the router is blocked, not busy. The untested surface is therefore a second client attaching into a session that already holds more than one tab; a clean attach into a single-tab session is what this node measured, and it did not stall.
