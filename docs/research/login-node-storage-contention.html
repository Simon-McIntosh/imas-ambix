§1 — What was measured

On the night of 2026-09-23 to 24 the login node 98dci4-srv-1006 (48 cores, 503 GB) reported a load average of 143, and every git, plan and reckon crew operation took minutes. The node was not busy computing. Three vmstat samples two seconds apart at about 03:45Z read 95–98% idle, 1–4% user and a run queue of 0–6. Load average counts tasks in uninterruptible wait, and those were the load: 25 of the lead's processes sat in D state on cxiWaitEventWait, the GPFS client wait. Single stat calls at about 03:48Z took 8.5 s on ~/public/imas-ambix/lane.json, 5.5 s on ~/.config/reckon/crew/live and 2.6 s on /work/projects/imas_gpu. Load fell from 143 to 130 over the next half hour as the contributors below were removed.

§2 — The instrument that hid it

The login-node panel from imas-codex host iter showed this node at "100% CPU". Its bar is os.getloadavg()[0] / cpu_count (imas_codex/cli/host.py, _format_load_row), so it reports load average under a CPU label. On a node whose load is storage waits, it shows full CPU while the CPU is idle, and it has no filesystem column at all. It also lists only imas-codex processes, so the orphans below were invisible in it.

§4 — Why it happened, as process gaps

  1. Nothing ends a follower when the session that armed it ends. A monitor or follower whose owning session exits is reparented to init and polls forever. Ten had accumulated for one week-old session. Orphans are a symptom of missing cleanup, and cleanup has to be bound to the session's end, not remembered.
  2. Every agent process runs on the shared login node. Claude sessions, crew producers, followers, dispatches, promotions and their git walks all share one GPFS client, whose metadata queue then serves editors and interactive users too.
  3. Polling loops run full-tree untracked walks. A git status --untracked-files=all every few seconds is a filesystem crawl, and on GPFS its cost lands on every other client.
  4. The dashboard measures the wrong thing. Load average under a CPU label, with no filesystem signal and no view of the lead's non-codex processes, meant the contention was reported as CPU and its causes were not visible.

§5 — Where each fix is owned

  • Relocating every background agent process to a dedicated interactive SLURM node, so that the login node runs editors and interactive shells only: slurm-hosted-agent-fleet (imas-ambix), with the allocation side in reckon's the-fleet-shares-one-allocation.
  • Ending followers and monitors with their session, and a reaper for any that survive: reckon's a-follower-outlives-its-monitor.
  • Replacing full-tree walks in polling loops with scoped or event-driven checks: reckon's crew-observability-truth.
  • A host dashboard covering all of the lead's processes on the login nodes and the interactive worker node, with CPU, memory and filesystem load reported separately as correct percentages: a new plan in imas-codex, extending imas-codex host.
  • Agent guidance: a session stops every monitor and follower it armed before it ends; load average is never read as CPU. Both belong in ~/.agents/AGENTS.md.

§6 — Root causes, with the evidence for each

These were gathered while the load was being removed. Shares come from a 20 s /proc sampler (fsload.py, in this session's scratchpad), which records each process's fraction of time blocked on the GPFS client wait and attributes it to its owning Claude session through the socket ids under /run/user/39486/cc-socks. At 04:31Z the nova S19 session held 30.1% of GPFS-blocked time, the per-project producers about 30%, this session 17.1%, orphaned imas-efit followers 7.6% and reckon-e5 5.6%.

  1. A follower that does not hold its session's registration never checks whether its owner is alive. In reckon/cli.py, _check_consumer returns at once unless registration.held, so only one follower per session can ever notice that its session died. Every read-only follower polls until it is killed.
  2. A monitor's expiry kills its wrapper, not the follower inside it. The follower is reparented to init and keeps polling, so each re-arm adds one more. The ten nova orphans were 6:21, 5:17, 4:47, 3:42, 3:03, 2:29, 2:19, 1:48, 1:16 and 0:45 hours old, one per 30–60 minute re-arm. imas-efit-49 reported the same mechanism for its three, and imas-ambix-b6 saw a follower outlive its wrapper by about 14 minutes. Reckon's plan a-follower-outlives-its-monitor assumes the host kills the follower; tonight's evidence is that it does not.
  3. Reckon spawns followers internally. This session's orphan (pid 2400006, 9 h) ran as python -c "… main() crew follow …", not as the command armed by hand, so a follower's parent can be a transient process whose exit orphans it at once.
  4. Background scripts outlive the session that launched them. A nova wave7.sh (pid 2588585, 7 h 28 min, parent init) kept issuing crew dispatch calls after its session had stopped, so nova work reappeared after its coordinator had stopped everything it could see.
  5. Per-project producers have no lifetime bound and can spin. The imas-codex producer ran for 3 days at 21% CPU with no runs to watch, and the reckon producer showed 37% CPU. The sample producer had lost its registration (crew unwatch reported "no registered watcher"), so it could only be stopped by pid.
  6. Polling loops run full-tree untracked walks. git status --untracked-files=all appears in reckon/crew/dispatch.py:5524, reckon/crew/routing.py:355 and reckon/ledger.py:895. crew dispatch and crew complete processes that stay alive for hours repeat it every few seconds.
  7. MCP reads have no bound. A single read_plan held this session's reckon MCP server blocked on GPFS for over 30 minutes. imas-ambix-b6 measured 1806 s for one read before the harness aborted it.
  8. A resumed session skips placement. Per imas-ambix-78, reckon crew resume runs the worker on the login node even where dispatch places it on the interactive node.
  9. An unbounded crawl had no timeout. The 13 h bfs over /work/projects/imas_gpu was gone before its owner could be identified. bfs is the finder Claude Code's own file-search tools use, so the likeliest origin is a session tool call over that tree with no bound. This is an inference, not a measurement.
  10. The instruments misreport. imas-codex host shows load average as CPU (§2). The H200 reporter gpu-watch (dotfiles) reads vLLM-named Prometheus metrics while the lane serves SGLang, and its "tok/s out" gauge was already recorded as a last-batch figure, not a rate.

Recovery, measured. After the owners stopped their processes, load fell from 143 to 31 and stat latency from 8.5 s to under 0.3 s by 04:41Z. GPFS-blocked process-equivalents fell from 11.6 to 0.7.
