§1 — What was measured

On the night of 2026-09-23 to 24 the login node 98dci4-srv-1006 (48 cores, 503 GB) reported a load average of 143, and every git, plan and reckon crew operation took minutes. The node was not busy computing. Three vmstat samples two seconds apart at about 03:45Z read 95–98% idle, 1–4% user and a run queue of 0–6. Load average counts tasks in uninterruptible wait, and those were the load: 25 of the lead's processes sat in D state on cxiWaitEventWait, the GPFS client wait. Single stat calls at about 03:48Z took 8.5 s on ~/public/imas-ambix/lane.json, 5.5 s on ~/.config/reckon/crew/live and 2.6 s on /work/projects/imas_gpu. Load fell from 143 to 130 over the next half hour as the contributors below were removed.

§2 — The instrument that hid it

The login-node panel from imas-codex host iter showed this node at "100% CPU". Its bar is os.getloadavg()[0] / cpu_count (imas_codex/cli/host.py, _format_load_row), so it reports load average under a CPU label. On a node whose load is storage waits, it shows full CPU while the CPU is idle, and it has no filesystem column at all. It also lists only imas-codex processes, so the orphans below were invisible in it.

§4 — Why it happened, as process gaps

  1. Nothing ends a follower when the session that armed it ends. A monitor or follower whose owning session exits is reparented to init and polls forever. Ten had accumulated for one week-old session. Orphans are a symptom of missing cleanup, and cleanup has to be bound to the session's end, not remembered.
  2. Every agent process runs on the shared login node. Claude sessions, crew producers, followers, dispatches, promotions and their git walks all share one GPFS client, whose metadata queue then serves editors and interactive users too.
  3. Polling loops run full-tree untracked walks. A git status --untracked-files=all every few seconds is a filesystem crawl, and on GPFS its cost lands on every other client.
  4. The dashboard measures the wrong thing. Load average under a CPU label, with no filesystem signal and no view of the lead's non-codex processes, meant the contention was reported as CPU and its causes were not visible.

§5 — Where each fix is owned

  • Relocating every background agent process to a dedicated interactive SLURM node, so that the login node runs editors and interactive shells only: slurm-hosted-agent-fleet (imas-ambix), with the allocation side in reckon's the-fleet-shares-one-allocation.
  • Ending followers and monitors with their session, and a reaper for any that survive: reckon's a-follower-outlives-its-monitor.
  • Replacing full-tree walks in polling loops with scoped or event-driven checks: reckon's crew-observability-truth.
  • A host dashboard covering all of the lead's processes on the login nodes and the interactive worker node, with CPU, memory and filesystem load reported separately as correct percentages: a new plan in imas-codex, extending imas-codex host.
  • Agent guidance: a session stops every monitor and follower it armed before it ends; load average is never read as CPU. Both belong in ~/.agents/AGENTS.md.
