§1 — What was measured

The local lane swapped checkpoints at 2026-10-23T20:14:30Z: job 1280470 served the September weights and job 1294597 has served DeepSeek-V4.1-Flash-1017 since. Both jobs are recorded in lane-cycles.jsonl, so every clive-backend run dispatches entirely to one side of that instant. This document compares the implementation runs on each side.

  • Before window: 2026-10-20T20:14:30Z to 2026-10-23T20:14:30Z, three days ending at the boundary.
  • After window: 2026-10-23T20:14:30Z to 2026-10-26T20:14:30Z, three days starting at it.
  • Seven-day before window (a sensitivity check, not the main comparison): 2026-10-16T20:14:30Z to the boundary.

Every mounted project's run ledger was read (~/Code/*/docs/state/*/runs/*.json, 12,527 records). A record counts only when its role is implement and its backend is clive; that pair selects 2,865 records across all history. Runs whose dispatch-to-completion interval straddles the boundary are excluded from both windows, because the work a straddling run did is attributable to neither checkpoint alone.

Project mix. The windows do not hold the same kinds of work, and the comparison says so rather than assuming it away. §5 — Sensitivity: the seven-day before window

A three-day before window is short, and the day it starts on may be unrepresentative. Against the seven-day window (683 runs) the direction of every material result holds: first-attempt gate pass +0.160 [+0.054, +0.263], repair or resume share −0.076 [−0.182, +0.027], input tokens per promoted run −5.65M [−8.94M, −2.21M], output tokens −45,807 [−60,781, −30,410]. The token reductions are smaller against the longer baseline, which is expected if the lane was already converging on a shorter working pattern before the swap; the first-attempt gain is not, which is the result the verdict rests on.

§6 — Moved-boundary control

The same analysis was run with the boundary moved to 2026-10-22T08:14:30Z, the midpoint of the before window, so that both sides hold runs from the same checkpoint and the same weeks. The positive control still passed on both sides, and neither primary metric shows a detectable difference: promotion rate +0.005 [−0.015, +0.030], first-attempt gate pass −0.042 [−0.147, +0.058]. The instrument therefore reports no change where the weights did not change, which is what makes the real boundary's first-attempt result worth reading.

§7 — What the instrument could not measure

  • Cached tokens are not recorded. Every row of requests-2026-10-25.jsonl (3,088 rows; the same holds for the other days) carries cached_prompt_tokens: null. The metric is reported as unmeasured rather than as a zero, because a zero here would describe the recorder, not the lane.
  • Promotion rate is at its ceiling. 297 of 300 before and 97 of 97 after promoted, so the metric is reported and its interval is real, but it has no room to show an improvement. A regression would still show.
  • Wall time is heavy-tailed. The before mean carries a standard error wide enough that the interval spans both a large improvement and a large regression. The median would be tighter, and the mean is what the section asked for.
  • Failed and aborted requests are counted over the whole lane (141,782 before, 42,093 after), not only over implementation runs, because the request record's run_id is absent on the router-level rows that fail before a run is attributed.

§8 — Verdict

Better. The local lane's implementation runs pass their gate on the first attempt 17.5 points more often after the swap (95% CI +6.5 to +29.1 points), need a repair or resume round 12.2 points less often (−23.5 to −0.5), score 0.36 points higher on the reviewers' fit dimension (+0.10 to +0.61), and spend about a third less input and half less output per promoted run. Both restrictions hold the direction, the positive control passed in both windows, and the moved-boundary control is clean.

The limits of the claim are worth stating plainly. This is a before/after comparison of work that was not assigned by design: the tasks differ, the project mix differs, and the after window is a third the size of the before window. It answers "did the lane do our work better after the swap" and not "is 1017 better than the September weights at the same task". The second question needs the paired bake-off, which b300-bring-up-and-open-model-bakeoff §7 already names and which this result does not replace.
