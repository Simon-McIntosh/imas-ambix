§1 — Why this record exists

These figures were produced across 2026-09-21 to 2026-09-24 and lived only in one session's conversation. Every session retires at the end of this exercise and its successors receive their work through the planning layer, so anything not written here is either re-derived at cost or, worse, re-derived wrongly — one figure below was already wrong once, propagated for two days, and corrected only by a deliberate re-measurement.

Each entry states what was measured, on what, and what it does not support. Where a figure has been retracted it is kept with its retraction rather than deleted, because the retracted number is the one a successor is most likely to rediscover.

§2 — The lane degrades without refusing, and the mechanism is not width

RETRACTED — do not cite: a throughput knee at ~22 workers. Reported 2026-09-21 as aggregate falling from ~500 tok/s to 340 at 28 workers. Two nodes re-measured it on 2026-09-23 and traced the curve to a window mean taken over a moving width, not to the engine. One more running request pinned the pool, other agents' prefixes spilled from a full host tier, and they returned as recomputed prefill. The control this implies is the opposite of the knee's: a knee argues for lowering everyone's ceiling, a tail argues for catching the ~3.5% of intervals that collapse. It is why the router gate's width went up rather than down.

The lesson that survives both readings. waiting == 0 and a prefix hit rate near 0.98 are not headroom: both stayed green across the whole degrading range and preemptions never fired. A session inside the condition cannot see it. Observed 2026-09-23: the lane sat at 35 running against a published ceiling of 19 for about three hours with nothing reporting it, and a node budgeted at 25 minutes took 68.

§3 — The relay is not the constraint

Measured on ambix-router by sacct: AveCPU 00:00:03 over Elapsed 00:55:38, MaxRSS 32 MB — about 0.09% of one core while holding two. It resolves an upstream, merges the catalog, clamps output tokens and relays. Any admission logic placed there pays two cores to do nothing and sits in the request path while it does.

§4 — What a per-consumer admission filter cost, when one existed

A filter keyed on client host joined with user-agent lived in the relay until 2026-09-14 (removed at 76a6a235). Every harness process on one login node resolved to a single bucket, so a whole fleet shared six request slots. Over one afternoon:

measurevalue

of which queue timeouts252, each burning 30 s first
engine KV occupancy meanwhile0.0%
eight concurrent completions872 tok/s direct vs 110 tok/s through the bucket

Its worst cost was not throughput. A worker that exhausted its context tried to compact; the compaction request was refused by the queue; the run died reporting "Prompt is too long — automatic compaction failed". That message is true, actionable, and points at node sizing rather than at admission. A refused request is not equivalent to a slow one, and the one request that must never be refused is a compaction — it is what a worker sends when it has no room left to retry.

This is history, not a live defect, and it is recorded because the same shape returns whenever a bound refuses instead of absorbing.

§5 — The lane document changes shape when it drains

At running: 0 the published lane document reports sizing_verdict: "do-not-size", headroom: null, and concurrent_requests is absent entirely — only concurrent_requests_instant remains. Confirmed again at running: 2 on 2026-09-23.

So a guard written as hold when headroom is zero never fires on a drained lane, and cannot distinguish a drained lane from an unreadable one. Key on presence, and treat a missing key as a state rather than as permission.

Dispatch reads this document and fails open. From a real run record, 2026-09-21T19:23:41Z:

lane_reading = {"headroom":"unknown","mean_context":"unknown","state":"unknown",
                "binding_observed":"unknown",
                "detail":"lane document carries no numeric 'headroom'"}

It read the document, got nothing usable, and dispatched anyway. The degradation is per-document rather than per-field: one missing precondition blanks all eight, so a null binding_observed discards a perfectly good running count. Half of this was repaired in reckon 7fbfc3ae, which carries binding_observed per field; dispatch.py lines 2287 and 2292 still return the blanked reading when headroom or mean_context is non-numeric, which is the path that produced the record above.

§7 — Compaction loses integrals, not just resolution

Measured 2026-09-23 by compacting two serves that restart inside one minute of one boot. Job 1001 advances to 1,500,000; job 1002 restarts at 0 and reaches 20,000. One row comes out, carrying job 1002 and 20,000. The first serve's closing value is gone and every token behind it with it.

The cause is that a run is defined twice: the reader ends one at a change of host, boot or job or at a counter that fails to advance, while the compactor groups by host and boot alone. This is the reason retention must not ship before compaction is repaired, and it is scoped in serving-record-warehouse §8 with the equality that licenses deletion.

Two consequences that are live today rather than pending: the minute and hour tiers already under-report across every restart, so any week or month figure drawn from them is low; and the index ingests raw and compacted files into one sample table with nothing distinguishing them, because key_kind names host and boot resolution rather than tier.

§9 — Login-node hazards, measured the hard way

Two unbounded searches were left running on the login node and found on 2026-09-24: one of mine over /work/projects/imas_gpu for 13 h 50 min, reaped at 21:54:18 once GPFS released it; and an imas-efit worker's find / -name wall.h5 | head for 10 h 49 min.

| head does not bound a search. It bounds the output. The producer learns only when it next tries to write and receives EPIPE, so with a rare filename head blocks waiting for an EOF that arrives only when the walk finishes. The success of the search terminates it; the failure runs forever — and the failing case is the one whose author has already moved on. What bounds a search: naming the subtree, -maxdepth, or timeout N find, which bounds the producer rather than the consumer.

A process blocked in GPFS sits in D state with wchan: cxiWaitEventWait; SIGTERM and SIGKILL both queue in ShdPnd and are delivered only when the filesystem returns. It cannot be killed sooner, and a single such process contributes 1 to the load average — so stopping one will not move a load figure of 150, and the real cost is its continuous metadata traffic.

§10 — A selector that cannot see itself

Recorded because it recurred five times in one session and each instance read as authoritative. A grep, glob or pattern that includes the process or the region running it answers a question nobody asked:

  • An alternation grep answers a disjunction while the claim asserted a conjunction — "6 hostname/boot_id references" was hostname 6, boot_id 0.
  • ls -dt .../*node-name* matched the review run as well as the implement run and sorted the review first, so the wrong manifest was read twice.
  • A tag-stripping regex over a 2,600-character window fused five separate comments into one narrative, which read as a record-keeping defect that did not exist.
  • ps -u $USER | grep '<session-id>' matches the shell running it, because the id is in that shell's argv by construction. Bracket a character and filter on elapsed time: the bracket stops the pattern matching itself, not the shell carrying it.
  • Grepping crew.json for a run id and reading a hit as "this run is reconciled". The id appears there for other reasons; reckon crew list reported both runs unreconciled.

Each was true about the set it selected and false about the set intended.
