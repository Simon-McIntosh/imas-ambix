Decode batch log harvester

The recorded gap reproduced at base. The plan states that a search for the Decode batch marker across imas_ambix/, tests/ and scripts/ returns zero executable matches. At base e3adfca that is what git grep -c "Decode batch" HEAD -- imas_ambix tests scripts reports: exit status 1, no match on any path. The existing receipt_bins collector is a different instrument and does not substitute for it — it bins differenced Prometheus counters over sampling intervals, where this section needs (running width, generation rate) pairs taken from engine log intervals.

What was built. imas_ambix/agent/decode_bins.py parses Decode batch lines into records carrying the interval timestamp, the running width, the speculative accept length and rate, and that step's generation throughput. Each record carries a limb — whether the width was rising, falling or flat — derived from the width trajectory across the log as the first difference against the preceding interval, never from anything printed on the line. The earliest interval has no predecessor and its limb stays unset; the report renders that group as unknown rather than calling it flat, because a no-change label would assert a comparison no interval made. The harvest reports, per exact width, the interval count, the median generation rate and the median accept length, each also split by limb.

A decode line that cannot be parsed is reported, not dropped. Each unreadable line lands with its line number and the field that failed to match, so a harvest cannot present a smaller sample as if it were the whole one. The line number is the check: it is only populated by the refusal path, so a non-empty malformed list shows the guard fired.

A carriage return inflated the line count before the splitter ran. The engine rewrites its shard-loading progress bar in place, so this log carries 332 bare carriage returns. Reading it in text mode translates each one to a newline — inside Path.read_text, before any splitting code is reached — so a text-mode and a byte-mode read of the same frozen file disagree by exactly the number of carriage returns it holds: wc -l reported 7,123 while a text-mode read reported 7,456. The over-count equalling the carriage-return count exactly is the diagnosis rather than a coincidence about it — the same population appearing once as input and once as error. The inflation is not cosmetic: a rewritten progress bar is one physical line, so an interval logged beside one would be cut in two and then reported as malformed. The repair reads bytes and splits on newlines alone, rounding off a trailing carriage return so that a CRLF log counts one line per record. Verified against a frozen copy, where the harvest's lines read and wc -l agree exactly.
