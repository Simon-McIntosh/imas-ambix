The recorded gap reproduced at base. The plan states that a search for the Decode batch marker across imas_ambix/, tests/ and scripts/ returns zero executable matches. The existing receipt_bins collector is a different instrument and does not substitute for it — it bins differenced Prometheus counters over sampling intervals, where this section needs (running width, generation rate) pairs taken from engine log intervals.

What was built. imas_ambix/agent/decode_bins.py parses Decode batch lines into records carrying the interval timestamp, the running width, the speculative accept length and rate, and that step's generation throughput. Each record carries a limb — whether the width was rising, falling or flat — derived from the width trajectory across the log as the first difference against the preceding interval, never from anything printed on the line. The earliest interval has no predecessor and its limb stays unset; the report renders that group as unknown rather than calling it flat, because a no-change label would assert a comparison no interval made. The harvest reports, per exact width, the interval count, the median generation rate and the median accept length, each also split by limb.

A decode line that cannot be parsed is reported, not dropped. Each unreadable line lands with its line number and the field that failed to match, so a harvest cannot present a smaller sample as if it were the whole one. The line number is the check: it is only populated by the refusal path, so a non-empty malformed list shows the guard fired.

A carriage return inflated the line count before the splitter ran. The engine rewrites its shard-loading progress bar in place, so this log carries 332 bare carriage returns. Reading it in text mode translates each one to a newline — inside Path.read_text, before any splitting code is reached — so a text-mode and a byte-mode read of the same frozen file disagree by exactly the number of carriage returns it holds: wc -l reported 7,123 while a text-mode read reported 7,456. The over-count equalling the carriage-return count exactly is the diagnosis rather than a coincidence about it — the same population appearing once as input and once as error. The inflation is not cosmetic: a rewritten progress bar is one physical line, so an interval logged beside one would be cut in two and then reported as malformed. The repair reads bytes and splits on newlines alone, rounding off a trailing carriage return so that a CRLF log counts one line per record. Aggregate decode throughput against concurrency width, both pool configurations

Two jobs, one quantity, no controlled arm. Job 1272783 served the 4,000,000-token pool (deepseek-v4-1-flash-1272783.log, 4,059 decode intervals, logged 2026-09-17 11:37:47 to 16:29:45 local). Job 1273074 served the 8,000,000-token pool (deepseek-v4-1-flash-1273074.log, 1,003 intervals at a cut of 2026-09-17 19:53 local). Zero malformed decode lines on both. The two windows are adjacent and non-overlapping, but the 8M job was still RUNNING at the cut, so its arm is a snapshot; the 4M job had ended.

Verdict. Throughput is flat across widths 17–32 on both arms. The 4M job's slope of per-width median aggregate throughput is +0.09 tok/s per width (95 % stratified bootstrap CI −2.00 to +2.69, gain −4.1 %); the 8M job's is −0.55 (CI −1.61 to +0.34, gain +4.1 %). #queue-req is 0 at every width, so the plateau is not admission queueing.

The 8M arm's earlier snapshot was not flat, and more data dissolved the effect. At 596 intervals that arm read a slope of +5.38 (CI +2.39 to +9.94); at 1,003 intervals the same quantity is −0.55 (CI −1.61 to +0.34). The positive slope lived entirely in six low widths holding five to seven intervals each and in one width-17 ascending interval reading 74.3 tok/s, and it does not survive adequate sampling. A read taken on the smaller sample would have concluded that widening buys 17 %.

Limb split. Labelling each interval from its width trajectory separates the two strata an unlabelled curve blends. Descending exceeds ascending at 15 of 15 in-range widths on the 4M job and 15 of 16 on the 8M job; pooled over 17–32 the medians are 400.6 against 363.2 tok/s on 4M (n 142 / 145) and 383.9 against 343.9 on 8M (n 294 / 268). A throughput figure quoted without its limb is quoting a mixture whose weight depends on whether the lane was ramping up or down.

The pool increment met its own target and changed no throughput. Median full-token usage at width 32 is 0.830 of the 4M pool against 0.370 of the 8M pool — 3,311,360 and 2,962,560 tokens respectively, so the 4M job ran within 17 % of a cap the 8M job now sits at about a third of. Occupancy rises with width on both arms while throughput is flat, which is the direct counter-evidence to reading the plateau as a capacity limit.

Interpretation limit. Pool size, window and traffic mix move together between the two arms as run, so nothing here separates them and none of it supports a claim that the 8M pool causes or cures the plateau.
