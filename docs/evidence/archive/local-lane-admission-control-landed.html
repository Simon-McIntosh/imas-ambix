The throughput knee, measured on the engine decode log

The instrument is the engine's own per-step log, not a window aggregate. The scheduler emits one decode step per line carrying the running request count, the speculative accept length, and that step's aggregate generation rate. The reader groups those intervals by exact running width and takes the file's per-width median, with a percentile bootstrap interval, so a width bin is a width and not an average over a window in which the width moved.

Two serve logs were read on a compute node, never on the login node. The five-day job (1273253) yielded 79,436 decode intervals with 0 unreadable, spanning 2026-09-17 22:01:09 to its cancellation at 2026-09-23 06:12:04; 36 widths cleared the 20-interval threshold. Its live replacement (1276246) is a snapshot taken while it grows.

The aggregate rate rises steeply to about width sixteen and is then flat from width 17 to 32. Over that plateau the per-width medians sit between 365.8 and 389.9 tok/s. The observed operating band, widths 29 to 31 pooled, reads 379.1 tok/s against a plateau median of 378.5 — a ratio of 1.0. The two counts are the same point.

The maximum-median width is the engine's cap, and it is confounded

The largest per-width median anywhere in 1 to 32 is 389.9 tok/s at width 22, a mild local high inside a 380 to 390 band; widths 23 to 32 then sit at 366 to 384, not at 340. The overall maximum is 436.7 tok/s at width 36 (24 intervals, 95% interval 418.5 to 448.9) — the engine's running cap, so no wider bin exists. The ratio of the operating band to that peak is 0.868. On the live replacement job the peak sits at width 35 and the same ratio is 0.868.

That peak is reported as measured, not as a knee. Every interval at width 29 and above was logged in one mid-run window, 2026-09-18 11:xx to 2026-09-21 21:xx, and the width-36 bin carries a higher speculative accept length (3.82) than the operating band (3.65). Its throughput advantage therefore tracks the acceptance of that window rather than width alone. No width above 36 was ever logged, so no knee below the cap appears in this instrument, and the engine log does not contradict the profile's reason for setting the cap at 36.

Which earlier claim the data supports, and why they disagree

The data supports the profile's flat claim, not the ~22 knee. The flat profile claim covers widths 17 to 32, and the measurement reproduces it there (band to plateau ratio 1.0). The later claim that aggregate output peaks near 22 concurrent at about 500 tok/s and falls to about 340 past it is not reproduced: the maximum median in 1 to 32 is at width 22 but only 389.9 tok/s, and nothing on this lane reaches 500 tok/s at any width. The two disagree because they measure different objects. The ~22 knee is a window mean: its ordinate is a window-averaged aggregate rate and its abscissa a mean concurrency (one such window reads 23.05 with a peak of 34), so one bin mixes many instantaneous widths and the knee it finds is where per-client rate collapses, not where the engine's aggregate rate stops rising. The decode-log instrument pairs a per-step rate with the exact instantaneous width; it separates widths cleanly and finds a flat band with no interior peak.

The pipeline is checked against a planted peak

The same reduction, run on a synthetic log with a generation peak planted at width 12 and again at width 25, reports back width 12 and width 25. A pipeline that reported a peak regardless of its input would fail this; it is asserted on every run and the run exits non-zero on a mismatch.

A declared pause is enforced at the gate, and it drains rather than cuts #

What is enforced. The gate file router-gate.json beside lane.json gains "paused": true with a "reason" string. While the flag is set the generation gate admits no new generation, whatever its width: the pause outranks the width == 0 bypass and the FIFO head's admission test alike. Requests already admitted run to completion, so the pause is a drain and not a cut. A request that arrives during the pause joins the same FIFO as any other caller, and clearing the flag admits it in arrival order. A request still waiting past wait_seconds receives the existing HTTP 529 overloaded_error with the fixed five-second Retry-After — the same reply a full gate gives, so a caller needs no new handling to observe a pause.

A pause is published, because a zero count does not name its cause. A lane with nothing running and a lane that is refusing to run anything look identical in the counters alone, so lane.json carries paused and the reason under router_generation_gate. That is the field a dispatch-side holder reads: the mechanism here stops the router admitting, and the paused field is what lets a caller outside the router know not to try.

The operator surface round-trips the file. imas-ambix agent pause --reason <text> writes the flag and the reason and prints the lane's running and waiting counts; imas-ambix agent resume clears the flag and the reason and prints the same counts. Both preserve the width and the wait bound a launch set, and both create the gate file when none exists rather than failing. A gate file that does not hold a JSON object is reported and left untouched rather than overwritten. The router reads the file live, as it already did for width, so neither command needs a restart.

What the tests measure

The paused-gate admission test declares a pause on a width-2 gate while one request, first, is in flight. With the gate at width 2, a gate that ignored the pause would admit a second request at once. The test asserts that the observed maximum concurrently running stays 1 while two later arrivals, second and third, sit waiting. It also asserts that the in-flight request completes with 200 during the pause, and that clearing the flag admits the two held requests in the order first, second, third. A second test shows a paused gate returning 529 with Retry-After: 5 and an overloaded_error body to a request held past its wait bound, with no generation started. A third shows a pause outranking a disabled width (width 0 and paused still refuses). A fourth asserts the lane snapshot publishes the pause and its reason. The CLI tests cover pause and resume round-tripping the file, preservation of width and wait bound, the counts each prints, gate creation when absent, and a malformed gate being reported rather than overwritten.

The gate's automatic width seeks the throughput knee (2026-09-25)

The automatic width now measures the lane's plateau rather than computing it from memory. _GenerationGate.observe_lane in imas_ambix/agent/router.py takes the engine's cumulative generation_tokens counter alongside the readings it already received, and derives a rate as the counter delta over the interval between scrapes, discarding any delta whose reading lands below its predecessor, since a counter that restarted describes two processes and is not a rate. Sixteen scrapes (σ 60 tok/s per window, pre-declared) make one judgement against a material-change margin of 3.2 × 60 ÷ √16 = 48 tok/s, about three standard deviations of the judged mean; a passing climb or descent moves the width by two. A prefix hit rate under 0.95, KV occupancy at 0.6, and a per-stream rate under 10 tok/s each step the width down without waiting for throughput to react. Nothing is scored while the gate holds no queue, because a rate measured with demand below the width describes the lane and not the width. ims_ambix/agent/lane.py gains the counter as a LaneCapacity field declared compare=False, so it takes no part in lane identity. The published gate block gains width_mode and width_reason for an automatic gate only.

Over a synthetic surface rising to a knee at 12 and flat past it, with a fixed seed, the width settles at 12 from a start of 36 and from a start of 4, and the last forty scrapes from either side are 12 alone.
