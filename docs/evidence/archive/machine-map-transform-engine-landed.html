§3 existed to replace a convention held in someone's head with a declared boundary. It did that, and in doing so it produced the evidence §2's map-expressiveness decision was waiting for — which is the more consequential result.

What the boundaries say about campaign as a key

Boundaries: 11766, 12417, 12533, 12561, 12878, 12905, 12964, 12990, 13021, 13049, 13379. Only 11766 coincides with a campaign boundary. Campaign is therefore not a usable key for geometry — a map keyed per campaign would smear ten distinct machine descriptions into one. Shot range is a usable key: the ranges partition the corpus exactly, so the design rule §2 states (one map per shot range, no conditionals) is sufficient here and needs no conditional expressions. It simply needs more maps than there are campaigns.

Qualification carried forward

The repeated 1004↔938 filament-count alternation is not physical. A machine does not swap PF filament counts back and forth across adjacent shot ranges, so at least some of these boundaries record variation in the EFIT setup arrays the signature is sampled from rather than a change in the machine. The partition and lookup invariants hold either way, but the transition count is an upper bound on real machine changes and must not be read as eleven distinct machines. Separating setup-file churn from machine change is work the map authoring node inherits.

The boundaries stopping at 13379 is consistent with the independently recorded frozen efm signature from 13370 onward.

Ten catalog bindings are not representable at their declared DD paths

This is the node's most useful output, and it was invisible to everything upstream. The zarr/netCDF array-count gap of 30 (10 per shot) is not a rounding difference: ten declarations from the landed catalog cannot round-trip through imas.DBEntry.

  • Nine saddle-probe arrays — b_field_tor_probe_saddle_{l,m,u}_{phi,r,z} — each have source shape (12, 28) but target a scalar DD leaf.
  • One coordinate target — magnetics/b_field_phi_probe/position is a DD structure, not a writable leaf.

The catalog's own validation could not see this. linkml-validate checks schema conformance, not DD representability, and the zarr engine emitted all ten happily with their DD declarations attached. Only writing through the real Access Layer refuted them. That is a decision-relevant property of the IMAS-netCDF arm beyond its read rate: it is the arm that cannot silently accept a DD binding that the Data Dictionary does not actually support, so it functions as a validator even where it loses on throughput. The ten were emitted by zarr and recorded missing from the authoritative netCDF fixtures rather than being quietly dropped; the VLEN string fallback was not applicable because none is an encoding failure.

The Data Dictionary simply has no home for them. DD 4.1.1 carries no saddle-probe outline or contour leaf, and b_field_phi_probe/position/r|z|phi are FLT_0D leaves under each probe, so they cannot accept the nine (12, 28) outline arrays.

Retraction: a saddle loop is a flux loop, not a field probe

The nine saddle arrays were qualified against the wrong Data Dictionary structure. The search that produced the verdict looked under b_field_tor_probe and b_field_phi_probe, following the MAST source names, and correctly found nothing there. It never asked whether a saddle belongs somewhere else in the DD. It does.

The representation that exists
DD pathTypeWhat it gives
magnetics/flux_loop/type magnetics_flux_loop_type_identifier option 2 = saddle (beside 1 = poloidal_flux, 3–5 diamagnetic, 6 differential)
magnetics/flux_loop/position STRUCT_ARRAY, 1…N "coordinated list of physical points (R, Z, phi) defining the spatial trajectory" — a multi-point loop, not a single location
…/position/r, /z, /phi FLT_0D each per-point coordinates, so an (N loops × M points) source is representable

So a flux loop in the DD is either a full toroidal loop or a saddle, distinguished by its type identifier — and the trajectory structure that the earlier search concluded was missing is exactly what flux_loop/position provides. The correct binding is magnetics/flux_loop[]/position[]/{r,z,phi} with type/index = 2, and the nine SourceQualification records are being removed.

The 30 pf_passive shape-angle arrays were about to repeat the same mistake and were caught before commit. DD 4.1.1 models a parallelogram directly: pf_passive/loop/element/geometry/oblique carries alpha and beta inclination angles with length_alpha, length_beta, r, z and thickness, selected by geometry/geometry_type. A slanted passive element is an oblique element with a beta angle. (Documentation quirk to bind around: alpha and beta are annotated with units m although they are angles.)

What this says about the method, not just the result. "Unrepresentable in the DD" was asserted twice from a search anchored on the source's own naming. Both times the DD had a representation under a different concept — a saddle filed as a loop type, a parallelogram filed as an oblique primitive. A negative representability claim is only as good as the concepts searched, so it needs an explicit search of the DD's own vocabulary before it is recorded, not a failure to find the source name. The full-corpus writable-leaf test remains correct and valuable; it proves a declared target is representable, and never that no target exists.

⚠ Cardinalities superseded 2026-08-13. The counts above were taken over 11 declared ranges, nine of whose boundaries were later shown to be mesh refinement rather than geometry change. The three properties still hold; the numbers are corrected in the recount below.

The changed-field counts are the point of the design. A global digest would compress each boundary to "different"; here the 1004↔938 filament changes stay inspectable, which is what lets the earlier finding — that some boundaries record EFIT setup churn rather than machine change — remain visible rather than being absorbed into a hash. Pulse /data and /time leaves are excluded because they describe the experiment, not machine identity.

The "6 versus 10" asymmetry was the signal, not a curiosity. When identity first landed, the boundary at 12417 moved 6 fields while every later one moved exactly 10. That uniform 10 was the discretisation fingerprint: those boundaries were all the same mesh change repeated. The one boundary that behaved differently was the only real one.

§5 — Reader retirement: bounded, but not currently executable

Read-only audit at source revision 81785a8. 55 non-test modules import from imas_ambix.gs.geometry; 41 invoke a legacy description-read API (8 library, 33 scripts); 14 touch only table types or the version constant. Classification is 41 description-consumers and 0 reconstruction-consumers — the modules often go on to reconstruct, but nothing fitted is read across this boundary, so §5's scope line is intact.

The conclusion is specific rather than discouraging: retirement is bounded, and it is blocked on one named dependency — a description-complete, DD-path-driven, machine-neutral MachineDescription → GeometryTable adapter that reproduces probe orientation, complete active and passive conductor topology, turn and current weighting, acquisition addressing, exact table ordering, and the byte-stable setup signature. No such adapter exists; the transform emits a collection of EmittedArray objects and nothing converts them into the legacy table.

Description content is demonstrably metric-perturbing

An independent change of machine-description content moved the frozen spine metric by +3.218% and +3.271% (magnetics_residual_whitened_rms 0.7401→0.7639 on greens-matvec, 0.7396→0.7638 on grid-delstar). Those pass the wider 7.93% source-cutover budget but exceed the 1% same-source budget. The arm measured was not the transform engine, so it proves only that changing description content is observable — which is exactly why a cutover cannot be assumed non-perturbing. There is no committed frozen-spine stamp using transform_machine_description, so the landed engines currently supply no evidence either way.

The frozen chain runs spine_bench.runner.CampaignGeometrySource.table_for → heldout_mse_gate_eval._campaign_table → read_efm_geometry + setup_signature + build_table_for_shot → spine_label_factory.factory_shot_payloads → gs.operator.build_operator, latent.gs_solve.EquilibriumGrid, latent.patch_basis.PatchBasis, latent.boundary_disc.disc_read.
