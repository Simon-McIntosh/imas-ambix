The warm serve cache is content-addressed to the bound header

The persistent-cache measure resolves by derivation rather than by a weaker artifact comparison. The image's load_jit creates a BuildSpec containing the K kernel's direct cuda_files source, then calls compute_build_key. That function SHA-256 hashes the bytes of every direct source before it looks for a cached build. The launch-time bind therefore changes the build key before a stale unpatched artifact can be selected.

The cache has a second independent guard: each published leaf records SHA-256 digests for compiler-scanned dependencies, and find_prebuilt re-hashes those files before accepting the leaf. The direct header is required in that record or the build is not published. This is a fresh server process at each serve launch, so the per-process digest memo cannot carry an image-header digest across the bind boundary.

Verdict: content-addressed; standing bind is safe. The factory's JIT cache defaults through SGLANG_JIT_CACHE_DIR, not SGLANG_CUTE_AOT_CACHE_DIR; the latter is a separate CUTE object cache. No per-launch cache override is required for this header, because the source bytes themselves select the reusable artifact.

A hypothesis of mine, refuted by the data

Mid-test I read num_running_reqs of 1.0 from the live metrics and inferred that large prefills serialise on prefill bandwidth, because max_prefill_tokens caps a step at 16,384. The measurements refute it: aggregate throughput nearly triples from width 4 to 12, which serialisation forbids.
