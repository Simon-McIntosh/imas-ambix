The cumulative-ratio trap is in the code, and it reproduces. The plan warned that a cumulative hit-rate reading had misled four sessions on this lane. The survey found the reason: serving_receipts.py computes the hit rate as a lifetime ratio and assigns that same value to every emitted row. Two operational findings that change the swap procedure

agent serve exposes no pool-size option. The committed V4.1 profile pins max_total_tokens = 3485952, which is 1.24× the V4-Flash baseline pool rather than the 5.3× the experiment's premise rests on. Serving the profile as committed would answer a question nobody asked. The 14,999,808 pool — the one load-proven through a 32-way sweep with zero OOM — has to become an explicit, reviewable setting rather than a hand-edit at serve time.

The lane refresher claim was wrong, and the correction is the more useful record. The survey reported the refresher as a separate ambix-lane SLURM job needing to be stopped by exact job id. No such job exists in squeue, yet lane.json is rewritten every thirty seconds. RouterApp publishes it from an internal task, having been moved there because a separate job “spent a core of a 30-core GPU reservation on one HTTP read every thirty seconds, while a peer's GPU work pended on Resources with two cards idle”. The router already survives serve rotations and re-reads the endpoint document on every resolution, so it is left running through the swap and the lane reading follows the new serve within one interval.

The survey was not careless, and a first attempt at this correction was itself wrong. generate_lane_refresher_script is still in slurm.py arguing for the separate job in exactly those terms, and it is reachable — agent lane --submit --refresh N calls it and submits a standing ambix-lane job. It is a supported path, not dead code, and an earlier note here proposing to delete it would have removed a live CLI feature.

The codebase therefore carries two publication mechanisms whose docstrings argue against each other, and the one in use is not the one that argues hardest: router.py makes the opposing case, cites the reservation core the separate job wasted, and is what runs. A question aimed at the source returned a true answer about the mechanism that is available rather than the one that is running. The swap-time consequence is a precondition rather than a deletion: require squeue to show no ambix-lane job before swapping, and stop one by exact id if it has appeared.

The warm serve cache is content-addressed to the bound header

The persistent-cache measure resolves by derivation rather than by a weaker artifact comparison. The image's load_jit creates a BuildSpec containing the K kernel's direct cuda_files source, then calls compute_build_key. That function SHA-256 hashes the bytes of every direct source before it looks for a cached build. The launch-time bind therefore changes the build key before a stale unpatched artifact can be selected.

The cache has a second independent guard: each published leaf records SHA-256 digests for compiler-scanned dependencies, and find_prebuilt re-hashes those files before accepting the leaf. The direct header is required in that record or the build is not published. This is a fresh server process at each serve launch, so the per-process digest memo cannot carry an image-header digest across the bind boundary.

Verdict: content-addressed; standing bind is safe. The factory's JIT cache defaults through SGLANG_JIT_CACHE_DIR, not SGLANG_CUTE_AOT_CACHE_DIR; the latter is a separate CUTE object cache. No per-launch cache override is required for this header, because the source bytes themselves select the reusable artifact.

Calibrated single-stream prefill bracket

A disposable TP4 serve ran with the engine cap raised only in its own worktree to the native 1,048,576 context. The running receipt confirmed context_length=1048576, chunked_prefill_size=32768, and max_prefill_tokens=16384. It was never committed; the persistent profile remains capped at 204800.

Method finding. Raw character repetitions are not a prefill-token coordinate. Two initially fatal inputs, labelled only by 360,000 and 180,000 repetitions, produced a disconnected client and no usage receipt because the engine died first. Treating those labels as a bisection axis would create a confident number about an unknown quantity. The final serve called /tokenize first: ten repetitions of both " a" and " b" returned ten tokens. Only then were the following requests admitted as bisection evidence.

Prompt coordinateReceiptGPU free MiB/cardResult

The result is a warmed-process operational bracket of 90,004 completed and approximately 135,004 fatal, 45,000 tokens wide. The midpoint followed the successful lower request in the same process, so this is not promoted to a fresh-process per-request ceiling. A clean successor should restart once per calibrated candidate; it inherits a trustworthy lower point and input instrument rather than a fabricated ceiling.

Memory attribution. At the first fatal allocation, 23,599 MiB (23.05 GiB) had been free at idle and 1.47 GiB remained. Thus the prefill had already consumed roughly 21.6 GiB before FlashInfer asked for a further 7.52 GiB fused-MoE workspace. The completed 90,004-token request independently raised the per-card high-water mark by 22,550 MiB (22.02 GiB). The same 7.52 GiB workspace request appeared at all fatal sizes, which is consistent with chunk-bounded workspace allocation rather than a workspace proportional to total sequence length. It does not make the context pin safe to remove: total-prefill activation leaves only 1.47–1.49 GiB for that late workspace. There is no fitted linear or superlinear rate: one completed point and post-crash absences are not a curve.
