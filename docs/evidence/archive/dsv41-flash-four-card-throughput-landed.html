A reuse survey at da3c816 mapped the six capabilities the measurement needs. It found no reason to author serving, dispatch, endpoint or restore machinery — all four already exist — and two measurement seams that do not.

The cumulative-ratio trap is in the code, and it reproduces. The plan warned that a cumulative hit-rate reading had misled four sessions on this lane. The survey found the reason: serving_receipts.py computes the hit rate as a lifetime ratio and assigns that same value to every emitted row. On two controlled snapshots differing by +2,000 queries and +1,800 hits — an interval truth of 0.9000 — the recorder reports 0.8253. A test codifies the behaviour and passes.

The repair is additive rather than a redefinition: emit interval delta fields alongside the retained cumulative fields under their existing names, so historical rows remain readable as what they actually were. Renaming the cumulative field in place would silently change the meaning of every row already recorded.

§2b — Receipt rows now retain both the cumulative and interval cache readings

Commit e112152 adds prefix_cache_query_delta, prefix_cache_hit_delta, and prefix_cache_hit_rate_interval to every receipt row without changing prefix_cache_hit_rate. The first row has no preceding snapshot, so all three interval fields are null; later rows use the same reset-safe counter differencing as throughput, and the interval ratio is null when no positive query delta exists.

Two operational findings that change the swap procedure

agent serve exposes no pool-size option. The committed V4.1 profile pins max_total_tokens = 3485952, which is 1.24× the V4-Flash baseline pool rather than the 5.3× the experiment's premise rests on. Serving the profile as committed would answer a question nobody asked. The 14,999,808 pool — the one load-proven through a 32-way sweep with zero OOM — has to become an explicit, reviewable setting rather than a hand-edit at serve time.

The lane refresher is a separate SLURM job, not a model profile. A profile shutdown will not stop the standing ambix-lane job, so a swap that starts a second refresher leaves two of them racing to publish, one of which advertises the retired origin. It must be stopped by exact job id. --all would stop it and would also stop serving jobs, so it is not the shortcut it looks like.
