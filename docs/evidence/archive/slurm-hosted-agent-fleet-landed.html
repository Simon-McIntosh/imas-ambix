What the share measures

The share is stalled CPU thread-time over the thread-time the ceiling permitted. Four cores allowed once per 100 ms period permits four times the period in thread-time, so the permitted total over the accounted periods is the quota multiplied by nr_periods with the period cancelling out. Thread-time was chosen over a simple period count because it is the quantity that compares a four-core slice against a twenty-eight-core allocation directly.

The share can exceed one, and it does. The throttled_usec counter sums over every task that was stopped, while the budget is one quota per period: once more tasks are runnable than the quota admits, several of them stall together for the remainder of each period, and the thread-time lost passes the thread-time the ceiling allowed. A value above one is therefore a statement about oversubscription, not an arithmetic fault, and the sampler leaves it unclamped.

The sampler, and how to repeat this

imas_ambix/agent/throttling.py reads cpu.max and cpu.stat text from a directory the caller supplies — never a fixed path — and prints the cumulative and interval readings as JSON. It carries its own _parser() / main() entry point rather than routing through the operator CLI, so a monitor can read a slice without importing it:

# one reading
uv run python -m imas_ambix.agent.throttling sample \
    --directory /sys/fs/cgroup/user.slice/user-39486.slice

# a reading plus the share over the next 60 seconds
uv run python -m imas_ambix.agent.throttling interval \
    --directory /sys/fs/cgroup/user.slice/user-39486.slice --seconds 60

A missing share carries its cause rather than reading as one null. There are two ways for a share not to exist, and a monitor has to act differently on each: a group with no ceiling can never produce one however long it is watched, while a group whose counters account no period yet has simply not been measured over a window and may state a share at the next reading. The JSON therefore writes "throttled_share": "unbounded" or "no_periods" in place of a number. Where both hold — an unbounded group that has also accounted no period — the ceiling's absence is reported, because no later reading removes it. A number is always a number, so a caller testing for a float distinguishes all three cases from one field.

The unit gate is uv run --no-sync pytest tests/agent/test_throttling.py, covering the cumulative share, the delta share across two samples, the refusal of a counter that went backwards between samples, the unquota-ed reading where cpu.max is the literal max 100000 and the share is undefined rather than zero, and the two undefined causes as distinct states — through the function, through the payload, and through the CLI's own JSON. The payload's key set and the top-level shape of both subcommands are pinned by equality, so a regression in what a monitor parses fails the gate rather than passing it.

Dispatch placement inside a scheduler allocation — the verdict

Verdict: no change required. The dispatch contract already treats where a worker runs as configuration a backend declares rather than as something reckon decides for it, and the branch a fleet session inside an allocation takes is the one already in force today: the worker is a direct child of the process that dispatched it, so placing the coordinator places its workers with it. What an allocation does require — a placement declared for the lane, one reservation held once, its job id published into shared state — is implemented already and is configuration rather than a contract change.

How a dispatched worker process is created

A CLI launch is composed in three steps and none of them names a host. The backend and its dialect turn one node's prompt into a LaunchPlan — argv, working directory, environment — whose working directory is the assigned worktree (reckon/_backends.py:1729, :1774). apply_backend_placement (reckon/crew/dispatch.py:4057, called at :3547) gets the first and only chance to move it. The plan then goes to _spawn (reckon/crew/dispatch.py:4201, called at :3549), which starts it with subprocess.Popen (:4226).

The worker is a child of the calling coordinator process. It is started with start_new_session=True (reckon/crew/dispatch.py:4233) so a coordinator that ends its turn does not take its workers down with it, and its pid is registered with the parent's reaper (:3682, :3890) — but it is a child, which :4201's own docstring gives as the reason the pid means anything. Nothing on this path consults a scheduler, selects a node, or moves the process out of the control group it inherits.

Reckon chooses no placement unless the backend declares one. apply_backend_placement reads the declaration through flight.placement_for (reckon/flight.py:341) and returns the plan untouched when there is none (reckon/crew/dispatch.py:4076-4078). The declaration is schema rather than code: PlacementConfig (reckon/_flight_schema.py:234) carries scheduler, options, job_id_probe, requirements, state_query and reason_query (:238-243), and the field is documented with the login-node child launch as what a backend declaring none keeps (:218).

The allocation shape this plan needs already exists

Where a placement is declared, one reservation is held once and every session's workers are placed into it as steps. ensure_reservation (reckon/crew/placement.py:197) submits a single salloc with --no-shell and publishes its job id into the shared crew state (:96, path at :74), so a second session reports the live reservation instead of minting a second allocation; the id is answered from the scheduler rather than from a pid (:158). A launch then runs inside it as an overlapping step: step_prefix (:139) builds --overlap --jobid=<id> (:147), which apply_backend_placement prefixes to the resolved argv (reckon/crew/dispatch.py:4092-4101). Because --overlap makes the reservation a place to run rather than a quota to queue behind, the concurrency authority is reckon's own roster cap (reckon/crew/placement.py:59, refused at :284, enforced before a run exists at reckon/crew/dispatch.py:415, called at :488). The operator surface is reckon crew placement --ensure (reckon/cli.py:2266, reckon/crew/runs.py:2278).

A declared placement is also where a worker's visibility requirements are checked before anything launches: check_placement_requirements (reckon/crew/dispatch.py:2104, called at :2408) refuses a path or an endpoint the worker would need and could not reach, naming which and why.

Every path the launch writes is on shared storage

Crew state resolves through crew_home() (reckon/crew/runs.py:38) to _config_home()/crew (:40), and _config_home (reckon/_store.py:121) prefers ~/.config/reckon — the same home path on every node. The watcher's lock, transition stream and follower registrations sit under the same root (reckon/crew/runs.py:104-140), and worktrees are placed beside the repository rather than in a runtime directory (skills/reckon-ship/references/sprint-orchestration.md:303-316). Measured rather than assumed: findmnt -T /home/ITER/mcintos reports source HPC_T2[/ITER/HPC/home] of type gpfs, so the home holding all of it is the cluster filesystem and not per-node storage.

The one host-local hazard is named and refused. _is_node_local_path (reckon/crew/dispatch.py:2061) treats /run/user (:2071), XDG_RUNTIME_DIR (:2073) and any tmpfs mount as node-local, and its docstring states the failure it exists to catch: such a path exists on every node, so a launch against it succeeds and the worker then finds different bytes where it runs. A placement declaring one is refused by name (:2138).

The unbounded allocation is the case that must not be got wrong

This allocation is deliberately unbounded, so the scheduler reports its TimeLeft as the literal text UNLIMITED. That token is not a duration: the remaining-time reader maps it to None, so it cannot be parsed as a number, compared against the warning threshold, or reported as expiring. The single place a remaining time is compared to a threshold is the warning line, and an unbounded — or unreadable — value never reaches it. A finite remainder below thirty minutes adds that warning, because moving sessions off an allocation takes operator minutes and the notice has to arrive while there is time to act.

A throttling reading names the machine it came from

What the payload said before. The emitted object carried the control group directory, the cpu_max ceiling and the counters, and nothing that identifies the machine. The only host-distinguishing input was the --directory operand, and that operand is not host-distinguishing at all: /sys/fs/cgroup/user.slice/user-39486.slice resolves on every node in this cluster with different contents. The comparison the plan's step seven rests on is a before-and-after throttled share, so two readings taken on different machines would have compared as though they were the same one.

What it says now. A host block carries the hostname, the kernel's per-boot identifier and the time since boot:

FieldSourceWhat it settles
hostname socket.gethostname() Whether two shares describe the same computer at all
boot_id /proc/sys/kernel/random/boot_id Whether a fall between two readings is a recovery or a restart
uptime_seconds first field of /proc/uptime How long the counter run behind a reading has been going

The boot identity is the load-bearing half of the second requirement. The counters are cumulative since boot, so a reboot restarts them and the arithmetic reads as a sudden improvement: throttled_usec and permitted_usec both fall, and their ratio falls with them. Without a boot identity the two readings are indistinguishable from a machine that was just throttled less. The uptime makes that difference readable rather than merely detectable — the counter run behind the reading is roughly as old as the uptime says.

The host identity is passed into the command as the control group already is, defaulting to the running machine. That keeps the module's existing contract — the caller decides what is measured — and lets the tests assert the fields over a fixture machine rather than over whatever host the suite happens to run on.
