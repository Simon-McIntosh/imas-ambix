The default is guarded by a negative

The load-bearing assertion is not that local mode works — it is that nothing else can silently displace it. A route once selected by whether a personal credential happened to be readable made the launcher's default model hostage to one account, and gave holders of that file dead picker slots while everyone else got the working route. That is now fenced by test rather than by intent:

  • an unqualified launch and an explicit --mode local launch generate byte-identical content, so a cautious caller can assert the default instead of trusting it;
  • a well-formed hosted credential present on disk changes zero bytes of that output;
  • only an explicit --mode hybrid embeds any hosted slot or invokes proxy installation;
  • an unrecognised mode value exits non-zero naming both valid values rather than falling back;
  • the axis parses independently of the existing harness selection it must not collide with.

Two mechanisms, and why both were needed

Alias slots decide dispatch; curated rows decide presentation; a row is not a name a delegated worker can be sent to. Building only the prettier one would have produced a picker whose models no worker could reach.

Rows are derived from the catalog the launcher already fetches, so a two-item fixture emits two independently-labelled rows — 2×H200 int4 512k against 4×H200 fp8 256k — with topology and context read from each card rather than a shared default. A five-item catalog emits five rows against four alias slots, proving row count is not capped by the slot count, and a release the launcher has no built-in knowledge of still gets one. All four slots now declare supported capabilities, which the launcher previously left unset, leaving the harness to guess.

Telling a session where local work goes

Routing already worked and needed no harness change, because a delegated worker's model is requested by alias. The gap was knowledge. The default local launch now states that sonnet is the primary local worker, carrying that release's own validated accelerator count, family and exact max_model_len from its catalog card, the division of labour — bulk, parallel and mechanical work local, adjudication and physics-critical judgement on a frontier slot — and the plain fact that local-only mode has no frontier slot. It describes the mapping rather than creating one, so every alias resolves exactly as before.

Landing that statement exposed a contradiction worth recording. The hybrid branch had inherited a mapping that gave its local release to haiku and sonnet to a hosted model. A session told sonnet is local in the default lineup would have reached a hosted model after switching mode — exactly the confusion an alias mapping exists to remove. Hybrid now places the first local release on sonnet and the second on haiku, with no hosted id on either.

A regression this sprint caused, and how it was caught

The mode axis moved hosted paths behind explicit selection and broke six older launcher tests. Each node's gate ran only its own focused file, so nothing caught it until a whole-surface verification node was dispatched for that gap. The repair changed no production file: tests that supply a hosted release now select hybrid explicitly, picker cases assert the current alias mapping, and assertions on the retired selection surface were replaced by their equivalents against the mode axis that superseded it. Every property still has a test on it — notably the credential test stays unqualified and local, and the catalog-failure test still proves no hosted fallback. Final measure: tests/test_agent.py 183/183, focused launcher suites 13/13.

The launcher's numbered prompt, now fenced

Two different things render a release list and only one of them was observable from a test. The launcher's own numbered prompt is emitted by the generated script, which decides interactivity from [[ -t 0 ]] and reads the answer back from a descriptor pointing at that same terminal — so --print cannot show it and neither can any run whose stdin is a pipe. Every launcher test that captured pipes therefore observed nothing about the prompt, which is why it had never been asserted.

Attaching the deployed script to a pseudo-terminal makes it observable. Against a two-release catalog the prompt renders exactly two rows at 1-based indices, each carrying its own release's label and no harness alias:

Clive global models:
  1) release-alpha · 2×H200 · fp8 · 512k ctx
  2) release-beta · 4×H200 · int4 · 128k ctx
Select model:

Writing an index to the terminal selects that release, recorded as ANTHROPIC_MODEL in the harness environment; an index outside the catalog refuses with 1 through 2 and never starts the harness; and an explicit --model renders no prompt at all. Six tests, passing.

The fence was shown to fire, not merely to pass. A passing suite cannot distinguish a guard that works from one that never runs, so the row's label expression was replaced with the harness alias claude-sonnet-5 in the generated script and the same terminal driver was run against it. The mutated rows read 1) claude-sonnet-5 and 2) claude-sonnet-5, which the label assertion rejects, while the same driver against the script as generated renders both release labels and passes. The assertion is load-bearing rather than incidentally true.

The alias measured where the request arrives

The dispatch statement is fenced by reading the environment and arguments the launcher exports, which is a statement about where a request departs. Nothing in the suite crossed that boundary: every launcher test hands a recording stub its argv and environment and stops there, so the suite would have passed unchanged had the harness ignored the alias mapping entirely. That gap is now closed from the engine side. A new module stands up a recording origin on loopback, runs the generated launcher with the real harness binary on PATH, and asserts on the inference request that arrives.

Three properties are asserted from the recorded request. The model named is the local release id, never the alias string and never a hosted id. Four credentials planted in the environment (ANTHROPIC_AUTH_TOKEN, ANTHROPIC_API_KEY, OPENROUTER_API_KEY, and an ANTHROPIC_BASE_URL pointing at a foreign origin) appear nowhere in the request, headers or body. And a control run rewrites the sonnet slot to a sentinel hosted id, which the recorder does report — so a local reading is known to mean one rather than being what the instrument emits regardless.

One clause of the measure does not hold as written, and is recorded rather than quietly weakened. The node asked that the request carry no Authorization header. Measured, the harness must attach one, and the launcher supplies the fixed non-secret placeholder it already carries for exactly this reason: the request arrives bearing Authorization: Bearer clive-no-auth. That placeholder is load-bearing rather than incidental — it is what stops the harness falling back to the operator's claude.ai login when no other credential is present. The test therefore asserts the credential-absence the clause stands for: any Authorization present must be exactly that placeholder, no x-api-key may be sent, and no planted credential may appear anywhere.

Measure: tests/test_agent_clive_alias_dispatch.py 3 passed at 32b6b62, whole-tree ruff check imas_ambix tests exit 0. The module needs the real harness on PATH and skips with that reason when it is absent, because a stub echoing its own argv restates the very boundary this fence exists to cross.

Every hybrid slot declares its capabilities

The capabilities fence covered the default lineup only, because it ran the launcher in local mode, where all four aliases resolve to the one selected release. The hybrid branch is the case with something to get wrong: it fills the slots from two different places, taking sonnet and haiku from the first two catalog releases and opus, fable and the custom model option from the hosted set, so a slot added there is exactly where a declaration is easiest to forget.

The test drives the generated launcher in hybrid mode and compares the declared capability variables against the slot roster as an exact set rather than a membership check. Five slots are covered, each carrying thinking: the sonnet, haiku, opus and fable model slots, plus the custom model option. The roster is derived from the harness's own registration convention — a slot variable is one that carries a _NAME companion — so it is not a list the test restates, and a slot arriving without its declaration enters the roster and cannot match the mapping.

The fence was shown to be load-bearing rather than merely green: deleting the custom model option's capability declaration from the generated launcher makes the assertion reject it, while the unmodified launcher passes. The hybrid branch imposes three prerequisites no launcher unit test meets by default, and the module supplies them rather than skipping the mode — the catalog card and endpoint document carrying the release string, a user manager promising the proxy is already active, and a listening loopback port for the readiness probe performed before the harness is launched.

One catalog origin, shared by the launcher tests

Three launcher modules each stood up their own closure over a ThreadingHTTPServer to answer the release-catalog fetch the generated script makes, and each recorded the requests it saw. The copies had drifted: one yielded a SiteConfig, the others a bare address, so the same concept lived under three interfaces. One module now serves every launcher test's catalog origin and records what the launcher asked for.

What is not proven here

The launcher's numbered prompt is now asserted to render and to select. The curated rows inside the harness picker are a different surface and remain asserted only to be generated correctly, not to render: they are consumed by the harness, which no headless node can drive to a picker, so confirming them still requires a human at a terminal.

The same boundary applies to the capability declarations. What is asserted is the declaration set the launcher exports in hybrid mode, which is the launcher's own output rather than the harness's behaviour. Whether the harness reads those declarations, and what it is handed when a model carries none, is harness-side and remains unmeasured here: the fence protects the export, not the consumption.
