The 401 is fixed, measured against the live endpoint

The fault that took the shared launcher down was the local model returning 401 Unauthorized through the proxy, because litellm's anthropic/ provider authenticates with x-api-key and vLLM accepts only Authorization: Bearer. Declaring the local model in the openai/ form at a /v1 base makes litellm send Bearer. Retested through the proxy on the same request that used to 401:

POST 127.0.0.1:18399/v1/messages   model=deepseek-v4-flash
→ "Hi there! How can I help you today?"      (was: {"error":"Unauthorized"} 401)

Re-verified after the provider-form correction and a redeploy, returning ok.

The default invocation is provably unaffected

The premise the removal rested on was wrong, and checking it is what reopened the decision: the or-* models were never reachable by anyone but their key-holder. The route was gated on a per-user mode-600 file, --deploy installed the systemd unit into the deploying user's own $HOME, and the unit's ExecStart pointed at a pipx install in one home directory. A second key-holder would have seen clive: could not start imas-ambix-llm.service and exit 1 — not extra models.

What actually caused the outage was narrower: the picker default was routed through the proxy. So the restoration is gated on an explicit flag, and the default path no longer consults OpenRouter state at all — there is no key-file test left anywhere in the script. Verified live through the module-published launcher with ~/.config/openrouter/key still readable:

InvocationResult
clive -p … (key present)default still direct, exit 0
clive -p … after the picker workpicker fixed, exit 0
~/public/bin/clive -p …mirror ok, exit 0

A dedicated test asserts that a readable provider key alone produces zero proxy calls, so the property cannot silently regress.

The transport decision, settled by measurement

The plan deferred the local-model transport to a measurement rather than a preference, on the suspicion that the OpenAI translation would cost Anthropic prompt caching. It does not. Four calls, an identical 78,178-byte payload carrying cache_control on a 6,500-word system block, 6,510 input tokens each:

  • Proxy path: usage exactly {"input_tokens": 6510, "output_tokens": 2} both times — cache_creation_input_tokens and cache_read_input_tokens absent.
  • Direct control: the same shape, both fields also absent.

So the telemetry is not lost by the translation — the local endpoint never reported it. Repeat latency through the proxy fell 97.1%, indicating vLLM's own prefix reuse survives. The openai/ form therefore costs nothing the direct route provides, and the decision is locked on evidence.

The model picker on the local route

The hand-written model descriptions were never lost: they only ever existed on the OpenRouter branch, and the pre-fix local branch at 6503254 set the tier aliases with no _NAME or _DESCRIPTION at all. The owner had simply never seen that path, because a readable key always routed around it.

Read out of the CLI binary, each tier row renders as label: _NAME ?? modelId and description: _DESCRIPTION ?? "Custom <Tier> model" — so "Custom Opus model" was the unset-fallback. More seriously, an unset alias does not remove its row: the assembler pushes a built-in Claude entry instead (s.push(kn() ?? fo()) always pushes, and the finaliser's pt() re-inserts a missing sonnet or opus row). The Fable row visible before this work was exactly that — selecting it would have sent fable to a server holding only deepseek-v4-flash.

One row is therefore not reachable through environment variables. The chosen rendering keeps every tier variable resolving to the served model, so nothing unservable can be selected, while presenting the non-default tiers as inert: _NAME is a single em dash and _DESCRIPTION reads unused tier - routes to <model>. The default entry is the only row that names a model.

Three corrections made at integration

Each was a defect in a node contract rather than in a worker's execution, and each was caught by auditing the merged result rather than the report:

  • All four or-* entries were put on the Anthropic provider, yielding malformed ids anthropic/openai/gpt-5.5 and anthropic/z-ai/glm-5.2, because the dispatch said "the four or-* entries keep the anthropic/ form" when only the two Claude models should. Corrected in 6061e62; the OpenAI-family entries are back on openai/ at the /v1 base while the Claude entries keep the Anthropic-native passthrough that preserves cache_control. Not verifiable while the provider quota is spent — all four models hit the quota check before wire format matters.
  • Two inert exports (ANTHROPIC_MODEL_NAME, ANTHROPIC_MODEL_DESCRIPTION) were added by a worker; the binary does not read them. Removed.
  • ANTHROPIC_SMALL_FAST_MODEL was deleted along with its labels, read as a "redundant triplet". It is consulted on its own branch, independent of the haiku alias, so background work was briefly free to request an unservable id. Restored in 6f9a4ce.

What remains unverified, and why

The four or-* models cannot answer. The provider key reports limit 3250, usage 3250.229, limit_remaining 0 and limit_reset: null — spent, with no automatic reset. Every model returns 403 Key limit exceeded (total limit). This is account state, not code, and it also blocks confirming the provider-form correction above. Adding credit to the key is the only way to close it.
