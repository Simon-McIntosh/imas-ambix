Machine Description as Data — Sprint Record

Execution record for three plans run as one sprint: move machine-description production out of the physics solver into a data layer that is measured before it is built. The per-plan detail lives in the benchmark record and the map/engine record; this document is the sprint-level account of what was decided and why.

Verdict

Qualified pass. The storage question is answered and locked, the producer is built and its output is convention-correct, and the one thing the sprint set out to finish and did not — retiring the machine-specific reader — is blocked on a named, measured dependency rather than on effort. Two plans shipped; the third stands with its remaining work stated as concrete sections.

Decisions, and the evidence that forced them

Experimental data → zarr carrying DD-path metadata (locked)

Not close: ~9× native and ~3.2× IMAS-netCDF at every scale tested. This is the access pattern whose cost is paid continuously for the whole of training, so the read-rate term dominates and nothing else measured competes. The DD-path and units attributes ride along at no measured cost.

Machine description format → left to the owner, with evidence attached

Read rate does not decide it and the plan anticipated that. Description is read once per run and amortises to nothing — 0.0202 s zarr against 0.2073 s native on the whole-load cell, immaterial against a training run — so every arm is fast enough and the choice turns on publishability. The supporting finding is the one that makes a split recommendation coherent rather than a fudge: the IMAS shape costs ≈3.2× as storage and ≈nothing as interchange, because the Data-Dictionary tensorization logic is reusable by subclass into a non-IMAS container. Semantics and container are separable; only the container is expensive.

Map expressiveness → one map per shot range, no conditionals (locked)

Locked on measurement rather than on the plan's stated preference. The declared ranges partition the corpus exactly, so shot range alone expresses every observed change and no conditional is needed. What the evidence refuted was the assumption that campaign is the natural range. The schema now has no conditional, expression or code-hook slot at all, so the rule is enforced structurally rather than by convention.

Source convention declaration → once per machine, with an optional override (locked)

Per-binding would repeat one value across 254 declarations and invite exactly the drift a declarative catalog exists to prevent. A single immutable value is also wrong, because the convention determination explicitly allowed for a store matching no single COCOS — and a store carrying one subsystem in another convention is that phenomenon at smaller scale. MAST declares COCOS-4 once with 0 overrides; DIII-D declares an explicit undeclared marker rather than a guess.

Four conclusions retracted, and the failure mode behind them

These are recorded prominently because the pattern matters more than any single correction. Three of the four were the same error: searching the Data Dictionary under the source's naming, finding nothing, and recording "no representation exists". A negative representability claim is only as good as the concepts searched.

The mesh retraction had the widest blast radius: it invalidated the transition count, the catalog's eleven ranges, and the identity cardinalities, all of which had already been recorded as landed. It also explained an anomaly already visible in the evidence — the boundary at 12417 moved 6 fields while every later one moved exactly 10, and that uniform 10 was the discretisation fingerprint. The one boundary that behaved differently was the only real one.

Two live defects found in already-shipped code

The declared MAST coordinate convention was wrong. imas_ambix/cocos.py declared MAST_SOURCE_COCOS = 3; measurement against real data says 4. COCOS 3 and 4 differ in σRφZ, so ip_like and q_like carry opposite signs — and the shipped tests asserted the COCOS-3 values. Three bound targets were being written with the wrong sign: magnetics/ip, pf_active/coil/current, pf_active/solenoid/current. The determination is what exposed it, and the both-polarity requirement is what made the determination trustworthy: several Sauter sign relations involve a convention coefficient multiplied by sgn(Ip), so a single-polarity test cannot separate a convention error from a current-sign error.

The netCDF engine collapsed any one-element structural array to a scalar. _read_ids_path returned rows[0] whenever a struct array had length one, affecting 20 arrays across four singleton passive families — and it would have silently corrupted a single saddle loop. The fix is generic: binding source rank minus DD leaf rank determines how many trailing structural dimensions survive.

What the evidence says about method

Three findings generalise beyond this sprint.

The IMAS-netCDF arm is a representability check, independent of its read rate. Ten catalog bindings targeted DD paths the dictionary does not support. LinkML validated them — it checks schema conformance, not DD representability — and the zarr engine emitted all ten happily with their DD declarations attached. Only writing through the real Access Layer refused them. So the arm that loses on throughput by ~3.2× cannot silently accept a binding the Data Dictionary will not hold.

A frozen count is a rot clock. Three separate expected-count literals went stale after legitimate model changes during this sprint: emission counts after the catalog grew, a first-shot assumption after ranges coalesced, and identity cardinalities after transitions collapsed. Each was repaired by deriving the expectation from the model — from the loaded catalog, from the resolved range, from build_geometry_transitions — while keeping the concrete numbers as printed receipts. Deriving retires the pattern; re-freezing only resets its clock.

An identity gate belongs before the measurement, not after it. The first transport comparison reported 481× by timing a 447-point live array against a 1652-point mirrored one. Timing is now hard-gated on shape agreement and np.array_equal, with a test that monkeypatches perf_counter to prove a mismatch cannot begin timing. The honest ratio is 41.1× — the bogus one was inflated roughly twelvefold.

Negative and qualified results, preserved

  • Reader retirement is bounded but not executable. 55 modules import gs.geometry; 41 invoke a legacy description-read API (8 library, 33 scripts); 41 description-consumers, 0 reconstruction-consumers. The blocker is one named thing: a description-complete, machine-neutral MachineDescription → GeometryTable adapter.
  • Description content is metric-perturbing. An independent description-content change moved magnetics_residual_whitened_rms by +3.218% and +3.271% — inside the 7.93% source-cutover budget but well outside the 1% same-source budget. A cutover cannot be assumed non-perturbing, and no frozen-spine stamp through the transform engines exists yet.
  • Ten bindings remain qualified, not bound. Nine name legacy fields absent from the level-2 store; one is corpus-observed — magnetics/coordinate shape (28,) — because flux_loop/position points expose writable r/z/phi but no writable coordinate-index leaf, point order being carried structurally instead.
  • DIII-D is declared but unvalidated. No DIII-D corpus and no authenticated PTDATA/MDSplus service on this host, so its single binding is source-only and its convention is explicitly undeclared.
  • Transport scope is narrow. Measured over 24 of 11,573 shots (0.207%), the extent of the refreshed mirror.
  • 16 of 11,573 stores lack static-description arrays. A source omission — missing evidence — not a configuration split, and not to be read as a machine variant.
  • The pf_passive geometry subtree is DD lifecycle alpha. Eighty bindings sit on alpha-lifecycle paths.
  • The query tool and the installed dictionary disagree. DD 4.1.1 as installed lacks pf_active/circuit/identifier and pf_active/coil/element/identifier although the imas-dd tool reports them; …/name is the writable equivalent. Claims from the tool need checking against the installed version.
