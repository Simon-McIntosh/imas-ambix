§3 — Payload parity and the tensorizer seam

Seam VERIFIED. Cross-arm parity exact: 3/3 channels, 64/64 samples each, 192/192 scalar values identical under np.array_equal in both converted arms against native level-2. Commit b9fb2cf, merged as 0ff5be9; 4 tests added.

The question §3 posed was whether a zarr writer can be a sibling subclass of imas-python's tensorizer rather than a reimplementation of the Data Dictionary shape rules, because a hand-rolled twin would diverge silently at the next DD version. It can. IDSZarrWriter subclasses public imas.backends.netcdf.ids_tensorizer.IDSTensorizer — a sibling of imas.backends.netcdf.ids2nc.IDS2NC — and reaches no single-underscore attribute or method anywhere.

Every emitted zarr array carries its IDS-qualified DD path and units as attributes — summary/time [s], summary/global_quantities/ip/value [A], summary/global_quantities/power_radiated/value [W] — which is the property that makes DD vocabulary separable from the IMAS container.

The seam verdict, corrected at the version the project runs

The zero-wrapper subclass seam is REFUTED at imas-python 2.2.0 and VERIFIED at 2.3.0. This is the correction the §3 qualification was carried for, and it changes the §3 headline rather than merely annotating it.

get_dimensions, get_attributes, get_shape_dimensions and get_shape_attributes are public in 2.3.0 and absent in 2.2.0. The writer remains a direct subclass of public imas.backends.netcdf.ids_tensorizer.IDSTensorizer calling inherited public include_coordinate_paths, collect_filled_data, determine_data_shapes, tensorize and filter_coordinates, with no private imas name reached at either version — but on 2.2.0 those four helpers must be defined locally over public NCMetadata/IDS metadata.

So the plan's stated trigger for reimplementation is not met: a four-method compatibility shim is not a hand-rolled twin of the DD shape rules. The shim is nonetheless pure version-lag cost, and it disappears on imas-python ≥ 2.3.0. Project environment measured: imas-python 2.2.0, numpy 2.4.4, xarray 2026.4.0, zarr 3.2.1, netCDF4 1.7.4.

§4 — The proposal

Two formats, decided separately, because the two access patterns are not the same problem.

Experimental data → zarr carrying DD-path metadata

Decided on the measurement, and it is not close. DD-annotated zarr is 9.02–10.28× native level-2 and roughly 3.2× IMAS-netCDF, at every scale and batch size tested, with zero crossings over a 64× payload range. This is the access pattern whose cost is paid continuously for the whole of training, so a ~9× read-rate difference is the dominant term and nothing else measured here competes with it. The DD-path and units attributes ride along at no measured cost, so the vocabulary is kept without the container.

Machine description → left to the owner, with the evidence attached

Read rate does not decide this one, and the plan anticipated that. Description is read once per run and turned into geometry, so its cost amortises to nothing: the whole-load cell is 0.0202 s for zarr against 0.2073 s for native, a difference that vanishes against a training run. Every arm is fast enough. The choice therefore turns on publishability, not performance, which is an owner call rather than a measurement:

  • IMAS-netCDF — Access-Layer compliant by construction, publishable as real IMAS data with no conversion project. Costs the four-method compatibility shim while the project stays on imas-python 2.2.0.
  • zarr + DD paths — one store technology across both patterns, so one engine and one dependency surface. Not AL-compliant without a conversion step.
  • both — netCDF as the published form, zarr as the working form. Two writers to keep in step, but each does the job it is good at, and the tensorizer seam means they share the DD shape rules rather than duplicating them.

What the IMAS shape costs as storage versus as interchange

These are different questions and the numbers separate them cleanly.

As storage it costs about 3.2×. IMAS-netCDF reads 2.38–3.11× faster than native level-2 but 9.02–10.28×/2.38–3.11× ≈ 3.2× slower than DD-annotated zarr, consistently across the grid. That is the price of the container on the training path, and for streamed experimental data it is not worth paying.

As interchange it costs approximately nothing. The expensive part of IMAS compliance is the Data-Dictionary shape logic, and that is reusable: a zarr writer subclasses the same public IDSTensorizer that the netCDF backend subclasses, so DD-correct tensorization and DD-path/units annotation are available to a non-IMAS container for the cost of a subclass. The conclusion is that IMAS semantics and the IMAS container are separable, and only the container is expensive — which is the finding that makes the split recommendation above coherent rather than a compromise.

Unresolved and held under an authority exemption: the live-versus-mapped transport ranking, which needs a mirror refresh before it can be measured on identical payloads. It bears on distribution, not on either storage choice above.
