GLM-5.2 local serving performance — landed evidence

Cumulative execution record for GLM-5.2 local serving performance. It preserves the six measured H200 configurations, the method corrections needed to compare them, and the capacity-versus-latency trade-offs that determine deployment choice.

Matrix verdict

Six configurations completed 84/84 cases each: 504/504 passed, 0 failed. No configuration is a universal winner. DeepSeek-V4-Flash leads single-stream decode at two cards, while its eight-card arm has the largest KV pool and the highest 32-worker aggregate. GLM-5.2 with multi-token prediction gives much stronger aggregate throughput than the same eight-card deployment without drafting, despite losing single-stream decode. GLM-5.2 at four cards is the strongest GLM single-stream arm and is stable at a 32K context, not at 64K.

The comparison is therefore a qualified pass: every active report uses the corrected 1,024-output-token concurrency method, but the useful choice remains workload dependent. Use the two-card DeepSeek arm for best single-stream speed, the eight-card DeepSeek arm for capacity and high concurrency, the four-card GLM arm for the best measured GLM single stream, and eight-card GLM with drafting when aggregate throughput matters.

Method corrections and qualifications

  • Concurrency length corrected. Warmed-up concurrency rows originally generated 256 output tokens per worker while the throughput headline used 1,024. All six active reports were regenerated at 1,024 tokens; superseded reports are excluded from the tables.
  • GLM four-card context corrected. Three clean launches of the same configuration exposed 6.41, 3.14, and 6.33 GiB KV pools. A 64K context requires about 5.65 GiB and is therefore not repeatably available. The recorded configuration uses 32K, which requires about 2.8 GiB and clears the lowest observed allocation.
  • Two stale profile fields were not treated as measurement authority. The two-card DeepSeek report inherited four-card TP/GPU fields in its profile provenance, while its direct /v1/models metadata reports two H200 accelerators and the run identity is the two-card arm. The no-MTP GLM report inherited the profile's MTP declaration, while its run identity and absent draft metrics establish that drafting was disabled. Configuration labels above use the direct run facts.
  • Topology is discrete. Tensor parallelism must divide 64 attention heads, so the feasible matrix widths are 2, 4, and 8 cards; six cards is not a valid arm. GLM cannot fit below four cards because its weights would require about 218 GiB per card.
  • The figures are qualified. Their selectable, theme-neutral SVG text remains useful, but their five-run content is not a substitute for the final six-run tables.
