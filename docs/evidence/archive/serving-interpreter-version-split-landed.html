Serving interpreter split — closed without implementation

Closure record for the serving interpreter split, which is retired without being built. The work it describes was already done under a different plan, and what remained of its premise turns out to belong to an upstream wheel matrix rather than to this repository.

The locked decision is already satisfied

The plan carried one locked decision, kernel-environment-boundary, chosen separate-environments and carried forward from an earlier plan. Its stated ground was that the kernel needs to be reachable by the engine, not co-resident with it, and co-residency is the only thing imposing the interpreter floor.

That separation exists in the tree. imas_ambix/agent/envs/ktransformers/ is its own environment and is the only one declaring the kernel:

# The KTransformers CPU-offload kernel. This is the sole reason this
# environment exists: it is what pins the interpreter to cp312.
"kt-kernel",

imas_ambix/agent/envs/sglang/ does not depend on it, and records why in its own header: KTransformers CPU-offloading is served from its own environment, which is what keeps this one free of the kernel's cp312 wheel pin. So the co-residency the decision named as the sole cause of the floor is gone, and the engine that actually serves the production lane is no longer behind it for that reason.

What remains is not what the plan described

All three serving environments still declare requires-python = ">=3.12,<3.13" while the repository declares >=3.14 and the formatter targets py314. That residue is real, but its cause is no longer the kernel. Raising the floor in the two kernel-free environments depends on whether the engine stack publishes cp314 wheels — SGLang, torch, flashinfer and sgl-kernel — which is an upstream matrix this repository neither owns nor can schedule. A plan whose closing condition is another project's release cadence is not an executable plan, and holding a sprint open against it reports work that no worker here can take.

The recurring breakage is already guarded

The plan's urgency came from the serve having broken four times on repository syntax the older interpreter cannot parse, an unparenthesized exception tuple each time. That class is now caught before it can reach a serve, by two tests in tests/test_agent_serve_registry.py:

test_agent_package_modules_parse_with_serving_python
test_serving_python_guard_rejects_unparenthesized_exception_tuple

Run at closure, both pass — 2 passed, 7 deselected in 1.73s. The second is the control that matters: it asserts the guard rejects the offending grammar, so a guard that had silently stopped checking would fail rather than pass quietly. The exposure that justified the plan is therefore covered by a cheaper mechanism that runs on every gate, rather than by a rebuild that costs a coordinated lane stop.

What would reopen this

Three facts would each make this worth rebuilding, and none holds today. If the engine stack publishes cp314 wheels, raising the two kernel-free environments becomes a small change with a real benefit and no upstream blocker. If a repository module imported by a serve needs syntax the guard cannot express as a parse check, the guard stops being sufficient. If a profile reintroduces the kernel into an engine environment, the co-residency returns and with it the original cause. The first is the one to watch, and it is observable without any work here.

What was not established

This record does not claim the interpreter floor is harmless, and it does not claim the two kernel-free environments could move today. Neither was tested: no attempt was made to resolve the engine stack against a 3.14 interpreter, so the wheel-availability question is stated as the open one rather than answered. The narrower claim is the one the evidence supports — that the boundary this plan was written to create already exists, and that the failure it was written to prevent is caught by a passing guard.
