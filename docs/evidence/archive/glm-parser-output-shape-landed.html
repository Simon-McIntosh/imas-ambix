What landed

Both defects are closed, and in both cases the measurement moved the problem away from where the plan had placed it. Neither was a correctness fault — the engine called tools correctly and reasoned correctly throughout — which is why they were split out of a bring-up rather than allowed to hold it.

The marker: not synthesised, emitted

The plan offered two candidate owners — the reasoning parser closing a block it never opened, or the tool path failing to filter. Probes against the live engine eliminated both, and named a third:

ProbeResult
tool request, thinking disabledone tool_use block plus the exact 8-byte marker in adjacent text
same prompt, no toolszero occurrences
raw completion, no chat templatezero occurrences
OpenAI probe with token idsgenerated token 154842 maps exactly to the closing marker; reasoning_tokens=0

So the model emits the token itself, immediately before its tool-call opener, and the engine's parser passes it through as content precisely because no block was opened. Nothing can suppress a token the model produced, so the fix had to live where the response is still shapeable.

That place already existed. Every serve loads our own ASGI middleware through the generated script's --middleware argument — the same mechanism that injects launch-owned metadata into the model catalog. A second layer now strips the orphan marker from assistant content in buffered JSON and in incremental SSE, covering both LF and CRLF event boundaries. The root cause remains upstream; this reaches every consumer of our serves without waiting on it.

The guards matter more than the strip, because an over-eager filter would be worse than the stray token: a genuine thinking block keeps its markers, a marker-free response stays byte-identical, and a marker appearing in ordinary prose survives.

The budget: truncation, not swallowing

The plan read this as reasoning consuming the cap so no final block was reachable. A six-point sweep showed something simpler:

Output capStop reasonFinal text block
256, 512, 768, 1024max_tokensabsent
1536, 2048end_turnpresent, at 1484 total tokens with 1025 thinking

The response was being cut off, not withheld. No change was needed here: the launcher's per-release reservation already derives from the selected card's own context and emits 16,384 for this release — an order of magnitude above the 1,536-token threshold — so the condition cannot arise at any budget it produces.

Deployment note

A running engine carries the middleware only from its next restart, since the layer is registered by the generated serve script. The marker is cosmetic rather than a correctness fault, so that restart is not urgent and was deliberately not forced on a healthy endpoint.
