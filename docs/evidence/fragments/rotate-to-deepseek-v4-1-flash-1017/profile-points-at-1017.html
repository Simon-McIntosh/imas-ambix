The profile names the 1017 release

ModelConfig gained an optional revision field, and the deepseek-v4-1-flash profile now declares the 1017 release by repository (deepseek-ai/DeepSeek-V4.1-Flash-1017), by the commit 1bae0e1088993b9b82de08f59de5be5a34e42170, and by a weights directory of its own (weights_slug = "deepseek-v4-1-flash-1017"). Neither is a property of this update: a repository's default branch can move, so a profile naming only the repository leaves the weights a deployment loads to depend on the day it ran, and a directory of its own is what keeps two releases from sharing a shard set. served_name is unchanged, so the release answers to the one client-visible name deepseek-v4.1-flash.

The generated serve script names both halves of the release it serves, and the plan's MODEL_DIR clause is met by one moved line: the directory is now /work/projects/imas_gpu/agents/deepseek-v4-1-flash-1017/model. The directory is not the only difference. A profile that declares a revision carries it into the serve script as a REVISION value echoed into the job log beside the model directory, because a directory name is not a record of which checkpoint a run loaded — one repository can publish more than one release, and a default branch moves after a download. Only a declared pin emits those lines: the nine profiles that pin nothing generate scripts byte-identical to the base revision's generator, and this profile's script differs from its own September-directory equivalent by the MODEL_DIR line alone, which is what the test asserts — equality modulo the weights directory and the pin, not a substring.

The 48 shards already in that directory were verified against the repository's own listing at the pinned commit — size and SHA-256 per shard, all 48 matching — by SLURM job 1294295 on sirius. The log is shard-verify.log beside this fragment; its slurmstepd warnings are inherited TMPDIR noise from the five-day-old allocation the job was submitted from, not a fault of the run, whose last line reads EXIT=0.

The generated download script resolves the pin before it transfers anything and passes it on: the client is asked for --revision "$REVISION", and a models info --expand sha call through that same client runs first and ends the job if the repository does not publish the revision. Both call the same variable, so the check and the transfer cannot disagree about what was published. The refusal matters beyond a fast failure: a client that cannot resolve a revision follows the repository's default stream, which is the substitution the pin exists to prevent. Profiles declaring no revision are untouched — all nine were compared against the previous generator at a7d24c5a and generate byte-identical scripts, while this profile's script differs only by the REVISION line, the check and the flag (download-script-delta.log).

Both halves were shown to fail. The shard verifier: a scratch directory holding 47 symlinks to the real shards and one full copy of model-00001-of-00048.safetensors with a single byte flipped at offset 5,000,000 reported MISMATCH for that shard and VERDICT: FAIL. Its first attempt also failed honestly: the recursive listing endpoint paginates at fifty entries, served only thirteen shards of the forty-eight, and the verifier's own control refused that listing rather than reporting the thirty-five absent from it as missing files. The refusal: deleting the check from a scratch copy of the generator left the script running the transfer to completion against an unpublished revision — exit 0, download complete — and the refusal test failed on it, so the guard is load-bearing rather than decorative. The copy was restored under a trap and the restore is verified by checksum, not assumed. The serve script's revision record: suppressing the emission makes the dry-run test fail on the absent commit, so the record is load-bearing rather than a line along for the ride. The control logs are outside the tree, at ~/.config/reckon/crew/runs/r-20261023T140736542637-profile-points-at-1017/.
