llm-watch's head line names the loaded checkpoint

The served name is identical across the lane's weights-only rotation, so a head line carrying only the name reads the same before and after it. llm_watch's head line now carries the release the served engine actually loaded, read from the endpoint document's checkpoints map: on today's map it renders deepseek-v4.1-flash · DeepSeek-V4.1-Flash-1017@1bae0e10 · 4×H200 · gpu-0003 · 262k ctx. The label is the repository's last path part and an eight-character commit, as gpu-watch draws it from the same map.

The lookup key is built with registry._engine_id, the function that wrote the map's keys, so the same short host form is used on both sides: gpu-0003.iter.org:18810 for the entry whose host is 98dci4-gpu-0003.iter.org at port 18810. A key assembled here from the entry's raw host would be a plausible string that misses every entry, so both directions are asserted — the engine id resolves, and the same record keyed by the raw host does not.

A document that records no checkpoint for the served engine states checkpoint unrecorded in yellow rather than leaving the slot blank, because a blank reads as "no checkpoint applies" and is indistinguishable from a label that was dropped. An empty map is the same absence as an absent one.

The document build reads endpoints.json through SiteConfig.from_env().endpoint_document when the caller gives no path, once per build — which is once per refresh — and carries the map at the document's top level as checkpoints. The head line was already drawing its card count and context ceiling from the endpoint entry, which the live view received empty, so the site path is what makes both the existing figures and the new label reachable without a command-line flag. live_panel.py is unchanged: the checkpoint is a fact about the deployment, not a per-poll reading.
