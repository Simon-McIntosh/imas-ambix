A serve records the checkpoint it loaded

A registration carries a new optional checkpoint field, written by the generated serve script from its profile as <hf_repo>@<revision>. The profile's hf_repo and revision are joined at script generation (slurm.py); a profile that pins no revision writes <hf_repo>@unpinned, so an absent pin is visible rather than passed off as an identity, and a record written before the field existed reads null and still builds. The published document carries the checkpoint in a new checkpoints map at its top level, keyed by the engine id, and the recorder's serve_config gains model_path, read from the engine's own /server_info report rather than from the launcher, because every checkpoint has its own directory and the engine's resolved path is what identifies the weights a row was measured against.

Measure: ruff check imas_ambix tests exits 0, and the three declared test files pass with the new tests (81 passed, EXIT=0). The engine entry's key set is asserted against the base revision's seven fields — model_id, host, port, accelerator_family, accelerator_count, checkpoint_precision, max_context — rather than read off the entry object, which would agree with whatever field had been added to it. Negative control: restoring checkpoint as an entry field fails that assertion with 'checkpoint' reported as an extra item in the entry key set, and turns the document red against the published launcher, giving 10 failed, 29 passed and EXIT=1. A second negative control covers the recorder: with _merge_serve_config mutated to let the caller's (profile) model_path win over the engine's report, the as-reported test fails on a fixture whose engine path differs from the profile, giving 1 failed, 1 passed and EXIT=1.
