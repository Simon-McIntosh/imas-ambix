Probe-angle catalogue binding — blocked by missing engine support

Outcome: blocked. Binding magnetics/b_field_pol_probe/poloidal_angle in imas_ambix/data/machine_maps/jt-60sa.json cannot make read_geometry_table/geometry_table_from_description return a finite angle through data alone. Two independent refusals in the netCDF description path and one hard-coded NaN in the adapter all require code changes under imas_ambix, which this node's done-when forbids and its exclusive write scope does not grant. No catalogue or test change was committed, because any executable binding to this leaf raises and would break every JT-60SA description transform.

The three gaps, each reproduced

  1. Unsupported COCOS transformation. The DD marks magnetics/b_field_pol_probe/poloidal_angle with cocos_label_transformation = "pol_angle_like". transform_engine._apply_cocos_convention resolves that label and calls cocos.canonical_factor("pol_angle_like", source_cocos=…), which delegates to nova.io.cocos.transform_factor. nova's TRANSFORMATIONS is {psi_like, b0_like, dodpsi_like, q_like, ip_like, one_like} — no angle class — so the call raises and the engine reports BindingTransformError: targets unsupported COCOS transformation 'pol_angle_like' for every source COCOS, including the target 17.
  2. Unvalidated sign refused. transform_engine._apply_sign_convention accepts only identity, negate and not-applicable; the plan-mandated sign_convention: unknown-unvalidated raises BindingTransformError: has unresolved sign convention 'unknown-unvalidated' (recorded defect from run 3a1ebf28, whose value the schema and DIII-D still declare).
  3. The adapter never reads the angle. geometry_adapter._b_probes builds each BProbe with angle_deg=float("nan") and flags "poloidal angle is absent from the emitted description", regardless of any poloidal_angle array in the description. So even a successfully emitted angle would not reach geometry_table_from_description. The only angle fill today is description_reader._supply_declared_probe_angles, applied only when probe_angle_source == "acquisition-address" (MAST), and probe_angle_source == "description" (JT-60SA) applies nothing.

Reproduction

A scratch catalogue (in $TMPDIR, never the repository) added the probe-angle binding to both phases and set sign_convention to each candidate value. transform_machine_description(catalog, 101173, "netcdf", JT60SA_DESCRIPTION_DIR) returned: 

unknown-unvalidated EXC BindingTransformError binding
'jt60sa-op1-magnetics-b-field-pol-probe-angle' has unresolved sign convention
'unknown-unvalidated'
identity EXC BindingTransformError binding
'jt60sa-op1-magnetics-b-field-pol-probe-angle' targets COCOS-dependent DD path
'magnetics/b_field_pol_probe/poloidal_angle' …

The store's poloidal_angle values were read and are finite for all 17 probes (MP1..MP17) in both phases; the blocker is the emit path, not the data.

Adjacent pre-existing regression

The gate is red at this base for an unrelated reason: commit 6172d751 made a selecting binding's source_rank count only struct levels below the consumed selector level, but the catalogue's two tf-coil-coordinate-element bindings still declare source_rank: 1 while tf/coil/name has no struct level below the selected coil entry. Every description transform raises binding 'jt60sa-op{1,2}-tf-coil-coordinate-element' source rank 1 cannot be reconstructed from leaf rank 0 and 0 structural arrays. This is outside the probe-angle goal and is reported as a follow-on.

What unblocks it

A node with write access to imas_ambix/cocos.py, imas_ambix/data/transform_engine.py and imas_ambix/data/geometry_adapter.py must (a) give the factor table a pol_angle_like class, (b) let an unknown-unvalidated binding emit its value unchanged while recording the unresolved sense, and (c) have _b_probes read the emitted poloidal_angle when present. The catalogue binding then becomes a one-line insertion per phase; the store data is already correct.
