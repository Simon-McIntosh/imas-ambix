G-EQDSK psi bound into profiles_2d/psi

E101011's G-EQDSK is a 2-D poloidal-flux grid, so the EDDB channel fetch a signal map normally drives cannot serve it. write_geqdsk_store in imas_ambix/data/geqdsk_store.py reads the file through load_geqdsk and stages it into a per-shot Zarr group laid out exactly as imas_alambic.eddb's cache writer lays a fetched channel — {shot}.zarr/GEQDSK/PSI with a PSI_time sibling and the R, Z grid-coordinate arrays — so VirtualZarrView reads it like any cached channel. The store keeps the file's own COCOS 1 flux (Wb/rad) unchanged; the COCOS 1 → 17 conversion is owned by the map rule, so a reader can measure the source without the map's assumed factor.

One rule in maps/jt-60sa/maps/equilibrium.json binds it:

{
  "semantic_id": "equilibrium_psi",
  "source_group": "GEQDSK",
  "source_array": "PSI",
  "source_unit": "Wb/rad",
  "source_cocos": 1,
  "transformation": "psi_like",
  "unit_factor": 1.0,
  "channel_factor": 1.0,
  "target_path": "equilibrium/time_slice/profiles_2d/psi",
  "target_unit": "Wb",
  "validation_state": "source-only"
}

equilibrium_psi's convention_factor is −6.283185307179586 (−2π), the COCOS 1 → 17 psi_like factor. The rule system carries no separate coordinate slot, so the grid coordinates are bound by the store's own GRID_R/GRID_Z arrays rather than by a second rule.

Measured difference

The served psi (minted through the engine at the G-EQDSK's declared ≡ 4000 ms snapshot) equals the G-EQDSK psi times −2π on the file's own (Z, R) grid. Normalised RMS difference over the flux range (8.7816 Wb):
