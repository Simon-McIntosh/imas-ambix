Ports named in site configuration

No TCP port is named anywhere in the EQDB or EDDB configuration read. The EQDB transport is a socket client — eqdbsockclient_connect and its siblings (_ftp, _joinlist, _joineqio, _joinimage, _close) in /analysis/lib/JT60SAEQDB/libEQDBMSPIC.so, over SOCKET_EQDBIO / SOCKET_FAMEIMAGE — and the *.eqdbms files carry paths, owner and admin lists but no port number. The SSH port (22) is the only transport named anywhere, and the survey policy forbids a port scan. So the "port named in site configuration accepts a TCP connection" measure has no subject: no port is named in the sources read. The companion resolution measure is done and reported above. The site's own scripts that would drive the socket (eqdball, length_put, … under /analysis/lib/JT60SAEQDB/eqdbms.20230523/) are mode-restricted and return Permission denied to d240044, so the socket could not be exercised even were a port named. A further port probe is deferred rather than guessed.

Where FAME's FAME3 records sit

Every FAME store path the configuration names was tested from intr26-2 and none exists:

  • /JT60SA_EQ/FAME3 — not present (No such file or directory).
  • /analysis_DB/FAME3 — not present. Its parent /analysis_DB is mounted (from anastr01) and holds only EDASDB/ and MBDB/, each a tree of per-account directories, no FAME/EQDB content.
  • /dbhome/h060028/FAME3 — not present; /dbhome is not mounted at all.

So on the one server this survey reached, FAME3's records were not found: no migrated store, archived dump or copy is present on nakasvr26's mounted filesystems. The configurations that once named the alternatives (echoFameDir's commented /analysis_DB/FAME3 and /dbhome/h060028/FAME3; echoFameHost's commented #echo fame3 / #echo nakasvr17) point at hosts and mounts that are gone — every one of fame3, nakasvr17, dbsvr17p is unresolvable. nakasvr23 could not be reached (above), so no claim is made about it. Result: none found on the reachable server.
