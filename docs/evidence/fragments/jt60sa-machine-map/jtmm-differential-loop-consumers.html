Blocked: the staged map cannot serve the 53-loop and 27-loop stores at once

This node carries a type-6 magnetics/flux_loop entry through the geometry adapter, read_geometry_table and build_operator, as the prediction of its indices_differential second loop minus its first, and makes the JT-60SA map's flux-loop position bindings expand over the type-1 entries only. The adapter and operator carriers are implementable inside this node's write scope. The map half is not, without a decision the plan does not settle: the transform engine offers exactly one route to a uniform read of the type-1 positions or the type-6 indices, and that route is per-entry struct_array_entry selection, which raises — it does not degrade to a missing binding — when the named entry is absent.

Measurement

Two probes were added to a copy of the staged map: a position read selected on entry FL1 (magnetics/flux_loop/position/r, source_rank 0, struct_array_entry: FL1) and an index read selected on entry FL7-FL1 (magnetics/flux_loop/indices_differential, source_rank 1). The same map was run against both stores.

== live-27 store: /work/projects/imas_gpu/jt60sa/maps/machine_description
   transform RAISED BindingTransformError: binding 'jt60sa-op1-flux-loop-fl7fl1-idx'
   selects struct-array entry 'FL7-FL1' on 'magnetics/flux_loop/indices_differential',
   but flux_loop carries no entry with that name
== staged-53 store: .../superseded/differential-loops-staged
   status=emitted
   per-entry probe arrays: [('jt60sa-op1-flux-loop-fl1-r2', [1.8798]),
                           ('jt60sa-op1-flux-loop-fl7fl1-idx', [7, 1])]
   whole-array flux-loop bindings missing:
     ['jt60sa-op1-magnetics-flux-loop-r', 'jt60sa-op1-magnetics-flux-loop-z']

So per-entry selection reads the type-1 position (1.8798 m) and the type-6 pair (7, 1, i.e. loop 1 minus loop 7 by the DD convention second − first, here stored as [7, 1]) from the 53-loop store exactly as the done-when requires. But the identical map refuses the 27-loop live store outright, because entry FL7-FL1 does not exist there and _select_struct_array_entry raises BindingTransformError rather than reporting the binding absent. The whole-array position bindings the map carries today are, in turn, dropped on the 53-loop store: their ragged position struct array (position:shape 1 for type-1, 0 for type-6) makes the family read a missing binding, which is the six-red-adapter-test failure the store node already measured.

Evidence log: negative_control_log.txt in the run directory.

Why no single binding form works

The transform engine reads a struct-array path in one of two ways only. Without a selector it stacks every entry, so a ragged sub-array such as flux_loop/position/r or flux_loop/indices_differential raises BindingTransformError on the 53-loop store. With struct_array_entry it selects one entry by name and reads only that entry's sub-arrays, which is uniform but per-entry and, as measured above, fatal on a store where the entry is absent. There is no wildcard, no entry filter, and no list-valued selector: ChannelBinding carries the single optional struct_array_entry and nothing else. Consequently the map cannot express "the type-1 entries only" in one read, and it cannot carry both stores without the absent-entry case either erroring or being tolerated.

The engine lives at packages/imas-alambic/src/imas_alambic/transform_engine.py, which is outside this node's granted write paths.

Options, and the decision needed

  1. Per-entry expansion with a per-store map (in scope, no engine change). Replace each flux-loop position binding with 27 per-entry bindings (name, r, z) selected on FL1…FL27 and add 26 per-entry indices_differential bindings selected on FL7-FL1…FL7-FL27; the adapter gains an indices_differential role and a two-index carrier, and the operator subtracts. The staged map then serves the 53-loop store only, and the six adapter tests read the live 27-loop store through the live map, not the staged one. This is the only route with no out-of-scope edit, but it needs the plan to confirm that the staged map is not required to read the live 27-loop store (the done-when's "points its tests at the copy through IMAS_ALAMBIC_MAP_PATH" reads as if it is).
  2. Add an entry-list selector to the engine (out of scope). A struct_array_entries list-valued selector, or absent-entry tolerance that reports the binding missing instead of raising, lets one map carry both stores with a single position binding per role. Requires granting this node packages/imas-alambic/src/imas_alambic/transform_engine.py (and the ChannelBinding schema in machine_map.py).
  3. Carry the differential pairs in the map as data (out of scope as written). A new catalog section listing the 26 pairs would let both stores read with the current engine, but the plan says the pair is read from indices_differential, and adding a catalog section is again a machine_map.py edit.

Leaning: option 1, because it keeps every edit inside the granted scope and matches the established per-entry struct_array_entry idiom the map already uses for the 12 PF coils and the TF coils. It costs roughly 130 added bindings per binding set and a new adapter role, and it changes the done-when's reading of which map the live-store half uses.
