Blocked: the type-6 carrier lives outside this node's write scope

This node is the operator-side consumer of the 53-loop JT-60SA flux-loop bindings the differential-loop store node produced. Its done-when asks read_geometry_table and build_operator to carry each type-6 magnetics/flux_loop entry as the prediction of its indices_differential second loop minus its first. That requires two pieces of state which do not exist anywhere in the current tree and which cannot be created inside the granted write scope.

Reproduction

Reading the staged 53-loop store (/work/projects/imas_gpu/jt60sa/machine_description/superseded/differential-loops-staged) through read_geometry_table(100595, machine="jt-60sa", store_root=...) returns zero flux-loop sensor rows: only the 17 mapped B-probes survive. The transform reports both flux-loop position bindings absent:

missing ('jt60sa-op1-magnetics-flux-loop-r', 'jt60sa-op1-magnetics-flux-loop-z')
emitted 83 arrays; 2 declared arrays are absent from the pulse store
sensor_map rows: 17  (all b_probe)

The cause is the ragged position struct array: the store's flux_loop.position.r/z is (53, 1) with a position:shape variable that is 1 for the 27 type-1 entries and 0 for the 26 type-6 entries, so _stack_struct_array_rows raises and the whole flux-loop family is dropped. flux_loop.indices_differential is likewise ragged ((53, 2) in the file, empty for type-1). The 53-loop store also carries flux_loop/name (53,) and flux_loop/type/index (53,), both uniform, so those two read cleanly through the transform engine.

Probe log: recon-53loop-read.log in the run directory.

Why it cannot be fixed in scope

Carrying a type-6 row as "loop(second) − loop(first)" needs two integer indices per sensor row. The sensor-row record SensorMapping in imas_ambix/gs/geometry.py has no field for them (amb_channel, kind, efm_index, r, z, angle_deg, residual_m, flag), and GeometryTable has no side table either. Both are outside this node's write paths, and a probe write outside the scope is refused read-only, so the breakage is not resumable by writing outside the fence.

The plan assigns that carrier to the sibling node jtmm-differential-loop-adapter: “the JT-60SA map's flux-loop position bindings expand over the type-1 entries only, and a type-6 entry is carried by its indices_differential in place of a position”. That node also owns the tests/data/test_jt60sa_machine_map.py bindings and the jt-60sa.json catalog, and it has not been dispatched: no run matching jtmm-differential-loop-adapter exists in the crew run store at the time of this report.

Options

  1. Dispatch the adapter node first and redispatch this node once a carrier field exists on SensorMapping and the adapter emits type-6 rows. This node then only consumes.
  2. Grant this node the adapter scope (imas_ambix/gs/geometry.py, imas_ambix/data/geometry_adapter.py, imas_ambix/data/machine_maps/jt-60sa.json, tests/data/test_jt60sa_machine_map.py), and implement the carrier here together with its operator consumer.
  3. Implement a within-scope carrier that abuses an existing string field (e.g. encode the pair in SensorMapping.flag), or resolve the pair by parsing the DD channel name FL7-FL1 in the operator. Both deviate from the done-when's "read from indices_differential" and would conflict with the adapter node's real carrier.
