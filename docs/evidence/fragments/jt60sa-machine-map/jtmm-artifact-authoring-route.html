The question is how the JT-60SA machine artifact is authored from the §4 source without a JT-60SA module in nova. Read from the code, the answer is: nova already holds a machine-arbitrary packing, verification and caching layer, but no entry derives a machine's identity from DD-shaped IDS input, and both producers that exist are hard-wired to one machine. A JT-60SA artifact can be produced and verified today by calling the generic entry directly — the probe below does exactly that from the OP1 store and gets a nova-jt-60sa-machine-artifact manifest with matching digests — but the identity such a manifest must carry (physical digest, registry digest, shot ranges, field evidence, channel drives) has no producer and no owner for JT-60SA. That missing producer is the thing to add, it can live in ambix, and it is the only piece absent: the mechanical layer it would call is complete, machine-parameterized and importable, so nothing JT-60SA-specific needs to enter nova. The rest of this record names the entries, their inputs and writes, how verification works, the files a JT-60SA route would touch, and the exact call that fails without the producer.

The generic layer exists and is machine-arbitrary

Four functions in nova/imas/machine_artifact.py carry no machine constant at all; each takes the machine by name and a directory of already-authored IDS containers. Their signatures were read with inspect.signature in the probe:

entrymachine-arbitrary?role
create_machine_artifact_manifest(source_directory, *, machine, dd_version=None, registry_digest, physical_digest, shot_ranges, complete, unresolved_gaps, field_evidence=(), channel_drive=()) yes — machine is a parameter hash every file in the source directory and assemble a canonical, validated manifest (manifest_schema(machine) → nova-{machine}-machine-artifact)
materialize_machine_artifact(source_directory, cache_directory, manifest) yes verify the source files against the manifest, then publish atomically into a content-addressed cache with renameat2(RENAME_NOREPLACE)
resolve_machine_artifact(cache_directory, digest, *, expected_dd_version=None, expected_registry_digest=None, expected_physical_digest=None, allow_incomplete=False) yes re-hash every file against the manifest, re-validate the manifest, and enforce any supplied expected identity
MachineArtifactManifest.semantic_identity() yes content address over the dictionary pin, physical and registry identity, shot extent and field provenance, excluding the file table (which carries library write metadata)

What this layer does not do is read the IDSs to derive an identity. create_machine_artifact_manifest hashes bytes and checks nothing about their contents beyond the file inventory; the dictionary version, the physical digest, the registry digest, the shot ranges and the field evidence are all inputs. So the entry answers “package and verify this directory as machine X”, not “author machine X from a DD-shaped IDS set”. Removing the five identity arguments is not optional:

create_machine_artifact_manifest(OP1, machine="jt-60sa", dd_version="4.1.1")
  -> TypeError: missing 5 required keyword-only arguments:
     'registry_digest', 'physical_digest', 'shot_ranges', 'complete', and
     'unresolved_gaps'

The two producers that exist are each hard-wired to one machine

producermachineidentity source
nova.imas.mast_geometry.publish_refined_artifact (nova/imas/mast_geometry.py:541) and publish_provisional_artifact (:601) "mast", written literally into create_machine_artifact_manifest(..., machine="mast", ...) at publish_refined_artifact line 570 MachineGeometryRegistry.default() — nova's packaged MAST geometry catalogue; the physical and registry digests, the shot ranges and the evidence all come from the MAST catalog, the channel drives from nova.imas.mast_channel_drive
nova/scripts/diiid_machine_artifact.py publish_diiid_machine_artifact MACHINE = "DIII-D" (module constant) nova.imas.diiid_machine_ids.build_diiid_machine_ids over SOURCE_PATH (DIII-D's own native source), then _artifact_digests over the leaf snapshot

DIII-D is the precedent that a second machine is added by writing a machine-specific producer, not by widening a generic one. Its producer is a module-private script (nova/scripts/ DIII-D-specific), reads a single netCDF file diiid_machine_description.nc holding the whole IDS set, derives the dictionary version from the file itself (_declared_dd_version) and the digests from its own converter's snapshot, and only then calls the generic publish_diiid_machine_artifact->create_machine_artifact_manifest. No part of that path reads an arbitrary DD IDS directory; the identity still comes from the machine's own converter.

On the ambix side there is exactly one entry and it is MAST-only. imas_ambix/gs/artifact_resolution.py exposes resolve_machine_description(cache_directory=None, digest=None) and author_pinned_description(durable_root=None): neither takes a machine, and author_pinned_description hard-imports the MAST producer at line 316, from nova.imas.mast_geometry import publish_refined_artifact. The call a JT-60SA caller would want fails:

  -> TypeError: publish_refined_artifact() got an unexpected keyword

Probe: a JT-60SA artifact authors, verifies and caches from the OP1 store

Read-only w.r.t. nova/, maps/ and every cache. The §4 source OP1 was opened with imas: it holds five DD 4.1.1 netCDF (HDF5) containers — magnetics.nc, pf_active.nc, pf_passive.nc, tf.nc, wall.nc — each declaring version_put.data_dictionary = 4.1.1, plus a receipt.json that is a converter receipt and not an IDS. The two digests above are probe-derived stand-ins (sha256 over a file table the probe computed), not published identities; they are quoted only to show the manifest is structurally complete and its OCI tag self-consistent. Materializing it demonstrates the verification path: into a node-local cache under /tmp, materialize_machine_artifact returned a VerifiedMachineArtifact whose digest (sha256:bd2145a2…3cefb) equals the manifest's own digest, so the round trip through → verify-and-publish → resolve-and-verify closes. Materializing into the run directory (GPFS) instead is refused, and that refusal is itself load-bearing:

materialize_machine_artifact(staging, <run-directory>/probe-cache, manifest)
  -> MachineArtifactError: the cache filesystem does not support atomic
     no-clobber directory rename, so an artifact cannot be published there
     without risking a half-visible object

This is why ambix does not author into the durable cache directly: it authors into staging_cache_root() (node-local TMPDIR) and mirrors with its own publish_object, which fsyncs and uses a plain no-clobber rename that GPFS accepts. A JT-60SA producer inside ambix inherits that pattern unchanged. The probe script, its JSON report and its stderr are under the run directory: probe_jt60sa_artifact_route.py, probe_output.json, probe_stderr.log.

Files a JT-60SA authoring route in ambix would touch

The route the plan §7 describes touches these ambix files — all of them §7's own pin-table and machine-keying work, none of it new to this question:

  • imas_ambix/gs/artifact_resolution.py — the pin table keyed by machine replaces the three module constants; author_pinned_description takes each machine's authoring route from that table (retiring the hard import at line 316) and resolve_machine_description gains the machine.
  • imas_ambix/gs/machine_identity.py — default_registry() (line 145) keyed by machine; the JT-60SA key returns the registry built from the JT-60SA artifact
  • imas_ambix/gs/artifact_geometry.py — MachineArtifactGeometryReader.machine becomes required (today machine: str = "mast" at line 758).
  • imas_ambix/gs/machine_selection.py — ArtifactMachineSelector gains a required machine and passes it to the identity registry, the acquisition read and the geometry reader.
  • imas_ambix/spine_bench/machine_artifact_arm.py — the expected physical and registry digests come from the machine-keyed pin table instead of the MAST constants it defaults to.
  • New: a JT-60SA producer that reads the §4 stores (maps/jt-60sa/machine_description/{OP1,OP2}, DD 4.1.1 netCDF IDSs), derives the physical digest, registry digest, shot ranges, field evidence and channel drives, and calls nova's generic create_machine_artifact_manifest and materialize_machine_artifact (or ambix's publish_object for the durable mirror). This is the entry that is missing, and it is the only new file.

Can the route stay inside ambix? Yes. The mechanical layer the producer needs is entirely machine-arbitrary and already importable from ambix (artifact_resolution.py imports it lazily today), so the producer adds no JT-60SA constant to nova. The one decision the producer must make that the MAST producer never does is what to do with a non-IDS file in the source directory: create_machine_artifact_manifest inventories every file it is handed, so the OP1 store's receipt.json would otherwise be packaged into the artifact as a member. The producer either excludes it or stages only the .nc files, as the probe did. Nova needs no change for any of this; the alternative of parking the producer in nova/scripts/ beside diiid_machine_artifact.py is available but would put a JT-60SA constant in nova, which §7 rules out.

Negative control: lines that refuse or mis-key a non-MAST machine today

A reading taken from naming alone would say “the machine-artifact code is generic, so JT-60SA works”. Each of these lines falsifies that, and each is what a JT-60SA caller meets on the current route:

  • imas_ambix/gs/artifact_resolution.py:316 — from nova.imas.mast_geometry import publish_refined_artifact: the ambix authoring entry reaches MAST and only MAST, so author_pinned_description for any other machine cannot exist without a code change here.
  • imas_ambix/gs/artifact_resolution.py:288 — if require_pin and semantic_identity != PINNED_SEMANTIC_IDENTITY: a JT-60SA description cannot satisfy the single MAST pin, so resolve_machine_description() refuses it.
  • imas_ambix/gs/machine_identity.py:152 — from nova.catalog.mast_geometry import MachineGeometryRegistry inside default_registry: every resolver that falls back to it (“all four” in §7) answers a JT-60SA question with MAST's registry unless a machine key is added.
  • imas_ambix/gs/artifact_geometry.py:758 — machine: str = "mast": the one silent default on the selection route, which would tag a JT-60SA selection SetupSignature(machine="mast") and collide with MAST's SetupSignature.key.
  • nova/imas/mast_geometry.py:570 — machine="mast" written literally into create_machine_artifact_manifest: the MAST producer cannot produce another machine's artifact, which is why the generic entry must be called directly (as the probe did) and why a producer is needed.

The probe turns four of these into observed refusals rather than read lines: the two TypeErrors above and the two-entry no-machine TypeError/MachineArtifactError in the entry table, all reproducible from probe_output.json. The generic layer is real, and the machine keying is not: both facts are needed to read the route correctly.
