The SELENE reference loader's axis source and the profiles_2d psi binding route

Two design points §7 leaves open are settled here from code and cached data, read-only. Axis: the loader may not pass PSRC's plasma centre to build_geometry_from_arrays as the axis — PSRC's own plasma centre calCCSRc/calCCSZc is a coarse geometric centre, while PSRC carries the magnetic axis directly in calRp0/calZp0; the loader must pass the latter, and no argument on build_geometry_from_arrays rescues a wrongly-sourced origin. psi binding: a signal map cannot bind a file-backed G-EQDSK into equilibrium/time_slice/profiles_2d/psi — signal sources are store arrays read through a registered engine, and a text .geqdsk matches neither format the engine accepts; psi must instead be staged into a store the engine reads and bound with an ordinary rule whose psi_like convention factor performs the COCOS 1 → 17 step. The open question eqdb-reader is overtaken by decision jt60sa-psi-q-source.

Axis: what PSRC's centre is, and which array the loader must pass

The G-EQDSK at /work/projects/imas_gpu/jt60sa/101011.geqdsk, read through imas_ambix/challenge/loader.py load_geqdsk at its declared snapshot (4000 ms, COCOS 1), gives a magnetic axis at rmaxis = 3.274936 m, zmaxis = 0.216996 m on a 129×129 psi grid with 301 boundary points. Its stored psi spans −0.438183506 to +0.959444888 Wb/rad.

The matching PSRC cache for this shot, /work/projects/imas_gpu/jt60sa/101011.zarr, carries only PSRC/Ip and PSRC/Ip_time. PSRC's centre, axis and boundary arrays are not cached for E101011, so the axis comparison cannot be drawn on 101011 itself. This is a real data gap, not an instrument failure: the same read path returns all of those arrays for the populated shot E101154 (below). Nothing here is fetched over ssh to close it.

On the populated shot (101154.zarr) at 4.0 s the PSRC inventory fragment jtmm-psrc-selene-inventory.html assigns calRp0/calZp0 to the magnetic axis (m) and calCCSRc/calCCSZc to the geometric centre (m). The two do not coincide:

The geometric centre is quantised and cannot stand for the axis. Over the full E101154 time series calCCSRc takes only 5 distinct values on a 0.2 m grid ({0, 2.6, 2.8, 3.0, 3.2}) and calCCSZc only 7 values; the axis arrays calRp0 and calZp0 are continuous (5348 and 5539 unique values). A 0.2 m quantisation is far larger than the ~0.11 m offset between the two points and larger than the ~0.000035 m agreement the inventory fragment already measured between calRp0 and the reference axis at 6.0 s on E101154. So PSRC's "plasma centre" is a coarse geometric marker, and PSRC's magnetic axis is the array that carries the axis.

Recommendation. The loader may pass PSRC's centre as the axis to build_geometry_from_arrays only when it passes the magnetic-axis arrays calRp0/calZp0 — never calCCSRc/calCCSZc. The function takes axis_r/axis_z as the origin for the LCFS-radius resample (axis_r[i], axis_z[i] at equilibrium_labels.py:508) and exposes no geometric-versus-magnetic flag: there is no argument that makes a geometric centre behave as an axis, so the choice must be made at the array the loader reads. Pass calRp0/calZp0 with no flag. (On E101011 specifically, PSRC carries no axis array in cache, so the axis must come from the G-EQDSK's rmaxis/zmaxis — the same value the figure overlays.)

psi binding: a signal map cannot bind a file-backed G-EQDSK

A signal map binds a store array, not a file. In imas_alambic/signal_map.py a SignalRule names its source only as source_group/source_array — there is no source-path or source-file field at all. The store is resolved through a registered engine, and the engine accepts exactly two formats. The refusal is explicit in transform_engine.py: 

raise TransformEngineError(
    f"unsupported store format {store_format!r}; available={TRANSFORM_ENGINE_FORMATS}"
)

TRANSFORM_ENGINE_FORMATS is ("zarr", "netcdf"), and the machine-description side repeats the same closed set — _DESCRIPTION_STORE_FORMATS = {"netcdf", "zarr"} in machine_map.py, refused with "description_store_format must be one of ...". A text .geqdsk is neither zarr nor netcdf, so no SignalRule can name it, and no binding node can point equilibrium/time_slice/profiles_2d/psi at the G-EQDSK directly. This is the code line the negative control asked for: the engine refuses a non-store source kind by name, so the answer rests on a quoted refusal rather than on convention.

Route. The G-EQDSK psi must be staged into a store the engine reads, then bound with an ordinary rule — the same route §7 already uses for every other equilibrium signal, adding no second reader of either source. A binding node writes:

filewhat the node writes
a converter module under imas_ambix/reads the shot's G-EQDSK through load_geqdsk and writes the psi grid (and its R/Z coordinates) into a per-shot store group the engine reads
maps/jt-60sa/maps/equilibrium.jsonthe psi SignalRule binding that store array to equilibrium/time_slice/profiles_2d/psi, with transformation="psi_like" and source_cocos=1
teststhe rule's convention factor and the staged-store round-trip

The COCOS 1 → 17 step. The G-EQDSK psi is COCOS 1 (σBp = +1, eBp = 0, per radian), so the binding carries source_cocos=1 and transformation="psi_like". The engine then folds the convention into the rule's static_scale through convention_factor = canonical_factor("psi_like", source_cocos=1) = transform_factor("psi_like", source=1, target=17), which computes to exactly −2π (−6.283185307179586). That factor is the whole COCOS 1 → 17 conversion: psi is multiplied by −2π on the way into profiles_2d/psi. SignalRule.validate requires source_cocos for any non-one_like transformation, so the rule cannot be authored without stating the source convention.

The equilibrium is minted through the engine's writer (write_pulse, per jt60sa-pulse-ids.html §2), which joins the machine description and the signal maps into IDSs. Note that equilibrium is not among pulse_writer.IDS_NAMES = ("pf_active", "pf_passive", "wall", "magnetics", "tf"), so writing profiles_2d requires the writer's IDS set to be extended to include equilibrium — a separate, recorded follow-on rather than something this read-only node changes.

eqdb-reader is overtaken by jt60sa-psi-q-source

Open question data-id="eqdb-reader" (§7) asked for a Python/C entry point to the SELENE equilibrium DB (eqdbms/eqdbget), opened 2026-10-05. Decision jt60sa-psi-q-source (lead, 2026-10-07) takes E101011's G-EQDSK as the one psi/q reference and PSRC for the rest, because the FAME EQDB server dbsvr17p is decommissioned and unreachable. With psi and q sourced from the G-EQDSK, §7's psi binding no longer depends on any EQDB psi/q reader, so yes — eqdb-reader is overtaken: it is moot for this binding route and should be closed against the decision rather than pursued.
