What the site's own documentation says FAME is

The EDDB catalogue itself carries the expansion. eddbreadCatTable() returns a desclist parallel to its catlist; the entry for the FAME category reads verbatim:

'Fast Analyzer for Magnetohydrodynamic Equilibrium (FAME)'

So the site documents FAME as Fast Analyzer for Magnetohydrodynamic Equilibrium. What it computes is fixed by the EQDB reader's own schema (/analysis/src/edas2/v2.2.1/edas_share/eqread_pac/default/Fledd.py NameList, and the Fortran reader /analysis/lib/JT60SAEQDB/eqdbms/eqdbget.f): a Grad–Shafranov equilibrium — poloidal flux PSI on an NSR×NSZ (129×129) RZ grid, separatrix and X-point, axis, current TTCU, and the flux-surface profiles PDS (p′), FDS (FF′), SIV, VLV, QQV (q), PRV and BTV. Its EDDB FAME bank, by contrast, carries 100 scalar summaries (Q95, QAXIS, QEFF, TTCU, RAXIS, RSEP, BETA, …), not a grid.

Candidate routes and the one E101154 read attempted for each

Each route below is a place /home/d240034 (or the code and files it names) holds, reads or points at an equilibrium. For each, one E101154 slice read was attempted from intr26-2; the exact call and its return are quoted.

Route 1 — FAME EQDB record, eqdb=0 (present, unreadable)

The record keyed by shot that carries PSI and QQV. Reader: eqread_pac (/analysis/src/edas2/v2.2.1/edas_share) over the prebuilt /analysis/lib/libFLEDDPIC.so. Endpoints it names: server dbsvr17p (echoFameHost, SERVER_NAME in every .eqdbms) and data root /JT60SA_EQ/FAME3 (echoFameDir). The E101154 attempt: 

tool = FleddTool("/analysis/lib/libFLEDDPIC.so")
tool.GetTimeList(0, 101154)      ->  105 slices   (500 .. 11500 ms; the local index lists)
tool.GetEqData(0, 101154, 500)   ->  IRET = 300   (library printed "eqtyp, code, sshot, ttime = 0 1 101154 500")
tool.GetEqItem("PSI")            ->  shape (0,)    ; RG, ZG, QQV, SIV, TTCU all shape (0,)

The slice data is refused. The index resolves locally, so the slice times list, but the record's fields come back empty: IRET 300 is the transport refusing because dbsvr17p cannot be reached from intr26-2 (see Route 7). This node's declared negative control — "a read of the dbsvr17p route that the locate node found unreachable still returns IRET 300 from intr26-2" — was reproduced above, exactly.

Readable for E101154, but it is a bank of scalars. It supplies neither a psi grid nor a q profile. (The dname must be bare — Q95, not /FAME/Q95 — the prefixed spelling returns irc 1032.)

Route 3 — SELENE's own EQDSK output (writes psi and q per run; no E101154 run)

The writer is /analysis/src/SAselene_v2.0_forPSRC/efitout.f (the EQDSK/G EQDSK emitter), which sets neqdsk = 95 and writes a G-EQDSK: rmaxis, zmaxis, simag, sibry, bcentr, then fpol, pres, ffprim, pprime, then ((psirz(i,j),i=1,nw),j=1,nh) — the psi grid — and (qpsi(i),i=1,nf) — the q profile — followed by the boundary rbbbs/zbbbs. The run tree /analysis/src/SAselene_v2.0_forPSRC/RUN/ holds one stale run only. The E101154 attempt:

Answer: no route reachable from intr26-2 reaches E101154's psi grid and q profile

The only source keyed to E101154 that carries both a psi grid (PSI, 129×129) and a q profile (QQV) is the FAME EQDB record at eqdb=0 — 105 slices on the local index — and it is unreadable from intr26-2 because its server dbsvr17p is unresolvable and /JT60SA_EQ is unmounted (GetEqData returns IRET 300). Every reachable alternative returns something other than the pair:

  • the EDDB FAME bank — readable for E101154, scalars only;
  • the EDDB PSRC (SELENE processed) bank — readable for E101154, no grid or q profile;
  • EQDSK files in /home/d240034 (FBEQU outputs, LOCALDB) — carry psi and q but only for shot 101011.

Best route. None reachable from intr26-2 reaches E101154's psi grid and q profile. The nearest paths, in order, are: (1) the FAME EQDB eqdb=0 record for E101154, which needs dbsvr17p / /JT60SA_EQ/FAME3 mounted or reachable — only the JT-60SA side can grant that; (2) running SELENE/FBEQU for E101154 so efitout.f writes a per-shot G-EQDSK, which computes an equilibrium rather than reading an existing one; (3) the OP1 EQDSK files already on disk for shot 101011, which prove the EQDSK reader (prova/eqdsk.py) yields psi and q but are the wrong shot.
