probe-angle engine: no COCOS digit for a poloidal angle, and the description route supplies it

Node jtmm-probe-angle-engine · date 2026-10-06 · plan jt60sa-machine-map §6

The transform engine gained a pol_angle_like branch in transform_engine._apply_cocos_convention. A directed poloidal-probe angle states an installed sensitive-axis orientation, so no COCOS-digit factor expresses it; the branch calls canonical_factor for no angle binding and takes the rotation sense only from the binding's authored sign_convention. identity keeps the stored angle and negate mirrors it; every other value & mdash; unknown-unvalidated included — is refused with BindingTransformError naming the convention rather than served. The branch precedes the source_cocos is None refusal, so an angle binding needs no declared source convention. In _emit_arrays the generic sign pass is skipped for a pol_angle_like binding, because the branch now owns that negation, so a negate binding negates exactly once on the emit path.

cocos.py retires the directed-angle helper mast_angle_to_canonical: its only caller was its own test, its negation is what a binding's sign_convention negate now expresses, and project_poloidal_field (the forward-operator seam) is untouched. read_geometry_table gained the description route's supplier: when the catalog declares probe_angle_source description, each probe's angle_deg is filled from the emitted magnetics/b_field_pol_probe/poloidal_angle array, converted from the array's declared target unit (the DD leaf is radians, the geometry kernel reports degrees), beside the acquisition-address supplier. A description that emits no such array leaves the probes' absent-angle flag standing; a count mismatch between emitted angles and mapped probes is refused rather than guessed.
