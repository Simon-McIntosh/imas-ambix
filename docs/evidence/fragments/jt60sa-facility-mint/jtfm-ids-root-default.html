A development IDS root through the bundle ids_root role

Node jtfm-ids-root-default · date 2026-10-07 · plan jt60sa-facility-mint §12 · base f3b13ba1

Change. resolve_settings now also falls back, past the IMAS_ALAMBIC_HOME default, to a store role a reachable bundle declares. The IDS root resolves in the order --out, IMAS_ALAMBIC_IDS_ROOT, IMAS_ALAMBIC_HOME/ids, the bundle's ids_root role, otherwise unset — HOME stays above the bundle so the facility launcher always wins. The bundle lookup is the helper the cache already used, renamed _store_root_from_bundle(role, kind, maps), so the source reads bundle ids_root role in the same grammar as bundle eddb_cache role. imas_ambix/data/bundle.py declares the role from paths.JT60SA_IDS_DIR (its one owner), and scripts/figures_jt60sa_signals.py drops its interim settings.ids_root.value or paths.JT60SA_IDS_DIR fallback, asking resolve_settings through require_setting alone. bundle_for_machine's unknown-machine refusal now names the map-path variable alongside the machine, read from settings.ENV_MAP_PATH through the function-local import machine_map.py already carried, so the name keeps one owner.

Gates. With no IMAS_ALAMBIC_* variable set, uv run imas-alambic config at the base (git archive of f3b13ba1, the main checkout's module) reports ids_root: (unset); the same command at the head, with this worktree's packages/imas-alambic/src and the repository root on PYTHONPATH, reports ids_root: /work/projects/imas_gpu/jt60sa/ids [bundle ids_root role] — the value the done-when names. packages/imas-alambic/tests is 40 passed / 0 failed at the head against 33 passed / 0 failed for the same command against the base tree, so the change adds no failures (the seven-test difference is the new IDS-root-order and refusal pins). uv run --no-sync ruff check imas_ambix tests packages exits 0. test_settings.py pins each step with synthetic bundles: a flag beats the variable, the variable beats HOME, HOME beats the bundle role, the bundle role beats unset, and no declared role leaves it unset. test_bundle_discovery.py pins the refusal through load_packaged_machine_map("jt-60sa") against a valid map-path bundle that does not carry the machine, asserting both jt-60sa and IMAS_ALAMBIC_MAP_PATH appear.
