one command installs the engine into the shared IMASDB folder

Node jtfm-imasdb-install · date 2026-10-07 · plan jt60sa-facility-mint §5 · commit cf788ff5

packages/imas-alambic/install/imasdb.sh <IMASDB> installs imas-alambic into the shared folder in one command. It builds the engine and COCOS wheels here with uv build (imas_alambic-0.1.dev5957+gcf788ff5b, nova_cocos-0.11.0.post10072+g91c03e49b), pulls the private bundle from ghcr.io/simon-mcintosh/imas-alambic-jt60sa:2026.10.07 (digest sha256:6af476ebe1d560e290b90aeef83113f25a4b2982e24548542c556f7ebf7d3f90) with oras and the gh token, relays the wheels and the bundle to jt-60sa over ssh, and runs every remote command under nice -n 19. No GitHub credential is placed on the server.

On intr26-2 the remote half installs the engine as a uv tool on a uv-managed CPython 3.12 (IMASDB/tools/python/cpython-3.12.12-linux-x86_64-gnu), writes IMASDB/bin/imas-alambic as a launcher that clears PYTHONPATH and points the engine at the folder, places the bundle under the version directory with maps/current pointing at it, opens the tree to other users read-only, checks it, and only then removes the older ~/imas-alambic. The layout names are read back from imas-alambic config (layout: maps=maps/current ids=ids current=current), so the shape of the folder is owned by the engine's settings rather than by a second copy in the installer.

Measure, all on intr26-2 and all captured to the run log: /home/SharedFolder/d240044 is mode 1755; every directory under IMASDB grants others r-x, every file grants others r--, and no real file or directory grants others write; uv pip show reports imas-alambic installed, not editable, from a wheel under IMASDB/tools/imas-alambic; uv pip check reports all 24 packages compatible; IMASDB/bin/imas-alambic --version exits 0 both with PYTHONPATH naming the python/3.12 module site-packages and with it unset; and with no IMAS_ALAMBIC_* variable set, config reports maps: IMASDB/maps/current [IMAS_ALAMBIC_HOME/maps/current], ids_root: IMASDB/ids [IMAS_ALAMBIC_HOME/ids] and machine: jt-60sa [inferred from the single reachable bundle]. The old install's top level was listed (bundles compare_maps.py env.sh remote_finish.sh remote_setup.sh src .venv), removed, and ls shows it gone.

Three things the engine forced, recorded so the next reader is not surprised. imas-alambic config resolves the machine and the writer's cache through the map search path and raises MachineMapError on a search-path entry that carries no bundle.json, so it raised before the layout existed. The installer now seeds the search path by placing the staged bundle at the engine's default map path, reads the names the engine reports, then moves the bundle to its version directory; the seed names one path that the installer would otherwise take from config, and is the one place the layout is spelled. A follow-up on the engine — tolerate a search-path entry without a bundle — would let the installer drop the seed entirely. Second, find IMASDB -perm -o+w prints maps/current: a symlink's own mode is always 0777 and carries no permissions, so the no-write check is taken over real files and directories. Third, files are set to others r-- exactly, so another facility user runs the launcher through the group bits, which uv sets, not through the others bits. An earlier probe had also left a python3.12 shim in the account home pointing at a temporary interpreter; it was repointed at the account's own uv-managed Python.
