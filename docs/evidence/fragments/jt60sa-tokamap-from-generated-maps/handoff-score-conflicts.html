Count conflicting rows in the hand-off score

The score could not previously tell a genuine disagreement from a target the hand-built maps simply do not cover: both read as an imported value rule that is not agreeing. score_handoff now returns a conflicting count on every IDS row, every structure row and the TOTAL, and a conflicts list on each row naming the two arrays.

Definition. A conflict is an imported value rule (draft or pending) whose target_path and target_index carry a hand-built rule that it does not agree with. Agreement is the existing _agrees predicate — same target path and index, same source group and source array, and the same signed (or, when the sign is unscored, unsigned) scale. A row on a target with no hand-built rule is not a conflict, and an agreeing row is not a conflict. Each conflict entry carries target_path, target_index, imported_source_array and hand_built_source_arrays.

This is the case imas-codex flagged: MMSYS curUFPdisr and curLFPdisr are disruption-induced currents sharing the UFP and LFP identifiers, so one may bind to pf_active/coil/current/data as if it were the coil current. Bound to the same target and index by a different source array, it now reads as a conflict against the hand-built rule rather than as a silent non-agreement.

Demonstration

In tests/data/test_handoff_score.py, a hand-built rule for magnetics/b_field_pol_probe/field/data whose source array is other against an imported row bound by magPbTC11 yields conflicting == 1 with the entry {target_path: magnetics/b_field_pol_probe/field/data, imported_source_array: magPbTC11, hand_built_source_arrays: ["other"]}. A row whose target carries no hand-built rule yields conflicting == 0, and an agreeing row yields conflicting == 0.

The printed score-handoff table carries a conflicting column; tests/test_maps_cli.py shows the header and the magnetics row reading 1 on the same fixture.
