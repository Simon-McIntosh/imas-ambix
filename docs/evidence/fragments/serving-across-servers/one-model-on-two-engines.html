A session key is held to one engine inside a pool. A request is keyed by x-reckon-session, else x-reckon-run-id, else the caller's host. RouterApp._select_engine places a key with no pin, follows the pin on later requests, and lets the pin go only on a pause, on the engine leaving the catalog, on a queue wait past the operator's bound, or on the key going idle past its 180-second horizon. Fifty consecutive requests under one session header all reach the same engine (test_fifty_requests_from_one_session_all_land_on_one_engine), measured against two engines bound to distinct loopback aliases so the pair is a pool rather than one server's rotation.

Placement counts pins per unit of gate width. A new key goes to the engine carrying the fewest pinned keys divided by its gate width, using an exact rational so two engines are never separated by floating-point rounding; a paused gate is skipped, and a tie falls back to the ranking that already decides a rotation — wider engine, then newer. Sixteen sessions against gate widths 4 and 12 land 4 and 12, exactly the 1:3 the widths imply (test_sixteen_sessions_split_by_the_gate_widths_they_land_on).

The three departures are each recorded. A request row now carries routing: placed when its key had no pin, pinned when it followed one, failed-over when the pin no longer held, and null when no engine was chosen. Pausing the pinned engine sends that session's next request to the peer with the row reading failed-over and naming the peer's upstream, and the request after that returns to pinned at the new engine (test_pausing_the_pinned_engine_fails_the_session_over). A key aged past the horizon against the same pause is placed instead, which is what separates an expiry from a failover (test_a_pin_expires_after_its_idle_horizon).

The rotation overlap takes new keys on the incoming engine. Two engines of one model on one server are a rotation: the wider one is current and the other drains. With the old engine at gate width 4 and the new one at 12, a session pinned to the old engine before the cutover stays there, while every fresh session lands on the new engine (test_rotation_overlap_takes_new_keys_on_the_new_engine_and_keeps_old_pins).

A row's routing is read by watch tools, so it must state what the request did rather than what the routing code nearly did. Three cases previously recorded the wrong thing.

An engine appearing is still a placement. Readiness polls until the catalog resolves, and placement ran inside that closure with its reason discarded — so a request admitted in the interval where the engine first appears wrote routing: null over a key it had in fact just been placed on. The reason now leaves the closure to the caller that writes the row (test_a_request_held_for_its_engine_records_why_it_was_placed).

A move to the same engine is not a failover. When every candidate gate is paused, the placement fallback is "unpaused or live", which can return the engine the key is already pinned to. That was recorded as failed-over and re-pinned the key at the current time — an expiry reset and a failover that did not happen, from one branch. The placement now compares the chosen engine against the pin: an unchanged engine keeps the row at pinned and refreshes the idle clock without moving the pin (test_a_placement_that_stays_on_the_pinned_engine_is_recorded_as_pinned). The branch is asserted directly on _select_engine, because a paused gate holds rather than refusing, so the same-engine landing cannot be driven end-to-end without hanging the request.

The wait is the whole queue, and the engine named is the one that admitted. A request that timed out at its pinned engine's gate and then waited at the alternate's recorded only the second wait — the placement's own queue cost vanished from the row — and named no engine, leaving gate_engine populated on refusals only. The row now carries the sum across both gates and the engine whose gate admitted the request (test_a_failover_records_the_wait_at_both_gates_and_the_admitting_engine). The gate wait at the pinned engine is bounded at 0.4 s in that test, so the pair sums to at least 0.35 s where the second wait alone is microseconds.

Two paths that had no test now do. A pin whose engine drops out of the catalog fails over on the next request rather than holding a reference to an engine that is gone, and the row after that one is back to pinned at the new engine (test_a_pin_whose_engine_leaves_the_catalog_fails_over). The key itself falls back from x-reckon-session to x-reckon-run-id to the caller's host: three requests carrying one of each key form land on one engine, and the host-keyed pair that follows is recorded pinned rather than placed (test_the_key_falls_back_from_the_session_to_the_run_to_the_caller_host).

The wait bound defaults to 30 s and is set in the gate control file. DEFAULT_FAILOVER_WAIT_SECONDS is 30.0 and a per-engine failover_wait_seconds entry overrides it, validated as a finite non-negative number at read time so a malformed value stops the read rather than silently pulling an engine's sessions (test_the_failover_bound_defaults_to_thirty_seconds_and_the_file_sets_it). The bound is applied as a cap on the pinned engine's gate wait, and only when an alternate engine exists, so a one-engine lane keeps the gate's own 300-second wait rather than failing over to nowhere.

Negative control. With the bound at 0 s, a pinned session whose engine is full — one slot, held by another admitted request — moves to the peer and its row reads failed-over; with no bound set the same session waits at its own engine and keeps pinned.
