A site declares its servers once, and the document lists each one

Work at 12bf8d57, node servers-declared-once. A site could describe exactly one GPU host: every partition, account and reservation came from flat fields, so a second host could not be expressed at all, and the endpoint document had no way to say which host an engine ran on.

Declarations. SiteConfig gains a servers list (SiteServerConfig): name, host, SLURM partition, account and reservation, accelerator family and card count, the per-card power cap, and the reservation groups the job table labels. A site that declares none resolves to a single entry built from its flat fields (SiteConfig.declared_servers), so nothing an existing configuration does changes. AMBIX_AGENT_SERVERS carries the list as JSON for a site configured by environment.

Placement. imas-ambix agent serve <profile> --server <name> resolves the name through SiteConfig.resolve_server and generates the script for that server's partition, account and reservation. A name no declaration matches raises before any script is generated, naming the servers the site does declare, because the alternative is a job requesting a partition, account and reservation nobody configured. The generated script records the placement (registry write --server <name>) only when the site declares servers; an unconfigured site writes no such flag, which is what keeps its script byte-identical. The accelerator family a serve registers follows its placement rather than a module constant.

A replacement keeps the placement it is replacing. restart and agent key --rotate regenerate a serve's script, and both now resolve the server from the running serve's registration — the server name it recorded, else the declared server whose host it ran on — and pass it through. Generating from the site instead would resolve the first server's partition, account and reservation for a serve running on the second, moving the replacement off the node it was running on; on a site whose servers carry their own reservations, the replacement would not be admitted where the job it replaces was. The placement is read before the old job is cancelled. A registration that names no server the site still declares falls back to its recorded host, so renaming a server does not move a serve.

The document. registry.build_endpoint_document — the document's existing owner, so the grouping cannot disagree with the engines it groups — now returns the endpoints plus a servers array, and the caller passes the site's declared servers into it rather than the registry reading site configuration itself. endpoints.json carries the array beside endpoints and routing_origins.

Each declared server is a row, engines or none. The array is the site's declaration, not a summary of what is running: every declared server appears with its name, host, accelerator family and card count as declared, plus the power cap and reservation groups, and an engines list that is empty when nothing runs there. A reader that renders the site's servers therefore shows an idle server as idle instead of omitting it, which reads the same as a server nobody declared. Running engines are grouped under the server their registration named, and an engine whose registration names no declared server falls under an entry named by its host, so nothing is dropped for want of a declaration.

The card count and the accelerator family are the node's, not the serve's, and are published only where the site declares them. A serve may take fewer cards than its node has, so deriving the count from an eight-card engine would publish a four-card node wherever a four-card serve ran; and a family filled in from a declaration default states, as a property of a server, a fact nobody wrote down. Nothing an engine reports is a statement about its node and no unset field is, so no declaration means null: an unconfigured site's single entry declares neither, its document entry carries accelerator_count: null and accelerator_family: null, and the node's real card count comes from the hardware probe. A server the site does not declare at all is in the same position, so its entry carries null for both as well. Each engine's own values stay on its endpoint, where they belong.

A serve still records the family of the cards it runs on, because routing reads topology from the registration and the engine's catalogue middleware requires a label. That value is the placement's family where the site declares one, and otherwise the launch's own statement of this site's hardware (slurm._SITE_ENGINE_ACCELERATOR_FAMILY) — never the declaration class default, which would silently answer for a site that declares nothing and would keep answering after a card change. A second server of another family therefore registers under its own family, and an unconfigured site's script is unchanged byte for byte.

The deduplication key moves from the model id to the engine id (<host short name>:<port>). Two engines serving one model are two engines and now both appear in endpoints and in their server's engine list, so a second serve of a release is capacity instead of a replacement. A restarted job keeps its predecessor's engine and still supersedes it, which is what the model-id key was there to do. A host short name drops the cluster component only when a node name remains after it, so 98dci4-gpu-0003 is gpu-0003 while gpu-0003 is itself.

Two tests in the gate files were stale against landings that preceded this work (the publish fixtures supplied scheduler rows with no jobid and one with two fields where the parser reads seven or eight; a registry test gave two live registrations different ports while asserting the shared-port behaviour its own docstring describes). They are repaired here rather than triaged, since the gate measures this change and the files are in this node's scope.
