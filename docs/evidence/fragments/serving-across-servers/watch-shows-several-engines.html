The watch view carries one entry per engine at every level it reports, and a lane of one engine renders exactly as it did before the engine dimension existed.

What the view now says

  • A router line above the bands — the router's address, when the reading was taken, and how much the document spans: 3 servers · 3 engines · 2 models. A reader needs it before attributing any row below to one engine.
  • An engines table, one row per engine, naming the model it serves and the engine id it answers on, with its running count, router queue, output rate, per-stream rate, time to first token, KV pool and available percentage. The model and the engine id are separate columns: in one column the two DeepSeek engines truncated to the same prefix and became indistinguishable.
  • An engine column in the account detail, carrying the engine that took the engine-dominant share of each project's or session's held time.
  • One history line per engine, on the same two strips as the total — in flight against the gate's width, and the median gate wait — so a reader can see which engine is filling rather than only that the lane is.
  • One outcomes line per engine, because a lane in which one engine fails everything it accepts and another completes everything reads as a healthy lane in the total alone.
  • The ledger grouped by model, and --engine choosing whose bands are drawn. With several engines one engine's three bands are drawn — the busiest unless one is named — because three bands per engine do not fit a terminal; the table above carries every engine's figures.

The document

  • callers.held_by_engine splits each account, project and session row's held time by engine; callers.engines lists every bucket the window holds.
  • history.engines carries one bin series per engine, and outcomes.by_engine counts each request's ending under the engine it ended on.
  • live_panel joins the pool document's engines array to the per-engine live entries by engine identity -- the host narrows the pool to one node and the served model separates the engines on it, a pair neither separates being left unjoined rather than paired by position -- keeps an engine that appears on only one side, and publishes a top-level engines array only when there is more than one. Every pool document the lane's lanes index names is read, so a second model served by a single engine reaches the view as well.
  • Every one of those keys is absent for a single-engine document. The one-engine document is byte-identical to the base revision's agent watch --json --live output, and the one-engine render is byte-identical to its committed golden.

Why the split can be trusted

Every request row lands in exactly one bucket: the engine its upstream names, or a (router) bucket when the router answered it itself after its gate wait ran out. A request given to an engine it never reached would make the split disagree with the total it is a split of, so the reconciliation is asserted rather than assumed:

abs(sum(row["held_by_engine"].values()) - float(row["held"])) < 0.01

The declared negative control — attribute every request to the first per-engine sum test fails at that assertion: the account's buckets sum to 0.6 s against a held total of 0.3 s. The log is kept with the run record as negative-control.log.
