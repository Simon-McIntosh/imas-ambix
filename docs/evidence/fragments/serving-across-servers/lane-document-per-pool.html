RouterApp._publish_lane now composes one lane document per pool from each engine's own reading, and is the only writer of any lane document. The default pool's document is lane.json itself, carrying a lanes index that maps each model to its own file; every other pool writes lanes/<model id>.json. The default pool is never written a second time under lanes/, so no two files carry the same fields and the index maps the default model to lane.json instead of a duplicate.

  • One engine. The document is that engine's own reading, every field keeping its own meaning. The golden test drives the composer through a fixture metrics endpoint and compares the result with the one-engine writer's output for the same reading: the key sets differ by exactly lanes plus the router's gate block (router_generation_gate, admission, engine_headroom, availability_percent), which the base revision also merged into lane.json after writing the reading, and no key it published is missing.
  • Several engines. Counts and capacities sum — running, waiting, pool tokens, the concurrent-request ceiling, headroom, the gate's width, and its in-flight, waiting and worker-slot counts. The aggregate token rate sums. Per-request figures (mean working context, rate per run) are weighted by each engine's running count, so a busy engine's traffic counts for more than an idle one's, and an engines array carries each engine's own reading, gate and engine id. A pool whose engines disagree on whether they can size publishes do-not-size and its withheld estimate rather than a figure only some engines support.
  • An unreadable engine. A pool whose engines all failed to answer has its document replaced by the explicit unavailable state, naming the reason and the model, so a stopped engine cannot leave a plausible reading ageing into a lie while its neighbour's pool stays a measurement.

A test walks imas_ambix/ and finds no call to lane.write_lane_document, lane.write_unavailable_document or lane.write_document outside the composer, and asserts that every such call in the router sits inside RouterApp._publish_lane — so a guard covering only one of the two functions that can write lane.json cannot pass while the other keeps overwriting it.
