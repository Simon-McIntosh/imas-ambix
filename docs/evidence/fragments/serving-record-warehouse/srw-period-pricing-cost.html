A period's price walk reads the index once per listing, not once per cut

Node srw-period-pricing-cost · date 2026-10-15 · worktree imas-ambix-0405601943d2/4fd309f5-d84d-4f4d-97a9-75ac19ce3494/srw-period-pricing-cost

The profile named the repeated work, and it was not the price history. One watch_document render at a fixed now of 1792051200.0 (2026-10-15T08:00:00Z) against the live index spent 55.2 s of 221.3 s inside _price_walk, which re-totalled each period's prompt and generation counters through _span over exactly the window period_row had just totalled: 8 of the render's 20 partitioned_total calls. The price-history reads the section suspected are not measurable here — the live slug carries one listing and an empty schedule, so every period is one segment and the history is read four times per render. provider_prices.rate_in_force does not appear in the profile at all.

_price_walk now walks the cuts the section's rule defines and prices them one stretch at a time: consecutive cuts whose listing in force is the same are totalled together and priced once, and a period no listing cuts is priced on the totals its caller already holds. The rate is fixed between two listings, so a stretch's figure is unchanged — and price_segments still reports the cuts the rule makes, which is what the schedule moves.

Correction: the first cut of this change mis-priced one reachable configuration

The first version of the grouping keyed on which listing a cut sat under, on the assumption that the rate is fixed between two listings. The assumption fails wherever the listing yields no median: the walk then borrows the headline, and a row priced by time of day moves its headline between one hour and the next. A day whose only listing is below the precision floor, with no headline in the history, was therefore priced entirely at its first hour's rate — 33.135 for a day that costs 78.255 rendered hour by hour. The live table carries hour-varying schedules for deepseek/deepseek-v4-pro-0813, tencent/hy4-preview and tencent/hy3, so the configuration is reachable even though the slug this node measured has an empty schedule and was unaffected.

The claim above that no figure changes held only for the configuration measured; it was not general, and this paragraph is the correction.

The grouping now follows the selected rate itself. Hours that select different rates stay one read each, and hours that select the same rate are still totalled together — so the read count the change won is kept wherever the rate really is fixed, and an hour is never priced at another hour's rate. All four costs and all four token totals are byte-identical to the pre-repair render at the same fixed now.
