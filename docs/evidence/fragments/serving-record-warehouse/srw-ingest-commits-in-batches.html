The ingest commits in bounded batches, not once per row

Node srw-ingest-commits-in-batches · date 2026-10-02 · worktree imas-ambix-0405601943d2/0c4316b2-553f-4a0a-ae02-c42d88de747c/srw-ingest-commits-in-batches

TelemetryIndex.ingest committed once per sample: _insert opened a transaction around every row, so a 1000-row source paid SQLite's journal and fsync cost a thousand times. The index is built by scanning receipts on shared storage, where that cost dominates, and it is a rebuildable derivation of the record, so the commit boundary is free to move.

What changed

  • imas_ambix/agent/telemetry_index.py: _insert no longer opens a transaction. ingest accumulates up to DEFAULT_BATCH_ROWS (1000) lines and then commits them together with the source row that advances its offset, size, modification time and prefix digest to the end of the batch's last line. The digest is extended incrementally from the region already consumed, so a batched pass records the same byte-region identity an unbatched one does. ingest takes batch_rows so tests can lower the boundary; an uncommitted batch is rolled back when the pass raises, so no half-written state survives and the next pass resumes at the last committed batch.

The instrument first: the commit count is read from the connection's own set_trace_callback, so it counts the COMMIT statements the store issued rather than the source's intent; a 1000-row source at batch_rows=250 issues 4 commits, against the bound of 6. The resume test makes _insert raise on its 501st call, so the pass dies inside the third batch: the source offset is asserted equal to the end of the second batch's last line, and the second pass is asserted to insert exactly the remaining 500 rows with zero duplicates — both halves, because a resume that re-read the whole file would also end at 1000 samples while counting 500 duplicates. The digest test asserts the batched pass's prefix_sha equals an unbatched pass's and the whole file's own sha256.
