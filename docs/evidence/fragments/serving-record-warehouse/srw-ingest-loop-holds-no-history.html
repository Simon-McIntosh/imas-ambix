The scheduled ingest loop now runs forever without accumulating a report per tick, and its tests observe the hand-off a tick makes rather than the state the index happens to hold.

The defect, reproduced before it was repaired. run() appended every TickReport to one list and kept it for the life of the loop, so the shape a standing service needs -- iterations=None, run until the process ends -- grew without bound. Driven 1000 ticks through an injected sleep and counting the reports still strongly reachable from the loop, the unfixed code kept 1000 alive. With the repair it keeps 1 (the latest), and the test asserts the peak live count is at most 1 over the whole run. The count is taken inside the loop at each sleep, not after it returns, because a traceback released after the loop would free an unbounded list and report zero either way -- an instrument that cannot see the defect it exists to catch.

Zero iterations performs no tick. run(iterations=0) returns an empty list before entering the loop, so its TelemetryIndex reports sample_count() == 0 even though the directory holds a row to ingest, and the injected sleep is never called. A vacuous version would have passed on an empty directory; this one does not.

The reader-side change is named as separate work that has not landed.
