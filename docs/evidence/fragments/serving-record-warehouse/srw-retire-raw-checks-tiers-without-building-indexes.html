The retention tier check totals tiers from their rows, without an index

Node srw-retire-raw-checks-tiers-without-building-indexes · date 2026-10-02 · worktree imas-ambix-0405601943d2/0c4316b2-553f-4a0a-ae02-c42d88de747c/srw-retire-raw-checks-tiers-without-building-indexes

compare_tiers judged a raw receipt against its compactions by building a TelemetryIndex for each of the three tiers and ingesting the files into it, then asking each index for a partitioned total per UTC hour. The index reads and digests the whole file to build a local SQLite store, which is the wrong instrument for a comparison that only needs the rows in front of it: a raw receipt grows about 8.7 MB a day and never rolls. This node reads the rows directly, buckets them by UTC hour, and reproduces the same partitioned-total arithmetic — one run per two-serve restart, a compacted row's carried opening as the base where a run begins inside the window — so the verdicts are unchanged and no index is built.

What changed

  • imas_ambix/agent/telemetry_retention.py: compare_tiers no longer builds a TelemetryIndex. New helpers read a tier's rows (_read_tier_rows), extract a dotted counter (_counter_value) and a compacted row's carried opening (_counter_opening), partition the same run predicate the compactor uses (_counter_runs), and total a run over a window (_run_window_total). A counter absent from every row of a tier in an hour totals None, not 0.0; a tier holding a value where raw holds none is a disagreement.
  • tests/test_telemetry_retention.py: one test asserting the absent-versus-zero rule, and one asserting the check over a 20,000-row synthetic raw file and its compactions completes in under 10 s.
