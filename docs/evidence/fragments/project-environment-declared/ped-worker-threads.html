The negative control moves _resolve_torch() ahead of pin_thread_pools() in the cap; the test that records os.environ at the moment torch is resolved then sees the three variables unset and fails. A pin-last ordering is the defect this cap exists to prevent, so that mutation is the load-bearing one. threadpool_limits is scoped to the blas API in the cap: capping the openmp API caps the same runtime torch reports, which would satisfy the torch assertion without the explicit torch call.
