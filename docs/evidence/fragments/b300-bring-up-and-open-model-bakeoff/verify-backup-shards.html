Backup checkpoints verified shard-for-shard against their pinned revisions

Both backup checkpoints downloaded for the bake-off were hashed in full and compared, file by file, against the Hugging Face repository listing at the revision each profile pins. Every one of the 274 files the two listings name is present, and every one of the 235 LFS files matches its listing entry in both size and SHA-256. Nothing is absent, nothing is short, and no hash disagrees. Nothing was deleted or modified: the run only reads the store.

  • What "every shard" covers. The listing at a revision names 119 files for Kimi K3 and 155 for the MOPD checkpoint, including non-weight files (config.json, tokenizer data, README.md, .gitattributes). All 274 are checked. The 39 files that are plain git blobs carry no SHA-256 in the listing, so their check is size only — and those sizes match too. The 235 LFS files carry an lfs.oid, which is the SHA-256 of the file content, and each was hashed in full and compared against it.
  • Bytes hashed. 2,134,488,498,219 bytes (1.94 TiB) read and hashed at 2.92 GB/s across ten processes in 730 s, on the fleet compute node 98dci4-clu-2068 (job 1291586), never on a login node. The hashing is sha256sum-equivalent streaming SHA-256 over each file; no file was written to.
  • The comparison can fail. A scratch copy of one small shard (model-00095-of-000096.safetensors, 92,289,328 bytes) run through the same code path reads state=ok with SHA-256 01d41139abb8cf3b5288a97318cc4ab92676671b4eb141031cd80d7c3ced6122; the same copy with its last byte flipped reads state=sha_mismatch, SHA-256 f8bd06d01dfd94091df88b1ea17eb3dc8217f617a0a8ce7099986f48372264a9, at the same size — so the check reports a one-byte change in a 92 MB file as a mismatch. The control runs as model-store-audit.py control-shards, so it is re-runnable rather than a transcript (CONTROL PASS).
  • The hashes are the provenance. Neither checkpoint directory carries a Hugging Face hub ref to read a commit from, so the pin in the profile is the only declared revision. That every LFS file's content hashes to the lfs.oid the listing at that revision gives is stronger evidence of the revision than a stored ref would be: it is a content match against the pinned commit's own bytes, not a record left by the downloader.
  • On-disk volumes agree with the catalogue, with one exception. Kimi K3's listing totals 1,560,998,988,078 bytes (1.42 TiB), matching the profile's size_gb = 1454. The MOPD checkpoint's listing totals 573,489,510,141 bytes (534.1 GiB) against size_gb = 527 in mimo-v2-6-pro.toml — a 1.3 % difference that is a catalogue figure rather than a download defect, since every file matches its listing exactly.

The comparison is the shards phase of docs/evidence/fragments/b300-bring-up-and-open-model-bakeoff/model-store-audit.py, an extension of the store audit that previously compared only the first shard's hash and every shard's size. The gate log is verify-backup-shards.log, which carries the command, the per-checkpoint summary and the control.
