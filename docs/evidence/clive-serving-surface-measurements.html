§1 — Scope and method

Everything below was measured on 2026-09-01 against live services, a live scheduler, and the shipped harness binary. Where a claim could not be measured it is marked as such rather than asserted. Two facts recorded here contradicted the reasoning they were gathered to support, and both changed a decision: the GPU node turned out to be a single-node partition, which retired the case for relocating the origin, and a translating proxy turned out to be unnecessary because every leg already speaks the same protocol.

The embedding service on the other GPU node needs no credential and answered every path: health and info returned 200, and a single-text request returned a normalised 256-dimensional vector. Reported state at the time: Qwen3-Embedding-0.6B on a Tesla P100, native dimension 1024 reduced to 256 on output, 25,164 requests served at a mean 125 ms.

§3 — The engine's Anthropic surface is complete

This is the measurement that removed a translation layer from the design. The engine's own path list contains /v1/messages, /v1/messages/count_tokens, /v1/models, /v1/chat/completions and its render variants. Exercised rather than listed:

ProbeResult
/v1/messages, non-streaming200
/v1/messages, stream: true200; correct SSE — message_start, then content_block_start of type thinking, then thinking_delta events
/v1/messages with a tool definition200
/v1/messages/count_tokens200

Because a hosted Anthropic endpoint is the same protocol, no leg in the intended topology needs its format converted. A translating proxy would convert to a different dialect and back, and that round trip is where thinking blocks, tool-use identifiers and cache directives are lost. The prior failure of exactly this kind is on record: the proxy's local route emitted x-api-key with no Authorization header while the engine accepts only Bearer, so a correct credential returned 401 on every request — measured as Bearer 200, x-api-key 401, no header 401.

§4 — What the serve log does and does not contain

Prompts do not reach the operator's job log. Two independent confirmations: the engine build defaults request logging to false, with a separate output-logging flag also defaulted off and neither passed by the generated batch script; and a search of the 2.7 MB live log for request-body and prompt markers returned zero hits.

What the log does contain is per-consumer access metadata — client address, path, status, timestamp:

CountRequestStatus
403POST /v1/messages?beta=true200

Caveat worth keeping: request logging being off by default is not the same as payload being structurally unable to appear, since an engine traceback can carry fragments. Separately, prefix caching is enabled, so concurrent consumers share a key-value cache — not a logging matter, but shared state between users.

Naming: sinfo -p betelgeuse returns exactly one node, which is why the serve host does not move between relaunches and why the origin was locked there. There are six login nodes on one subnet; the cluster's single published login name resolves to a different subnet with no reverse record, so it is an entry point rather than a host a service can bind. User services persist across logout — lingering is enabled — and three already run on one login node, including a proxy bound to all interfaces, so the pattern for a pinned host service is established rather than new.

§6 — Harness model mechanisms

Alias resolution is per-slot. Two alias slots were pointed at the local release and one at a deliberately invalid identifier, then each alias was requested in a headless run against the live endpoint:

Alias requestedErrorModel used
sonnetnodeepseek-v4-flash
fablenodeepseek-v4-flash
opusyesnone — the invalid mapping

The failing slot is the load-bearing observation: it shows each alias resolves through its own variable rather than a shared default, so aliases can carry different models. Since delegated workers are requested by alias, this is the mechanism by which a session sends bulk work to a local engine while keeping a frontier model for adjudication.

An arbitrary local identifier is accepted directly. A headless run selecting the local release by name completed without error and reported a context window of 524288, the local release as the canonical model, and an unknown cost basis. It emits an unrecognised-model telemetry line but is not blocked.

Curated picker rows are a separate mechanism. Read from the shipped binary: a settings key takes an ordered list of rows, each carrying its own model identifier, label and description, plus a boolean that replaces the built-in lineup instead of appending to it. When that boolean is set, only a default row and the supplied rows are shown and the built-in lineup, gateway-discovered models and the single custom-model variable are all hidden. It is honoured from managed settings, from an explicit settings file and from user settings, but not from a project checkout, and the highest-precedence source defining it wins outright with no merging. Row eligibility passes an unrecognised identifier straight through, so local identifiers qualify. Each alias slot and the custom option additionally accept a supported-capabilities declaration, none of which the launcher currently sets.

Two honest limits. The row semantics were read out of the binary rather than from published documentation. And while a settings file carrying curated rows was accepted without error, a headless run cannot display a picker, so the rows were not observed rendering — that confirmation is a done-when item, not a result.

One nearby find, recorded so it is not mistaken for a general restriction: a telemetry path names suppression of curated rows under a foreign base URL, but the function carrying it is gated to a single editor entry point and concerns showing unavailable rows, not curation generally.

§8 — Capacity state at the time of writing

Both GLM checkpoints completed downloading: the INT4 requant at 321 GiB over 248 files, and the vendor FP8 release at 704 GiB over 149 files. The relaunched DeepSeek serve holds 2 cards and 8 cores, sized by probing the scheduler with a no-op allocation at 6, 8, 10 and 12 cores — all of which would have started immediately — rather than by scaling the profile default, which would have taken 15. That leaves 7 of the 30 reserved cores free alongside a co-running job holding 15.

The core constraint is the one that binds: the node carries two overlapping 30-core reservations, and a serve sized at the proportional default has previously left a training job pending on cores while the GPUs it wanted were idle.
