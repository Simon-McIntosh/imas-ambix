§1 — Target boundary

Nova becomes the sole production owner of equilibrium reconstruction, the physics spine, plasma transport, passive structures and circuits, machine-description and IMAS mechanics, and CPU/GPU execution of those capabilities. Ambix owns corpus selection, label orchestration, label-store policy, ML training and evaluation, and thin adapters that call Nova. Existing Ambix physics remains only as a frozen comparison oracle until parity evidence allows deletion.

§2 — Work packages

  1. Dependency and adapter: add a pinned Nova dependency and an imas_ambix.physics compatibility layer whose public calls are labeler-oriented, not a second physics API.
  2. Consumer rewiring: route equilibrium, topology, passive-circuit, screening-circuit, current-diffusion, machine-description and IMAS calls through Nova. Preserve Ambix dataset identities, batching, retry and label-store semantics.
  3. GPU label path: move the H200 JAX kernels and rollout substrate into Nova. Ambix submits and monitors batches, while Nova selects CPU/GPU backends and returns stable standard-name-keyed results.
  4. Parity and deletion: compare old Ambix and Nova paths on frozen shots, topology classes and transient windows. Delete donor implementations only after API, numerical, performance and provenance gates pass.

§3 — Research and evidence gates

Every work package starts with a research document that records source code, scientific references, data cohorts, numerical conventions and acceptance thresholds. Every landing produces a separate evidence document linked back to this plan and to the relevant Nova source plan. Evidence includes commit SHAs, environment and dependency lock, test commands, machine/shot cohorts, numerical tolerances, benchmark artifacts and negative results. Neither research nor evidence carries an implementation percentage.

  • G1 API: Ambix imports Nova from a pinned package and no longer imports migrated donor modules directly.
  • G2 science: frozen CPU parity holds for axis, LCFS, profiles, topology, flux/current ledgers, transport state and passive-current trajectories.
  • G3 GPU: the Nova backend reproduces the validated CPU path within declared tolerances and reports H200 throughput and memory use.
  • G4 ownership: repository searches and dependency tests prove there is one maintained implementation; Ambix contains only adapters, orchestration and frozen fixtures.

§4 — Continuous tandem integration

Ambix follows reviewed Nova revisions rather than waiting for a final API freeze. Each integration checkpoint migrates changed APIs, runs the focused consumer contract and records both the consumed Nova revision and the corresponding Nova validation identity. Optional in-flight capabilities stay capability-gated; they do not block unrelated Ambix inference work. Donor deletion remains serial and waits for scientific, numerical, performance and provenance parity.

The first tandem checkpoint is banked: Ambix moved to Nova 9c18d31f8bf0f424bd94d0a5c4ce5f1622d9fd8f, adopted the traced flux-surface geometry API and canonical correction-scale contract, and passed 48 Nova-facing tests before commit 1b7e341. Independent imas-efit GHCR validation remains Nova-owned; Ambix consumes its evidence rather than reproducing that solver-validation campaign.

§4.1 — How the dependency is wired, and where provenance lives

Both repositories are under simultaneous active development, so Nova is consumed as an editable path dependency on the sibling checkout rather than re-pinned to a reviewed SHA per checkpoint. pyproject.toml declares nova-stella through [tool.uv.sources] exactly as imas-ink already is, and a checkpoint becomes a Nova-side pull plus a sync rather than a push, a re-pin and a reinstall.

That removes the re-pin ceremony and it removes something the plan needs, so the second half is not optional. Revision provenance moves out of the source tree and into the evidence record, captured from the consumed checkout at gate-run time. A pinned SHA carried its own provenance as a literal; a path dependency does not, so every gate run records the consumed Nova revision alongside its result, and the four sites that assert the revision as data read it from the installed distribution rather than from a hardcoded string. A consumed revision that is recorded nowhere would satisfy the convenience of this decision and none of its purpose.

Two operational consequences follow. Syncing the single root environment is authorised for the dependency change itself, which makes it the one node that deliberately drops --no-sync — so it is serialised against every other worker, because the sync mutates the environment they share. And the API-stability guarantee does not travel: the drift inventory measured 74 of 74 consumed symbols unchanged only as far as aeffde05, so any commits the local checkout carries beyond that revision are unmeasured and are re-probed at the checkpoint rather than assumed.

§5.1 — What the boundary design is fenced by

The design rung is read-only by construction: it produces the boundary, not the migration. No importer moves and no repository file changes until a boundary shape is recommended and its identity consequences are measured. Five constraints are already known and must not be rediscovered.

  • The consumer surface is measured, not estimated. The 58 files and their 64 import lines are banked in the donor census and its geometry-importers.log. Start from that list; a design that classifies fewer symbols than the consumers actually import has not covered the contract.
  • The design does not wait on the pin advance. The drift inventory measured resolve_machine_artifact and MachineArtifactManifest as unchanged between the pinned de3277a3 and the recommended aeffde05, so the Nova-side surface this boundary maps onto is stable across that move.
  • One Nova symbol pair is outside that guarantee. Ambix does not currently import mast_solve_inputs.describe_machine or DescribedMachine, so the 74-of-74-unchanged result says nothing about them. A design that recommends adopting either must probe both revisions and record what it found rather than inheriting the guarantee.
  • Identity is the expensive axis. The artifact signature change from fc938 to fc70 rebuilt every efm-keyed compute cache and checkpoint. A boundary that alters the table hash or SetupSignature carries that cost again, so the identity-bearing stores are enumerated with a per-store verdict, never asserted as preserved.
  • Unresolved turns stay unresolved. The pinned description carries NaN turns on the P6 pair. The boundary must be able to carry an unresolved-turns value across itself; fabricating a weight to make a type total is a defect, not a simplification.

Representation is part of the deliverable: where the boundary's layering is clearer as a diagram than as prose, the design carries a diagram, and where a classification is clearer as rows and columns it stays a table rather than becoming a picture of one.

§5.2 — The boundary the design recommends

✓ designed 2026-08-20 A projection facade over a private, hash-frozen kernel. Of the 22 imported names only 7 are Nova-sourced, 12 are genuinely Ambix runtime concerns and 3 are private test leaks, which is why re-exporting the table and adopting DescribedMachine directly were both rejected. All 5 identity-bearing store families are PRESERVE EXACTLY. Full record: geometry boundary.

Consumers ask a shot-addressed service for one of three narrow projections — GeometryIdentity, OperatorGeometry, SensorGeometry — and the table type together with its record constructors stays private for the whole migration. That is the property that distinguishes this shape from the rejected one: an import-path change would relocate the coupling, because the aggregate and its constructors would remain the de facto API.

Two constraints carry into the migration and neither is negotiable at the boundary.

  • Representation identity, not physical identity, keys the stores. Keying the caches or checkpoints on Nova's physical digest was rejected: physical identity merges distinct discretizations, so it would collide or orphan the representation-dependent matrices. The kernel's own key, digest and version are copied into GeometryIdentity, and Nova's serialization is never hashed.
  • The dependency rewire lands before the facade. The facade's value is a golden-key proof that a frozen input still selects the identical path and reads an array-equal matrix. The description the rewire brings in republishes two flux-loop positions that currently sit past the fail-closed mapping bound, so freezing golden keys first would bake in a superseded description and force an immediate rebaseline of the very goldens the proof rests on.

The migration then runs in four measured tranches, boundary producers first so that the parity gate has something to bite on: C = 3 producers behind frozen six-shot operator and identity parity, then B = 13 projection consumers, then A = 18 scripts needing only a derivation id, then D = 25 fixture and contract tests. The terminal gate is zero imports of imas_ambix.gs.geometry across the current tree with no facade re-export of the table, and the private kernel is deleted only once the byte-stable hash has a separately owned, golden-tested home.

§ Decisions

Where does production physics live after the transition?

The user set the boundary explicitly: Nova owns all physics-spine, equilibrium, transport, circuits/passives, IMAS and GPU physics work; Ambix is primarily a labeler and ML consumer.

How is the Nova dependency wired while both repositories are in active development?

The tandem-integration model pinned an exact reviewed Nova SHA per checkpoint. Both repositories are under simultaneous active development, so every Nova change required a commit, a push and an Ambix re-pin before Ambix could consume it, and every verification required re-provisioning the single root environment.

The user wired it this way explicitly and authorised the sync: both projects are in active development, so a per-checkpoint SHA re-pin taxes every Nova change with a push-and-repin cycle. The consequence is that revision provenance leaves pyproject.toml, where it was a literal, and moves into the evidence record, where it is captured from the consumed checkout at gate-run time. The plan keeps recorded provenance and drops only the re-pin ceremony; a consumed revision that is never recorded anywhere would not satisfy this decision.
