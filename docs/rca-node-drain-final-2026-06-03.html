Verdict

The node drains were caused by an environmental, node-level condition — a kernel-driver wait that occasionally fails to resolve — not by anything our code did, and not by scancel, SIGKILL, or SLURM --time expiry. The defensive machinery built around those triggers (never-scancel, STOP-FILE contract, three-layer time-limit rule) was tested against its own threat model and the threat model failed: every kill mechanism we were avoiding was fired deliberately at live CUDA/NCCL workloads, repeatedly, and never drained the node. Those guards were removed from this repository on 2026-06-10. The remaining fixes are admin-side configuration and lightweight forensic instrumentation.

§1 — The mechanism (proven, mechanism-agnostic)

Every drain followed one chain, observed directly in the slurmctld log and slurmstepd stderr:

  1. A process enters uninterruptible D-state — a kernel sleep inside the NVIDIA driver (os_acquire_rwlock_*, uvm_*), the CXI Slingshot fabric (cxiWaitEventWait), or the GPFS client. The kernel cannot deliver SIGKILL until the wait resolves.
  2. The D-state outlives KillWait (30 s) + UnkillableStepTimeout (60 s) — both values confirmed from scontrol show config.
  3. slurmstepd logs "JOB NOT ENDING WITH SIGNALS" / "giving up after 63 sec"; slurmctld sets the node to DRAINING with Reason=Kill task failed.
  4. Recovery requires a manual admin nvidia-smi --gpu-reset or reboot, then scontrol update … state=resume.

This is documented SLURM behaviour, working as designed. The only open question was ever: what makes a D-state last >90 seconds instead of the usual sub-millisecond?

§2 — Most likely root cause

A node-level driver/firmware disposition toward occasionally sustained kernel waits — stochastic, environmental, and outside user-space control. The supporting evidence:

  • Independence from code. Five drains in 8 days (2026-05-26 → 06-01) were triggered by at least two unrelated user groups running completely different software — including one drain that predates our GPU work entirely. Same node, same Kill task failed signature. Parsimony forbids five separate code-level causes for one failure mode on one device.
  • Non-reproducibility. 16 deliberate attempts to drain the node — infinite GPU kernels with blocking syncs, driver rwlock-deadlock constructions, NCCL teardown corruption, SIGKILL mid-collective, --time expiry into a live hung process, and the verbatim frozen code of a job that had previously drained the node — produced zero drains.
  • D-state is normal and transient. A separate-allocation observer captured 10,514 process-state samples across all three driver surfaces during live GPU work: hundreds of D-state entries, all sub-second, all reaped cleanly. Sustained D-state is the anomaly, and nothing we run controls it.

The distal trigger inside the driver stack (GPU context residue, GSP firmware state, fabric or GPFS server-side stall) could not be isolated and very likely cannot be from user space. The 15-hour first outage — before any of our code ran — is the strongest hint that this node has a hardware/firmware disposition not seen elsewhere.

§3 — Claims tested and refuted

Each of these was, at some point, written into an RCA or a binding AGENTS.md rule. All were refuted by direct measurement:

Consequently the STOP-FILE contract, the --signal=B:USR1 + soft-wall-clock three-layer rule, and the never-scancel rule defended against mechanisms that do not exist on this stack. They were removed from AGENTS.md, the training code, and the sbatch headers on 2026-06-10. scancel and ordinary --time limits are the supported ways to stop a job.

§4 — What remains good practice (evidence-backed)

  • In-process, load-the-model-once GPU code (AGENTS.md §2b). Justified by measured performance (~55× on the 100-shot bench) and by one real, code-level deadlock: the legacy prefetch producer/consumer hang of 2026-05-27. That was a genuine bug worth eliminating regardless of drains.
  • Graceful SIGTERM/SIGINT handlers and per-batch watchdogs. Not drain protection — hang protection. A watchdog converts a stuck job from "wastes the GPU allocation until someone notices" into a fast self-exit, demonstrated repeatedly during the campaign.
  • Offline-mode env vars + preflight asset checks on betelgeuse (no outbound network). A blocked download stalls a job for its whole time limit; failing fast is simply correct.
  • Symmetric collectives (every rank participates). Rank-asymmetric collectives desynchronise the ring and hang the job — a real correctness bug even though it was exonerated as a drain trigger.

§5 — Recommendations

Admin-side (the actual fix — filed in proposal-drain-auto-recovery.html)

  1. Epilog GPU reset on job completion, clearing residual contexts before the next allocation.
  2. Auto-resume policy (HealthCheckProgram or cron): resume the node automatically when GPUs check out clean — turns a multi-hour outage into minutes.
  3. Review UnkillableStepTimeout (60 s → ~120 s) so transient D-state spikes cannot cross the drain threshold.

Repo-side: instrument, don't superstition

With the guards removed, the residual risk is that an organic drain recurs and we again lack process-level evidence. The mitigation is a forensic sidecar, not behavioural rules:

  • In-job sidecar (default-on): scripts/slurm/drain_sidecar.sh, launched as one background line in every long-running GPU sbatch. It ignores SIGTERM/SIGINT, samples every PID in the job cgroup (state + wchan + cmdline) once per second, snapshots nvidia-smi and kernel NVRM/Xid lines, and appends to GPFS so the record survives the job. Because it ignores SIGTERM it keeps sampling through the KillWait window — exactly the period that identifies which PID was in D-state and in which kernel symbol when a kill fails. Cost: one bash loop and a few KB/min of GPFS writes.
  • Separate-allocation observer (on demand): the campaign's scripts/drain-tests/instrumented/observer.sbatch survives the workload's SIGKILL and the drain itself, adding node State/Reason= tracking through the give-up window. Use it when actively investigating, not routinely.
  • If a drain recurs: pull /work/projects/imas_gpu/logs/drain-sidecar-<jobid>.*, identify the D-state PID/wchan, attribute via sacct, and attach the evidence to the admin proposal. Do not reinstate behavioural guards without a measurement showing they address the observed mechanism.
