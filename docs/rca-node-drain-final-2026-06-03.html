Verdict

The drain mechanism is confirmed and fully evidenced. The root cause is environmental, not code-specific. It cannot be reproduced on demand. The fix is admin-side configuration, independent of any code change.

§1 — What we know (proven by direct observation)

The proximate mechanism — confirmed

Every drain on 98dci4-gpu-0003 followed this exact chain, observed directly in the slurmctld log and slurmstepd stderr:

  1. A process enters uninterruptible D-state (kernel-level sleep waiting on the NVIDIA driver, CXI Slingshot fabric, or GPFS client). D-state means the kernel cannot deliver SIGKILL to the process until the wait resolves.
  2. The D-state persists longer than KillWait (30 s) + UnkillableStepTimeout (60 s) = ~90 seconds total. These values are confirmed from scontrol show config on the betelgeuse partition — they are not defaults assumed from documentation.
  3. slurmstepd reports: "JOB NOT ENDING WITH SIGNALS" and "Container … has N processes, giving up after 63 sec".
  4. slurmctld sets: update_node: node 98dci4-gpu-0003 reason set to: Kill task failed → state set to DRAINING.
  5. New jobs cannot start. The node requires manual admin intervention (nvidia-smi --gpu-reset or reboot, then scontrol update … state=resume) before it accepts work again.

This is documented SLURM behavior (UnkillableStepTimeout in slurm.conf man page) — not a bug or misconfiguration. SLURM is working correctly. The problem is that a process is in D-state long enough to trigger it.

D-state is normal on this node — but usually transient

A separate-allocation observer running alongside GPU workloads captured 10,514 process-state samples across all three driver surfaces:

  • 387 samples: os_acquire_rwlock_write (NVIDIA driver)
  • 347 samples: os_acquire_rwlock_read (NVIDIA driver)
  • 17 samples: os_acquire_semaphore (NVIDIA driver)
  • cxiWaitEventWait (CXI/Slingshot fabric)
  • uvm_gpu_retain_by_uuid (NVIDIA UVM)

All of these D-state samples were transient (sub-second). None of the 14 instrumented test runs — including deliberate attempts to create sustained D-state — drained the node. The trigger for sustained (>90 s) D-state is not the normal operation of any GPU job. It is something environmental and probabilistic.

The cause is infrastructure-level, not code-specific

The drain history covers 5 events across 8 days. At least 2 separate user groups (Group A = grpa, Group B = distinct account and job pattern) drained the node with completely different code:

Two independent user groups, different code, same "Kill task failed → drain" failure mode, same node. Parsimony forbids separate root causes for the same failure on the same hardware. The shared element is the node — not any user's code.

§2 — What we don't know

The proximate mechanism (D-state → drain) is fully confirmed. The distal cause — what specifically makes D-state last >90 seconds instead of the usual milliseconds — is not known and could not be established from this investigation.

Three surfaces are candidates:

  • NVIDIA GPU driver — a kernel lock (os_acquire_rwlock_write/read) on a driver resource that another process holds indefinitely. Possible causes: GPU context not fully released after a prior job, GSP firmware state, UVM mapping issue.
  • CXI Slingshot fabric driver — cxiWaitEventWait blocking on a network event that the remote peer never delivers. Possible causes: NVLink / HCA state after a hung collective, fabric reset not completing cleanly.
  • GPFS client driver — d_alloc_parallel blocking on a filesystem metadata operation to a server. Possible causes: GPFS server overload, client cache state, node identity issue after a prior drain.

All three surfaces have been captured in D-state on this node. Any of them could be the source on any given drain. The 15-hour first drain (2026-05-26) is the strongest signal that the node has a hardware or firmware disposition toward sustained D-state not seen on other nodes. Whether this is a driver version issue, a firmware bug, accumulated state, or physical hardware degradation is unknown.

§3 — Can it be reproduced?

No — and that is itself the finding.

16 deliberate attempts to drain the node (14 prior tests + 2 in-window Track A runs) produced zero deliberate drains. The attempts included:

  • Infinite GPU kernel + blocking event synchronisation (gpu_block_sync, job 1210259) — reaped cleanly at time limit.
  • NVIDIA driver rwlock deadlock (gpu_lock_deadlock, job 1210274) — readers never blocked; 150,000+ malloc/free cycles progressed.
  • Frozen MWE-01 v1 (the exact code from the confirmed drain artifact 1209813), verbatim — watchdog fired at 600 s, clean exit (run 1210688).
  • Same, with NCCL watchdog disabled — SLURM time-limit fired into a live hung process, clean TIMEOUT exit (run 1210787). No drain.
  • Six rapid kill/relaunch cycles of the real production finetune pipeline — all exited cleanly.

The zero reproduction rate on a clean, single-user node, with the exact code that previously drained it, means the trigger is stochastic and environmental. Something in the accumulated hardware/driver/firmware state of the node — which resets on reboot — creates the conditions for sustained D-state. A fresh node cannot be drained on demand with these workloads.

This is not a failure of the investigation. It is the answer to "why can't we fix it by changing code" — because there is no code to fix.

§4 — What to change

The fix targets the recovery half of the outage, not prevention. Even if we knew the exact driver condition causing sustained D-state, it arises at the hardware level and cannot be intercepted by user-space code. But the multi-hour outage is entirely caused by manual recovery latency — the admin being notified, accessing the node, and running the recovery commands. This can be automated.

Admin configuration changes (filed in proposal-drain-auto-recovery.html)

  1. Job epilog GPU reset. Add a SLURM epilog script for the betelgeuse partition that runs nvidia-smi --gpu-reset (wrapped in timeout 120) on job completion. Clears any residual GPU context automatically, preventing accumulated dirty state from making the next job's D-state sustained.
  2. Auto-resume policy. Configure HealthCheckProgram (SLURM 23.11+) or a 5-minute cron job that checks GPU health (nvidia-smi -q, zero active processes) and runs scontrol update nodename=98dci4-gpu-0003 state=resume reason="" automatically when the node is clean. Reduces outage from hours to <5 minutes.
  3. Review UnkillableStepTimeout. The current 60 s + KillWait 30 s = 90 s total before drain. For workloads that hold GPU contexts for multi-second teardown operations, a modestly longer timeout (e.g. 120 s total) may prevent drains from transient D-state spikes without materially delaying detection of genuinely stuck processes.

Code practices (unchanged — still valid, but not the root fix)

The STOP-FILE contract, SIGTERM handlers, per-batch watchdog timeouts, and three-layer time-limit defence in AGENTS.md remain the correct practices. They minimise the frequency of D-state by ensuring clean teardown paths and reducing the likelihood of a process being in a blocking kernel call when SLURM fires. They do not and cannot prevent environmental D-state in hardware/driver paths outside user-space control. They are belt-and-braces, not the root fix.
