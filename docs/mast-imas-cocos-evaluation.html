MAST → IMAS Coordinate / Sign (COCOS) Convention Evaluation

Requested by the lead, who feared sign-convention misunderstandings are silently hurting progress. This evaluation traces the full sign chain, tests it against real MAST data, and weighs the benefit of IMAS mapping.

Executive verdict

Is sign-convention confusion impacting progress? — PARTLY, and NOT where it was feared.

  • MAST-only pipeline (today's actual work): sign-SOUND. The chain is internally self-consistent and empirically verified. On four held-out shots the geometry-only Green's-function forward operator, run on a genuine pre-breakdown vacuum slice, predicts the raw amb magnetics with correlation 0.83–0.87 and a least-squares slope of 0.86–0.99 (sign and magnitude coherent — see Fig. 2). Ip sign is preserved in the physics constraint; the topology read is sign-agnostic by construction (a strength, not a hack). The negative boundary/LCFS skill scores the lead worried about are not sign flips.
  • The premise "MAST → IMAS → pipeline" does not describe the current architecture. MAST is read raw from FAIR-MAST zarr. There is no master.h5, no imas.DBEntry, and no COCOS auto-conversion anywhere on the MAST path. The IMAS reader exists only as a machine-agnostic seam, exercised against ITER machine-description geometry — never MAST, never signals.
  • The real exposure is a LATENT North-Star risk at the not-yet-wired IMAS ingestion seam. IMAS data is COCOS-11 (axis = flux minimum for Ip>0); the pipeline's working convention is axis = flux maximum (matching MAST EFIT). There is currently no COCOS-normalization layer, and one unverified COCOS assumption (imas_geometry.py:74, poloidal-angle) sits on that seam. This does not hurt MAST progress today, but it will bite the first time a second machine is ingested through IMAS — which the machine-agnostic North Star requires.

Recommendation: write a small, focused COCOS-hardening plan (sketched in §6), but treat it as a North-Star prerequisite, NOT an urgent fix — MAST-only progress is not blocked by sign conventions.

§1 — What actually flows where (the premise, corrected)

The lead's question assumes a "raw → IMAS → pipeline" flow. The code says otherwise. MAST enters the pipeline raw, straight from the FAIR-MAST level-1 zarr store (/work/projects/imas_gpu/mast/level1/shots/*.zarr):

  • Machine geometry (sensor (R,Z), orientations, PF filaments, limiter) is read from EFIT's static setup arrays in the zarr efm group by MastZarrGeometryReader / build_table_for_shot (imas_ambix/gs/geometry.py).
  • Raw magnetics (amb flux loops [Wb] / B-probes [T]) and coil currents (amc [kA·turn]) are read as zarr arrays, aligned to the operator by channel name (imas_ambix/latent/data.py).
  • The EFIT reconstruction (efm/psirz, psi_axis, …) is read only inside the firewalled evaluator for scoring — never as an input or label.

The one IMAS reader in the repo — ImasGeometryReader using imas.DBEntry (imas_ambix/gs/imas_geometry.py) — is a second, parallel implementation of the same GeometryTable seam, written for ITER-style machine-description IDSs (pf_active, wall, magnetics). It reads geometry only, no signals, and is not on the MAST path. A filesystem sweep confirms there are no MAST IMAS pulse files (master.h5) present. So no COCOS auto-conversion happens today at all.

§2 — The traced sign / COCOS chain

Canonical IMAS conventions are COCOS-11 (confirmed against the DD: magnetics/ip is ip_like, magnetics/flux_loop/flux and equilibrium/…/psi_axis are psi_like, b_field_pol_probe/poloidal_angle is pol_angle_like, b_field_pol_probe/field is one_like i.e. COCOS-invariant). COCOS-11 has σBp=+1 and eBp=1, which fixes two things: (a) ψ carries the full 2π (total flux, not per-radian), and (b) for Ip>0, ψ increases from axis to boundary, so the axis is a flux minimum.

§3 — Real-data findings

The audit script scripts/mast_cocos_audit.py reads real MAST zarr for shots 18502–18505 and answers two questions concretely.

3.1 — What convention is the MAST reconstruction actually in?

All four shots have a clearly positive plasma current (median Ip +640…+921 kA) and, at every reconstructed slice, ψaxis > ψboundary (median ψaxis−ψboundary ≈ +0.06…+0.07 Wb/rad). Axis is a flux maximum for positive Ip — the σBp=−1 (COCOS-3-like) EFIT-native convention, the exact opposite of COCOS-11. The matches_cocos11 flag is False for all four. This is a fact about the data, and the pipeline is built to match it, so it is not a bug — but it is precisely the sign that would flip if the same data were ever routed through an IMAS COCOS-11 conversion.

3.2 — Is the forward sign chain coherent end-to-end?

The strongest test: on a genuine pre-breakdown vacuum slice (PF coils energised, Ip still NaN, so raw amb is a pure PF signal), does the operator's vacuum prediction G_pf · I_pf reproduce raw amb? Across the four shots the name-matched sensors give correlation 0.83–0.87, sign-match fraction 75–85%, and — decisively — a least-squares slope of 0.86–0.99. A slope near unity means the entire chain (kA·turn→A conversion, μ0, filament Green's-function sign, and the BRcosθ+BZsinθ projection) is coherent in both sign and magnitude. The ~15–25% sign disagreements are all on near-zero, noise-dominated sensors (clustered at the origin in Fig. 2).

§4 — Impact assessment (against the lead's fear)

The lead specifically asked whether the negative boundary/LCFS results are sign-related. Evidence says they are not:

  • The negative numbers are skill scores, not physical sign flips. "LCFS −6" and "axis_Z −0.19" are skill (worse-than-baseline) metrics recorded in the patch-current force-balance work, attributed there to spurious saddles in a non-force-balanced low-DOF current representation. A genuine ψ-sign or Z-flip would corrupt the axis-R read too — but axis skill went positive (+0.019) in the same run. A sign fault cannot be selective like that.
  • Sign-agnostic reads are principled, not a cover-up. Using argmax|ψ−ψedge| for the axis and sign(ψbnd−ψaxis) for the ray-cast is the mathematically correct way to be invariant to a convention you don't want to hard-code. This is exactly what a machine-agnostic model should do; it is not masking an unresolved bug. The forward-coherence test (Fig. 2) independently confirms the underlying sign is right, so the agnosticism is belt-and-braces, not a crutch.
  • No per-shot sign flips exist in the loaders. The only abs() on a signed quantity is the plasma-on detector; the physics keeps Ip signed. The "falls back to ψ_norm if frames disagree" hedge in the flux-map report is a plotting robustness fallback for absolute-level comparison, and the report notes the absolute frames do agree (axis = flux max on both sides).

Net: sign confusion is not what is holding back the boundary/closure readout. Time spent hunting a MAST sign bug would be misdirected; the representation (force balance, saddle robustness) is the real frontier, as the current plan already states.

§5 — Is mapping MAST to IMAS worth it?

Weighing the machine-agnostic North Star (one latent world model, MAST → JET → ITER by construction) against the concrete cost:

Benefit of IMAS mappingCost / risk
COCOS standardization — one convention across machines removes the per-machine sign bookkeeping entirely (the exact latent risk in §2 disappears). Silent auto-conversion. imas-python will happily COCOS/DD-convert on a mismatched dd_version; a wrong version corrupts ψ sign and the 2π factor without erroring. The repo's IMAS rules already guard this, but the guard must be honored on the MAST path too.
DD-versioned, machine-agnostic geometry. The GeometryTable seam already exists and is reader-agnostic — the ITER reader proves the seam works. Portability to JET/ITER is a schema read, not a rewrite. MAST native ≠ COCOS-11. Mapping MAST into IMAS naively would flip the working sign (axis-max → axis-min for Ip>0) and force a decision the pipeline currently dodges. Worth it only if the forward operator + topology are made explicitly COCOS-tagged at the same time.
Apparatus metadata portability — coil/probe/wall descriptions arrive in a documented, self-describing schema instead of EFIT array conventions that differ per campaign. Effort now, payoff later. MAST-only work needs none of this; the value is realized only when the second machine lands.

Conclusion: IMAS mapping is worth it — it is the mechanism that makes the machine-agnostic North Star real and permanently retires per-machine sign bookkeeping — but it is only worth it done properly: the conversion must be an explicit, fail-loud, tested seam, and the forward operator/topology must declare their working COCOS so the seam has something to convert to. Mapping MAST to IMAS without that seam would inject exactly the sign hazard the lead fears.

§6 — Recommendation

Yes — write a separate, focused COCOS-hardening plan, but scope it as a North-Star prerequisite (to land before, or together with, the first non-MAST machine ingestion), not as an urgent fix for current MAST progress. MAST-only work is sign-sound and should proceed unblocked. Suggested sections:

  1. Declare and pin the pipeline's working COCOS. Add an explicit constant + docstring stating the forward operator's convention (eBp=1 total-flux, σBp=−1 axis-max sign). Add a regression test pinning sign(ψaxis−ψboundary) = +sign(Ip) for a known synthetic current — so the sign can never silently drift.
  2. Verify the poloidal-angle assumption at the IMAS seam. Open a real COCOS-11 magnetics IDS (ITER machine description or a synthetic reference), confirm the BRcosθ+BZsinθ projection reproduces a known field with the correct sign, and resolve the flagged assumption at imas_geometry.py:74 with a round-trip test.
  3. Build one COCOS-normalization boundary in the IMAS readers. A single, fail-loud seam that converts COCOS-11 (ψ, Ip, flux, poloidal_angle) into the declared internal convention (or converts the pipeline to COCOS-11 — decide once). No silent auto-conversion; unknown/missing COCOS raises.
  4. Add a cross-convention self-consistency gate. Feed the same physical equilibrium through the raw MAST path and through a synthetic COCOS-11 IMAS pulse; require identical topology (axis, LCFS radii, X-points) after the normalization seam. This is the acceptance test that the machine-agnostic seam actually is machine-agnostic.
  5. (Optional) Document the plasma-on abs(ip) detector in code so it is never mistaken for a physics sign flip, and audit that every other Ip use is signed.
