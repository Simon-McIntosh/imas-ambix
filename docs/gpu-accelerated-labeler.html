§1 — Overview: one on-device rollout substrate, three deployment dimensions

Sequencing. This plan lands after greens-filament-solver (SHIPPED 2026-07-20: grid-free analytic-ψ substrate GO, contour-free GPU-native FSA PASS, campaign-scope matrix cache) and after connectivity-topology-reader (the on-device differentiable topology read) — both are depends_on. The grid-free substrate is the port target. Crucially, greens-filament-solver §4 confirmed on CPU what this plan asserts: no per-solve iterator (Picard, Anderson, Newton–Krylov) clears the ≥3× throughput gate, because the wall is the sequential, non-smooth, host topology read (it corrupts NK’s Jacobian and Anderson’s history alike) — not the arithmetic. So the 3×+ is a batched-over-shots GPU result that lives HERE, and greens-filament-solver §5 (adopt + integrate + re-score at corpus scale) folds into this plan’s ONE jax engine (§4 offline corpus + gate G-C). Green-field GPU-first design starts now so the substrate is optimised for H200 compute from the beginning, not retrofitted.

The problem, and the honest negative that motivates it. The reanalysis engine produces firewall-clean equilibrium labels; the label factory must run the free-boundary Grad–Shafranov solve over the ~12.6k-shot MAST corpus (~600k slices) to feed the learned cross-machine operator — ~37 core-days at today’s CPU rate. The obvious move — port the solver to the 8×H200 node — does not work per-solve: the greens-filament-solver §2 spike measured the grid-free matvec at 1.67× SLOWER than the cached grid solve on a single CPU slice, and the lead’s own prior jax GPU port of the nova scheme showed no material speedup. This plan is the re-architecture that does work.

Why a per-solve GPU solver fails (three independent reviews agree). A single equilibrium is close to the canonical anti-GPU workload:

  • Batch-1 is a memory-bound GEMV. The plasma→grid Green’s matvec (6305×1500, ~38 MB) has arithmetic intensity ~0.5 FLOP/byte — ~600× below the H200 tensor-core ridge (~295 FLOP/byte). The tensor cores that are the H200 sit ~99.5% idle; the 38 MB matrix stays hot in CPU L3 across all sweeps, so the CPU wins.
  • The fixed point is strictly sequential — a chain of 40–120 dependent sub-20-MFLOP kernels; latency-bound, not throughput-bound.
  • The topology read forces a per-iteration HOST round-trip (device→host ψ → NumPy critical-points + ndimage.label → host→device jφ) — the dominant killer, idling the GPU every sweep.
  • The anti-pattern is nested twice: the time-integration loop (resistive diffusion + passive circuits) is ALSO a Python loop with per-step host scalar reads, so even a perfectly batched per-slice solve re-serialises in time.

The cure — one substrate. The parallelism is across solves, not within one. The whole causal rollout runs on-device as a single vmap(batch) × scan(time) × fixed-point graph; the GS matvec becomes a batched GEMM (compute-bound past B ≈ 600); the topology read is a fixed-shape on-device stencil (no host round-trip). What changes between deployments is only what fills the batch axis.

Strategic framing — a green-field substrate that can beat EFIT before ML. This is not a faster EFIT. The engine folds in resistive flux diffusion, passive/vessel currents, and firewall-safe measured moments that single-slice EFIT ignores; on the held-out MSE pitch gate it already reaches 0.362 rad — beating persistence CI-clear and approaching the classical EnKF bar (0.225) without any ML. The differentiable rollout (§7) is the durable strategic asset: it is the world model’s labeler/teacher (self-calibrating η / passive-R / priors against EFIT-free held-out magnetics via autograd), a 4D-Var successor to EnKF (gradient-based variational assimilation that handles the nonlinear GS fixed point better than ensemble linearisation), and a physics-in-the-loop layer the ML world model can embed — NOT an EnKF the ML model retires. The ML operator beats classical on the high-bandwidth residual; this engine is the physics floor beneath both bars. That is why jax (autograd) is presumptive and why the rollout is designed differentiable from the start.

§5 — In-pulse real-time streaming to the control room (the third dimension)

The ITER-scale use case: during a long (~3000 s) pulse, push as many reconstructed slices as possible to the control room, keeping pace with a high-frequency data rate at a bounded latency. This is neither offline (throughput, whole-trajectory) nor post-shot (latency-tolerant, whole-trajectory) — it is a continuous causal stream with a hard keep-pace constraint.

  • Streaming sliding-window PinT. Accumulate incoming slices into a window; solve the window as a batched-over-slices PinT (causal, warm-started from the previous window → 1–2 outer iterations); emit; slide forward. The passive modal state + profile carry continuously across windows (exact ZOH) over the whole pulse — a continuous rollout, not a fixed-length shot; periodic re-anchoring to measured moments prevents drift over 3000 s.
  • Throughput↔latency knob. The window/batch size sets GPU utilisation (toward the B ≈ 600 ridge) vs latency: larger window = better tensor-core fill + higher latency; smaller = lower latency + below-ridge. Tune to the data rate and the control-room latency budget; the batch here is slices-in-flight, so utilisation is bounded by the window size (not the full ridge) — the win is still G-amortisation + launch-count collapse + pipelining.
  • Pipelining. Overlap ingest / batched-solve / emit across CUDA streams (and pin a card to the stream) so the GPU stays busy: solve window N while N+1 accumulates. This decouples the data rate from the solve latency.
  • Graceful degradation (never fall behind). If the data rate outpaces solve capacity, drop to the truncated 1-outer-iteration fast path or coarsen the rollout, emitting the best-available equilibrium with an under-determined / confidence flag (label-honesty in real time) rather than lagging the pulse.
  • Multi-GPU for in-pulse. Prefer pipelining stages / parallel windows across cards over sharding a single window (hard latency penalises cross-device comms); a few cards can also fan out independent reconstructed quantities.

Gate G-D: on a replayed long pulse, sustained slices/s ≥ the target data rate at a bounded p99 latency, with streamed equilibria matching the post-shot (§3) reconstruction to tolerance; the truncated fast-path variant validated against the converged rollout before any real-time use.

§7 — (Stretch) differentiable rollout → 4D-Var calibration + physics-in-the-loop

Once the topology read is smooth, the whole rollout is differentiable via an implicit-function / deep-equilibrium adjoint at each GS fixed point (no unrolling) + per-slice checkpointing across the time scan. Three durable payoffs, none retired by the ML world model: (1) self-calibration — gradient-based fit of η(ψ_N), the passive resistances, and the priors against EFIT-free held-out magnetics, replacing the current gradient-free search and improving the labels the world model trains on; (2) a 4D-Var successor to EnKF — variational assimilation through the nonlinear GS+dynamics rollout, better-conditioned than ensemble linearisation; (3) physics-in-the-loop — the differentiable engine embedded in the world model as a physics-constrained layer / differentiable-simulator regulariser, or supplying training gradients. This is the strategic reason jax (autograd) is presumptive. The learned operator is also the natural coarse propagator for a future parareal variant of §5.

§ Decisions

Which framework for the batched on-device rollout?

Spike-confirmed on the H200 (gpu:0, real 6305x5084 fp64 campaign Green's matrix): the inner GS step is 0.65 ms (jax) vs 0.81 ms (torch) at B=512 fp64 - raw speed comparable (~1.2x jax), NOT the decider. The evidence is one-sided on the qualitative axes: the on-device differentiable topology read (connectivity_boundary / flood_fill_core / stencil_nulls) exists only in jax; autograd through the fixed-point map (learned-operator / 4D-Var asset) is jax-native; fixed-shape vmap over slices is the labeller's core pattern. torch would require re-porting the read. No fp64 blocker found (fp64 GEMM saturates ~56 TFLOP/s; GPU/CPU parity 7.5e-14). Artifact: imas_ambix/latent/artifacts/patch_gate/gpu_labeler_foundation-v0.json.

What deployment modes does the engine target, and do they share a substrate?

Locked by the lead (2026-07-20): the engine is a world-model labeler AND a real-time reconstruction tool. Offline (A) maximises throughput via pure shot-batching; post-shot (B) minimises single-shot latency via parallel-in-time; in-pulse (C) keeps pace with a ~3000s pulse's data rate at bounded latency via a pipelined causal sliding-window PinT with graceful degradation. All three wrap the same single-shot on-device rollout, so it is built and validated first (§3), then the outer batch (§4, offline) and the sliding window (§5, in-pulse) are added. PinT is the analogue of shot-batching where no shot-batch can be filled (B, C); offline it is pure waste (pure shot-batching dominates).

Where does the axis/X-point + core-mask topology read run?

Locked (2026-07-20): all three reviews agree the per-iteration host round-trip is the dominant reason the per-solve jax port flatlined; without an on-device read Amdahl caps everything at ~3x. DELIVERED BY THE PREREQUISITE PLAN connectivity-topology-reader — a connectivity flood-fill boundary (continuous through the marginal transition) + nova's stencil axis/X primitives, GPU-native and differentiable; this plan consumes it. A final exact-read CPU polish for the EMITTED label is retained where sub-mm axis is a hard requirement (validated against the on-device read + the Ejima/flux-budget ledger).

What numerical precision for the H200 rollout?

Locked by the lead (2026-07-20), spike-validated: dropping precision on the H200 is a LARGE win where it is safe. The GEMM is the dominant arithmetic once batched and the H200 tensor cores run bf16/tf32 at ~990/495 TFLOP/s vs fp64 34–67 (~14x); the Ip renormalisation self-corrects the matvec each slice, so bf16-in/fp32-accumulate is tolerable there. But the CROSS-SLICE RECURRENT STATE (resistive diffusion, exact-ZOH passive integration) accumulates error over the rollout → keep fp64; the topology argmax needs fp32 for sign-change detection / sub-mm axis. bf16 must NEVER leak into state that crosses a slice boundary. §2 validates axis/LCFS/Ejima-ledger under the mixed-precision boundaries before locking; warm-starting (few sweeps) reduces the accumulation exposure. Green-field: the data layout is designed around these boundaries from the start, not retrofitted.

How is the flux-surface geometry supported in time between slices — ZOH-hold or time-interpolated (smoother)?

Locked by the lead (2026-07-20) — an EnKF-smoother analogue and a strong exploitation of the PinT structure. Because the batched rollout solves past AND future slices of a window simultaneously, the transport integration between slices can use a time-interpolated (two-sided) flux-surface support rather than the causal ZOH — higher-order-accurate in time (Crank–Nicolson vs backward-Euler-with-frozen-geometry) and smoother-quality (uses future data), which improves LABEL quality (a smoother beats a filter). Offline (A) and post-shot (B) get the full two-sided smoother over the whole trajectory; in-pulse (C) gets a fixed-lag smoother over the causal window, ZOH only at the very frontier. Validate the smoother labels reproduce the ZOH labels in the ZOH limit + improve the flux-budget/Ejima ledger.

Single-rate or multi-rate — does the transport roll out at the same cadence as the flux-surface/equilibrium support?

Locked by the lead (2026-07-20). The equilibrium GEOMETRY is quasi-static / slowly-varying relative to the fast transport + magnetics; rolling the transport (resistive diffusion, passive circuits) at a finer Δt on a time-interpolated geometry (see time-support) captures high-bandwidth dynamics without re-solving the equilibrium every substep. GPU compute makes the fast substeps cheap, and it fits the existing frozen-geometry-per-interval structure of diffuse_psi (now generalised: interpolated, not frozen). This is the path to higher-bandwidth reconstruction than the flux-surface support cadence — the equilibrium is refreshed coarsely, the transport rolls fine. Validate against a single-rate reference; the geometry-refresh cadence is a controlled accuracy knob.

Does the GPU-native engine still run on CPU?

Locked (2026-07-20): jax targets CPU and GPU from one codebase — the GPU-native rewrite loses NO CPU capability; it is a backend switch (fp64 enabled on both). CPU cost is nuanced: at batch-1 a jax-CPU solve ≈ the current numpy grid-free path (the dense matvec dominates either way — no material gain/loss), but the BATCHED form is a CPU speedup over the per-shot loop (XLA-CPU threaded GEMM). Avoid a parallel _v2 engine family: the frozen numpy grid-GS remains the byte-frozen reference oracle the jax engine is validated against; it is not maintained as a second production path.

What is manipulated at solve time — the matrices, or only the current vectors?

Locked by the lead (2026-07-20), confirmed in code: ψ = ψ_coil (once/slice) + ψ_pass (frozen columns · a_pass vector) + G_plasma · i_cell, with every G block frozen geometry. The plasma "turns" update is a pure VECTOR op — i_cell = fixed cell-area weights × the force-balance current density × Ip/Σ — the matrix is never touched (same as nova; there is no matrix manipulation to remove, we are already there). This is the load-bearing GPU invariant: the resident matrices are static and only the current vector streams (GEMV→GEMM over the batch). The ONE small per-sweep assembly is the K≈6 profile-coefficient LSQ (basis images on the evolving core + soft-prior/KKT rows) — necessary, tiny, NOT the interaction matrix; keep it small and batch-friendly. Freeze geometry at campaign scope (§4) so the matrices build once for the whole corpus (~2 signatures). The follow-on must NOT introduce per-iteration interaction-matrix manipulation.
