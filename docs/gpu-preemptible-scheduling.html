Reading note. This is a research/advice document. The question: the H200 node caps a job at 4 GPUs, but nothing stops several 4-GPU jobs queueing — so can we run low-priority jobs that get paused when higher-priority work arrives and then resume (we already have robust checkpointing)? And is that a bespoke admin job or something we can do ourselves? Acronyms are expanded on first use; the SLURM mechanics are in §8.

§1 — The question

The shared node 98dci4-gpu-0003 (8× H200, split into Group A = 4 cards and Group B = 4 cards) limits any single job to 4 GPUs. Multiple 4-GPU jobs simply queue. We want backfill-style low-priority jobs that opportunistically use idle cards but step aside (checkpoint + pause) the moment a higher-priority job needs those cards, then resume where they left off. Our world-model trainer already checkpoints every 500 steps and resumes from latest.pt, so the "resume" half is solved. The open question is the "pause when something better arrives" half — and whether it needs SDCC admin work or can be done from our own submit scripts.

§2 — Research findings (the cluster's SLURM configuration)

Finding 1 — native preemption is OFF cluster-wide. scontrol show config reports:

  • PreemptType = (null)
  • PreemptMode = OFF
  • PreemptExemptTime = 00:00:00, PriorityType = priority/multifactor

and the betelgeuse partition itself is PreemptMode=OFF, PriorityTier=1. Consequence: SLURM will never evict a running job for a higher-priority one. Priority (QOS, --nice, age, fairshare) only changes the order pending jobs are scheduled when resources free — a higher-priority job waits behind a running one. So the behaviour we want does not exist out of the box.

Finding 2 — QOS priorities exist, but none preempts. The QOS table:

QOSPriorityPreempt listPreemptMode
god10,000,000—cluster
high / debug_high100—cluster
mid10—cluster
normal1—cluster
low0—cluster
gpu_0003_grpa / gpu_0003_grpb0—cluster (DenyOnLimit)

No QOS carries a Preempt= list, and every QOS inherits the cluster PreemptMode=OFF. So even the large priority gaps (god ≫ high ≫ normal) only affect queue ordering, never eviction.

Finding 3 — the A/B split is reservation + NUMA + QOS, and Group B is access-restricted. Both groups are persistent reservations on the one node (the partition is ReqResv=YES — you must name a reservation):

  • gpu_0003_grpA — CoreIDs 15–29,47–61 (30 cores), unix group sdcc-slurm-gpu_group-a.
  • gpu_0003_grpB — CoreIDs 0–14,32–46 (30 cores), unix group sdcc-slurm-gpu_group-b.

The reservation comment states "QoS enforces GPU/mem; use NUMA binding in srun" — i.e. the 4-cards-per-group cap is a QOS limit, and cards follow NUMA core affinity. My account (grpa) is denied the Group B reservation — a --test-only submission to gpu_0003_grpB returns "Access denied to requested reservation" because it is gated to the sdcc-slurm-gpu_group-b unix group. My associations give me only account=grpa with QOS normal (prio 1) and gpu_0003_grpa (prio 0). I have no path to submit via Group B's reservation.

Finding 4 — but Group A jobs BURST onto Group B's physical cards anyway (confirmed empirically). The reservation reserves only cores; our jobs run under QOS=normal (not gpu_0003_grpa), so the gres/gpu=4 group cap is never applied; and SLURM's GRES selection hands out any free GPUs from the node-wide pool of 8. A 4-GPU Group A job submitted while Group A already held 4 GPUs (the live DSv4 server + the world-model retrain) started immediately and was assigned physical GPUs SLURM_JOB_GPUS=2,3,6,7 — spanning the A/B boundary onto cards 6–7 (Group B's nominal range), taking the account to 8/8 cards. The job's CUDA_VISIBLE_DEVICES is remapped to 0,1,2,3, so it never knows it is on B's silicon. The 4-cards-per-group split is therefore a convention, not an enforced limit: a Group A submit can use up to all 8 cards, and reaching cards 4–7 needs neither admin nor Group-B access — only a normal submit when those cards are free.

§3 — Feasibility verdict

There are exactly two ways to get "pause-on-arrival", and they differ in who must act:

(A) Native SLURM preemption(B) Cooperative (user-space)
Who enables itSDCC admin (slurm.conf + QOS)Us (submit scripts + a watcher)
How it pausesSLURM sends SIGTERM (GraceTime) then requeues the job automaticallyThe job polls the queue and requeues itself
LatencyImmediate (GraceTime window, e.g. 120 s)Poll interval + requeue + reschedule (seconds–minutes)
RobustnessGuaranteed; works against any higher-pri job, any userBest-effort; only yields jobs we control
Needs admin?YesNo (but Group-B access still needs admin)

Verdict.

  • True auto-preemption is bespoke admin work. PreemptType/PreemptMode/QOS-preempt-lists live in slurm.conf and the accounting DB; a user cannot set them. Today they are OFF, so option (A) requires an SDCC ticket (§7).
  • The cooperative scheme we can build ourselves — it is just a watcher plus scontrol requeue plus our existing checkpoint/resume (§5, demonstrated in §4). It needs no admin.
  • Reaching Group B's cards needs no admin — we burst onto them (Finding 4). A normal Group A submit already lands on idle 4–7 cards. The cooperative scheme is therefore useful immediately and broadly: any fill job we run on idle cards can yield when priority work arrives.

Finding 4 flips the problem. Because a normal Group A submit already bursts onto the free cards (including Group B's 4–7), we can reach idle capacity ourselves today — no admin, no Group-B access. The real question inverts from "how do we get onto 4–7" to "how do we get off them gracefully when Group B wants them." With preemption OFF, a burst job holds those cards until it finishes, blocking Group B. The cooperative-yield watcher (§5a) is precisely that give-back, fully in user space: burst to use idle cards, and wrap the job in the watcher so it checkpoints + requeues the instant Group B — or any higher-priority job — appears. The flip side is etiquette: bursting onto 4–7 without a yield makes us a bad neighbour, since Group B cannot evict us (preemption is OFF).

GPU-specific caveat (important): for a GPU job the pause mode must be REQUEUE (or CANCEL), never SUSPEND/GANG. SUSPEND only sends SIGSTOP — the process stays resident and keeps its VRAM, so the higher-priority job still cannot get the card. Only killing the process (requeue/cancel) frees the GPU, which is exactly why our checkpoint-and-resume design is the right partner.

§4 — Trial

The Group-B reservation is access-denied (§2, Finding 3), but a Group A submit bursts onto Group B's physical cards anyway (§2, Finding 4): a 4-GPU probe ran immediately on cards 2,3,6,7 while the account already held 4 GPUs. So we can place GPU jobs on 4–7 — just not through Group B's reservation. What we cannot demonstrate is native preemption: it is OFF, so submitting a "high-priority" job evicts nothing (a no-op). What we can and do trial is the half we own — the cooperative watch→checkpoint→requeue→resume give-back cycle — below.

Instead we trial the part we can own: the cooperative watch→checkpoint→requeue→resume cycle, on a CPU debug partition we have access to, with two jobs forced to contend for one node (--exclusive). A low-priority job (--nice=10000 --requeue) runs a counter + checkpoint loop with a queue-watcher; a default-priority job is then submitted for the same node; we observe the low-pri job yield, the high-pri job run, and the low-pri job resume from its checkpoint.

PoC result (vega_debug, jobs 1219666/1219667) — the cooperative cycle works end-to-end, all four facts confirmed. Timeline: low-pri RUNNING (counter→3) → high-pri submitted (PENDING/Resources) → low-pri detected it within one 3 s poll, checkpointed (counter 4) and scontrol requeued itself (RUNNING→COMPLETING→PENDING) → high-pri RAN on the freed node → high-pri done → low-pri RESUMED from checkpoint (logged RESUMED counter=4, then 5→9, never reset to 0). Verified: (1) a user CAN scontrol requeue their own running job (rc=0); (2) --nice=10000 sorts the low-pri job below default-nice (multifactor priority 0.0000255 vs 0.0000278) so the high-pri schedules first; (3) checkpoint continuity held (resumed at 4, not 0); (4) end-to-end latency (high-pri submit → high-pri RUNNING) was ~41 s, dominated by SLURM's post-requeue BeginTime anti-thrash hold (~60 s) + the scheduler cycle — the detect+requeue itself is ~5 s. Caveats: poll-interval detection lag; add hysteresis (yield only if the competitor has waited > N s) to avoid thrashing; drop the --nodelist pin in production; and for GPUs the mode MUST be requeue, never SUSPEND (SIGSTOP keeps VRAM mapped, so it would not free the card). Net: the user-space give-back is proven; the only cost vs native preemption is ~tens of seconds of latency.

§5 — Implementation plan

(B) Cooperative scheme — what we build (no admin)

  1. Submit wrapper. Low-priority jobs go in with --nice=<large> (so they sort below normal work) and --requeue (so a requeue re-runs the batch script). Our existing WM_OUT_DIR/latest.pt resume handles continuity unchanged.
  2. Yield watcher (a small Python/bash helper launched in the background by the job): every P seconds run squeue for PENDING jobs that (a) target the same reservation/cards and (b) outrank this job (higher QOS priority or lower nice). On a hit: set the trainer's STOP flag (reuse the SIGTERM path so latest.pt is flushed), then scontrol requeue $SLURM_JOB_ID and exit so the cards free.
  3. Resume. The requeued job re-enters PENDING; when the cards free it re-runs and resumes from latest.pt — identical to our drain-recovery path.
  4. Tuning. Poll interval P trades latency vs squeue load (≈10–30 s is fine); add a minimum-runtime guard so a job that just started does not immediately yield and thrash.

This is small, self-contained, and reuses the SIGTERM/checkpoint machinery already hardened for the GPU-node drain history. Its limits are honest: best-effort latency, and it can only make our jobs step aside — it cannot force another user's job to yield.

(A) Native preemption — what we ask SDCC to enable (robust)

The clean, automatic version. SDCC sets, in slurm.conf + the accounting DB:

  • PreemptType = preempt/qos and PreemptMode = REQUEUE (REQUEUE, not SUSPEND — frees the GPU; pairs with our checkpointing).
  • A grace window, e.g. PreemptParameters = "..." with a per-QOS GraceTime = 120 s, so the preempted job gets SIGTERM + 120 s to checkpoint before SIGKILL (our handler flushes in < 5 s).
  • A new preemptable low-priority QOS (e.g. gpu_0003_low, priority 0) and the group QOS (or normal) carrying Preempt=gpu_0003_low so normal work evicts the low lane.

We then submit fill jobs to the low QOS with --requeue; everything else is automatic.

§6 — Recommendation

  1. Do it ourselves now — burst + cooperative yield (no admin). Run opportunistic fill jobs as ordinary Group A submits; they already land on idle cards including 4–7 (§2, Finding 4). Wrap each in the §5a watcher so it checkpoints + requeues the moment Group B or a higher-priority job needs those cards. This delivers the requested "low-priority fill that pauses for priority work" today, in user space, on our existing checkpointing.
  2. File the SDCC ticket for native QOS preemption (§7) for the robust version. Cooperative yield is best-effort and can only make our own jobs step aside; admin-configured preempt/qos + REQUEUE + GraceTime lets Group B (and any priority job) reclaim cards automatically and guaranteed — the right long-term answer, and a natural fit for our checkpointing.
  3. Flag the unenforced group cap to SDCC. The gpu=4 per-group limit lives in the gpu_0003_grpa/_grpb QOS, but our jobs run under QOS=normal so it is never applied — exactly why bursting works. If the A/B split is meant to be hard, the group QOS must be enforced (or GPUs put in the reservations); if shared use is fine, native preemption (rec. 2) makes it safe.

§8 — Glossary

  • Preemption — SLURM stopping a running job so a higher-priority one can use its resources.
  • PreemptType — how preemption is decided: preempt/qos (by QOS), preempt/partition_prio (by partition tier), or (null)/none (disabled — our case).
  • PreemptMode — what happens to the preempted job: REQUEUE (killed + re-queued — frees the GPU), SUSPEND (SIGSTOP, stays resident — does NOT free GPU VRAM), CANCEL (killed), GANG (time-slice), OFF.
  • QOS — Quality of Service: a named policy carrying a priority, limits, and (optionally) a preempt list.
  • PriorityTier — a partition-level rank; higher-tier partitions' jobs can preempt lower under preempt/partition_prio.
  • GraceTime — seconds a preempted job is given (SIGTERM → wait → SIGKILL) to checkpoint before it is killed.
  • --nice — a user-settable priority penalty (larger = lower priority); the one priority knob a normal user controls.
  • --requeue / scontrol requeue — return a job to the pending queue so it re-runs (from our checkpoint).
  • Reservation — a named, access-gated carve-out of nodes/cores; betelgeuse requires one (ReqResv=YES).
