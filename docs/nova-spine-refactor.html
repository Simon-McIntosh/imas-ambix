§1 — Objective and strategy

Refactor nova in place into the physics-spine package (repo-mechanics decision locked 2026-07-23): nova keeps its name, identity, history, and core test set; the 2.0 core — canonical Biot kernels, operator assembly, machine-description compilation, identity caching, batched topology, IMAS IO — is built on a develop branch from nova's keep-set (~35k LOC) plus imas-ambix's physics tier (~12k LOC), while the live 1.x line continues to support the ongoing ITER-assembly work until that work extracts to its own repository. The evidence base and option analysis are in the research doc nova-scoping-review (§7a assesses this route); this plan is the execution record. Priority zero is the protection of the GP-interpolation and SSAT/in-pit coil-fitting code — §2a's characterization harness (1 µm tolerance gate) lands before any branch surgery. Strategy pillars, fixed unless a decision below reopens them:

  • One canonical home, curated transfer. Whether the spine lives in a new repo or in a refactored nova (see the repo-mechanics decision), each component becomes canonical in the spine as it lands and the donor copy is deleted in the same series — no parallel version families, no long-lived duplication. Assembly/structural work is out of scope for the spine in every variant.
  • Pandas-free core. The frame layer is rebuilt as a typed columnar store (schema + dict-of-numpy-columns + accessor objects); pandas and xarray appear only as export/interchange shims. Forward-looking floors across the stack: python ≥ 3.14, numpy ≥ 2.
  • JAX-first evaluation, numpy assembly. Green's-function assembly stays numpy/scipy (assemble-once); evaluation, dynamic plasma turns, null-finding, topology, and the GS fixed point run on the jitted path with a batch axis over shots/timeslices.
  • Access Layer only at the boundaries. Ingest transcodes IDSs once into a standard-name-keyed zarr signal cache; the hot path sees dense arrays only; egress assembles true IMAS IDSs at end of run.
  • Fast tests only. Every transferred unit test runs without live DB/UDA access and the whole suite stays in the seconds-to-low-minutes range; DB-bound tests are rebuilt on synthetic or bundled HDF5 fixtures or left behind.

§2a — Assembly protection and port program (priority)

Protected scope: the GP-interpolation and coil-fitting cluster for SSAT and in-pit operations — nova/assembly/gaussianprocessregressor.py, fiducialfit.py, fiducialfit_relative.py, fiducialpit.py (2.8k), fiducialsector.py (1.5k), fiducialccl.py, fiducialtransform.py, sectordata.py, sectorfile.py, windingpack.py/uniformwindingpack.py, SM6_fit.py — plus the vault spectral-proxy and coil-gap asymmetry work (fouriervault.py, vault.py, gap.py and the Fourier data files: constant_adaptive_fourier.txt, constant_ssat_fourier_shift.txt, Gap_Size_18_Coils.txt, vault.nc) — not a live path today but preserved with the same rigour. The recorded fit corpus is input/ITER/*.xlsx (CCL_Deformed_Coils, TFC18_asbuilt, TFC1_CL…) and data/Assembly/. nova/structural travels with assembly (fiducialdata/asbuilt/ansyspost are imported by the fitting cluster). This code supports live ITER work; its behaviour must be provably unchanged across every branch and repo move.

Acceptance gate is tolerance-based, not byte-identity. The requirement is agreement to 3 decimal places on mm measurements (1 µm absolute) for positional, gap, and deviation outputs — well below the measurement noise floor — with a per-quantity tolerance table for non-length outputs (angles, spectral coefficients, GP hyperparameters) derived the same way: at least two orders below the physical noise of that quantity. Byte-identity was the original proposal and is retained only as a free fingerprint: under the pinned environment (single-threaded BLAS, fixed seeds, captured uv.lock) outputs are usually byte-stable, so the sha256 manifest doubles as a cheap change detector — a hash mismatch triggers the tolerance comparison rather than failing the gate. This keeps the gate meaningful across BLAS/dependency bumps without re-baselining ceremony.

Characterization harness (lands on main before any branch surgery): inventory every fitting entry point (sector fit, pit fit, relative fit, CCL transform, winding-pack fit, GP predict, vault spectral proxy, gap asymmetry); run each on its recorded inputs; serialise canonical outputs (float64 arrays, sorted-key .npz/netCDF, deterministic layout); record a manifest of input digests, entry point, output artifact + digest, tolerance class, and environment-lock hash. Excel fixtures load via openpyxl cell values (full float precision, never display strings); assertions run on canonical arrays, never on xlsx bytes.

Test pyramid (assembly currently has almost no tests — only test_assembly.py and test_transform.py — so the port builds one):

  • Kernel unit tests — GP kernel evaluation and regression against analytic cases, rigid-body/quaternion transforms (round-trip, composition), Fourier gap-proxy identities. Synthetic, milliseconds, no data files.
  • Invariance property tests — fits invariant under fiducial-order permutation and global frame rotation/translation; transform → inverse-transform round-trips at 1 µm.
  • Component tests — each fit entry point over a small recorded fixture, gated at the tolerance table. Fast lane, runs on every commit.
  • Replay lane — the full recorded corpus re-fit and compared against the manifest. Slower; runs on demand and in the extraction gates.

Data registry (the corpus does not belong in the repo — but it must be versioned): recommended shape is OCI artifacts on GHCR pushed with ORAS — content-addressed digests (immutable, exactly what the run records below need), tags per campaign, private packages under the existing GitHub org/auth, no repo bloat, trivially pullable in CI. Alternatives on the assembly-data-registry decision: git-lfs (simplest, but quota-priced and couples data churn to the repo), private GitHub Releases (simple, coarse-grained), DVC (adds a tool dependency; useful if data science workflows grow). The goldens manifest references corpus items by digest, so the registry choice is swappable later.

Run records and replayability: every production alignment emits a run-record artifact — code git sha (+ dirty flag), uv.lock hash, input-data digests, fit-configuration hash, outputs with their tolerance class, timestamp, operator — stored beside the outputs and pushed to the registry. An alignment is replayable by construction: restore the lock, check out the sha, pull the digests, rerun, compare within tolerance. Fit-parameter control across coils: per-coil/per-campaign fit configurations (GP lengthscales, nuggets, weighting, constraint switches) become versioned, schema-validated declarative files whose hash enters the run record — no parameter lives only in a script or a notebook. This is the same provenance pattern nova's IMAS metadata stamping already uses, applied to metrology.

Excel decoupling comes after the transfer, deliberately. One change at a time: the port moves code with behaviour pinned by the harness; the internal data store (netCDF/parquet, replacing Excel as operational interchange) is designed afterwards in the assembly repo, seeded by the harness's Excel→canonical reader, which is precisely the ingest layer that store will need. The recorded goldens are never converted — they are the record.

Independence from nova: yes, and cheap. The audited import surface of nova/assembly into the nova core is tiny — definitions.root_dir, the Plot/Plot1D/2D mixins, database.netcdf/filepath cache utilities, utilities.time.clock, and geometry.line/polygon — a few hundred lines to vendor (the fieldless Plot mixin copies verbatim; the geometry bits sit on shapely/scipy). With nova/structural travelling alongside, the assembly project targets zero nova dependency: its stack is numpy/scipy/scikit-learn/pyquaternion/openpyxl/xarray + vendored helpers.

Hardened extraction sequence (belts + braces): (1) harness + manifest green in nova CI on main; (2) cut legacy/v1 + tag, branch-protect; (3) corpus pushed to the data registry, digests recorded; (4) create the assembly repository via git filter-repo so nova/assembly + nova/structural + their data/input trees carry full history; (5) the same suite runs in the new repo against the same manifest — the tolerance gate that must pass before the new repo is canonical; (6) dual-run window with both CIs green; (7) wheel-install check; only then does assembly work switch homes and nova main drop the assembly tree. The full port program (test pyramid build-out, registry setup, run-record tooling, store redesign) is authored as a dedicated repo-local plan; this section holds the baseline protocol and its gates.

Done-when: harness + manifest green on nova main; baseline tag + protected branch exist; corpus versioned in the registry by digest; the new assembly repo passes the manifest at the 1 µm gate; dual-run window observed; dedicated assembly-port plan authored; extraction sign-off recorded here.

§3 — Columnar frame core

Port the frame layer onto a typed columnar store, preserving the public API surface consumers actually use (insert, Loc/sLoc/loc/sloc label indexers, aloc/saloc array accessors, += union, store/load):

  • Carry near-verbatim: MetaFrame (schema, ~90 column defaults, column groups, locks, version hashes), Energize (It ⇄ Ic·nturn), SubSpace (independent-DOF projection with subref/factor mapping), Select, MultiPoint, the metamethod loader.
  • Replace: the 7-deep pandas subclass tower and the runtime-manufactured private-API indexers (nova/frame/indexer.py) with explicit accessor objects over {index: ndarray, columns: dict[str, ndarray], schema} — the shape the hot path already has in metaframe.data. Row insertion becomes array concatenation; label lookup is index get_loc + slice.
  • Shims: to_pandas() / to_xarray() exports; xarray→netCDF/zarr persistence for frames at rest (replacing the pandas round-trip in frameset.store).
  • Geometry columns (shapely poly, vtk) stay object-typed columns with the existing lazy loads.

Done-when: nova's frame test files (test_frameset, test_framespace, test_framelink, test_dataarray, test_energize, test_select, test_multipoint, …) pass against the new store; a coil-construction micro-benchmark shows construction no slower than the pandas path; zero pandas imports in nova.frame.

§7 — IMAS IO layer (standard names)

  • Name semantics come from ISN/ISNC — nova owns no standard-name schema. The controlled vocabulary, grammar, units authority, and DD-path links live in the already-managed imas-standard-names (ISN — machinery: strictyaml/pydantic/pint validation, name API) and imas-standard-names-catalog (ISNC — the catalog: data-only, zero runtime deps, pre-built SQLite, 18 domain files including equilibrium and both magnetics domains). Both are fork RCs converging on a first upstream release. Spine signals missing from the catalog are contributed to the ISNC fork (it stabilises fast), never authored as a nova-side YAML. What nova.io keeps is strictly the consumption side: the zarr store layout, the ingest/egress transcoders, the round-trip validators, and the application of codex-discovered facility-signal → standard-name maps.
  • Dependency mechanics on the fork RCs (recommendation): primary path is test-PyPI wheels with uv explicit index pinning — [[tool.uv.index]] entry for test.pypi with explicit = true plus [tool.uv.sources] routing only imas-standard-names/imas-standard-names-catalog through it, exact ==X.Y.ZrcN pins — this rehearses the very packaging path the upstream release will use and gives consumers real wheel semantics, while explicit indexing prevents test.pypi from leaking into any other resolution. Fallback wherever test-PyPI friction bites (retention, publish overhead): git-tag pins on the forks (pkg @ git+https://…@vX.Y.ZrcN — the pattern ISNC's own dev group already uses for ISN). Vendoring a catalog snapshot into nova is rejected (schema drift — the exact failure the user's correction forecloses). Convergence: when the upstream PR lands and releases to real PyPI, the pins flip to normal PyPI ranges (>=1,<2) in one commit. Two hardening items to land in the forks before upstream release: move ISN's fastmcp hard dependency to an [mcp] extra (the spine needs name lookup + pint units, not an MCP server stack), and reconcile the python floor — ISNC requires >=3.13, so nova 2.0's floor becomes 3.13 (harmless here; ambix already runs 3.14) unless ISNC relaxes to 3.12.
  • Ingest transcoder: whole-IDS full get() + bulk extraction (lazy get for selective channels) → standard-name-keyed zarr/xarray signal store, reusing the AL tensorizer semantics; cache keyed by URI + DD version.
  • Egress: IDS assembly from arrays via IDSFactory + single put() (HDF5 or netCDF); coordinate-ordering handled so validate() passes.
  • Streaming seam (interface now, implementation later): ring-buffer signal API compatible with memory-backend put_slice feed for real-time-adjacent operation.
  • The zarr signal store is the primary data plane, not just a cache ("IMAS in all but AL"): world-model training loaders and the spine both consume the standard-name-keyed tensorized zarr store directly; true IMAS pulses (HDF5 / IMAS-netCDF) are the interchange format materialised at the boundary by the egress builder. Guardrail: a round-trip test (zarr → IDS → validate() → zarr) runs in CI so the store cannot drift into a private schema; COCOS/units/provenance are carried as store attrs.
  • Placement in the codex → distil → ambix pipeline (io-contract-home decision): imas-codex discovers facility data and generates the mapping transformations (the standard-names LLM pipelines build off it); imas-ambix distils to the tensorized store and trains. The four-layer split: name semantics in ISN/ISNC (managed there, hardened there — see above); store mechanics — zarr layout, ingest/egress transcoders, round-trip validators, machine-description ingest — in nova.io, depending on ISN/ISNC; facility mapping discovery in codex (emitting maps that validate against ISN's published schema, no nova dependency); distil pipelines in ambix. No new repository is created — the "third repo" for semantics already exists as ISN/ISNC.

Done-when: a MAST or ITER test shot ingests once and re-reads at cached-store speed (≥100× the AL full-get, per the measured baseline); a synthetic run's results egress as a valid IMAS equilibrium IDS readable by imas-python at the written DD version.

§ Decisions

Repository mechanics — three viable routes: (a) new imas-nova repo populated by curated transfer (clean dependency/CI baseline; nova untouched); (b) in-place major refactor of nova — current state parks on a protected legacy branch (assembly work continues there, destined for its own repo), main becomes the refactored core as a 2.0 (keeps the nova name, identity, history, and test set; assembly branch is frozen against the old frame API until extracted); (c) rename nova → imas-nova and strip later. The refactor content is identical in all three — this decision is identity, history, and branch-discipline mechanics.

User decision 2026-07-23: keep nova's name, identity, history, and core test set; assembly is live and continues on the 1.x line while the 2.0 core refactor proceeds on a separate branch; assembly later extracts to its own repository with a hardened byte-identity gate (belts + braces: frozen baseline branch AND golden characterization suite carried to the new repo).

Identity-cache storage backend: zarr store (recommended — group deletion works, matches ambix's existing dependency, chunked/lazy reads) or keep nova's netCDF-group layout (proven, but eviction rewrites whole files)?

User confirmation 2026-07-23: content-hash keyed zarr store — native group deletion/eviction (netCDF4 cannot drop groups; nova today rewrites the whole file), chunked lazy reads, and one store technology shared with the standard-name signal data plane. Operators remain exportable to netCDF for interchange.

Frame-core migration path: build the columnar store directly (recommended — the SoA store is already latent in metaframe.data and the consumer API is narrow) or ship a composition-over-pandas wrapper first and hollow it out behind the accessor API?

User confirmation 2026-07-23: build the SoA columnar store as primary from day one — it is already latent in metaframe.data + ArrayLocIndexer, the external API is narrow (insert, Loc/sloc, aloc/saloc), and nova's transferred frame tests are the acceptance suite. One rewrite, no interim pandas dependency, immediate convergence with the JAX pytree shape.
