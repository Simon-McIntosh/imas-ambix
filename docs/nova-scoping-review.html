§1 — Executive summary and recommendation

Recommendation: create a new, importable imas-nova package — nova's extracted equilibrium core plus imas-ambix's curated physics elements — and make it the shared physics spine that both projects consume. Do not import nova as-is (dependency stack + pandas weld), and stop the piecewise porting (the duplication cost is real and already visible three times over). The evidence from six parallel code-review streams (nova frame, nova biot, nova imas/caching, nova triage, ambix census, IMAS IO benchmarks) converges on four load-bearing facts:

  • The split out of nova is unusually cheap. There are zero live import-time dependencies from the keep-set (biot, frame, imas, geometry, jax, linalg, database, graphics, utilities, control — ~35k LOC) into the leave-set (assembly, structural, thermalhydralic, dina, design, projects — ~55k LOC). Only three cosmetic __main__-guarded demo imports cross the line, and nova's own wheel build already excludes the leave-set (pyproject.toml:133-142).
  • The pandas weld does not reach the hot path. Nova's per-timestep loop is already numpy: dynamic quantities (Ic, nturn) live in a nova-owned numpy dict (metaframe.data) behind the aloc/saloc accessors, evaluation is a single matvec, and a jitted JAX operator (nova/jax/operate.py) already exists. Pandas is the construction substrate and labelling convenience — replaceable by a typed columnar store without touching the physics.
  • The porting strategy is already paying a duplication tax. ambix has re-implemented nova's cylinder kernel, its line/arc 3-D Biot–Savart, and its null-finder; meanwhile the polygon-section kernel flowed the other way (ambix completed what nova abandoned at an assert False stub). Two codebases, one author, three re-derivations and counting.
  • The IO wall is AoS reconstruction, not disk. Measured: a 400-slice/15 MB equilibrium costs 530 ms via HDF5 full get() but 53 ms via the netCDF backend and ~1 ms via warm xarray reads of the same bytes; lazy get is ~100×. A standard-name-keyed flat signal cache with the Access Layer only at ingest/egress removes the blocker for a real-time-adjacent spine.

Nova keeps its name and remains the home of the ITER machine-assembly and structural work (its recent commit history is entirely assembly-side); once imas-nova is stable, nova can depend on it and shed its duplicated core — the dependency then points the right way (assembly → physics spine, matching the existing one-way leave→keep import direction). The detailed staged transfer is in the companion plan imas-nova-transfer.

§2 — The two codebases today

Nova (~100k LOC) is two projects in one repository. The equilibrium core — biot (6.8k), frame (7.3k), imas (10.7k), geometry (4.9k), jax (1.6k), linalg, database, graphics, utilities, control — totals ~35k LOC. The ITER machine-assembly and structural analysis side — assembly (16.9k), projects (23.7k), structural, thermalhydralic, dina, design — totals ~55k LOC and is where all recent development activity sits (SSAT targets, fiducial assessment, gap analysis). The full cross-import audit found exactly three keep→leave references, all inside if __name__ == "__main__" demo blocks (frame/itergeom.py:227, geometry/polyline.py:652, geometry/frenet.py:194) — dead at import time. All leave→keep imports run the safe direction. Nova's hatch wheel config already excludes the leave-set, and its coverage config matches: the packaging boundary of imas-nova is already half-drawn inside nova itself.

imas-ambix carries ~8.6k LOC of pure numpy/scipy EM kernels and machine description in imas_ambix/gs/, plus ~13k LOC of physics inside imas_ambix/latent/ (the JAX free-boundary GS solver, connectivity boundary/LCFS, flux-surface averaging, null finding, boundary reads), alongside the ML stack (model/train/worldmodel/tokenizer/statespace, ~50k+). The layering is verified clean: gs/ imports nothing from latent/ or the ML side; latent/ imports gs/ downward; the sole ML→physics seam is the tokenizer reading geometry features (tokenizer/geometry_reader.py:36). Nova appears only as an importorskip-guarded test oracle — never a runtime import.

The duplication ledger (same author, both sides):

  • gs/cylinder.py re-implements nova's biot/{constants,cylinder,zeta}.py (docstring: "extracted from the nova.biot cylinder formulation… validated against golden values generated from nova itself").
  • gs/filaments3d.py re-implements nova's biot/{line,arc}.py + geometry/{polyline,rdp}.py.
  • latent/stencil_nulls.py ports nova.jax.select; latent/topology.py re-derives nova/biot/fieldnull.py.
  • Reverse flow: gs/polygon.py completes the Urankar Part V polygon-section Green's function that nova's biot/polygon.py abandoned mid-implementation (assert False at polygon.py:124) — the newest and only place where ambix leads nova on kernels.
  • ambix even duplicates itself: gs/elliptic.py re-implements cylinder._ellipp and is dead in production.

§3 — The pandas weld: anatomy and replacement verdict

Nova builds a seven-deep DataFrame subclass tower — pandas.DataFrame → FrameAttrs → DataFrame → DataArray → FrameLink → FrameSpace → BiotFrame — each layer overriding __getitem__/__setitem__/__setattr__. Three design facts determine the replacement strategy:

  • Metadata lives beside pandas, not inside it. The schema (~90 physics column defaults, units, column groups), the lock machinery, and the fast-access cache are all held in a plain MetaFrame dataclass stored in frame.attrs (metaframe.py:73). The service layers — Energize (It ⇄ Ic·nturn coupling), SubSpace (independent-DOF projection), Select, MultiPoint — are plain dataclasses that reference a frame. They survive any store swap almost verbatim.
  • The hot path already bypasses pandas. "Array" columns (Ic, nturn, plasma flags) live as numpy arrays in metaframe.data; the aloc/saloc accessors read/write them directly; operator evaluation is source_target @ saloc["Ic"] (biot/operate.py:51); cache invalidation is an xxhash of the numpy buffer. Zero pandas per timestep.
  • The genuinely fragile construct is not CoW — it is the indexer metaprogramming. frame/indexer.py:26-42 manufactures subclasses of pandas' private pandas.core.indexing._LocationIndexer at runtime and injects per-layer mixins. That breaks unpredictably across pandas minors regardless of CoW. The actual CoW-incompatible call sites are few (~a dozen: .values assignment at dataframe.py:311, subclassed inplace=True at dataframe.py:86 and framelink.py:204) and sit on the construct/store path, not the compute path. Notably, the triage grep found no API-removal forcing the pandas<2.2 pin — it is precautionary headroom around exactly these idioms.

The consumer surface is narrow and columnar: across nova, frame access is dominated by columns-as-numpy-arrays (aloc/saloc, ~104 sites), label reads/writes of currents (sloc/Loc, ~99 sites), and coil construction (.insert(, 129 sites). Genuine relational operations are rare and confined to nova/imas/ glue. The Biot subsystem touches geometry through exactly one method (BiotFrame.__call__, tiling a column into a (target, source) matrix) and imports pandas directly in only one file (biot/reduce.py, for an Index).

Verdict on the data model (options ranked):

  1. Typed columnar store (recommended). Promote what already exists — metaframe.data + the MetaFrame schema + the array accessors — to the primary store: index: ndarray[str], columns: dict[str, ndarray], schema. Construction becomes array concatenation; label reads are get_loc + slice (both already implemented in indexer.py:113-137 / framesetloc.py:35-60). Pandas disappears from every evaluation-path operation; the manufactured private-API indexers are deleted; the metamethod/subspace/energize dataclasses carry over nearly unchanged. Where a migration cushion is wanted, a composition wrapper (plain DataFrame held as an attribute behind the same insert/Loc/aloc API) is the intermediate step — consumers never see the difference because they already go through the accessors.
  2. xarray — yes, but only at the boundaries. Nova already stores solved Biot operators as xarray Datasets and serialises frames through to_xarray → netCDF. Keep and extend that: xarray is the right at-rest and interchange format (and the right shape for the IO layer in §6). It is the wrong primary row store: one-coil-at-a-time insert is its worst access pattern, the frame's heterogeneous dtypes (strings, bools, floats, shapely poly objects) fight its model, and label-alignment overhead lands exactly where the numpy cache exists to avoid it. The empty nova/xarray/ directory was an accessor experiment (renamed to nova/dataset/), not an abandoned store migration — the historical intent matches this verdict.
  3. Fixing pandas subclassing in place — rejected. Pandas 3.0 makes CoW mandatory and the private indexer surface keeps moving; the maintenance tax is unbounded and buys no architectural improvement. Polars is also rejected: immutability and the absence of numpy-view aliasing defeat the in-place Ic/cached-operator design, and there is no object dtype for shapely geometry.

§4 — The Biot subsystem: what extraction looks like

The element zoo is mature and tested: circle (complete elliptic), cylinder (rectangular section, K/E/Π + zeta quadrature — the kernel ambix already extracted), arc and bow (3-D filament/rectangular-section arcs, incomplete elliptic + Jacobi), line and beam (closed-form 3-D straight elements). The shared constants.py coefficient library (Carlson-form Π on elliprf/elliprj, singularity nudging) is the crown jewel and is nearly dependency-clean already. Validation runs against analytic solenoid fields and ITER sub-inductance matrices (tests/test_biotsavart.py and friends — a real regression net that transfers).

The operator architecture is the part ambix has not re-implemented and should not: per-element Green's matrices (matrix.py:245-292) fold turns and reduceat grouping/link reduction, while splitting the plasma row/column/corner into separate unit-turn sub-matrices; the ensemble assembler (solve.py) stores the four-block decomposition; and Operator.update_turns (operate.py:61-82) rewrites only the plasma blocks when the separatrix moves — ~99% of the coupling matrix is never recomputed. Version-hash guards (xxhash of the Ic buffer, nturn version counters) drive invalidation. This is the "update the plasma turns matrix dynamically while not touching the other calculated aspects" capability, and it is already numpy-native end to end.

The serial-topology complaint is already half-solved inside nova. The wired-in biot/fieldnull.py is a numba double-loop Kuijper saddle-count with per-null Python refinement — serial, unbatchable, non-differentiable. But nova/jax/null.py + jax/topology.py re-implement the same categorisation with lax.scan/vmap, fixed-size outputs, limiter/diverted adjudication under lax.cond, and demonstrated jax.grad through the O-point position — all jitted, just never wired in (grid.py:22 carries the commented-out import). Combined with ambix's own device-native stack (gs_solve, connectivity_boundary, flux_surface_connectivity, stencil_nulls — built fixed-shape for vmap-over-shots), the batched topology problem is solved; the extraction just has to pick one canonical implementation per function.

Extraction shape: lift constants + the six kernels + the matrix/solve assembly near-verbatim; replace BiotFrame with a ~100-line data-provider protocol; adopt ambix's polygon.py and hybrid_greens blend as the canonical additions; delete the serial null-finder in favour of the JAX path; consolidate the three zeta implementations to one; add the missing shot-axis vmap. Effort is ~55% mechanical rebinding guarded by existing analytic tests. Top performance blockers to remove at extraction time: the serial null-finder wiring, the absent batch dimension, and the numba dependency in zeta.

§5 — IMAS integration, identity caching, and the plot mixins (the jewels)

Jewel 1 — machine-description compilation. Nova reads machine geometry via imas-python AL5 (URI + DBEntry, lazy-by-default) and maps the DD's geometry_type integers to typed cross-sections through a clean dispatch (machine.py:274-306: outline, rectangle, oblique, annulus, thick-line — with battle-earned multi-machine fallbacks for WEST and MAST-U data quirks). Builders for pf_active, pf_passive, wall, ELM coils and coils_non_axisymmetric compile a single coherent machine dataset. The geometry→shapely side lifts cleanly; only the frame-insert step is pandas-coupled and gets re-pointed at the columnar store.

Jewel 2 — identity caching of data and solved model. The cache key is a content hash: xxh32 over the identity attrs plus per-source IDS content hashes plus Biot discretisation, used as the netCDF group name; nova version and $IMAS_VERSION are baked into the appdirs cache path. On a hit, Operate.load_operators rehydrates solved interaction matrices directly — no recomputation. The miss handler is a clean try-load / except get+build+store. Carry this design wholesale, with three hardenings: canonical serialisation instead of str(dict) hashing; make the DD version part of the hash rather than only the path; and replace netCDF group-delete-and-rewrite (netCDF4 cannot drop groups) — a zarr store keyed the same way removes that wart and matches ambix's existing zarr dependency. Ambix's own cache experience reinforces the lesson: its SetupSignature-keyed .npz caches omit the geometry/coil-model version strings from the key and have already caused silent stale-reuse incidents.

Jewel 3 — inheritance-attached plotting. The pattern the user values — downstream classes inheriting rich plot/processing methods — works because Plot (graphics/plot.py:341-485) is a fieldless, __post_init__-less dataclass mixin: placed leftmost it never disturbs the cooperative init chain, and its state is lazy cached_property. Keep it verbatim. Two tidy-ups on the way in: standardise the cooperative __post_init__ termination (the guard idiom appears 19 times, inconsistently), and pick a single plotting-attachment mechanism (today the Plot mixin coexists with a parallel metamethod loader — the main comprehension hazard in the MRO).

§6 — IO layer: measured reality and the standard-names architecture

Benchmarked on this venv (imas-python 2.2.0, IMAS-Core 5.7.0, DD 4.1.1) with a synthetic 400-slice / 15 MB equilibrium written to both backends:

Key facts for the architecture: the netCDF backend already performs exactly the AoS-flattening the spine wants (each DD leaf becomes one dense variable, AoS index promoted to a leading dimension) and its files open directly in xarray via group="equilibrium/0"; imas.util.to_xarray does the same from memory. Lazy get(lazy=True) is ~100–300× for subset reads (read-only objects, DBEntry must stay open). put_slice works on memory/HDF5/MDSplus (0.14 ms/slice measured) for incremental writes in increasing time order; the netCDF backend is batch-only. The IMAS Standard Names project (iterorganization/imas-standard-names + catalog) provides versioned per-quantity names with units and DD-path links — young and incompletely covered, so imas-nova should own its mapping table (versioned YAML: standard_name → ids, dd_path, occurrence, unit, cocos), seeded from the catalog and contributed back opportunistically, rather than depending on upstream completeness.

Recommended IO architecture (three boundaries; the Access Layer never in the hot path):

  • Ingest, once per shot: whole-IDS full get() + bulk numpy extraction (never per-slice loops), or lazy get for a few channels; transcode immediately into a standard-name-keyed zarr/xarray signal store (reusing the AL's own tensorizer). Warm re-reads then cost ~1 ms/variable instead of 530 ms — the transcode pays for itself the second time a shot is read.
  • Hot path: dense numpy/JAX arrays and device buffers only; for live operation a ring buffer fed by memory-backend put_slice or direct appends.
  • Egress: assemble fresh IDSs via IDSFactory and put() once at end of run (true IMAS data out); put_slice is the sanctioned path for streaming write-out later.

This answers the netCDF-vs-AoS concern directly: the AoS layout does not invalidate the netCDF layer — the backend's tensorization is precisely the flat representation needed, and the measured 10× win over the HDF5 AL read confirms it. The per-signal standard-names interface then addresses signals physically while a single owned mapping table is the only component that knows DD paths.

§6a — "IMAS in all but AL": the zarr store as the primary data plane (assessed 2026-07-23)

Verdict: workable, and the right call for the training workload. The proposal — store data tensorized in zarr object stores under Standard Names, with true IMAS materialised only at the boundaries — is the §6 ingest cache promoted from cache to canonical data plane, and the measured numbers justify the promotion: at 4.5 TB / H200-training scale the AL cannot sit in a loader path (530 ms per AoS-reconstructing get vs ~1 ms flat reads; the WM loaders already train from FAIR-MAST zarr today, so for MAST the pipeline is zarr→zarr re-keying plus unit/name normalisation — the AL enters only for ITER/WEST-style sources and for egress). Semantically nothing is lost: the transform is the same tensorization the IMAS netCDF backend performs (dense arrays, AoS index promoted to a leading dimension), just held in zarr and keyed by standard name instead of dot-joined DD path.

Interoperability — the "converge on a single data model" requirement — is preserved by two disciplines, both cheap: (1) the owned, versioned mapping table (standard_name → DD path/unit/COCOS) is the only component that knows AoS layout, so the store remains mechanically convertible to a true IMAS pulse; (2) a round-trip CI test (zarr → IDS assembly → validate() → re-ingest) prevents the store drifting into a private schema — the known failure mode of "IMAS-like" stores. COCOS, units, and provenance ride as store attributes (nova's metadata.py stamping pattern). The single data model is then: standard-name-keyed tensorized xarray-on-zarr with DD-compatible metadata, consumed identically by the physics spine and the world-model loaders; IMAS pulses are the interchange format at the boundary, not the working format. This is recorded in the transfer plan's IO section as a strategy pillar rather than an open decision — no measured evidence points the other way.

§7 — Options analysis

Option A — import nova as-is and fix in place. Rejected. The dependency stack (30+ hard deps including a provably dead optax, abandoned descartes, and heavy viz packages), the numpy<2/pandas<2.2/py<3.13 ceilings, and the pandas subclass tower would all flow into the spine. Fixing nova-side means chasing pandas' private indexing API indefinitely while carrying 55k LOC of assembly code the spine never uses. (Worth noting: the numpy 2 ceiling traces to a single line, graphics/plot.py:614 — nova-side hygiene is cheap, but it doesn't change the architecture verdict.)

Option B — keep porting piecemeal. Rejected as the steady state. Three re-derivations have already been paid, the projects drift (ambix's polygon kernel and JAX topology improvements aren't reaching nova), and each new port re-solves operator assembly, caching, and machine description — nova's hardest-won, least-glamorous parts.

Option C — a shared imas-nova physics-spine package. Recommended. One canonical home for kernels, operators, machine description, identity caching, IO, and batched topology; ambix keeps the ML/GPU side and consumes the spine; nova keeps machine assembly and later consumes the spine too (killing the duplication permanently, and delivering the polygon kernel back to nova's users). On naming/mechanics: prefer a new repository populated by curated transfer over renaming the existing nova repo — nova's active assembly work and its ITER remotes stay undisturbed, the new package gets a clean dependency/CI/test baseline (numpy≥2, python≥3.12, no pandas in core), and git history for transferred files can be preserved where valuable. The name imas-nova aligns it with the imas-* family and states the IMAS-native contract.

§7a — Option C variant: in-place nova refactor on a branch (assessed 2026-07-23)

A third mechanics route, raised after the initial review: keep nova, perform the major refactor in-tree — the current state parks on a protected legacy branch (assembly development continues there, destined for extraction into its own repository), and main becomes the refactored core released as a 2.x. Verdict: workable, and competitive with the new-repo route. The refactor content is identical in either case (columnar frame core, provider protocol, JAX topology wiring, dependency prune); the decision is purely identity, history, and branch mechanics. What the in-place route buys: the nova name and identity are retained, the mature kernels keep native git history (blame/archaeology over constants.py and the element kernels has real value), the core test set stays in place, and the polygon/topology back-flow from ambix lands directly where nova's users are. The structural facts make it cheap: zero live keep→leave imports means the ~55k LOC leave-set can be deleted from the refactor branch on day one, and the wheel already ships only the core.

Two costs to accept with eyes open. First, the legacy branch is a freeze, not a fork that merges back: assembly imports the frame/geometry/graphics layers whose API the refactor rewrites, so assembly-side commits on the legacy branch can never merge into the refactored main — the branch is a holding pattern that only ends when assembly moves to its own repo (git subtree-split / filter-repo carries its history out cleanly). If assembly extraction slips indefinitely, the repo runs two permanently-diverged lines, which is the failure mode to guard against — put a date or trigger on the extraction. Second, version discipline: the 2.0 core breaks 1.x consumers (numpy ≥ 2, python ≥ 3.12, no pandas frame), so the legacy branch should be tagged as the 1.x maintenance line explicitly. The trunk-based multi-agent workflow also needs a temporary two-branch exception spelled out in nova's AGENTS.md. On balance: if the assembly-extraction commitment is credible, in-place refactor is the better expression of "nova supports imas-ambix" — one name, one history, no imas-nova/nova naming split; the new-repo route remains the safer fallback if the legacy-branch constraint proves awkward.

IMAS-interface cost under this route: small — it is one of the cheapest parts of the refactor. The AL hookup (dataset.py ladder, database.py, uri.py, metadata.py) is numpy + imas-python and carries unchanged; the identity cache carries with the three §5 hardenings; only the machine-compilation insert step re-points at the new frame store, behind an unchanged insert() signature. The genuinely new IMAS work (either route) is the standard-names mapping table + ingest transcoder + egress builders — bounded, and where the measured value is. Order weeks, not months; the frame-core rewrite is the long pole, not IMAS.

Risks and mitigations. (1) Big-bang risk — mitigated by the composition wrapper step and by nova's analytic test suite transferring first, so every kernel/operator port lands against known goldens. (2) Two-home drift during transition — mitigated by declaring imas-nova canonical per component as it lands and deleting the donor copy in the same series (no _v2 families). (3) torch-coupled physics in ambix's latent/ (patch basis, structure residual, current diffusion…) — physics by content, ML by dependency; these stay in ambix initially and migrate only when re-expressed on the spine's numpy/JAX API, so torch never enters imas-nova. (4) Standard-names immaturity — owned mapping table decouples the spine from upstream catalog pace.

§8 — Target architecture of imas-nova

  • Data model: typed columnar SoA frame core (schema from MetaFrame; subspace/energize/multipoint services carried); pandas absent from core (export shims only); xarray at rest and at interchange.
  • Kernels: nova's constants + circle/cylinder/arc/bow/line/beam + ambix's polygon and hybrid blend; one canonical zeta; provider-protocol seam instead of BiotFrame.
  • Operators: nova's four-block plasma decomposition, turns/reduce/link machinery, and dynamic-turns update; JAX evaluation as the primary path with a shot/time batch axis; numpy fallback.
  • Topology: the JAX null/topology/connectivity/FSA stack (merged nova-jax + ambix implementations), fixed-shape and vmap-safe throughout.
  • Machine description: IDS readers + geometry_type dispatch + compilation into the frame core; identity cache (content-hash keyed, version-segmented, zarr-backed) caching frames and solved operators.
  • IO: standard-name mapping table (owned YAML); ingest transcoder → zarr signal cache; egress IDS assembly + put; ring-buffer interface reserved for streaming operation.
  • Plotting: the fieldless Plot mixin family as the single attachment mechanism; matplotlib as an optional extra rather than a core import.
  • Tests: nova's ~72 keep-set test files + ambix's ~20 gs/latent physics test files, curated to a fast, no-live-DB unit lane (synthetic fixtures for the handful of DB-bound tests); asv benchmarks for operator assembly/evaluation carried over.

Full staging, section-by-section deliverables, and test-transfer detail live in the companion plan: imas-nova-transfer.
