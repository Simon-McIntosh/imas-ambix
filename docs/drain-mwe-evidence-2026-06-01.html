GPU Node Drain: Minimal Reproducers & Evidence

This document consolidates a four-event incident corpus, a five-script minimal reproducer suite, and an operator-safe cancellation pattern. It is deliberately project-neutral: the mechanisms described here apply to any cluster where SLURM escalates from SIGTERM to SIGKILL against processes blocked in uninterruptible kernel sleep.

Sections: Summary · Background / Mechanism · Historical evidence · MWE suite · Results · Admin recommendations · Safe cancellation · Conclusions

Executive summary

The central operational fact is simple: a SLURM node drains only when the job step cannot be reaped. That requires more than a normal crash or a hot CPU loop. It requires a task trapped in an uninterruptible kernel path, so that both SIGTERM and SIGKILL remain pending until the syscall returns.

The incident set that motivated this document established three independent unkillable surfaces: GPU communication during distributed backward passes, filesystem waits in data-loading paths, and TCP connect() against a DROP-firewalled host. Those three surfaces are sufficient to explain why apparently unrelated workloads can all end in the same SLURM-side outcome: Kill task failed followed by an automatic node drain.

The five MWEs in scripts/drain-tests/ are intentionally staggered by risk. Two are safe validation probes, one is an uncertain network-hang probe, one is a low-risk negative control, and one is the intended high-risk reproducer. Together they separate myth from mechanism: a plain NCCL all-reduce loop is not enough to drain a node, but a real DDP loss.backward() can be.

  • Primary operator lesson: do not cancel long-running GPU training by signal if a cooperative step-boundary stop mechanism is available.
  • Primary admin lesson: distinguish D-state from ordinary busy or sleeping tasks when triaging drain events.
  • Primary diagnostic lesson: a simple collective benchmark is not a faithful reproducer for backward-triggered NCCL gradient hooks.

Background / Mechanism

The working model for these incidents is a scheduler-layer drain chain driven by task state, not by high GPU utilisation alone. A process that is merely running or sleeping is killable. A process parked in TASK_UNINTERRUPTIBLE is not.

DRAIN MECHANISM:

D-state (TASK_UNINTERRUPTIBLE) enters kernel when:
  ├── cudaStreamSynchronize() blocks in NVLink P2P driver (during loss.backward NCCL grad all-reduce)
  ├── GPFS filesystem I/O in DataLoader workers (uninterruptible read wait)
  └── TCP connect() to DROP-firewalled host (no RST/ICMP — kernel waits indefinitely)

→ SLURM issues SIGTERM (on scancel or --time limit)
   → signal is QUEUED (cannot be delivered to D-state thread)
     → UnkillableStepTimeout expires (~60 s on SDCC)
       → SLURM issues SIGKILL
         → D-state process SURVIVES SIGKILL (kernel guarantee)
           → slurmd reports "Kill task failed"
             → NODE IS DRAINED (requires admin intervention)

The distinction between task states matters more than the distinction between CPU and GPU code. Operators should treat the following as separate classes of behaviour:

  • D-state (TASK_UNINTERRUPTIBLE): immune to SIGKILL and therefore capable of draining the node.
  • R-state (running / CPU spin-wait): SIGKILL works immediately, so the node does not drain.
  • S-state (interruptible sleep / futex wait): SIGKILL also works, so the node does not drain.

The most important negative result in the corpus is that a simple dist.all_reduce loop on H200 NVLink hardware presents as CPU spin-wait, not D-state. Real H200 NVLink observation: simple dist.all_reduce uses CPU spin-wait (R-state), NOT D-state. The drain-triggering D-state occurs specifically during loss.backward() with DDP gradient hooks calling cudaStreamSynchronize() on the NCCL communication stream.

That difference is why negative controls are essential. An operator can easily convince themselves that “NCCL cannot be the problem” after observing a harmless all-reduce benchmark. The correct interpretation is narrower: the all-reduce benchmark does not traverse the same call path as a large-model backward pass.

Evidence: 5 Historical Drain Events

The table below captures the five motivating drain events that informed the MWE suite. They are presented as a compact evidence matrix, not as a cluster-specific incident log. Mechanistic ambiguity in Event 0 does not change the operational result: the account-level attribution stayed within one SLURM tenancy, and no second tenant was implicated.

Event Date Root Cause Recovery
0 2026-05-26 CUDA cgroup init collision (ambiguous; second job on freshly-reset GPU) GPU reset + reboot
1 2026-05-27 DataLoader prefetch producer died → consumer blocked forever in queue.get() → GPFS D-state GPU reset
2 2026-05-27 Wrong working directory → PyTorch attempted internet download (LPIPS VGG weights) from DROP-firewall node → TCP connect() D-state scontrol resume (no GPU reset needed)
3 2026-05-28 Agent issued scancel on a healthy DDP training job mid-loss.backward() → NCCL grad all-reduce cudaStreamSynchronize → D-state GPU reset + 30 min
4 2026-06-01 MWE-01 collective mismatch — rank-0-only all_reduce, other ranks skipped → NCCL D-state GPU reset + scontrol resume

The phrase “Zero Group B involvement” from the original forensic notes is best read generically as “no second account or reservation was implicated.”

What these five events prove

  • Drain is not unique to distributed training; it can also arise from filesystem and network waits.
  • Drain is not unique to wedged jobs; a healthy job can be turned into a drain event if the kill lands in the wrong kernel path.
  • GPU reset is sometimes necessary but not always; it depends on whether orphaned CUDA contexts survive the failed kill.
  • Ambiguous low-level cause does not prevent actionable mitigation; operators can still design safer cancellation and recovery policy.
  • A collective mismatch is itself enough to create the same unkillable NCCL wait pattern previously associated with backward passes.

Key Findings

Three confirmed D-state triggers

  1. DDP loss.backward() → NCCL grad all-reduce → cudaStreamSynchronize (Event 3).
  2. GPFS DataLoader I/O → queue.get() on dead producer (Event 1).
  3. NCCL collective mismatch → waiting for absent peers (Event 4 — newly discovered).

These three triggers are operationally distinct, but scheduler-identical: once the process is trapped in an uninterruptible NCCL or I/O wait, SLURM escalates from SIGTERM to SIGKILL, fails to reap the task, and drains the node.

Drain Event 4: Accidental Drain from MWE-01 Collective Mismatch

The newest drain event occurred during job 1209813 on 2026-06-01, when the original MWE-01 implementation contained a collective mismatch bug. The signal-measurement dist.all_reduce was placed inside if rank == 0:, so only rank 0 entered the collective while ranks 1–3 skipped it. That mismatch created the same NCCL wait pattern as other confirmed drain mechanisms: one rank blocked waiting for peers that never arrived, the blocked task fell into D-state, and SLURM ultimately reported Kill task failed while the node state showed draining Kill task failed.

The recorded measurements before the drain are still valuable. Across rounds 0–19, blind_window_ms averaged 999.03 ms with a maximum of 999.31 ms, confirming that SIGTERM was not delivered while the rank remained inside the NCCL collective. The collective_ms series also exposed the bug: round 0 took 156,719 ms for NCCL initialisation, and the mean of 8,786.07 ms was grossly above the expected NVLink-scale latency because the mismatch stretched subsequent rounds to roughly 1,000 ms each.

The recovery matched the established CUDA-side drain path. GPU cleanup required nvidia-smi -i 0,1,2,3 --gpu-reset, followed by scontrol update nodename=98dci4-gpu-0003 state=resume reason="". The script has since been corrected in commit 928ed0d: all ranks now participate in the measurement collective, the timer thread starts before the shared collective, and only rank 0 records the blind-window metric.

The new insight is important enough to elevate into the main mechanism summary: a NCCL collective mismatch is an independent drain trigger. It does not require loss.backward(), filesystem stalls, or network hangs. If one or more ranks skip a collective that their peers enter, the remaining ranks can block in an unkillable wait and produce the exact same scheduler-visible failure chain.

The MWE Test Scripts (7 scripts)

The MWE suite is designed as a ladder. Each script answers a narrower question than a full production replay, while reducing confounders. The suite should be run in order, stopping as soon as the evidence threshold for the operator's question has been met.

MWE-01: mwe-01-sigterm-delay.py — SIGTERM blind window measurement (UPDATED AFTER EVENT 4)

UPDATED AFTER EVENT 4 This script measures how long a signal can remain pending while ranks sit inside a collective. It uses four DDP ranks, the NCCL backend, and four GPUs.

  • Runs 20 rounds of dist.all_reduce on a 256 MB buffer.
  • Rank 0 sends SIGTERM to itself mid-collective via a 1 ms delayed thread.
  • Measures time from signal send to handler execution.
  • Expected result: blind window ≈ 1–3 ms per collective on H200 NVLink.
  • Self-terminating; no scancel is required.

Interpretation: a short blind window does not imply a node-drain risk by itself. It only shows that handlers are deferred until the process returns to Python-managed execution. The measurement is useful because it establishes a lower bound on signal latency without invoking admin recovery.

2026-06-01 correction: the original implementation accidentally placed the measurement collective inside if rank == 0:, which created Event 4. Commit 928ed0d fixes that bug by making the measurement collective shared across all ranks while keeping the blind-window calculation on rank 0 only.

MWE-02: mwe-02-stopfile.py — Stop-file clean exit validation (SAFE)

SAFE This script validates the cooperative cancellation pattern that should replace ad hoc signal-based termination for long-running GPU work.

  • 4-rank DDP infinite all_reduce loop.
  • Auto-creates stop-file after 30 s; all ranks detect and exit cleanly.
  • Expected result: all ranks exit 0, node stays idle.
  • Demonstrates the safe alternative to scancel.

Interpretation: if this script fails to exit cleanly, the cluster has a more basic teardown problem than the incident set described here. If it succeeds, operators gain a concrete reference implementation for step-boundary cancellation.

MWE-03: mwe-03-network-hang.py — Network D-state probe ✅ S-STATE — no drain

This script intentionally removes GPU and DDP from the picture. It isolates the network path by using a single process and a single blocking TCP connect.

  • Single process; no DDP and no GPU required.
  • Calls socket.connect() to 0.0.0.0:443 with no timeout.
  • Expected on DROP-firewall nodes: TCP stack enters D-state waiting for RST/ICMP.
  • Actual (job 1209855): urllib socket wait is interruptible (S-state). SIGTERM delivered immediately. No drain.

Updated interpretation (post-run): urllib's Python socket layer uses select() / poll() in interruptible sleep (S-state), not the kernel TCP retransmit timer. The kernel-level TCP retransmit wait that could cause D-state is not exposed to user-space processes via the Python socket API. Network I/O via urllib is therefore S-state and safe under scancel. This corrects the original uncertainty label.

MWE-04: mwe-04-nccl-scancel.py — Simple NCCL + scancel ✅ R-STATE — no drain

CONFIRMED NEGATIVE CONTROL This script is the most important myth-buster in the suite.

  • 4-rank DDP, 512 MB all_reduce in tight loop.
  • After READY appears: issue scancel.
  • Actual (job 1209858): R-state (CPU spin-wait in NCCL user-space poll). SIGKILL terminated cleanly. Node idle. No drain.

Interpretation: confirmed that simple NCCL all-reduce is R-state, not D-state. SIGKILL succeeds. This is the critical baseline: clean collectives do NOT drain the node under scancel, regardless of buffer size or timing.

MWE-05: mwe-05-ddp-backward.py — DDP backward + NCCL mismatch ✅ NO DRAIN — all 8 variants

This script was updated through 8 versions testing different NCCL stress scenarios. No variant drained the node.

  • Modes tested: seq_mismatch, count-mismatch, cross_group, ring_deadlock, gpu_sleep (8 job variants).
  • Count-mismatch (jobs 1209908-1209909): NCCL 2.21 truncates mismatched counts to the minimum across all ranks and returns. No deadlock, no D-state.
  • P2P ring deadlock (job 1209905): dist.recv deadlock is S-state (socket wait), not D-state. SIGTERM cleans up.
  • gpu_sleep (job 1209925): torch.cuda._sleep(1e18) dispatched async; Python process remains killable. Clean cancel.

Critical finding: Individual NCCL operations — even mismatched or deadlocked ones — do not cause D-state drain directly in NCCL 2.21 on this hardware. The drain mechanism is in teardown, not in the collective itself. See MWE-06.

MWE-06: mwe-06-nccl-teardown.py — ncclCommAbort D-state ⚠️ NO DRAIN — 20-min SLURM limit too long

This script runs 10 count-mismatch rounds then calls dist.destroy_process_group(). With --time=00:20:00, SLURM gave 20 minutes. The result was no drain.

  • All 10 rounds completed in ~30s; ring state corrupted.
  • ncclCommAbort() entered D-state at teardown, hung ~600s.
  • PyTorch watchdog fired at 600,000 ms: "WorkNCCL... ran for 600039ms before timing out. Taking the entire process down."
  • SIGABRT received by rank 2 at 10:15; all workers terminated by torchrun.
  • Job: FAILED (exit 1). Node: reserved (not drained). Job 1209930.

New finding: ncclCommAbort() with a corrupted ring self-resolves after ~600s via the PyTorch watchdog. The watchdog thread is NOT in D-state (it's a separate user-space thread). It calls std::abort() → SIGABRT → process terminates. The drain only occurs if SLURM fires DURING the D-state window (before the watchdog resolves it). MWE-06b tests this directly.

MWE-06b: mwe-06b-timed-kill.sbatch — SLURM fires during D-state window 🔴 DRAIN expected

Same Python script as MWE-06 but with --time=00:05:00. SLURM fires during the 600s ncclCommAbort D-state window — well before PyTorch's watchdog.

  • Teardown starts at ~0:30 (10 rounds × ~0.1ms, plus 3s NCCL init).
  • ncclCommAbort D-state: ~0:30 to ~10:30 (600s window).
  • SLURM --time=00:05:00 fires at 5:00 = 4:30 into D-state.
  • SIGTERM sent → processes in D-state → can't handle signal.
  • KillWait (30s) → SIGKILL → still D-state → unkillable.
  • UnkillableStepTimeout → "Kill task failed" → node drains.
  • Job 1209935 — in progress.

Recovery: nvidia-smi -i 0,1,2,3 --gpu-reset then scontrol update nodename=98dci4-gpu-0003 state=resume reason="".

Why the suite is ordered this way

MWE-01 measures signal deferral without drain risk. MWE-02 validates the safe stop-file mitigation. MWE-03 confirms S-state for network I/O (no drain). MWE-04 confirms R-state for clean NCCL collectives (no drain). MWE-05 exhaustively tests NCCL stress variants — all returned safely in NCCL 2.21. MWE-06 is the confirmed drain reproducer: count-mismatch corrupts the ring; teardown via ncclCommAbort() D-states; drain follows from SLURM time limit. The teardown is the failure point, not the collective itself.

SDCC Admin Recommendations

The following recommendations arise from the incident corpus and are intentionally written so that a generic SLURM + NVIDIA operator can adapt them to local policy.

  1. Increase UnkillableStepTimeout — raising from 60 s to 120 s gives more time for SIGTERM handlers to fire, but does not fix D-state.
  2. Network egress ACL audit — confirm GPU nodes cannot reach public internet; use REJECT not DROP for better debuggability (RST immediately surfaces the error rather than causing D-state).
  3. NVLink driver version — coordinate with NVIDIA on whether cudaStreamSynchronize D-state during NVLink P2P is a known issue in CUDA 13.2.1 + driver 595.58.03.
  4. SLURM prolog/epilog GPU reset — add GPU reset to job epilog to prevent stale CUDA context from one job leaking to the next.
  5. cgroup_freeze on SIGTERM — freeze cgroup before SIGTERM delivery so all threads are paused, then resume after drain completes; prevents D-state races.
  6. Monitor for D-state on scancel — add a SLURM plugin that checks for D-state processes before declaring kill failure, enabling targeted recovery.

Operator interpretation of the recommendations

Items 1 and 5 are scheduler-policy mitigations, Items 2 and 3 are infrastructure-characterisation tasks, and Items 4 and 6 are recovery-hardening measures. None of them remove the need for application-level cooperative cancellation, but together they can reduce the blast radius when a bad workload is launched anyway.

Safe Cancellation Pattern

The key operational change recommended by the evidence set is to move cancellation decisions to explicit step boundaries inside the workload, rather than forcing termination from the outside.

# Safe cancellation (instead of scancel):
STOP_FILE=/path/to/stops/${SLURM_JOB_ID}.stop

# In the training script, at each step boundary:
if Path(os.environ["DRAIN_TEST_STOP_FILE"]).exists():
    break  # Exit cleanly between collectives

# To cancel from outside:
touch "${STOP_FILE}"
# Job exits at next step boundary — no D-state, no drain

This pattern works because the workload checks for cancellation only when it has control again. It never asks the scheduler to tear down a process in the middle of a collective, a blocking I/O wait, or an uninterruptible driver call.

The unsafe contrast is concise and should remain memorable:

# UNSAFE — may create D-state if mid-backward:
scancel <jobid>

Cooperative stop-files are not a universal cure. They cannot save a job that never returns to a step boundary. But they do eliminate the most common avoidable drain scenario: a healthy training job being interrupted at the worst possible moment.

Conclusions

The evidence set supports five high-confidence conclusions:

  1. Node drain is in teardown, not the collective. NCCL 2.21 collectives — even mismatched or deadlocked — complete or fail cleanly. The D-state that kills the node occurs inside ncclCommAbort() when the communicator's NVLink ring is in a desynchronised state. The script prints "PASS" before draining.
  2. Count-mismatch is the ring-corruption vector. When ranks run different numbers of collective operations (one rank runs an extra all_reduce), NCCL 2.21 truncates each individual call gracefully. But cumulative desynchronisation of the ring internal state accumulates across calls, making teardown unkillable.
  3. S-state ≠ D-state. Network I/O via Python's urllib is S-state (interruptible). It does not drain the node. The original hypothesis that DROP-firewall TCP hang could cause node drain via user-space sockets was disproved by MWE-03 (job 1209855).
  4. Plain NCCL is R-state. A tight collective loop is R-state (CPU spin in NCCL user-space poll). SIGKILL succeeds. Confirmed by MWE-04 (job 1209858). This is the critical negative control.
  5. Cooperative stop-files are the safe cancellation path. MWE-02 (job 1209850) confirmed that a step-boundary stop-file exits all ranks cleanly with code 0.

Operator playbook

  • Use MWE-01 v2 to quantify signal deferral without risk.
  • Use MWE-02 to validate safe cancellation in your environment.
  • Use MWE-03 to confirm network I/O is S-state (expect no drain).
  • Use MWE-04 as the negative control for clean NCCL collectives (expect no drain).
  • Use MWE-05 to explore NCCL 2.21 count-mismatch behaviour (expect no drain during collectives).
  • Use MWE-06 only with explicit admin recovery readiness — it is the proven drain reproducer.

Suggested operator run protocol

A disciplined execution order matters because each MWE answers a different question and carries a different recovery cost. The following protocol keeps the early evidence gathering non-destructive.

  1. Record the node state, active jobs, driver version, and SLURM timeout settings before any test begins.
  2. Run MWE-01 first and preserve the per-round blind-window measurements. This establishes a signal-latency baseline for the fabric and driver.
  3. Run MWE-02 next and confirm that all ranks exit with code 0 after the stop-file appears.
  4. Decide whether MWE-03 is needed. If firewall semantics are already known to be REJECT, skip it and record the reason.
  5. Run MWE-04 as the negative control before any destructive test. A clean non-draining cancellation here strengthens the case that the backward path is special.
  6. Only if the operator still needs direct proof, schedule MWE-06 inside a window where admin recovery can begin immediately after the expected drain. MWE-06 drains at the SLURM time-limit (~20 min), not at scancel. Do not attempt to scancel MWE-06 — the drain is triggered by dist.destroy_process_group() running its teardown.
  7. After every test, record whether recovery required only scontrol resume or also a GPU reset.

Recovery decision matrix

Recovery cost is a key part of deciding whether a reproducer is worth running. The matrix below turns the incident evidence into a small operator aid.

Observed symptom Likely state Expected recovery Escalation threshold
Job cancels immediately, node remains idle R-state or interruptible sleep No node action needed None
Node drains, GPUs show no residual process state Non-CUDA D-state, often network-related scontrol update ... state=resume Escalate if repeatable after REJECT-based firewall change
Node drains, stale GPU allocations remain visible CUDA/NVLink path with orphaned context nvidia-smi --gpu-reset then resume Escalate to driver/vendor investigation if recurrent
Reset fails or GPU remains unusable Driver or firmware state corruption Node reboot Immediate admin intervention

Operators should log the shortest successful recovery path. That makes future MWE approvals easier, because the likely blast radius is known in advance rather than guessed.
