§1 — Overview: does a differentiable topology read cure the per-solve accelerator?

The hypothesis this plan tests. greens-filament-solver §4 (shipped 2026-07-20) reached an honest negative on the CPU throughput gate: no per-solve fixed-point iterator — relaxed Picard, safeguarded Anderson, or Newton–Krylov — clears ≥3×. It localised the cause to a single wall: the free-boundary solve re-reads the magnetic axis and the axis-connected core mask every sweep with hard-threshold host primitives (find_critical_points + ndimage.label). That read is non-differentiable, so finite-differencing the residual across a discrete mask flip corrupts Newton–Krylov’s Jacobian-free GMRES; the same mask-flip noise corrupts Anderson’s least-squares history; and the under-determined interior-null slices limit-cycle around ~1e-3 while the axis drifts to its Shafranov-shifted fixed point. The measured signatures: safeguarded Anderson gives ~1.3× on the well-posed slices only; NK diverges on 2/5 fixed-shape slices (axis 47–70 cm off). The prediction that follows is precise: make the topology read continuous and differentiable and the accelerators should converge cleanly — the mask no longer flips, the map is smooth, NK gets a clean Jacobian and Anderson a clean history.

The unblocker already exists. connectivity-topology-reader builds exactly the read this needs: a connectivity flood-fill boundary + a smooth core mask, continuous through the marginal limited↔diverted transition by construction, GPU-native and differentiable. This plan is the follow-on that consumes it on the CPU solve and closes the accelerator question.

Why a distinct plan (not folded into gpu-accelerated-labeler). That plan’s thesis is deliberately that per-solve GPU is a dead end and the throughput comes from batching over shots; putting a CPU-first, per-solve accelerator study inside it would muddy that clean argument. This experiment is conceptually separate: it isolates the accelerator effect of a differentiable map from the batching effect, settles the fixed-point-scheme choice, and validates the §4 causal claim as a first-class result. Its finding then informs gpu-accelerated-labeler’s inner-solve design (which assumes the warm-started inner fixed point converges in a small fixed budget).

§2 — Wire the differentiable read into the free-boundary solve; confirm the map is smooth

Replace the hard-threshold core-mask / axis read inside the free-boundary fixed-point loop (solve_equilibrium_lsq and the shared _read_axis / core-mask step) with the differentiable connectivity read from connectivity-topology-reader (smooth core-membership + soft level), as an opt-in path so the hard-mask solve stays byte-unchanged when off. The point is not speed yet but smoothness: the fixed-point map must become differentiable so the residual decreases monotonically instead of limit-cycling as the discrete mask flips. Gate D-A: on held-out slices the smooth-mask solve reproduces the hard-mask converged equilibria (axis / LCFS / profile) to tolerance on the well-posed population, AND the previously-limit-cycling under-determined slices (the §4 k4/k6 class) now show a monotone residual decrease under plain relaxed Picard (the mask-flip signature is gone) — the direct test that the map is now smooth. Stop rule: if the smooth mask cannot reproduce the hard-mask equilibria, STOP and surface (a lossy mask would corrupt the labels).

§3 — Retest the accelerators on the differentiable map (NK vs Anderson vs warm-Picard)

Re-run the §4 accelerator A/B on the now-differentiable map: relaxed Picard (baseline), safeguarded Anderson, and Jacobian-free Newton–Krylov, per-slice, reporting sweeps/matvecs to convergence, wall, and byte-comparability of the converged equilibrium — on the well-posed slices AND the previously-under-determined ones that a smooth map may now make solvable. Report against the frozen §4 CPU baseline (Anderson ~1.3× well-posed; NK erratic). Gate D-B: at least one accelerator converges the previously-limit-cycling slices cleanly and materially faster than relaxed Picard on the differentiable map, byte-comparably — validating the §4 causal hypothesis — OR an honest negative that the smoothness alone does not close the gap, localising the residual bottleneck. Quantify how close CPU per-solve now gets to ≥3× vs the §4 baseline. This §3 A/B settles the map-accelerator decision.

§4 — Verdict + hand-off to the GPU path

State the CPU per-solve verdict plainly: does a differentiable map let a per-solve accelerator clear (or approach) ≥3× on CPU, or is the throughput multiple still batching-bound? Either way the finding informs gpu-accelerated-labeler: if an accelerator wins on the differentiable map, it is the inner-solve accelerator the batched rollout should use (and CPU per-solve is a usable fallback); if not, the batched-over-shots GEMM is confirmed as the only route to the corpus throughput. Record the implication for the on-device rollout’s inner fixed-point budget.

§ Decisions

On the differentiable map, which fixed-point accelerator is adopted (and which retained as fallback)?

OPEN — to be settled by §3 on measured per-slice convergence + wall on the differentiable map. §4 (greens-filament-solver) locked "NK-primary" BEFORE the CPU ceiling was known and then measured NK erratic on the non-smooth map; this plan resolves the choice on the map the accelerators are actually meant for (a smooth one).

Does the differentiable (smooth-mask) read become the solve default, or stay opt-in?

OPEN — gated on §2 (D-A). The project norm is byte-identical defaults; promotion to default requires the reproduction gate to pass first.
