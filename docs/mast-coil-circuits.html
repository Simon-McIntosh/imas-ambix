§1 — Answering the two questions directly

"I thought MAST had a single geometry" — it does. Original MAST (shots ~11000–30000; this is not MAST-U) is one physical device with one fixed set of 13 active PF coils. What varies across the corpus is only the EFIT setup discretisation — how finely the static machine description chops each coil into filaments for the Green's-function table (938 vs 1004 filaments; probe count and position are identical across every signature we sampled, mp78 in every case here). §5 shows this directly: the B-probe positions from a 938-filament shot and a 1004-filament shot overlap to within 12.6 mm (measurement noise/rounding, not a real geometry change), while the filament count genuinely differs 938 vs 1004 for the same 13 coils.

"Are all coils properly powered?" — yes, all 13 active coils have their own dedicated power supply and a measured raw current channel, confirmed present on every sampled shot across both filament-count signatures (§2). But two things downstream of "powered" are NOT clean, and are worth the lead's attention:

  • The L2 / world-model actuator signal for P2–P5 uses the wrong unit. It reads *_FEED_CURRENT (the raw per-turn supply current, kA) while the GS/patch-current path correctly uses *_COIL_CURRENT (feed current already multiplied by the coil's turn count into amp-turns). The turn count varies 8–23× across coils, so a WM that treats these channels as comparable actuator magnitudes is wrong by a coil-dependent factor of up to 23× (§3).
  • P6U/P6L are completely absent from the L2/world-model actuator set. They are small (1.3–2.4% of total PF peak amp-turns across the 4 held-out shots) but non-zero and are dropped entirely, not down-weighted (§4).
  • Bonus finding, not requested but load-bearing: the GS operator's 8 cm nearest-centroid circuit classifier (operator.classify_circuits) silently folds 8 of the 10 structural coil-case circuits into the neighbouring active coil's Green's-function column and drives them with the ACTIVE coil's current — not their own measured (and physically distinct) case current. This is flagged for the T2 owner, not fixed here (out of this module's scope; see §6).

"Does our model drive series-tied coils independently?" — no, and it cannot. The ohmic circuit (solenoid1+solenoid2) is the ONLY series-tied pairing on the whole machine; traced end-to-end from the raw amc data through operator.classify_circuits/build_operator to the patch/latent model's actual training input (imas_ambix/latent/data.py's i_pf array), there is exactly ONE current channel and ONE actuator-vector column for the pair at every layer — the series constraint is enforced structurally by the machine's own instrumentation (a single measured current), not by a code convention that could silently break. No effect to quantify, no constraint left to wire in (§7).

Everything below is either a hardcoded, tested machine-description module (imas_ambix/gs/circuits.py) sourced from the MAST control-system XML and cross-validated against real data, or a directly measured number from four held-out shots (18502–18505) and three campaign signatures (11764, 12417, 18502) read via the repo's existing FAIR-MAST readers.

§3 — Red flag A: feed current vs coil current (measured, quantified)

For the 10 non-P6, non-solenoid coils, the amc group carries both a *_feed_current channel (raw per-turn supply current, kA) and a *_coil_current channel. Measured on shots 18502–18505 (every finite sample, median ratio, zero standard deviation — i.e. an exact integer relationship, not noisy):

The ratio matches the machine description's own supply-calibration constant exactly: coil_current = feed_current × (scalingFactor/1000). This is the coil's turn count — coil_current is the feed current already expressed in amp-turns, matching operator.py's documented ``_KA_TURN_TO_A`` convention. The GS/patch-current path's choice of *_coil_current is therefore correct (it is the actual field-producing amp-turn actuator); the turn-count spread across coils (8–23×, nearly 3× range) means a raw feed_current value is NOT on a comparable actuator footing across coils.

Mapped through the operator's own Green's function (operator.greens_bz_br, read-only import) to the peak field at each coil's most-coupled magnetic probe on shot 18502: feeding the raw feed_current number directly into the actuator (as if it were already amp-turns, which is what the L2/world-model path effectively does) reproduces only 1/turns of the real field — e.g. P4U's true peak field contribution at probe obr02 is 277 mT; using the raw feed number would imply 12.1 mT, a 23× underestimate. P2OU/P2OL (8 turns) underestimate by 8×; P2IU/P2IL (12 turns) by 12×. This is a genuine, coil-dependent actuator-scale error if the raw feed number is ever used as a physically-scaled quantity rather than a network-rescaled feature.

§5 — One machine, two campaign signatures (not two geometries)

Three sample shots span two fcoil discretisation signatures: mp78-fl46-fc1004-lim37-* (shots 11764, 12417 — earlier campaigns) and mp78-fl46-fc938-lim37-* (shot 18502 — the held-out set and most of the corpus, 449/493 sampled shots per the existing geometry summary). The "mp78" prefix is identical across all three — same 78 B-probes, same positions to within 12.6 mm (rounding/measurement noise, not a geometry change). The only real difference is the number of PF filaments EFIT's static setup uses to discretise the same 13 physical coils (938 vs 1004) — a finer or coarser Green's-function mesh over the identical machine, not a different machine. (The geometry module's own docstring also documents an mp81 probe-count variant elsewhere in the corpus; this report did not locate and directly inspect an mp81 sample shot within its time budget, so that variant is cited from the existing geometry-module documentation rather than independently re-verified here.)

§6 — Bonus finding: the geometry classifier confuses case circuits with active coils

Not requested by the audit brief, but discovered while cross-validating efm fcoil_circ against pfSystems.xml and worth flagging because it bears directly on "are all coils properly powered" at the level the GS operator actually uses: operator.classify_circuits (read-only import, not modified by this report) labels an efm fcoil circuit as a known active PF coil purely by 8 cm nearest-centroid distance to operator._PF_COIL_CENTROID. Directly measured (three sample shots, both signatures): the ``efm`` circuit numbering for the fine discretisation actually agrees with pfSystems.xml's pfCircuit numbering 1:1 (circuit 14 = "P2U case", exactly as in the XML) — but circuit 14's filaments (R≈0.50, Z≈1.77) sit only ~2 cm from the P2IU active coil's own centroid (R≈0.475, Z≈1.754), well inside the classifier's 8 cm match radius. The classifier therefore labels circuit 14 as a "redundant fine/coarse discretisation" of P2IU (per build_operator's own comment: "the EFIT fcoil model represents each physical PF coil with >1 circuit… we MERGE same-amc circuits into one column by AVERAGING") and folds its geometry into P2IU's G_pf column, driven by the ACTIVE P2IU coil current — not by the case circuit's own dedicated, measured, and typically much smaller p2u_case_current channel. This happens for 8 of the 10 case circuits (all except the two P6 cases, where it is harmless because the true case current is genuinely zero). imas_ambix/gs/circuits.py's CaseCircuit.geometry_confusable_with field records exactly which active coil label each case circuit will be folded into (verified equal, by test, to the actual classify_circuits output on real data) so this is now auditable rather than silent. Fixing operator.py is out of this report's scope (a different workstream owns that file); this is a flagged finding for that owner, quantified and reproducible via circuits.case_circuit_for_active_coil(coil_label).

§7 — Series-tied coil check: does anything drive solenoid1/solenoid2 independently?

The ohmic circuit (solenoid1 + solenoid2, circuit 1) is the only series-tied pairing in the whole 13-active-circuit MAST PF system — every other active circuit (P2IU/P2OU/P2IL/P2OL, P3U/P3L, P4U/P4L, P5U/P5L, P6U/P6L) is a single physical coil on its own dedicated supply (§2), so this is the only place the failure mode "our model drives series-tied coils independently" could even occur on this machine. Traced the full chain from raw data to the actuator vector the patch-current/GS-latent model actually trains on:

  • At the source: the amc group carries exactly ONE current channel for the whole ohmic circuit — sol_current. There is no solenoid1_current / solenoid2_current to even read independently; the machine's own instrumentation only ever measures one current for the pair (they are physically in series, so this is correct).
  • At the efm/GS-geometry layer: fcoil_circ assigns BOTH solenoid halves to a single circuit id (1) — verified directly on shot 18502: circuit 1 spans all 656 filaments (328 from each half, ``turnCount=0.5`` per filament, Σxmult = 328 total turns) as ONE group, not two. The series tie is baked into EFIT's own static setup, upstream of anything in this repo.
  • At the GS forward operator: operator.classify_circuits / build_operator therefore produce exactly ONE G_pf column labelled "sol", sourced from the single sol_current channel (confirmed: ForwardOperator.pf_amc_channels has 13 entries total, one per physical coil, including exactly one for the solenoid pair — see operator.py lines 615–639's own "ONE column per PHYSICAL coil" merge logic, read-only import, not modified here).
  • At the patch/latent model's actuator assembly: imas_ambix/latent/data.py::load_shot_windows builds the training input i_pf as a (n_slice, n_coil) array with n_coil = len(operator.pf_amc_channels) = 13, filled by ForwardOperator.assemble_pf_currents(amc_values). There is exactly one column for the solenoid pair; the model has no representation slot in which solenoid1 and solenoid2 could even be assigned different values.
  • Every other consumer checked (the tokenizer's geometry_reader.py coil-name map, camdyn/conditioning.py's conditioning-channel list) also carries exactly one "sol" / sol_current entry — a repo-wide grep for solenoid1 / solenoid2 outside this report's own new files returns nothing.

Verdict: no independent driving occurs, and none could — the series constraint is enforced structurally at the data-acquisition level (one measured channel), not by a convention in our code that could silently break. There is no effect to quantify and no circuit constraint left to "wire in" for this pairing; circuits.py's ActiveCircuit(series=True, pf_coil_names=("solenoid1","solenoid2")) already documents the physical fact for any future consumer that might otherwise assume 13 independently-drivable coils map to 13 independently-drivable physical windings (they map to 13 independently-drivable circuits, one of which happens to wind two physical coils in series).
